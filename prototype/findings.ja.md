# プロトタイプの実験記録

[計画](../docs/prototype-plan.ja.md) のマイルストーンごとに、条件と数値を記録する。生成データはシード 0 から始まる `mixed` プロファイル（1〜3本のバス＋0〜3本の囮信号）。実記録は `corpus/fixtures/real/` の9件（大きな flash 記録を除く）。

## M1: 読み込み・匿名化・評価の土台（2026-09-28）

- `.sr` をエッジ列へ変換し、チャンネル名を `D0…Dn` に置き換えて順序も入れ替えた。正解は `truth.json` に分離した。13 の実記録は合計 3.1 MB になり、Git に入れられる。
- `.sr` の未命名ビットも読み込むと、I2CDeviceDB の記録は 8 チャンネル中 5 本が静止線になる。静止線の検出を試す負例になる。
- 生成器は連続時間で波形を作り、最後にサンプル格子へ量子化する。同じシナリオを別のレートで描き直せ、ジッター・グリッチ・途中開始を足せる。

## M2: 単線の特徴（L1〜L3）

`m2_eval.py 300`（実記録＋生成 300 件）。

| 項目 | 結果 |
| --- | --- |
| 静止線の識別 | 186/186、誤検出 0 |
| UART のアイドルレベル | 173/173 |
| UART の速度（1位の時間単位が ±2% 以内） | 150/173（87%） |
| UART の速度（候補6個のどれかが ±2% 以内） | 172/173（99.4%） |
| I²C SCL / SPI CLK の周期（±5%） | 235/235、219/219 |
| クロック線のクロック様スコアが非同期様スコアを上回る | I²C 235/235、SPI 219/219 |
| UART 線のクロック様スコアが非同期様スコアを上回る（誤り） | 0/173 |

- **基本時間単位は約数に引っ張られる。** 真の単位の 1/2、1/3… もすべてのラン幅に整数倍で当てはまるため、当てはまりの良さだけで選ぶと 1/4、1/5 が1位になった（最初の版では1位の正答が 36/173）。「当てはまりが最良とほぼ同じ候補の中で最大の単位」を選ぶ規則に変えて 150/173 になった。
- 1位を外す残りのケースは、候補の中には真の単位がある。後段で全候補を復号して評価するので、L2 で必要なのは**順位より網羅**だと分かった。
- **予備実験の誤判定（SCL を UART と読むと形だけの一致率が 94〜99%）は L3 の段階で区別できる。** SCL は立ち上がり間隔の集中度が 0.98〜1.00、ラン幅の種類が 2〜3 で、UART_TX は集中度 0.41、ラン幅の種類が 6 だった。
- 実記録の SDA は、時間単位の候補に 10 サンプル（SCL の立ち下がりから SDA が変わるまでの遅れ）が出る。これは線単独の特徴ではなく線間の関係を表している。

## M3〜M5: 全系統の展開、多層スコア、判定

`evaluate.py`（実記録8件＋生成200件。v4 以降は対象内のバス 424〜427 本）。数値は評価のたびに変えた箇所とあわせて残す。

| 版 | 主な変更 | 確定（正） | 確定＋有力（正） | 誤確定 | 誤った有力 |
| --- | --- | ---: | ---: | ---: | ---: |
| v1（60件） | 最初の通し | 66% | 97.8% | 0 | 2 |
| v2（60件） | I²C の証拠量をバイト数に、余裕を変わった線の数で割る、SPI のフレーム数 | 61% | 94.2% | 0 | 0 |
| v3（60件） | SPI のフレーム証拠を (1/8)^k の偶然確率に | 66% | 99.3% | 0 | 0 |
| v4（200件） | 余裕のラベルから CS の有効レベルを外す | 84.2% | 97.2% | 0 | 2 |
| v5（200件、早期打ち切りあり） | SPI の位相集中度・CS 密着度、早期打ち切り | 72.4% | 98.8% | 0 | 0 |

確定したバスの復号一致率は、どの版も平均 99.99% 前後だった。v5 で「確定」が減ったのは、位相集中度を掛けたことで SPI の点数が全体に下がり、多くが「有力」に移ったため（係数の再調整が必要）。

### 効いた設計

- **下位の証拠を捨てず、上位で使う。** L3 のクロック様スコアを、I²C の SCL・SPI の CLK の係数にし、UART の減点にもした。これで「I²C の SDA を SPI のクロックとみなす」「クロック線を UART とみなす」仮説が退いた。
- **証拠の量を点数に入れる。** エッジが 20 本の CS 線でも、UART として 0.85 が付いていた。フレーム数・バイト数に応じた係数 1−exp(−n/8) を掛け、SPI では「全フレームが偶然 8 ビットの倍数になる確率 (1/8)^k」を使った。
- **余裕は組み合わせ全体で測る。** 「その主張と同等の仮説を禁止した最良の説明」との差を、割り当てが変わった線の数で割る。同じ線の組の中で1位と2位を比べる方式では、CS の有無だけ違う SPI や、MSB/LSB だけ違う仮説で余裕が 0 になっていた。
- **上位層の支持がないことを減点にしない。** 最初は合計点が 0.85 で頭打ちになり、ランダムなバイナリの SPI は確定できなかった。
- **SPI のデータ線の採否に位相集中度を使う。** 「サンプリング端から離れて変化する割合」は無関係な線でも約 0.75 になる。クロック周期内の変化位相の平均合成ベクトル長は、本物の線で 1 に近く、無関係な線で 0 に近い。SPI が2本ある記録で、一方のバスが他方のデータ線まで取り込む誤りが解消した。
- **CS の証拠。** CS の窓がクロックを含むことだけでは、同時に動く別のバスの CS や、SCL を CS とみなす仮説も通る。CS の切り替わりとクロック列の始まり・終わりが 8 半周期以内にあることを加えて、誤確定が解消した。

| ケース | 打ち切りなし | 打ち切りあり | 結果 |
| --- | ---: | ---: | --- |
| 実記録 i2cdb-qmp6988 | 8.6 秒 | 5.8 秒 | 同じ |
| synth-mixed-1（高速クロックの囮） | 27.7 秒 | 3.9 秒 | 同じ |

### 枝切り条件の検討（v4、`prune_study.py`）

生成データの範囲では、L3 で「SCL・CLK のクロック様 < 0.9」「UART 線の非同期様 < 0.9」の仮説を切っても、正解を1件も失わなかった。真の仮説は、その線を使う仮説の中で 99%（424 中 417）が1位だった。ただし生成データはきれいすぎる。実記録の RVSWD の SWCLK は、反射のひげでクロック様が 0.41 まで下がる。L3 の閾値で切るより、復号段の早期打ち切りのほうが安全と考える。

### RVSWD・SWIO（負例）

RVSWD（CLK+DIO）は物理層では同期シリアルで、SPI 寄りの方式である。L103 の記録で、正しい線の組の I²C 仮説は START を 2,667 回検出した（WCH の RVSWD は、フレームの区切りに I²C と同じ START/STOP 条件を使う）。しかし区切り間のビット数が 9 の倍数なのは 7.5% だけで、棄却された。SPI 仮説も、8 ビット単位でないこと、双方向で位相の集中度が 0.39 と低いことから 0 点になった。そのため、最も高かったのは SWCLK 単独の UART（0.49、拮抗）だった。SWIO（1線・パルス幅符号）はどの仮説も 0.11 以下だった。

→ 「未知の同期シリアル」を表す段が必要。エッジ列 → **同期ビット列**（クロック・データ・サンプリング端・区切り方）→ SPI / I²C / RVSWD などの段に分ければ、「CLK=D1・DATA=D3 の同期シリアル、既知の方式に該当なし」を結論として返せる。

### Rust での境界の比較（`boundary-bench/`、実 UART 線 7,396 エッジ、936 仮説×5回、最速の回）

| 変種 | µs/仮説 | ネイティブ比 | 備考 |
| --- | ---: | ---: | --- |
| Python + NumPy（プロトタイプ） | 約 260 | 5.2 倍 | 組み立て 188 µs＋カーネル 74 µs |
| Rust ネイティブ（初版、二分探索のまま） | 259 | — | アルゴリズムが NumPy 版と同じだと速くならない |
| Rust ネイティブ（線形走査に修正） | 50 | 1 | 基準 |
| ネイティブ・チャンネル単位で一括 | 50 | 1.0 | ネイティブでは呼び出しの粒度は効かない |
| cdylib プラグイン（組み立て）＋関数ポインタでホストのカーネル | 50 | 1.0 | 1仮説あたりホスト呼び出し約2回 |
| WASM プラグイン（組み立て）＋インポートでホストのカーネル | 66 | 1.3 | 1仮説あたり 126 KB の配列をメモリ間でコピー |
| WASM プラグインで丸ごと計算（エッジは最初に1回コピー、27 ms） | 71 | 1.4 | WASM 内の計算そのものの遅さ |
| 別プロセス・バイナリ・仮説ごと | 80 | 1.6 | 往復あたり約 30 µs |
| 別プロセス・バイナリ・一括 | 51 | 1.0 | 往復の費用がほぼ消える |
| 別プロセス・JSON 行・仮説ごと | 89 | 1.8 | 往復＋直列化で約 40 µs |

すべての変種で、指標はネイティブ版と完全に一致した。WSL 上の測定で、回によって全体が 1.7 倍ほど遅くなる揺らぎがある。

### 分かったこと

1. **境界の方式より、コアのアルゴリズムと呼び出しの粒度のほうが効く。** 同じ二分探索のままでは、Rust にしても NumPy と同じ 260 µs だった。線形走査に直して 5 倍速くなった。
2. **ネイティブ（cdylib）なら、細かい粒度でも境界の費用はほぼない。** 組み立てをプラグインに置いても差は測れなかった。ただしビルド環境・ABI・配布の負担がある。
3. **WASM は 1.3〜1.4 倍で済む。** 遅くなる主な原因は、ホストのカーネルの結果を WASM のメモリへコピーする量（1仮説 126 KB）。配列をコアに置いたまま**ハンドルで参照する API** にすれば、さらに減らせる見込み。
4. **別プロセスは、仮説ごとに呼ぶと往復 30〜40 µs かかる。一括にすればほぼ無料。** スコア部品（1記録 2.5 万回）や上位の解析器を仮説ごとに別プロセスで呼ぶと、1記録あたり 1〜2 秒増える。層ごと・ストリームごとに一括で渡す API が前提になる。

### 境界の設計案（本番の叩き台）

| 担当 | 置き場所 | 境界の形 |
| --- | --- | --- |
| エッジ列の保持、窓の切り出し、サンプル格子・連鎖・窓所属・位相統計・ビットのバイト化などのカーネル | コア（Rust） | — |
| 全系統の展開、早期打ち切り、組み合わせ探索、余裕の計算 | コア | — |
| 線レベルの復号器（UART / I²C / SPI、同期ビット列） | 標準はコア。追加はネイティブまたは WASM のプラグイン | **パラメータの格子を宣言し、コアが一括で評価**。配列はハンドルで参照し、戻り値は指標の小さな構造体 |
| 上位の解析器（行、NMEA、Modbus、機器固有） | プラグイン（WASM／スクリプト／別プロセスのどれでも可） | ストリーム（バイト・フレーム列）を**まとめて**渡す |
| スコアの計算・合成・判定の規則 | プラグイン（差し替え可） | ノードの指標の表を層ごとに**一括**で渡し、点数の列を返す |

次に確かめること: ハンドル参照の WASM API、スコア部品を一括にしたときの費用、同期ビット列の段をコアのカーネルにした場合の I²C（Python では 1 回 430 µs の状態機械）。

## 共通の下調べ、確実な除外、最良優先（2026-09-28）

### 共通の下調べ（`wsproto/survey.py`）

周波数・ビット数・線の相関を、プロトコルの解析器ではなく共通の段で1回だけ推定するようにした。

| 推定 | 方法 | 実データでの結果 |
| --- | --- | --- |
| クロックの周期とバーストごとのビット数 | 立ち上がり間隔の最頻値。4 周期超の空きでバーストに分け、立ち上がりを数える | SHT30 の SCL は 9n+1 形（10, 28, 37…）の割合が 100%。生成 SPI は 8n が 100% |
| 非同期線の 1 文字のビット数 | 各開始端から L ビットで連鎖させ、開始ビットと停止ビットの位置だけを検査（L=8〜13） | 真の L が同点の候補に入った割合 68/69。外れはストップビット 1/2 の区別だけ |
| ピン同士の相関（クロック × 他の線） | 同時活動率、クロック周期に対する変化位相の集中度、端の一致、バースト境界の一致 | 実記録の SCL→SDA は 0.89、SCL→UART は 0.00。生成 SPI の CLK→MOSI/MISO は 0.99、CS は境界一致 1.00 |

最初の文字長の推定（アイドルから離れる端の間隔の最小値）は、文字内部の変化を拾って 8N1 を 7 と読んだ。停止ビットの検査に替えて解決した。

### 確実に違うものだけを除く（`wsproto/exclude.py`、`exclusion_audit.py`）

復号せず、共通の下調べだけで判定する規則を置いた。各規則が正解の仮説を1件でも除いたかを、通常 208 件＋4種のストレス（各 150 件）で監査した。

| 規則 | 種類 | 除外した割合 | 正解の損失（通常／glitch／midstart／lowrate／jitter） |
| --- | --- | ---: | --- |
| uart.idle_level（推定アイドル・最初・最後のレベルがそろって逆） | 定義 | 34% | 0／0／0／0／0 |
| uart.bit_too_long（5% 点のランが 0.4 ビット未満） | 定義 | 45% | 0／0／0／0／0 |
| uart.char_len（文字長がほぼ確定したとき合わない形式） | 経験則 | 1.6% | 0／0／0／0／**2** |
| uart.pure_clock | 経験則 | 38% | 0（安全な集合には入れない） |
| i2c.idle_high（SCL・SDA のどちらかが確実に LOW でアイドル） | 定義 | 28% | 0／0／0／0／0 |
| i2c.no_coactivity（SDA の変化の半分以上が SCL のバースト外） | 定義 | 58% | 0／0／0／0／0 |
| i2c.sda_busier（SDA の変化が SCL の変化より多い） | 定義 | 44% | 0／0／0／0／0 |
| spi.no_data（CLK のバースト中に変化する線がない） | 定義 | 10% | 0／0／0／0／0 |
| spi.cs_idle（CS が確実に有効レベルでアイドル） | 定義 | 30% | 0／0／0／0／0 |
| spi.cs_too_busy（CS の切り替えが CLK の立ち上がりの半分より多い） | 定義 | 68% | 0／0／0／0／0 |
| spi.cs_no_boundary | 経験則 | 66% | 0 |

- 最初の `i2c.idle_high` と `spi.cs_idle` は、推定アイドルレベルだけで判定して正解を 8 件・29 件落とした。アクセスの疎な線（CS など）で、選択区間が長いと最長のランがアクティブ側になるため。**推定値・記録の最初・最後の3つがそろったときだけ除く**ようにして 0 件になった。
- 定義に基づく規則だけでも、提案の **UART 76%・I²C 82%・SPI 90%** を除ける。

### 最良優先の検討（`bestfirst_study.py`、実記録4件＋生成40件）

共通の下調べだけから、復号する前の「見込み点」を付けた（UART: 非同期様 × 単位の当てはまり × 文字長の検査、I²C: SCL のクロック様 × SCL→SDA の相関、SPI: CLK のクロック様 × 最良のデータ相関 × CS の境界一致）。確実な除外の後、見込み点の高い順に並べたとき、最終的な最良の説明に入る仮説が何番目に現れるかを測った。

- 除外後に残る仮説は 35%。最終の主張が出そろう位置は、中央値で残りの **1%（14 番目）**、90% 点で 12%、最悪で 61%。
- 遅れて出る主張を調べると、どれも**囮の線への弱い主張**（合計 0.33〜0.45、判定は「拮抗」）だった。本物のバスの主張は 0〜3 番目に出ている。
- したがって、見込み点の順に掘り、「残りの見込み点の上限で、今の最良の説明を覆せない」ところで止める探索が成り立つ見込み。止め方の上限（見込み点と最終の合計点の関係）はまだ測っていない。

### プロトコルの層の調査

[プロトコルの層と積み重なりの調査](../docs/protocol-layers.ja.md) にまとめた。この実験に直接関わる点は次のとおり。

- RVSWD と SWIO は線の段が違うだけで、どちらも同じ DMI トランザクション（7 ビット番地＋32 ビットのデータ＋op/status）を運ぶ。その上に RISC-V Debug Module（WCH の拡張番地 0x7C〜0x7F を含む）、さらに data0/data1 を郵便受けにした文字チャネル（WCH SDI printf、ch32fun の debugprintf、dmseq）が乗る。
- 共通の段の候補は、同期ビット列、パルス幅記号列、マンチェスタ／NRZI、時刻付きバイト列、トランザクション、状態付きセッション。

## 細かい段と型付きストリーム（`taxonomy.py`、`typed.py`、`stage_eval.py`）

最初の構成は、下調べの直後に UART / I²C / SPI の全系統を展開していた。そこで、ピンの分類から始めて段ごとに情報を整理し、下の段（より具体的なプロトコル）は**整理済みの型付きデータ**を受け取る構成を試した。判断の基準は、段ごとに**扱う情報の量が減るか**。減らない段は、兄弟の関係か統合の候補と見る。

~~~text
エッジ列 → T1 ピン分類（静止は除外）→ T2 まとまり
  同期の組   → SyncBits（サンプリング端で取った全データピンのビット）→ Frames（CS / START・STOP / 間隔）→ Words（8 / 9 ビット）→ SPI 転送・I²C トランザクション
  非同期の単独 → AsyncSymbols（ビット時間で量子化したラン）→ Chars（文字長 L）→ バイト
~~~

### 結果（実記録8件＋生成60件、真のバスに沿った経路、中央値）

| SPI | 6,448 B | SyncBits 1,219（×0.19） | Frames 110（×0.09） | Words(8) 60（×0.55） | バイト 50（×0.85） |

| RVSWD | 493,280 B | SyncBits 131,065（×0.27） | Frames 28,027（×0.21） | 84 ビットのフレームが最多（長形式 85 クロック） | — |

| --- | --- |

### 分かったこと

- **同期系は段ごとに確実に情報が減る。** エッジ → SyncBits で約 1/5、区切りの付与で約 1/5、語への整形でさらに 1/2〜1/3。親子の段として妥当。
- **UART の AsyncSymbols はほとんど減らない（×0.88）。** ランをビット時間で量子化しただけで、要素数はエッジと同じ。この段は Chars（文字）と統合する候補。UART の文字長を「段として先に決める」か「解析器の中で決める」かは、Chars が文字長 L を引数に取る形で、両方の構成を試せる。
- **段の中で決めきれないことは、兄弟の候補として下の段へ渡す。** 生成 I²C は SDA が SCL の立ち下がりと立ち上がりのちょうど中間で変わるため、サンプリング端を決める証拠がない（51 中 46 件）。両方の端の SyncBits を兄弟として出し、I²C の段が ACK 率で選ぶ形にして 51/51 になった。
- **CS の有効レベルは線単独ではなく線間の関係で決める。** CS 自身のアイドル推定を使うと、選択区間が長い記録で有効レベルを取り違えてフレームが 0 個になった（SPI の不一致 12/75 の原因）。「窓の中にクロックがある方」を有効レベルにして 75/75 になった。
- **多速度のクロックには局所周期が要る。** RVSWD の SWCLK は区間ごとに速度が変わり、記録全体で1つの周期を仮定したクロック様スコアは 0.33〜0.41 だった。前後 33 間隔の移動中央値との比較にすると 0.85〜0.91 になった（SCL・CLK・PWM は 1.0、データ線はおおむね 0.46 以下）。ピン同士の位相の集中度はまだ全体周期で測っており、V203 の SWCLK→SWDIO が 0.08〜0.14 と低く、組を作れていない。

## 周波数に依存しない下調べと、UART のボーレート切り替え

クロックのある方式（SPI、I²C、RVSWD）は、クロックの端でデータを取るので、本来は周波数に依存しない。SyncBits もクロックの端で取っている。それでも周波数が入り込んでいたのは下調べの側だったので、次のように直した。

| 箇所 | 前 | 後 |
| --- | --- | --- |
| クロックらしさ | 記録全体の周期の集中度 | 隣り合う立ち上がり間隔の比が 1 に近い割合（`local_clock`） |
| バーストの区切り | 全体の周期の 4 倍を超える空き | 前後どちらの間隔よりも 3 倍を超えて長い空き（`kernels.burst_split`） |
| ピン同士の位相 | 全体の周期で割った位相 | 前後のクロックの端の間での相対位置（`kernels.relative_phase_concentration`） |
| START/STOP・CS の検出窓 | 周期の倍数 | 前のバーストの終わりから次のバーストの始まりまでの空き |

### SPI・I²C でフレームごとに周波数を変えた生成データ（freqhop、×0.25〜×4、60件）

| 条件 | I²C 完全一致 | SPI（MOSI）完全一致 |
| --- | ---: | ---: |
| クロックのランが 3 サンプル以上 | 36/36 | 21/21 |
| クロックのランが 2 サンプル以下（周波数を上げた区間でサンプル不足） | 4/11 | 19/24 |

失敗は、すべてサンプリングが足りない区間で起きた。サンプルレートは元の周波数に合わせて選んでいるので、×4 の区間では 1 ビット 1〜2.6 サンプルになる。これはアルゴリズムの周波数依存ではなく取得の限界で、下調べで「クロックのランが 2 サンプル以下」を**取得品質の警告**として出すべきもの。通常の生成データの結果は変わらず、RVSWD の組は 1/3 から 2/3 に増えた。

### UART のボーレート切り替え（baudhop、途中で ×2/×4/×8、`baud_segment_eval.py`）

UART はクロックがないので、切り替えには区間を分ける処理が要る（ESP32 の書き込みで、途中で速度を上げる場合など）。

1. 各ランの前後 10 ランの最短ランを、局所的なビット時間とみなす（1 文字にはほぼ必ず 1 ビットのランがある）。前後の窓の中央値が 1.5 倍以上変わる所を、切り替えの候補にする。
2. 境界は、アイドルのランの中から選ぶ。遅い側のランは速い単位の整数倍でもあるので、「当てはまる」では位置が決まらない。**「その側の単位より短いラン」が最も少なくなる位置**を選ぶ。
3. 区間の単位は、当てはまりがほぼ最良の候補の中で、最短のランに近いもの（0.7〜1.15 倍）を選ぶ。短い区間では約数（1/2、1/3）を選びやすいため。

| 構成 | 区間の正しさ | 復号の平均一致 | 完全一致 |
| --- | ---: | ---: | ---: |
| 切り替えあり・単位を1つと仮定 | — | 0.48 | 0/39 |
| 切り替えあり・区間分け | 34/39 | 0.87 | 24/39 |
| 切り替えなし・区間分け | 36/36 | 1.00 | 36/36（単位1つの仮定では 35/36） |

残る失敗は、遅い区間が短いか倍率が 2 倍で切り替えを見落とすもの（5 件）と、境界付近の文字の取りこぼし。区間分けは切り替えのない記録を壊さず、最短ランの制約で通常の UART の単位推定も良くなった。

### 速度の変化も段として扱う（RateBlocks / RateSegments）

速度の変化への対処を、系統ごとに別の段として切り出した。

~~~text
単独の非同期ピン → RateBlocks（ビット時間ごとのブロックに分割）
                    └ ブロックごとの共通処理: 文字長の推定（survey.char_length）→ Chars → バイト
同期の組         → SyncBits ＋ RateSegments（速度が変わった区間の注釈。分割はしない）→ Frames → Words
~~~

- 文字長の推定は、区間とビット時間を引数に取る共通関数 `survey.char_length` にした。記録全体でも各ブロックでも同じ処理を使う。UART の評価も、正解の文字長を与えず、ブロックごとの推定値（同点の最良候補のうち最短）で行うように変えた。

| 条件 | UART | 同期系 |
| --- | --- | --- |
| 通常（60件） | ブロック1つ 40/40、文字長の推定 40/40、完全一致 **36/36** | 速度区間1つ（I²C 51/51、SPI 47/47）。RVSWD は 3/3 で複数区間（多速度を検知） |
| freqhop | 完全一致 38/38 | 速度の変化を注釈として検知（I²C 46/47、SPI 45/45）。復号は分割せずに変わらず（失敗はサンプル不足の区間だけ） |
| baudhop | 複数ブロックを検知 35/39、ブロックごとの文字長 73/74、完全一致 24/39 | 速度区間1つ（変化なし） |

- この段は情報を減らさず、**同じ性質の区間に分ける（分割する）**段である。減らす段（型の抽象化）とは性質が違う。その後の処理をブロックごとの共通処理にできる点に価値がある。段を「情報を減らす段」と「分割・注釈する段」に分けて、プラグインの単位を考える必要がある。

### RateBlocks → Chars の再利用（UART に似た方式、`plugins_uartlike.py`、`plugin_reuse_eval.py`）

段を分ける価値は、後続の処理を減らすことと、使う側が複数あることにある。確かめるため、UART に似た別方式の LIN と DMX512 を、共通段（RateBlocks → ブロックごとの文字長推定 → Chars）の出力を受け取るプラグインとして書いた。プラグインはエッジもビット時間も扱わない。

| 方式（生成 60 件） | 完全一致 | 方式固有の検査 | プラグインのコード |
| --- | ---: | --- | ---: |
| UART | 16/16 | — | —（共通段の出力そのもの） |
| LIN | 18/18 | 同期 0x55・PID パリティ・拡張チェックサムが全フレームで合う | 12 行（＋ブレークでの分割 7 行） |
| DMX512 | 26/26 | スタートコード 0 が全パケットで合う | 11 行（ブレークでの分割は LIN と共用） |

最初は LIN 0/18、DMX512 2/26 だった。原因はどちらも共通段にあり、直すと UART を含む全方式が良くなった。

- **ビット時間は、アクティブ側のランから推定する。** 文字間の空き（アイドル側のラン）はビットの整数倍とは限らず（LIN の文字間スペースなど）、約数を選んでいた。スタートビット＋0 のビットのランは必ず整数倍になる。単線の UART の速度推定（1位が ±2% 以内）も 150/173 から 165/173 に良くなった。
- **アイドルレベルは、記録の最初と最後のレベルがそろっていればそれを使う。** DMX512 では長いブレーク（LOW）が最長のランを占め、アイドルを LOW と読んでいた。
- **ブレークの検出は Chars の共通処理にした。** 1 文字より長いアクティブ側のランをブレークとして記録し、文字の区切りには使わない。LIN と DMX512 はこれを使って、ブレーク間の文字をまとめるだけで済む。

段を分ける基準の案: **後続の処理を減らす段**、または**使う側が 2 つ以上ある段**は分ける。使う側が 1 つしかなく、処理も減らさない段は統合してよい。RateBlocks と Chars は UART・LIN・DMX512（今後は MIDI、Modbus RTU の区切り、ESP32 のブートローダ等）が共有するので、分ける価値がある。

## 段構成のエンジン（`staged.py`）

下調べ → ピン分類 → 型付きストリーム → 型で受け取るプロトコルのプラグイン → スコア → 組み合わせ → 判定、までを通しで作った。プラグインはエッジに触れない。

| 受け取る型 | プラグイン |
| --- | --- |
| `frames.startstop` | I²C、未知の同期シリアル |
| `frames.select` / `frames.gap` | SPI、未知の同期シリアル |
| `chars`（RateBlocks → ブロックごとの文字長 → Chars） | UART、LIN、DMX512 |
| `bytes` | 行、NMEA、Modbus RTU、マーカー（既存の上位解析器を流用） |

### 総当たりのエンジンとの比較（実記録8件＋生成200件）

| エンジン | 確定（正） | 確定＋有力（正） | 誤確定 | 誤った有力 | 復号一致 | CPU 時間 | 壁時計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 総当たり v6（打ち切り＋除外） | 72.4% | 98.8% | 0 | 0 | 99.99% | 1,064 s | 210 s |
| 段構成 s1（最初の版） | 76.4% | 94.8% | 5 | 1 | 99.7% | 186 s | 32 s |
| 段構成 s3 | **78.1%** | 97.9% | **0** | **0** | **100%** | 227 s | **31.5 s** |

RVSWD の実記録3件は、s3 で3件とも「未知の同期シリアル（START/STOP 区切り、84 ビットのフレームが最多）」になった。総当たりのエンジンでは、SWCLK を UART と読む「拮抗」だった。SWIO はパルス幅の段がまだないので何も出ない。

### s1 から s3 で直したこと

- **I²C は立ち上がりでしか受け付けない。** 仕様上 SCL の立ち上がりで取るので、立ち下がりの兄弟ストリームは I²C プラグインでは受け付けない（定義に基づく除外）。サンプリング端の兄弟は SPI と未知の同期シリアルのために残す。
- **ACK 率の重みを下げた。** SHT30 の実記録は、測定待ちのポーリングで NACK が多い（アドレスの ACK が 33%）。NACK も正しい I²C の振る舞いなので、構造の証拠は 9 ビット単位の割合で見る。
- **「未知」は「既知の規則で説明できない」ことを根拠にする。** 同じクロック・データのすべての見え方（START/STOP、間隔、CS）について、9n（+1）・8n の割合から偶然の一致（2/9、1/8）を引いた値で割り引く。そうしないと、本物の I²C が「別のバスの CS で区切った未知の同期シリアル」に負けた。
- **クロックと連動するピンを単独の UART と読む仮説は、連動の強さだけ減点する。** RVSWD の SWDIO を UART と読む仮説が、未知の同期シリアルに勝っていた。
- **双方向の線の位相は2つの山を持つ。** 平均合成ベクトル長を、角度を2倍にしたものとの大きい方にした。L103 の SWCLK→SWDIO が 0.27 から 0.56 になり、組が作れた。
- **時間単位の近い候補（6% 以内）は、ランの整数倍からの残差が小さい方を残す。** UART のボーレートが 4〜5% ずれる誤確定がなくなり、単線 UART の速度推定（1位が ±2% 以内）は 165/173 から 173/173 になった。

### 非同期の線の組（TX/RX）と SCPI（`duplex.py`、`scpi_eval.py`）

SCPI や AT コマンドは TX と RX の2本がそろって意味を持つ。そこで、1本ずつ UART として解析した後に、**非同期の線どうしの相関を見る段**を置いた。この段は UART の主張と競わず、上に積む「関係」として別に返す。SCPI の検査が通れば、その支持を両方の UART に返す。

- 組の条件: 同じボーレート（3% 以内）と文字長。時間の重なりが少ないこと。**応答の形**（一方の線のメッセージが、必ずもう一方のメッセージの直後に来る）。証拠の量は応答の回数で割り引く（1 − 0.5^n）。
- 最初は「メッセージが交互に出る割合」を使い、34 組中 29 組しか見つけられなかった。SCPI のホストは、応答のないコマンド（`*RST`、`CONF:...`）を続けて送るので、交互にはならない。応答の形に替えて 34/34 になった。
- SCPI のプラグインは、双方向ストリームとホスト側の候補を受け取り、コマンドの文法、クエリー（`?` で終わる）に応答がある割合、クエリーに続かない応答の割合で点数を付ける。ホストがどちらかも決める。

| 生成データ（duplex、60件） | 結果 |
| --- | --- |
| SCPI の組の発見 | 34/34 |
| ホスト／機器の向き | 34/34 |
| やり取り（コマンドと応答）の完全一致 | 34/34 |
| 無関係な組（SCPI の生成データ／通常の生成データ 80 件） | 0 / 0 |
| 1本ずつの UART の確定 | 81/94 → 84/94（SCPI の支持が下へ返った分） |

### RVSWD → DMI → RISC-V Debug Module（`rvswd.py`）

同期ビット列の段の上に、RVSWD と Debug Module のプラグインを積んだ。

- **ひげを除いた兄弟の見え方（共通段）:** クロックに 4 サンプル以下のランが少数あるとき（反射のひげ）、クロックとデータのピンから短いパルスを除いた見え方を兄弟として追加する。除かない見え方も残し、どちらを採るかはプラグインの点数で決まる。
- **間隔による区切りの閾値も兄弟にした:** 前後の間隔の 3 倍と 1.8 倍。
- **RVSWD プラグイン**（`frames.gap` を受け取る）: RVSWD 固有の知識として、フレームの最後に長い間隔（周期の約 2.7 倍）と stop のクロックがあることを使い、フレームを切り直す。53 ビット（書き込み／読み出し）と 54 ビット（読み出し）を DMI トランザクションに復号し、ヘッダとデータの2つのパリティを検査に使う。
- **Debug Module プラグイン**（`dmi` を受け取る）: 番地が既知の DM レジスタか（WCH の拡張 0x7C〜0x7F を含む）を見て、抽象コマンドと data0/data1 の組からメモリ・レジスタのアクセスを組み立てる。

| 実記録 | 判定 | パリティ | 既知の DM 番地 | 参照（wch-protocols の dmi_decode.py）との照合 |
| --- | --- | ---: | ---: | --- |
| L103 target_info（50 MHz） | RVSWD 確定（0.91） | 100% | 99.1% | DMI 132 件中 110 件、並びの一致率 0.90（番地で照合）。メモリアクセス 40 件中 34 件（0.92） |
| V203 target_info（50 MHz） | RVSWD 確定（0.95） | 100% | 100% | 参照なし |
| V203 target_info（100 MHz） | RVSWD 確定（0.95） | 100% | 100% | 参照なし |

- 以前は3件とも「未知の同期シリアル」、総当たりのエンジンでは SWCLK を UART と読む「拮抗」だった。
- START/STOP で区切ると、速いフレームは 10〜14 ビットに細切れになった。読み出し中はターゲットが SWCLK の HIGH 中に SWDIO を変えるので、START/STOP に見えるためである。RVSWD の速いフレームは間隔で区切るのが正しい。START/STOP 区切りで最多だった 84 ビットのフレームは、アタッチ区間の低速フレーム（参照では RAW85）である。
- 残る差: アタッチ直後の低速フレーム3件（dmcontrol と dmstatus）が取れていない（参照ツールは低速区間の細切れのクロックをつなぎ直している）。1 か所で 6 件が欠け、誤った読み出し（番地 0x42）が1件ある。
- 生成データ 200 件の結果（s4）は s3 と同じで、兄弟の見え方の追加による悪化はない。

### SWIO（1 線）→ 同じ DMI → 同じ Debug Module

パルス幅記号の共通段（`typed.PulseSymbols`）を置き、その上に SWIO プラグインを載せた。SWIO は RVSWD と同じ DMI トランザクションを運ぶので、**Debug Module のプラグインは RVSWD 用のものをそのまま使えた**。

- **共通段:** アクティブ側のパルスの幅を、短い／長いに分ける。閾値は、幅の分布で最も多い2つの山の中間（対数）に置く。パルスの開始間隔が典型の 3 倍を超える所で、フレームを区切る。最初は分位点で閾値を決めたところ、V003 の記録に含まれる LinkE の 2 線形式の問い合わせ（4〜102 µs の LOW）に引っ張られ、1,590 ns になった。山の間に置いて 471 ns になった（参照の固定値は 500 ns）。
- **SWIO プラグイン:** 短い＝1。41 パルス（start 1・addr 7・R/W・data 32）と 33 パルス（高速読み出し、data0）を DMI にする。パリティがないので、証拠は DM 番地の既知率、41/33 フレームが占めるパルスの割合、件数。最初は「41/33 フレームの割合」を使ったため、同じピン上の別の通信（問い合わせ）で薄まっていた。

| 実記録 | 判定 | DMI | 参照（wch-protocols の swio.py、固定閾値）との照合 |
| --- | --- | --- | --- |
| V003 target_info | SWIO 有力（0.84） | 40 件、DM 番地 100% | **40/40 完全一致** |

Debug Module の段では、L103（RVSWD）の参照と同じ `REGW 0x7c0 = 0x300` や、接続時の 0x7E・0x7D への 0x5AA50400 の書き込みが、SWIO からも得られた。

## 後段に合わせた結果の取り出しと、分析前のヒント

### 取り出し方（`wsproto/export.py`、`ws.py`）

後段によって欲しいデータが違う。GUI は波形に重ねる中間の段（ビット、フレーム、語、文字）と確定データの両方を、元の記録のサンプル位置付きで欲しい。CLI や AI の分析は確定データだけで足りることが多い。そこで3つのモードにした。

| モード | 内容 | 想定する後段 |
| --- | --- | --- |
| `final` | 主張ごとの最上位の解釈だけ（I²C はトランザクション、UART は行または NMEA/Modbus、RVSWD/SWIO は DM のアクセス …） | CLI、スクリプト、AI |
| `all` | 主張ごとの全段（ビット列、フレーム、START/STOP 条件、語、ブロック、文字、ブレーク、DMI …）と証拠の指標、必要なら次点の仮説 | GUI の注釈、調査 |
| `select` | パスで指定した段・項目だけ（`i2c.transactions`、`uart.lines`、`*.final`、`spi.*` …） | 決まった問いへの後工程 |

- 中間の段は、エンジンがプラグインに渡した型付きストリームへの参照として主張に残す。プラグインを書く人は何もしなくてよい。
- 時刻はサンプル番号（`s`、`e`）で出し、見出しにサンプルレートを入れる。後段は元の記録を読まずに秒へ換算でき、GUI は元の波形へ戻れる。

| --- | ---: | ---: | ---: | ---: |
| SHT30（I²C＋UART） | 82 KB | 79 KB | 6.1 KB | 6.1 KB（`i2c.transactions`＋`uart.lines`） |
| L103 target_info（RVSWD） | 467 KB | 273 KB | 1.8 KB | 1.8 KB（`*.dm`） |
| V003 target_info（SWIO） | 53 KB | 61 KB | 0.4 KB | 0.4 KB |
| 生成 SCPI（UART×2） | 518 KB | 6.8 KB | 0.3 KB | 0.05 KB |

`all` はビット単位の情報を持つので、元のエッジと同じくらいの大きさになる。`final` はその 1/10〜1/250。

### ヒント（`staged.analyze(cap, hints)`、`hint_eval.py`）

分析の前に分かっていることを渡すと、試す範囲を絞れる。ヒントだけで結論は決めず、プラグインの検査による点数付けはそのまま行う。

- `protocols`: 使っている方式の一覧。一覧にないプラグインは動かさない。同期系・非同期系・パルス系の段ごと省ける。
- `pins`: ピンごとの方式・役割・ボーレート。非同期と指定したピンは同期の組から外し、同期と指定したピンは非同期の解析をしない。役割と合わない組は作らない。ボーレートが与えられたら、区間分割と時間単位の推定を省く。
- `exclude_pins`: 解析しないピン。

| なし | 15.9 s | 6,021 | 81.2% | 98.7% | 0 |
| 方式の一覧 | 13.8 s | 1,612 | 82.1% | 99.1% | 0 |
| ピンごとの方式・役割・ボーレート | 7.1 s | 970 | 82.1% | 99.1% | 0 |

| --- | ---: | ---: |
| V203 flash（100 MHz、161 万エッジ） | 151 s | 8.1 s |
| L103 flash（118 万エッジ） | 48 s | 10.8 s |

## 宣言的なフレーミング記述、デバイスの定義、どこまで見るか

### 宣言的なフレーミング記述（`decl/*.toml`、`wsproto/declarative.py`）

I²C・SPI・RVSWD のプラグインを、コードなしの TOML で書き直した（合わせて約 100 行）。語の幅・ビット順・欄の切り出し・固定値の検査・長さの規則（`9n|9n+1`、`8n`、53/54 ビットの固定配置とパリティ）・欄の役割を書く。方式固有のコードとして残ったのは RVSWD のフレームの切り直しだけで、これもコアのカーネルを名前で呼ぶ（`reframe = "rvswd_stop"`）。スコアの一部も、コアが提供する証拠の項目を名前で呼ぶ（`terms = ["select_boundary", "degenerate", "single_frame_penalty"]`）。

| 調整に使っていないシード | 87.3% / 97.9% / 0・0 | 87.5% / 97.9% / 0・0 |
| グリッチ | 62.2% / 95.0% / 0・0 | 62.2% / 94.1% / 0・0 |

| 低サンプリング | 62.2% / 97.5% / 0・0 | 75.6% / 97.5% / 0・0 |

途中で分かった点:

- **組の主張は、最も弱いピンと同じ強さしかない。** ピンの相関の平均を使うと、ランダムな囮の線（相関 0.33）が SPI の組に紛れ込んだ。線が多い方が組み合わせの評価で得をするので、囮を含む組が勝っていた。最小値にして解消した。
- **値の偏りの減点は、全ピンが偏っているときだけ。** ピンごとの積にすると、アイドルで `0xFF` が続くフラッシュの MISO を組から外してしまい、JEDEC ID が見えなくなった。
- **組の候補は緩く取り、判定は見え方ごとに測り直す。** グリッチ入りの記録では、クロックの偽のバーストのために CS の境界の一致が 0.4 になり、T2 で CS の候補から外れていた（CS なしの SPI として誤確定）。T2 の閾値を 0.25 にし、プラグインがひげを除いた見え方で測り直す形にした。
- **ピン同士の相関に証拠の量を掛けた**（バースト中の変化の回数で 1−exp(−n/8)）。変化が数回の線の位相の集中度は、偶然で高くなる。

### デバイスの定義（`decl/devices/*.toml`、`wsproto/devices.py`、`device_eval.py`）

データシートの書き方に合わせて、定義を3つの型に分けた。

| 型 | 例 | 検査 |
| --- | --- | --- |
| コマンド表 | SHT30（16 ビットのコマンド、応答の CRC-8）、SPI NOR（JEDEC の命令、`9F` の応答、SFDP の署名） | 表にある命令か、長さ、CRC、識別子 |
| レジスタ表 | QMP6988（8 ビットのポインタ、チップ ID `0xD1` = `0x5C`） | 識別用のレジスタの値 |
| メッセージの枠 | UART の上の NMEA・Modbus・SCPI（既存の上位解析器） | チェックサム、応答の対応 |

判定は証拠の強さで3段階に分けた。**識別**（識別子の値、または CRC などの検算が一致）、**整合**（表には合うが検算がない）、**アドレスだけ**（主張しない、候補の一覧だけ）。

| 検査 | 結果 |
| --- | --- |
| 実記録 SHT30（2件） | 2件とも SHT30 を識別（CRC 9/9、失敗 0） |

| 同じシナリオの SPI NOR 以外の SPI（37 本） | 機種の主張 0/37 |
| 調整に使ったシードのランダムな I²C・SPI の通信（60 件） | 機種の主張（識別・整合）0。アドレスだけの候補 71 件 |

**アドレスだけの判定は曖昧すぎる。** I2CDeviceDB の 83 機種では、71 のアドレスのうち 53 を 2〜5 機種が共有している（`0x44` は INA226・SHT30・SHT40、`0x70` は PCA9548A・QMP6988・TCA9548A）。

### どこまで見るか（出力の深さ）

`ws.py analyze ... --depth transport|frames|protocol|device`。

| 深さ | 内容 | QMP6988 の記録の大きさ |
| --- | --- | ---: |
| `transport` | 方式・役割・パラメータ・判定 | 0.5 KB |
| `frames` | ＋下位の結果（トランザクション、転送、バイト列、DMI） | 14 KB |
| `protocol`（既定） | ＋上位（行、NMEA、Modbus、SCPI、Debug Module） | 8 KB |
| `device` | ＋識別・整合した機種と、その命令・レジスタの解釈。アドレスだけの候補一覧 | 10 KB |

方針（解釈）:

- 上位の解釈は、下位の結果を置き換えず、注釈として重ねる。上位が外れても下位は正しいまま残る。
- 自動で上がるのは、検算できる証拠がある段まで（チェックサム、応答の対応、標準の識別子）。
- 機種は、識別の証拠が出たときだけ主張する。読み込んだパックにない機種は返さない。アドレスだけの一致は、候補の一覧として求められたときだけ出す。

### 定義の階層化と、機種が増えたときの確認

定義を `decl/devices/<方式>/<メーカーまたは分類>/<機種>.toml` に置き、パスのパターン（`i2c/**`、`i2c/sensirion/*`、`!` で除外）で選ぶ形にした（`devices.PackSet`、CLI の `--devices`、ヒントの `devices`）。

作業用フォルダに、実在の 3 件に加えてダミーの I²C の定義を 5000 件作り、実記録の SHT30 で試した。1000 件は SHT30 と同じ `0x44`、残りは 128 アドレスに散らした。SHT30 と同じ命令表を持つ SHT31 も 1 件入れた。

| 項目 | 結果 |
| --- | --- |
| 見出しの読み込み（初回 / 2回目） | 0.58–0.96 秒 / 0.22–0.25 秒（5004 件） |
| 照合 | 観測したアドレスに当たる 1036 件だけを読んで 170–210 ms |

実在の定義だけに戻して `device_eval.py` を実行し直した。識別・SPI フラッシュ・誤った主張の結果は変わらなかった（ランダムな通信の候補は 71 件から 69 件。同じアドレスの候補をまとめたため）。

分かったこと:

- 機種が爆発して問題になるのは、処理時間より出力の量だった。候補はアドレスごとに 1 件にまとめる。
- 命令表が同じ系列（SHT3x のように、データシートが 1 冊の機種群）は識別の証拠で区別できない。定義は系列単位で書くか、区別できないものをまとめて返す必要がある。
- 数千件を超えたら、見出しのキャッシュをアドレス索引ごと保存すれば、起動時にファイルを走査しなくて済む（未実装）。

## TOML の限界の確認: SWD と CAN（`decl/swd.toml`、`decl/can.toml`）

「前の値で後ろが変わる」SWD と CAN を、スキーマの小さな拡張とコアの名前付き処理だけで書けるかを試した。

### 足したもの

| 種類 | 内容 | 使った方式 |
| --- | --- | --- |
| スキーマ: 順に並ぶ欄（`[[sequence]]`） | 欄を順に読む。幅に式が使える（`"0 if (rtr if ide else rtr_srr) else 8 * min(dlc, 8)"`）。条件付きの欄（`when = "ack == 1"`）、派生の欄（`derive`）、欄ごとのビット順 | 両方 |
| スキーマ: 検査 | 固定値（`expect`）、許される値の集合（`valid`）、欄の名前で指定するパリティ、欄の範囲で指定する CRC | 両方 |
| スキーマ: 式 | 整数の計算、比較、and/or/not、三項演算子、min/max。AST のホワイトリストで制限 | 両方 |
| コア: ビットスタッフィングの読み取り | 何ビット続いたら入るかと、その値（`stuffing = { after = 5, from = "sof", to = "crc" }`）。違反したらそのフレームは不成立 | CAN（USB は `after = 6, value = 1` で書ける見込み、未確認） |
| コア: `frame.scan` | 各バーストの中で、検査がすべて通る位置を探して区切る | SWD（アイドルのクロックが止まらない場合） |
| コア: `nrzbits` | 非同期の1本線を、レベルの続いた長さ÷ビット時間でビット列にする。長いアイドルでフレームを区切る | CAN |

TOML の行数は SWD 約 40 行、CAN 約 45 行。方式固有の Python は 0 行。

| --- | --- | --- | --- |
| そのまま | 70% / 98% | 100% / 100% | 0・0 |

- 復号は、確定・有力の全件で正解と一致した（パケットとフレームの列）。
- 既存の9セット（調整に使ったシード、使っていないシード、ノイズの6条件、実記録）は前回と同じか少し良い。誤確定は 0 のまま。

### 途中で分かったこと

- **生成器の時刻が現実とずれていた。** 最初の生成器は、データを立ち上がりの 1/4 周期前に変えていた。コアはデータの変化から遠い立ち下がりだけを読み取りの基準に選び、立ち上がりで読む指定の SWD は仮説が作られなかった。データを立ち下がり直後に変える形に直し、TOML からは読み取りの辺の指定を外した。どちらの辺でも、検査で決まる。
- **周期的な線を読むと、同じ形の偽の通信が並ぶ。** 常時動く囮のクロックで SPI のクロックを読むと、偽の SWD パケットが覆う割合 0.8 で見つかった。値の偏りの減点（`degenerate`）を順に並ぶ欄の形にも入れた。同じ通信が 100% だったので、0.04 まで下がった。
- **未知の同期方式は、既知の方式の後に回す。** 囮のクロックと SWD の2本を含む4本組の「未知の同期方式」が、ピン数の多さで詰め合わせに勝っていた。既知の方式の仮説のほうが点が高く、ピンが重なる未知の同期方式は、詰め合わせから外した。
- **証拠の量は、検査の情報量で数える。** フレームの数だけで数える（`1-0.5^(n/2)`）と、CRC-15 を持つ CAN が3〜5フレームでは有力止まりだった。検査ごとの「偶然に通る確率」の −log₂ を合計し、`1-0.5^(bits/8)` に変えた。CAN は確定 70% から 100% に上がった。
- **先頭を探す方式では、試した位置の数だけ偶然の一致を差し引く。** 最初は、試した位置の数を「線全体のビット数÷見つかった件数」で見積もった。本物の SWD でも1件あたり約 5.5 ビットを引いてしまい、確定が 0 になった。見つかった通信の直後の位置ですぐ次が見つかるので、試した位置は「見つかった件数＋通信で説明できないビット数」とした。
- **遅いサンプリングでは、ビット時間を復号できたフレームから測り直す。** ジッターがあり1ビットが4サンプルのとき、ブロック単位の推定が 3.5% ずれた（CRC は通るのにボーレートが外れ、誤確定と数えられた）。SOF から最後の変化点までのサンプル数÷その間のビット数で測り直した。

### 線引き（更新）

- 順に並ぶ欄、条件、長さの式、スタッフィング、CRC まで広げても、1フレームの中で閉じていれば TOML で書けた。
- スクリプトが要るのは、次のものに絞られる。
  - フレームをまたぐ状態を持つもの（JTAG の TAP、DP の SELECT、DM）
  - 構文を持つもの（SCPI）
- 式は、これ以上広げない。ループと、フレームをまたぐ変数は入れない。

## マーカーで区間に分ける（`wsproto/markers.py`、`decl/markers/*.toml`、`ws.py segments`）

それまでマーカーは、UART の行がマーカーの書式に合うかを数える上位プロトコルの一つで、方式を判定する証拠に使うだけだった。行の時刻は捨てており、区間には分けていなかった。[ワークベンチのモデル](../docs/workbench-model.ja.md) の見出し型の規則で、区間の木を作るようにした。

- **方言は TOML で書く。**
  - `heading`: 見出し型。`#` の数が階層で、名前のない見出しは閉じるだけ。
  - `i2cdb`: 既存の記録の書式。`CASE_BEGIN` と `CASE_END` で囲み、`PHASE` は見出し、`INPUT` と `RESULT` は属性。
  - 行の種類は4つ（begin・end・point・attr）で、`heading` はこれとは別の見出し型の規則。
- **区間の範囲**: マーカーの行の送信が終わった時点から、閉じる行の送信が始まる時点まで。行の時刻は UART の各バイトの開始時刻から組み立て直した。
- **同じ名前**: 同じ親の下では `[0]`、`[1]` の連番で区別し、元の文字列を残す。
- **問題として記録するもの**: 階層の飛び、対応する見出しのない閉じ、閉じない区間、番号の飛び、名前の不一致、書式に合わない行。
- **マーカーでない行はイベント**: すべての UART の行を、時刻・ピン・文字列付きで同じ時間軸に並べる。親の区間では、子の見出しもイベントとして見える。CLI では既定で出さず（`--events`）、GUI 向けの全層出力には含める。
- **区間ごとの情報**:
  - 動いたピン、始まりと終わりのレベル、前後の静かな時間
  - 周期的な信号の周波数・デューティー比・ばらつき
  - 区間の中の復号結果

### 確認

| --- | --- |
| 実記録 SHT30（I2CDeviceDB） | 36 行すべてマーカーとして読んだ。`Single Measurement` の 6 回が `[0]`〜`[5]` に分かれ、`PHASE` の子区間に `INPUT` と `RESULT` が付いた。`polling-high` の区間では、`INPUT` の命令 `0x2400` と、区間の中の I2C の書き込み `2400` が対応した |

## 意図した信号の照合（`ws verify`、`wsproto/runlog.py`、`wsproto/verify.py`）

ArduinoCore-CH32 のキャプチャを使うテスト（`tests/manual/oep_*`）を調べた。前提が2つ違っていた。

- **コマンドはキャプチャに映らない。** OEP の `target.console`（dmseq）で送っている。
- **キャプチャはステップごとの単発で短い。** 1 サンプル 1 バイト、x035 は 20 MHz まで、おおよそ 64 KiB × 8 ÷ チャンネル数のサンプル。

そこで、マーカーは PC 側のログに持ち、キャプチャを開始した時刻で区間に合わせる形にした（ワークベンチのモデルの合成ソース）。区間の木は `markers.build()` をそのまま使う。CH32 のファームウェアは変えなくてよい（今の `testcmd.h` は `#` の行に ERR を返すが、マーカーを CH32 に送らないので関係しない）。

- **`runlog.Recorder`**（標準ライブラリだけ）: 見出し、コマンド、応答、キャプチャ（`.bin`、trace_kit と同じ形式）、区間ごとの期待を `run.json` に書く。
- **`verify`**:
  - 見出しの木を作り、キャプチャを区間に割り当て、期待を照合する。
  - 検査は `square`、`level`、`starts`、`ends`、`only_moving`、`pulses`、`i2c`、`spi`、`uart`。
  - I2C・SPI・UART はピンと役割を手がかりとして与えて復号する。確定かどうかの判定は使わず、指定した役割の仮説の復号と照合する（1 回の短い通信は、発見の証拠としては弱いが、テストが求めた内容である）。
  - マーカーの構造の問題は、期待の有無に関係なく NG にする。
- 出力は、1行ずつの OK/NG と、JSON（測定値付き）と、JUnit XML。NG があれば終了コード 1。

### 実機の記録（x035、ArduinoCore-CH32 の `oep_periph_trace` と `oep_i2c_trace`）

初めて実機の記録（2026-09-29、20 MS/s）で照合した。照合する側の誤りが 2 つ見つかった。

- **SPI で、CS のフレームが 1 つだけのキャプチャに cs の役割の仮説が出なかった。** 13 件のうち 6 件が「nothing decoded as SPI」になった。`pair_relation` の `boundary`（CS らしさ）を、クロックのバーストごとに「直前と直後の隙間に相手のエッジがある」で数えていたため、次の 2 つの形で 0 になった。
  - mode 2 / 3 で、転送の前に CLK が idle の High へ移るエッジ 1 本が、1 ビットのバーストとして数えられる（CS が落ちる前にあるので、枠に入らない）。
  - 4 MHz で、バイトの間の隙間でバーストが 4 つに分かれ、CS の窓 1 つに複数のバーストが入る。
  - 直し方: 立ち上がり 1 本だけのバーストは転送として数えない。バーストが相手の 2 本のエッジの間にあり（最初から最後のクロックエッジまでの間に相手のエッジがない）、同じレベルであればよい。1 つの窓に複数のバーストが入るときは、1 つの転送に見えることを求める。条件は、前後の余白の合計がクロックの幅以下であることと、バーストの間の隙間が最長のバーストの 2 倍以下であること。これがないと、遅い PWM やランダムな線が CS になる（合成の評価で誤りが 37 件、除外規則で正解を 18 件落とした）。条件を入れた後は、合成 200 件の評価（段構成・宣言型）と stage_eval は変更前と同じで、除外規則が落とす正解は 0 のまま。`spi.cs_no_boundary` で除く割合は 61 % から 79 % になった。
- **I2C で、STOP のないまま窓が終わった取引を捨てていた。** `frames_startstop` は閉じていない最後の枠を落としていた。障害の再現試験では「どこで止まったか」が知りたいことなので、枠を残して `open_tail` の印を付け、取引に `complete: False` と `pending_bits`（最後の完全なバイトの後に打たれたビット）を付ける。未完の枠は発見の証拠には数えない（I2C の得点、sync_unknown と宣言型のプラグインには `Frames.closed()` を渡す）。
- ヒントで同期バスのクロックとデータの役割がすべて与えられたときは、調査の段が組にしなかった組み合わせも試す（クロックが数回しかない短い取引）。

### UART の検査をボーレートの測定に使えるようにした

ArduinoCore-CH32 側で、F_CPU とボーレートの組み合わせを振り、実際のボーレートのずれを測る試験を作るための変更。

- `check_uart` は、発見用の復号をやめた（ヒントでボーを与えると、測定値がヒントのままになっていた）。代わりに、与えたボーとフォーマットで読む照合専用の受信器を使う。
- ボーレートは、1 文字の中の同じ向きのエッジどうしの間隔を d = k × u として最小二乗で求める。まず k ≤ 4 で求め、次にすべてで求め直す。良い文字がないときは全部の文字を使う。
- 窓の途中で始まる・終わる文字は数えるだけにした（`lead_in`、`cut_at_end`）。同期は、1 文字分以上の idle の後から取る。
- フォーマット（`bits`、`parity`、`stop`）と `max_errors` を足した。

合成データでの確認（16 バイトの塊、塊の間に 20 ビットの idle、窓の両端で文字を切る）:

- 1 ビットあたり 8〜22 サンプルで、測ったずれの誤差は 0.003 % 以内。立ち上がりの遅れ 1.5 サンプル、エッジのゆらぎ 0.5 サンプルを入れても変わらない。
- 8N1、8E1、8O2（idle Low）、7E1 で、エラーは 0。
- 次の誤った期待は、どれも理由付きで NG になる: パリティの有無の誤り、ストップビット数の誤り、ボーの 10 % の誤り、idle の誤り、途切れのない送信（同期できない）。

x035 の UART の掃引（F_CPU 6 通り × ボーレート、1 ビットに 8 サンプル以上かつ BRR ≥ 16 の 67 通り、6.7 MB）は、67 ok / 0 ng だった。測ったボーレートと F_CPU / BRR の差は +0.05〜+0.18 %、フレームエラーは 0。差は F_CPU ごとにまとまっている（48 MHz で約 +0.07 %、6〜8 MHz で約 +0.14 %）。ただし、掃引は F_CPU の順に約 80 秒で流れたので、時間（温まり）による HSI のずれとは、この記録では分けられない。

`uart(pin, None)` で測るだけのモードを足した（範囲外の設定で DUT が何を出すかを残すため）。合成データで、889341 baud（真値 889344）、9600、1 Mbps の 8E1 を測れた。1 ビット 6 サンプル（3.2 Mbps）では −0.4 % の偏りが出る。

v003 の UART の掃引（classic ESP32 の GPIO sampler、2 MS/s、ソフトの歩調取り）は 44 ok / 2 ng だった。NG は 230400 bps（1 ビット 8.7 サンプル）の 2 件で、195 文字中 2、165 文字中 1 のフレームエラー。受信器の誤りではなく、キャプチャの時間軸の乱れだった。

- エラーの文字では、エッジの一部だけが 1 ビットの格子から 3 サンプル前後ずれ、その後の文字では格子に戻る。スタートビットが 2 サンプルしかない文字もある。送信器はエッジを格子の上に置くので、こうしたずれはサンプラーが止まったことを示す。
- 記録全体で、文字の中のエッジと格子のずれは最大 0.5 ビット（1 ビット 20 サンプルで約 10 サンプル）だった。x035（PARLIO）では最大 0.13 ビット。1 ビットが 20 サンプルなら読めるが、8.7 サンプルではストップビットの判定が崩れる。
- `check_uart` は、各文字のエッジの格子からのずれを測定値（`edge_offset_max`、`edge_offset_p99`、エラーの位置とずれの `errors_at`）に出す。エラーの文字がどれも 0.2 ビット以上ずれていれば、NG の理由に「キャプチャの時間軸を疑う」と書く。エラーは NG のまま残す（隠さない）。

x035 の掃引を F_CPU の逆順（6→48 MHz）で流し直した記録（84 キャプチャ、11 MB）は、67 ok / 0 ng / 17 未検査だった。F_CPU ごとのずれは正順とほぼ同じ（48 MHz で +0.075 %、24 MHz で +0.117 %、6〜16 MHz で +0.13〜0.15 %）なので、時間ではなく F_CPU で決まる。範囲外（BRR < 16）の 17 区間は `uart(pin, None)` で測り、どれも F_CPU / 16 に張り付いていた（例: 6 MHz で 375.5 kbps、24 MHz で 1.502 Mbps。フレームエラー 0）。範囲外の設定で DUT が何を出すかを、測るだけのモードで記録に残せた最初の例。
