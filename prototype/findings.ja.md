# プロトタイプの実験記録

[計画](../docs/prototype-plan.ja.md) のマイルストーンごとに、条件と数値を記録する。生成データはシード 0 から始まる `mixed` プロファイル（1〜3本のバス＋0〜3本の囮信号）。実記録は `corpus/fixtures/real/` の9件（大きな flash 記録を除く）。

## M1: 読み込み・匿名化・評価の土台（2026-09-28）

- `.sr` をエッジ列へ変換し、チャンネル名を `D0…Dn` に置き換えて順序も入れ替えた。正解は `truth.json` に分離した。13 の実記録は合計 3.1 MB になり、Git に入れられる。
- `.sr` の未命名ビットも読み込むと、I2CDeviceDB の記録は 8 チャンネル中 5 本が静止線になる。静止線の検出を試す負例になる。
- 生成器は連続時間で波形を作り、最後にサンプル格子へ量子化する。同じシナリオを別のレートで描き直せ、ジッター・グリッチ・途中開始を足せる。

## M2: 単線の特徴（L1〜L3）

`m2_eval.py 300`（実記録＋生成 300 件）。

| 項目 | 結果 |
| --- | --- |
| 静止線の識別 | 186/186、誤検出 0 |
| UART のアイドルレベル | 173/173 |
| UART の速度（1位の時間単位が ±2% 以内） | 150/173（87%） |
| UART の速度（候補6個のどれかが ±2% 以内） | 172/173（99.4%） |
| I²C SCL / SPI CLK の周期（±5%） | 235/235、219/219 |
| クロック線のクロック様スコアが非同期様スコアを上回る | I²C 235/235、SPI 219/219 |
| UART 線のクロック様スコアが非同期様スコアを上回る（誤り） | 0/173 |

- **基本時間単位は約数に引っ張られる。** 真の単位の 1/2、1/3… もすべてのラン幅に整数倍で当てはまるため、当てはまりの良さだけで選ぶと 1/4、1/5 が1位になった（最初の版では1位の正答が 36/173）。「当てはまりが最良とほぼ同じ候補の中で最大の単位」を選ぶ規則に変えて 150/173 になった。
- 1位を外す残りのケースは、候補の中には真の単位がある。後段で全候補を復号して評価するので、L2 で必要なのは**順位より網羅**だと分かった。
- **予備実験の誤判定（SCL を UART と読むと形だけの一致率が 94〜99%）は L3 の段階で区別できる。** SCL は立ち上がり間隔の集中度が 0.98〜1.00、ラン幅の種類が 2〜3 で、UART_TX は集中度 0.41、ラン幅の種類が 6 だった。
- 実記録の SDA は、時間単位の候補に 10 サンプル（SCL の立ち下がりから SDA が変わるまでの遅れ）が出る。これは線単独の特徴ではなく線間の関係を表している。

## M3〜M5: 全系統の展開、多層スコア、判定

`evaluate.py`（実記録8件＋生成200件。v4 以降は対象内のバス 424〜427 本）。数値は評価のたびに変えた箇所とあわせて残す。

| 版 | 主な変更 | 確定（正） | 確定＋有力（正） | 誤確定 | 誤った有力 |
| --- | --- | ---: | ---: | ---: | ---: |
| v1（60件） | 最初の通し | 66% | 97.8% | 0 | 2 |
| v2（60件） | I²C の証拠量をバイト数に、余裕を変わった線の数で割る、SPI のフレーム数 | 61% | 94.2% | 0 | 0 |
| v3（60件） | SPI のフレーム証拠を (1/8)^k の偶然確率に | 66% | 99.3% | 0 | 0 |
| v4（200件） | 余裕のラベルから CS の有効レベルを外す | 84.2% | 97.2% | 0 | 2 |
| v5（200件、早期打ち切りあり） | SPI の位相集中度・CS 密着度、早期打ち切り | 72.4% | 98.8% | 0 | 0 |

確定したバスの復号一致率は、どの版も平均 99.99% 前後だった。v5 で「確定」が減ったのは、位相集中度を掛けたことで SPI の点数が全体に下がり、多くが「有力」に移ったため（係数の再調整が必要）。

### 効いた設計

- **下位の証拠を捨てず、上位で使う。** L3 のクロック様スコアを、I²C の SCL・SPI の CLK の係数にし、UART の減点にもした。これで「I²C の SDA を SPI のクロックとみなす」「クロック線を UART とみなす」仮説が退いた。
- **証拠の量を点数に入れる。** エッジが 20 本の CS 線でも、UART として 0.85 が付いていた。フレーム数・バイト数に応じた係数 1−exp(−n/8) を掛け、SPI では「全フレームが偶然 8 ビットの倍数になる確率 (1/8)^k」を使った。
- **余裕は組み合わせ全体で測る。** 「その主張と同等の仮説を禁止した最良の説明」との差を、割り当てが変わった線の数で割る。同じ線の組の中で1位と2位を比べる方式では、CS の有無だけ違う SPI や、MSB/LSB だけ違う仮説で余裕が 0 になっていた。
- **上位層の支持がないことを減点にしない。** 最初は合計点が 0.85 で頭打ちになり、ランダムなバイナリの SPI は確定できなかった。
- **SPI のデータ線の採否に位相集中度を使う。** 「サンプリング端から離れて変化する割合」は無関係な線でも約 0.75 になる。クロック周期内の変化位相の平均合成ベクトル長は、本物の線で 1 に近く、無関係な線で 0 に近い。SPI が2本ある記録で、一方のバスが他方のデータ線まで取り込む誤りが解消した。
- **CS の証拠。** CS の窓がクロックを含むことだけでは、同時に動く別のバスの CS や、SCL を CS とみなす仮説も通る。CS の切り替わりとクロック列の始まり・終わりが 8 半周期以内にあることを加えて、誤確定が解消した。

### 早期打ち切り

`ProbeConfig`（窓 600 エッジ×3か所、閾値 0.1、4,000 エッジ未満の線では使わない）。

| ケース | 打ち切りなし | 打ち切りあり | 結果 |
| --- | ---: | ---: | --- |
| 実記録 i2cdb-qmp6988 | 8.6 秒 | 5.8 秒 | 同じ |
| synth-mixed-1（高速クロックの囮） | 27.7 秒 | 3.9 秒 | 同じ |
| synth-mixed-197（500 万エッジのクロック） | 数時間でも終わらない | 185 秒 | 3バスとも正しく確定 |

### 枝切り条件の検討（v4、`prune_study.py`）

生成データの範囲では、L3 で「SCL・CLK のクロック様 < 0.9」「UART 線の非同期様 < 0.9」の仮説を切っても、正解を1件も失わなかった。真の仮説は、その線を使う仮説の中で 99%（424 中 417）が1位だった。ただし生成データはきれいすぎる。実記録の RVSWD の SWCLK は、反射のひげでクロック様が 0.41 まで下がる。L3 の閾値で切るより、復号段の早期打ち切りのほうが安全と考える。

### RVSWD・SWIO（負例）

RVSWD（CLK+DIO）は物理層では同期シリアルで、SPI 寄りの方式である。L103 の記録で、正しい線の組の I²C 仮説は START を 2,667 回検出した（WCH の RVSWD は、フレームの区切りに I²C と同じ START/STOP 条件を使う）。しかし区切り間のビット数が 9 の倍数なのは 7.5% だけで、棄却された。SPI 仮説も、8 ビット単位でないこと、双方向で位相の集中度が 0.39 と低いことから 0 点になった。そのため、最も高かったのは SWCLK 単独の UART（0.49、拮抗）だった。SWIO（1線・パルス幅符号）はどの仮説も 0.11 以下だった。

→ 「未知の同期シリアル」を表す段が必要。エッジ列 → **同期ビット列**（クロック・データ・サンプリング端・区切り方）→ SPI / I²C / RVSWD などの段に分ければ、「CLK=D1・DATA=D3 の同期シリアル、既知の方式に該当なし」を結論として返せる。

| spi | 7,900 | 13.3 | 9.4 | 493 | 626 エッジ | 2 |
| uart（試し復号） | 26,483 | 7.8 | 2.1 | 215 | 600 | 16 |

- Python では組み立て側（NumPy の小さな演算の固定費）が、カーネル内の約 2.5 倍かかっていた。

### Rust での境界の比較（`boundary-bench/`、実 UART 線 7,396 エッジ、936 仮説×5回、最速の回）

| 変種 | µs/仮説 | ネイティブ比 | 備考 |
| --- | ---: | ---: | --- |
| Python + NumPy（プロトタイプ） | 約 260 | 5.2 倍 | 組み立て 188 µs＋カーネル 74 µs |
| Rust ネイティブ（初版、二分探索のまま） | 259 | — | アルゴリズムが NumPy 版と同じだと速くならない |
| Rust ネイティブ（線形走査に修正） | 50 | 1 | 基準 |
| ネイティブ・チャンネル単位で一括 | 50 | 1.0 | ネイティブでは呼び出しの粒度は効かない |
| cdylib プラグイン（組み立て）＋関数ポインタでホストのカーネル | 50 | 1.0 | 1仮説あたりホスト呼び出し約2回 |
| WASM プラグイン（組み立て）＋インポートでホストのカーネル | 66 | 1.3 | 1仮説あたり 126 KB の配列をメモリ間でコピー |
| WASM プラグインで丸ごと計算（エッジは最初に1回コピー、27 ms） | 71 | 1.4 | WASM 内の計算そのものの遅さ |
| 別プロセス・バイナリ・仮説ごと | 80 | 1.6 | 往復あたり約 30 µs |
| 別プロセス・バイナリ・一括 | 51 | 1.0 | 往復の費用がほぼ消える |
| 別プロセス・JSON 行・仮説ごと | 89 | 1.8 | 往復＋直列化で約 40 µs |

すべての変種で、指標はネイティブ版と完全に一致した。WSL 上の測定で、回によって全体が 1.7 倍ほど遅くなる揺らぎがある。

### 分かったこと

1. **境界の方式より、コアのアルゴリズムと呼び出しの粒度のほうが効く。** 同じ二分探索のままでは、Rust にしても NumPy と同じ 260 µs だった。線形走査に直して 5 倍速くなった。
2. **ネイティブ（cdylib）なら、細かい粒度でも境界の費用はほぼない。** 組み立てをプラグインに置いても差は測れなかった。ただしビルド環境・ABI・配布の負担がある。
3. **WASM は 1.3〜1.4 倍で済む。** 遅くなる主な原因は、ホストのカーネルの結果を WASM のメモリへコピーする量（1仮説 126 KB）。配列をコアに置いたまま**ハンドルで参照する API** にすれば、さらに減らせる見込み。
4. **別プロセスは、仮説ごとに呼ぶと往復 30〜40 µs かかる。一括にすればほぼ無料。** スコア部品（1記録 2.5 万回）や上位の解析器を仮説ごとに別プロセスで呼ぶと、1記録あたり 1〜2 秒増える。層ごと・ストリームごとに一括で渡す API が前提になる。

### 境界の設計案（本番の叩き台）

| 担当 | 置き場所 | 境界の形 |
| --- | --- | --- |
| エッジ列の保持、窓の切り出し、サンプル格子・連鎖・窓所属・位相統計・ビットのバイト化などのカーネル | コア（Rust） | — |
| 全系統の展開、早期打ち切り、組み合わせ探索、余裕の計算 | コア | — |
| 線レベルの復号器（UART / I²C / SPI、同期ビット列） | 標準はコア。追加はネイティブまたは WASM のプラグイン | **パラメータの格子を宣言し、コアが一括で評価**。配列はハンドルで参照し、戻り値は指標の小さな構造体 |
| 上位の解析器（行、NMEA、Modbus、機器固有） | プラグイン（WASM／スクリプト／別プロセスのどれでも可） | ストリーム（バイト・フレーム列）を**まとめて**渡す |
| スコアの計算・合成・判定の規則 | プラグイン（差し替え可） | ノードの指標の表を層ごとに**一括**で渡し、点数の列を返す |

次に確かめること: ハンドル参照の WASM API、スコア部品を一括にしたときの費用、同期ビット列の段をコアのカーネルにした場合の I²C（Python では 1 回 430 µs の状態機械）。

## 共通の下調べ、確実な除外、最良優先（2026-09-28）

### 共通の下調べ（`wsproto/survey.py`）

周波数・ビット数・線の相関を、プロトコルの解析器ではなく共通の段で1回だけ推定するようにした。

| 推定 | 方法 | 実データでの結果 |
| --- | --- | --- |
| クロックの周期とバーストごとのビット数 | 立ち上がり間隔の最頻値。4 周期超の空きでバーストに分け、立ち上がりを数える | SHT30 の SCL は 9n+1 形（10, 28, 37…）の割合が 100%。生成 SPI は 8n が 100% |
| 非同期線の 1 文字のビット数 | 各開始端から L ビットで連鎖させ、開始ビットと停止ビットの位置だけを検査（L=8〜13） | 真の L が同点の候補に入った割合 68/69。外れはストップビット 1/2 の区別だけ |
| ピン同士の相関（クロック × 他の線） | 同時活動率、クロック周期に対する変化位相の集中度、端の一致、バースト境界の一致 | 実記録の SCL→SDA は 0.89、SCL→UART は 0.00。生成 SPI の CLK→MOSI/MISO は 0.99、CS は境界一致 1.00 |

最初の文字長の推定（アイドルから離れる端の間隔の最小値）は、文字内部の変化を拾って 8N1 を 7 と読んだ。停止ビットの検査に替えて解決した。

### 確実に違うものだけを除く（`wsproto/exclude.py`、`exclusion_audit.py`）

復号せず、共通の下調べだけで判定する規則を置いた。各規則が正解の仮説を1件でも除いたかを、通常 208 件＋4種のストレス（各 150 件）で監査した。

| 規則 | 種類 | 除外した割合 | 正解の損失（通常／glitch／midstart／lowrate／jitter） |
| --- | --- | ---: | --- |
| uart.idle_level（推定アイドル・最初・最後のレベルがそろって逆） | 定義 | 34% | 0／0／0／0／0 |
| uart.bit_too_long（5% 点のランが 0.4 ビット未満） | 定義 | 45% | 0／0／0／0／0 |
| uart.char_len（文字長がほぼ確定したとき合わない形式） | 経験則 | 1.6% | 0／0／0／0／**2** |
| uart.pure_clock | 経験則 | 38% | 0（安全な集合には入れない） |
| i2c.idle_high（SCL・SDA のどちらかが確実に LOW でアイドル） | 定義 | 28% | 0／0／0／0／0 |
| i2c.no_coactivity（SDA の変化の半分以上が SCL のバースト外） | 定義 | 58% | 0／0／0／0／0 |
| i2c.sda_busier（SDA の変化が SCL の変化より多い） | 定義 | 44% | 0／0／0／0／0 |
| spi.no_data（CLK のバースト中に変化する線がない） | 定義 | 10% | 0／0／0／0／0 |
| spi.cs_idle（CS が確実に有効レベルでアイドル） | 定義 | 30% | 0／0／0／0／0 |
| spi.cs_too_busy（CS の切り替えが CLK の立ち上がりの半分より多い） | 定義 | 68% | 0／0／0／0／0 |
| spi.cs_no_boundary | 経験則 | 66% | 0 |

- 最初の `i2c.idle_high` と `spi.cs_idle` は、推定アイドルレベルだけで判定して正解を 8 件・29 件落とした。アクセスの疎な線（CS など）で、選択区間が長いと最長のランがアクティブ側になるため。**推定値・記録の最初・最後の3つがそろったときだけ除く**ようにして 0 件になった。
- 定義に基づく規則だけでも、提案の **UART 76%・I²C 82%・SPI 90%** を除ける。

### 最良優先の検討（`bestfirst_study.py`、実記録4件＋生成40件）

共通の下調べだけから、復号する前の「見込み点」を付けた（UART: 非同期様 × 単位の当てはまり × 文字長の検査、I²C: SCL のクロック様 × SCL→SDA の相関、SPI: CLK のクロック様 × 最良のデータ相関 × CS の境界一致）。確実な除外の後、見込み点の高い順に並べたとき、最終的な最良の説明に入る仮説が何番目に現れるかを測った。

- 除外後に残る仮説は 35%。最終の主張が出そろう位置は、中央値で残りの **1%（14 番目）**、90% 点で 12%、最悪で 61%。
- 遅れて出る主張を調べると、どれも**囮の線への弱い主張**（合計 0.33〜0.45、判定は「拮抗」）だった。本物のバスの主張は 0〜3 番目に出ている。
- したがって、見込み点の順に掘り、「残りの見込み点の上限で、今の最良の説明を覆せない」ところで止める探索が成り立つ見込み。止め方の上限（見込み点と最終の合計点の関係）はまだ測っていない。

### プロトコルの層の調査

[プロトコルの層と積み重なりの調査](../docs/protocol-layers.ja.md) にまとめた。この実験に直接関わる点は次のとおり。

- RVSWD と SWIO は線の段が違うだけで、どちらも同じ DMI トランザクション（7 ビット番地＋32 ビットのデータ＋op/status）を運ぶ。その上に RISC-V Debug Module（WCH の拡張番地 0x7C〜0x7F を含む）、さらに data0/data1 を郵便受けにした文字チャネル（WCH SDI printf、ch32fun の debugprintf、dmseq）が乗る。
- 共通の段の候補は、同期ビット列、パルス幅記号列、マンチェスタ／NRZI、時刻付きバイト列、トランザクション、状態付きセッション。
