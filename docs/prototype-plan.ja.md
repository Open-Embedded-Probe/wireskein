# WireSkein — プロトタイプによる推定パイプラインの検証計画

2026-09-28 作成。[今後の検証計画](next-plan.ja.md) のうち「候補の探索、一致率」（3章）を最優先に切り出し、**動くプロトタイプを作りながら**確かめる計画に組み直したもの。プロトタイプは使い捨てであり、一定の成果が出た時点で本番実装を全面的に作り直す。

## 現在の状況（2026-09-28）

- 段構成のエンジン（共通の下調べ → ピン分類 → 型付きストリーム → 型で受け取るプラグイン）が通しで動き、総当たりのエンジンより精度が高く、約 15 倍速い。生成 200 件で正しい確定 82.7%、確定＋有力 98.4%、誤った確定・有力 0。調整に使っていないシード 200 件でも確定 87.1%、確定＋有力 97.8%、誤った確定・有力 0。6種のストレス条件でも誤確定は各 0〜1 件。
- 実記録 8 件（I²C＋UART 4、RVSWD 3、SWIO 1）はすべて正しい方式と判定。RVSWD・SWIO は DMI → RISC-V Debug Module まで積み、参照の解析結果と照合した。100 万エッジ級の記録 5 件も1件あたり数秒〜2分半で判定できる。
- 詳細は [プロトタイプの実験記録](../prototype/findings.ja.md)、段の構成は [プロトタイプの README](../prototype/README.ja.md)。

## 予備実験の振り返り

[初回の成立性調査](../experiments/initial-feasibility/README.ja.md) などの予備実験では、再現性・来歴・区間切り出しについて有用な観測が得られた。一方で、次の点が「微妙」だった。

| 問題 | 具体例 | 今回の対処 |
| --- | --- | --- |
| 既存デコーダ頼みで、推定そのものを作っていない | 復号は sigrok と wch-protocols の解析器に依存。チャンネル名（SCL/SDA 等）が既知の前提で処理した | チャンネル名を隠し、**未知の線から自前で推定**する。既存解析器は正解作りにのみ使う |
| 観察の記述が中心で、判断に至らない | 「単一スコアは危険」「未検証」が多く、何を採用するかが決まらない | 実験ごとに**合格基準を数値で先に置き**、採用・不採用を決める |
| 簡易試行の穴がそのまま残った | SCL を UART 8N1 と仮定すると形だけの一致率が 94〜99% になった | 周期性・線間関係・バイト列の性質で**反証する検査**をスコアに入れ、その誤判定を回帰試験にする |
| 標本が少ない | 実記録は I²C+UART 4件、RVSWD/SWIO のみ。SPI は生成2転送 | **パラメータを振れる信号生成器**で正解付き標本を大量に作り、実記録と両方で評価する |

## ねらい

未知のデジタル記録を受け取り、次の段階を経て「どの線が、どの方式で、どのパラメータで通信しているか」を根拠付きで返す。

~~~text
L0 読み込み     .sr / 生成データ → チャンネル名を匿名化したエッジ列
L1 基本情報     活動・静止線、アイドルレベル、エッジ数、バースト区間
L2 時間構造     ラン幅（HIGH/LOW 別）のヒストグラム、周期、基本時間単位、デューティ比
L3 線の分類     クロック様 / 非同期データ様（ラン幅が単位の整数倍）/ 同期データ様 / 静止 / 不明
L4 線間の関係   同じ周波数成分を持つ線、クロック端に同期して変化するデータ線、選択線（CS）候補
L5 仮説と復号   UART / I²C / SPI の候補を列挙し、自前の最小デコーダで実際に復号
L6 スコアと判定 復号結果の整合・反証・被覆率から「確定 / 有力 / 拮抗 / 不明」を決める
~~~

### 細かい段による絞り込み（2026-09-28 追加）

最初の実装は、下調べの直後に UART / I²C / SPI の全系統を展開していた。この構成では最初の段が深すぎる。そこで、**ピンの分類から始めて、段を下るたびに信頼できる情報が増え、分析の対象が減る**構成を試す。

| 段 | 決めること | 出力 |
| --- | --- | --- |
| T1 ピンの分類 | 静止／クロック様／データ様／まばら（CS 様）／パルス幅様。静止は除外する（常に LOW の CS のような線は識別できない） | ピンごとの分類の候補とスコア |
| T2 ピンのまとまり | 単独のピンか、クロックと相関の高いピン（＋選択線）のセットか | 単独ピン・ピンの組の候補 |
| T3 系統 | 同期シリアル（CS で区切る＝SPI 系、START/STOP 条件で区切る＝I²C 系、間隔で区切る）、非同期 NRZ（UART 系）、パルス幅記号 | 組ごとの系統の候補 |
| T4 語長・フレーム長 | 区切りごとのビット数（8n、9n+1、53/85 …）、UART の文字長 | 方式の候補（SPI、I²C、RVSWD 様、UART の形式 …） |
| T5 以降 | 方式ごとの復号、上位 | バイト列・トランザクション・上位 |

- 段ごとに、**残った候補の数**、**正解が残っているか**、**時間**を測る。候補が減らない段は親子ではなく兄弟の関係と見て、構成を見直す。
- 最初は段を細かく切って実験し、測定結果を見て、不要な段を統合する。段を細かくするとプラグインの単位は小さくなって書きやすくなるが、段の数だけ受け渡しが増えて遅くなる。この相反を測定で決める。
- 例えば UART のビット数は、「T4 で文字長を決めてから形式を絞る」構成と、「解析器の中で全形式を評価する」構成の両方を作って比べる。
- 段の判定は、確実な除外（正解を落とさないことを監査済みの規則）と、順位付け（見込み点）を分けて扱う。
- 速度の変化も段として扱う。クロックのある系統は、クロックの端でビットを取るので分割せず、速度が変わった区間を注釈として残す。UART のような非同期の系統は、複数のビット時間を検知したら**ビット時間ごとのブロックに分割する段**を置き、以降の文字長の推定・文字化・上位はブロック単位の共通処理にする。
- 段には「型を抽象化して情報を減らす段」と「同じ性質の区間に分割・注釈する段」の2種類がある。後者は情報量を減らさないが、後の処理を共通にする。
- 段を分ける基準は、**後続（プラグイン）の処理を減らすこと**と、**使う側が 2 つ以上あること**。使う側が 1 つしかなく処理も減らさない段は統合してよい。例えば RateBlocks → Chars（ブレーク検出を含む）は UART・LIN・DMX512 が共有し、LIN・DMX512 のプラグインは 11〜12 行で書けた。

### 多層スコアリングと全系統の評価

L3・L4 の結果で候補を**決め打ちしない**。各層は候補とその層のスコアを出すだけにし、下位層で点が低い候補も上位層まで展開して評価する。最終判断は、全層のスコアと、複数の線をまとめて説明する組み合わせで行う。

~~~text
線の性質 (L2/L3)  ─┐
線間の関係 (L4)   ─┼→ 仮説 = 方式 × 線の割り当て × パラメータ（全系統を列挙）
                    │      └→ 復号 (L5) → フレームの規則・被覆・反証
                    │             └→ 上位の支持（文字列らしさ、I²C アドレスの一貫性、CS との整合 等）
                    └→ 説明の組み合わせ: 線を重複なく割り当てた仮説の集合ごとに総合スコア
~~~

- 仮説ごとに**層別のスコアベクトル**を残す（時間構造への適合、線間関係、復号の規則適合、被覆率、反証、上位の支持）。総合スコアへの合成方法は複数試し、どの層が判定に効いたかを測る。
- 判定は1位の総合スコアだけでなく、**2位との差（余裕）**と反証の有無で「確定 / 有力 / 拮抗 / 不明」を決める。
- プロトタイプでは計算量を無視して**枝切りをしない**。全系統の評価結果から、どの層のどの条件で切っても正解を失わなかったかを測り、本番の枝切り条件はそのデータで決める。
- ただし、仮説の中での**早期打ち切り**は別に扱う。IR の解析で最初のフレームがずれすぎたら諦めるのと同じく、仮説ごとにまず数か所の窓（その仮説が使う線の活動の 10・50・90% 付近、各 600 エッジ程度）だけを試し復号し、**すべての窓で**層スコアが閾値を下回った場合だけ全体の復号を省く。先頭だけで判断しないのは、途中から始まった記録や先頭のゴミで正解を捨てないため。打ち切った仮説も「打ち切り」の印と窓での指標を付けて残し、打ち切りあり・なしの評価を並べて、失った正解の数と短縮できた時間を測る。
- 除外は2種類に分ける。**確実な除外**は、プロトコルの定義から「ありえない」と言える規則（例: I²C の線が確実に LOW でアイドルしている、CS の切り替えが CLK より多い）で、復号の前に共通の下調べだけで判定する。各規則は、正解付きのコーパスとストレス条件で「正解を1件も除かない」ことを監査してから使う。経験則による除外は、監査で損失が出たら使わない。
- 周波数、ビット時間、語長・文字長、アイドルレベル、ピン同士の相関（クロックと、それに相関の高い線の組）は、**プロトコルの解析器ではなく共通の下調べ**で推定する。解析器はそれを受け取って候補を作る。
- 掘る順番は、階層ごとの幅優先ではなく、共通の下調べから付けた見込み点の高い順に掘る**最良優先**を試す。止める条件（残りの見込み点で今の最良の説明を覆せない）を測って決める。
- 多数の系統の展開はコストが高い。例えば 500 万エッジのフリーランクロックが1本あるだけで、UART の総当たりが数時間かかる。早期打ち切りの有無を、本番の性能設計（窓の大きさ、並列化、ストリーミング）の判断材料にする。

### 後段に合わせた出力と、分析前のヒント（2026-09-28 追加）

- 同じ結果を、後段に合わせて**射影**して出す。`final`（主張ごとの最上位の解釈、CLI・スクリプト・AI 向け）、`all`（全段をサンプル位置付きで、GUI の注釈向け）、`select`（`i2c.transactions` のようなパスで段と項目を選ぶ）。sigrok の注釈／OUTPUT_PYTHON／OUTPUT_BINARY、Saleae のバブル／FrameV2／データ表と同じ3分けになる（[優先度の調査](protocol-priority.ja.md) 6 節）。
- 中間の段は、エンジンがプラグインに渡した型付きストリームへの参照として残し、プラグインの作者に負担をかけない。
- 次に試すこと: フレームの欄に役割（Header、Address、CRC、Ack … Pico の色分けに相当）を付け、GUI の色分けと推定の根拠の表示を同じ情報から作る。
- 分析前のヒント（使っている方式、ピンごとの方式・役割・ボーレート、除外するピン）で、試す範囲を絞る。ヒントだけで結論は決めず、プラグインの検査はそのまま行う。

### 解析器の段とスコアのプラグイン化

UART の上には行テキスト、AT コマンド、NMEA、Modbus RTU、実験マーカーなど、さらに上位のプロトコルが乗る。I²C・SPI の上にも機器固有のレジスタアクセスがある。そこで解析を**型付きの出力を受け渡す解析器の段**として組む。

| 段の出力型（案） | 例 | 次の段の例 |
| --- | --- | --- |
| エッジ列（線） | 匿名の D0〜Dn | UART、I²C、SPI の各復号器 |
| バイト列（時刻・誤り付き） | UART のバイト、SPI の MOSI/MISO | 行分割、Modbus RTU、SLIP/COBS |
| 取引・転送 | I²C のアドレス＋データ、CS 区間の SPI 転送 | 機器レジスタ、SHT30 の測定＋CRC |
| メッセージ | テキスト行、NMEA 文、Modbus フレーム | マーカー文法、コマンド列の抽出 |

- 各解析器は「受け付ける型」「出す型」「候補の提案（パラメータの列挙）」「その段のスコア項目」を持つ。エンジンは、ある型の出力が得られるたびに、その型を受け付けるすべての解析器を試す（枝切りなし）。
- **スコアは解析器の本体と分ける。** 段ごとのスコア項目の計算、項目から段の点数への合成、上位の支持を下位へ戻す規則、組み合わせの総合点と判定を、それぞれ差し替えられる部品にする。本番ではこれを利用者が追加できるプラグインにする予定なので、プロトタイプでも**同じ構造のまま合成方法を入れ替えて比較**し、必要なインターフェースを洗い出す。
- **段の切り方そのものも検証対象にする。** 例えば UART を「ビット → フレーム → バイト」と細かく分けるか「エッジ → バイト」とまとめるか、上位の支持を直下の段だけに返すか全段に返すかを比べ、スコアの説明しやすさ、プラグインの書きやすさ、計算量への影響を記録する。

プロトコルの対象は、まず **UART、I²C、SPI** の3つ。上位は、正解付きで作りやすく性質の異なる**テキスト行・NMEA（チェックサム）・Modbus RTU（CRC）・既存のマーカー文法**から始める。RVSWD / SWIO / 1-Wire などは「対象外なのに誤って確定しないか」を試す負例として使う。

## 評価の仕組み

プロトタイプの最初の成果物は、推定器ではなく**評価ハーネス**とする。

- **正解ラベルの分離:** 読み込み時にチャンネル名を `D0…Dn` に置き換える。元の名前と既知の方式・パラメータは別の正解ファイルに置き、推定器からは見えないようにする。
- **コーパス:**
  - 実記録: I2CDeviceDB の4件（UART_TX / SCL / SDA、8 MHz）、wch-protocols の RVSWD・SWIO（負例）
  - 生成: UART（速度・パリティ・ストップビット・極性）、I²C（100k/400k、クロックストレッチ、NACK）、SPI（モード0〜3、MSB/LSB、CS あり/なし）、紛らわしい信号（PWM、方形波クロック単独、ランダム遷移、静止線）、ジッター・グリッチ・途中開始
- **指標:**

| 指標 | 意味 |
| --- | --- |
| 正答率 | 線の割り当て・方式・主要パラメータが正解と一致した割合 |
| 誤確定率 | 間違った結論を「確定」と出した割合。**最も重視し、0 に近づける** |
| 保留率 | 正解があるのに「拮抗 / 不明」とした割合。誤確定よりは許容する |
| パラメータ誤差 | ボーレートやクロック周波数の推定誤差 |
| 復号一致 | 確定した場合の復号バイト列と正解の一致率 |
| 処理時間 | サンプル数・エッジ数に対する時間。本番の性能目標の手掛かりにする |

## マイルストーン

各段階は「作る → コーパスで測る → 結果を記録」を1サイクルとする。合格基準に届かない場合は、原因を記録して方式を変えるか、その段階の範囲を縮める。

| # | 作るもの | 合格基準（初期値。測定後に見直す） |
| --- | --- | --- |
| M1 | 読み込み（.sr、生成器）、匿名化、正解ファイル、評価ハーネスの骨組み | 実記録・生成データを同じ形式で読める。正解が推定器から見えない |
| M2 | L1〜L3: 基本情報、ラン幅ヒストグラム、基本時間単位、線の分類 | 静止線を100%識別。UART の速度誤差 ±2% 以内。クロック線と UART 線を取り違えない（SCL の誤判定を再現しない） |
| M3 | L4: 周波数成分の一致と同期関係から線の組を作る | I²C の SCL/SDA 組、SPI の CLK/データ/CS 組が上位1位に入る割合 ≥ 95%（生成）かつ実記録4件すべて |
| M4 | L5: UART / I²C / SPI の最小デコーダ（誤り・未解釈を位置付きで出す） | 正しい仮説での復号一致が生成データで ≥ 99%、実記録で sigrok の結果とバイト一致 |
| M5 | L6: 全系統の多層スコアリング、組み合わせ探索と判定 | 誤確定率 ≤ 1%、保留率 ≤ 10%（生成）。RVSWD / SWIO を UART / I²C / SPI と確定しない。各層で枝切りした場合に正解を失う割合を測れる |
| M6 | 厳しい条件でのストレス評価と、本番へ引き継ぐ知見の整理 | ジッター・グリッチ・途中開始・速度変更の影響を表にまとめ、本番の設計判断を列挙できる |
| M7 | 高速化するコアとプラグインの境界の検証（下記） | 段ごとの呼び出し回数・データ量・時間の実測と、境界方式ごとの見積もりから、どの段をプラグインにできるかを表にできる |

M2 までは単線の性質、M3 以降は線の組の性質を扱う。M5 のスコアは、[ワークフロー調査](../experiments/initial-feasibility/workflow-findings.ja.md) で挙げた項目（説明できた範囲、規則への整合、反証、上位からの支持、取得品質）を別々に計算し、それらから判定を導く形で試す。単一の数値にまとめるかどうかは、測定結果で決める。

## 高速化するコアとプラグインの境界

本番では Rust などで高速化するが、解析器やスコアは利用者がプラグインで追加できるようにしたい。どこで分けて、どうつなぐかを次の順で確かめる。

1. **計測:** エンジンで、解析器・スコア部品ごとの呼び出し回数、1回あたりの入出力の大きさ（エッジ数、バイト数、フレーム数）、時間を取る。
2. **カーネルの切り出し:** 解析器が使う数値処理（指定位置のレベル取得、ビット格子のサンプリング、フレームの連鎖、窓への所属判定、位相統計、ビットのバイト化、同期ビット列の抽出など）を、まとめて呼ぶ関数群（カーネル API）として分ける。解析器の時間が、カーネルの内側と外側（プラグイン側の組み立て）のどちらにかかるかを測る。
3. **見積もり:** 境界の方式ごとの1回あたりのオーバーヘッドとデータ受け渡しの費用を実測値に当てはめ、全体の処理時間を見積もる。

| 境界の方式（候補） | 想定する長所 | 確かめる短所 |
| --- | --- | --- |
| Rust のネイティブプラグイン（動的ライブラリ・C ABI） | 最速。カーネルと同じ速さで書ける | ビルド環境、ABI の互換性、配布の負担 |
| WASM プラグイン | 言語を選べ、隔離と持ち運びに強い | 呼び出しとメモリのコピーの費用 |
| 埋め込みスクリプト（Python など） | 書きやすく、試行錯誤が速い | 細かい呼び出しでの遅さ。まとめて呼ぶカーネル API が前提 |
| 別プロセス（パイプ・共有メモリ） | 言語を問わず、落ちても本体が巻き込まれない | 直列化の費用、呼び出しの遅延 |

仮説として、**エッジやサンプルを1つずつ扱う処理はコアのカーネルに置き、プラグインは「カーネルをまとめて呼ぶ組み立て」と「フレーム・バイト以上の上位処理」と「スコア」を担う**形を置く。予備の実測では、UART 解析器の時間の約半分が NumPy の searchsorted（カーネル相当）、残りが Python 側の組み立てだった。見積もりの定数は、Rust のツールチェーンを用意できた段階で小さなベンチマークで確かめる。

## プロトタイプの前提と範囲外

- **言語:** Python 3 + NumPy。速度より試行錯誤の速さを優先する。本番の言語（Rust が有力候補）とは切り離す。
- **置き場所:** `prototype/`。コードは本番へ移植しない前提で書く。構造の良し悪しより、測定できることを優先する。
- **範囲外:** GUI、プロジェクト保存、ライブ取得、プラグイン方式、アナログ・低頻度測定、上位プロトコル（CRC やマーカー文法による支持は M5 の追加検査として扱う）。これらは [今後の検証計画](next-plan.ja.md) に残す。

## 本番実装への移行

次がそろったら、プロトタイプを凍結して本番実装の設計に移る。

1. M5 の基準を満たすか、満たせない理由と代わりの方針が分かっている。
2. 各段階の入出力（エッジ列、ヒストグラム、線の分類、仮説、復号フレーム、スコア）の中身が固まり、本番のデータモデルの叩き台にできる。
3. 性能の見積もり（エッジ数あたりの処理時間、メモリ）が分かり、本番で必要な工夫（チャンク処理、キャッシュ、並列化）を判断できる。

本番へ引き継ぐのは**コードではなく**、評価コーパスと正解ファイル、評価指標、アルゴリズムの知見、失敗例の一覧である。評価コーパスは本番実装の回帰試験としてそのまま使う。
