# 設計の決定と理由

[English](design.md)

実装の方針として決めたことと、その理由をまとめます。ファイル形式と記録の形式の規則は [ファイル形式](wireskein-format.ja.md) と [記録の形式](run-format.ja.md) にあります。

## 1. 版と互換性

- **版 1 になるまでは、互換のない変更をしてよい。後方互換は考えない。** 古い形式のファイルを読む口や、古い名前の別名は作りません。形式の名前（`wireskein/1`、`wireskein-run/3`）は、互換のない変更のたびに上げ、知らない版ははっきりしたエラーで断ります。
  - 理由: 利用者が限られている今のうちに、形式と API の誤りを直せるようにするためです。黙って古い形式を読むと、意味の変わったキーを誤って解釈します。

## 2. 実装の言語と置き場所

- **参照実装は Python で進める。** 依存は numpy だけです。ファイル形式と記録の形式は言語に依存しない仕様として定め、互換があればほかの言語で実装してよいものとします。
  - 理由: 試験での照合（ピンや方式を与え、短い区間を読む）では、Python と numpy で足ります。遅いのは 1 ビットずつ回す Python のループだけで、そこは numpy の一括処理（カーネル）に寄せます。
  - Python の実装では、試験のスクリプトがそのまま import できるように、記録と保存（`wireskein.runlog`、`wireskein.fileformat`）は標準ライブラリだけで動かします。
- **ネイティブ（Rust など）の実装を作るなら、別のリポジトリにする。** このリポジトリには入れません。共有する資産は、TOML の定義（`decl/`）と、正解付きの評価コーパス（`corpus/fixtures/`）です。
  - そのために、TOML の式を「Python の eval」として定義しません（許す構文を限ったもの、§3.2）。

## 3. 復号（`wireskein analyze`）

### 3.1 段の構成

未知の記録を、次の段で読みます（`src/wireskein/_engine/staged.py`）。

```text
エッジ列
 └ 共通の下調べ: アイドル、ビット時間、文字長、クロックの局所周期、バースト、ピン同士の相関、CS 様の境界
    └ ピンの分類（静止は除外）→ ピンのまとまり（クロック＋相関の高いピン＋選択線 / 単独のピン）
       ├ 同期: SyncBits → Frames（CS / START・STOP / 間隔）→ Words → I²C、SPI、RVSWD、SWD、未知の同期シリアル
       ├ 非同期: RateBlocks（ビット時間ごとのブロック）→ Chars（ブレーク付き）→ UART、LIN、DMX512
       │    └ 時刻付きバイト列 → 行、NMEA、Modbus RTU、マーカー / TX・RX の組 → SCPI
       └ パルス: PulseSymbols → SWIO
                    RVSWD・SWIO → DMI → RISC-V Debug Module
```

決めたことと理由:

- **周波数・ビット数・ピンの相関は、方式の解析器ではなく共通の下調べで推定する。** 同じ推定を各解析器が繰り返さず、解析器はエッジに触れずに型付きのデータ（SyncBits、Chars など）を受け取ります。方式を足すときに書くのは、区切り方と解釈だけです。
- **段を分ける基準は、後続の処理を減らすことか、使う側が 2 つ以上あること。** どちらでもない段は統合します。例えば RateBlocks → Chars は UART・LIN・DMX512 が共有するので分けています。
- **段の中で決めきれないことは、兄弟の候補として下へ渡す。** サンプリングする端、グリッチを除く幅、フレームの区切りの閾値などは、どちらかに決めず両方の見え方を作り、プラグインの検査の点数で選びます。早い段で 1 つに決めると、正解を落とす例があったためです。
- **クロックのある方式は速度の変化で分割しない。UART は分割する。** クロックの端でビットを取る方式は周波数に依存しないので、速度の変化は注釈として残すだけです。UART はクロックがないので、ビット時間ごとのブロックに分けてから読みます（途中で速度を上げる書き込みなど）。
- **時間の推定は周波数に依存させない。** クロックらしさ、バーストの区切り、ピン同士の位相は、記録全体の周期ではなく、前後の間隔との比で測ります。

### 3.2 方式の書き方

- **1 フレームの中で閉じる方式は、TOML で宣言的に書く**（`src/wireskein/decl/*.toml`: I²C、SPI、RVSWD、SWD、CAN）。語の幅、ビット順、欄の切り出し、固定値、長さの規則、繰り返す語、パリティ、CRC、ビットスタッフィング、条件付きの欄まで書けます。同じ方式を Python でも書いて二重に持つことはしません。
  - 理由: コードなしで定型の大半を覆え、検証が機械的で、ほかの実装でも同じ定義を使えるからです。
  - 式は、整数の計算、比較、論理、三項演算子、min/max に限ります。ループと、フレームをまたぐ変数は入れません。
  - 定義では書けない探索（RVSWD の停止間隔での切り直しなど）は、コアの処理として名前で呼びます（`frame.reframe = "rvswd_stop"`）。例外をコアに閉じ込め、定義には持ち込みません。
  - 点数の付け方は解釈器が共通に持ち、定義は `[score]` で証拠の項目を選びます。例えば SPI は `count_frames` で、規則に合うフレームを 1 つずつ証拠に数え、k 個がすべて偶然に合う確率（`8n` なら (1/8)^k）を差し引きます。1 つの CS の窓に別のバス全体が入った仮説が、本当の区切りと同点にならないようにするためです。I²C は START/STOP の条件が区切りの証拠になるので、これを使いません。
- **フレームをまたぐ状態や構文を持つものは Python で書く。** RISC-V Debug Module（DMI の上の抽象コマンド）、SCPI などです。
- 埋め込みのスクリプト言語（JS、Lua、WASM など）は採りません。TOML と Python の 2 つで足り、3 つ目の言語を覚える費用を避けます。

### 3.3 判定

- **確定 / 有力 / 拮抗**（`confirmed` / `likely` / `ambiguous`）は、点数と、2 位との差（余裕）で決める。1 位の点数だけでは決めません。
  - 余裕は、その主張と同等の仮説を禁止した最良の説明との差で測ります。同じ線の組の中だけで比べると、CS の有無やビット順だけが違う仮説で余裕が 0 になるためです。
- **誤って確定しないことを最も重視する。** 正解があるのに保留する方が、誤確定よりは許されます。
- **証拠の量を点数に入れる。** 検査ごとに「偶然に通る確率」を見積もり、その情報量で数えます。数フレームしかない記録で、偶然の一致を確定と取り違えないためです。
- **上位の支持は下位に返すが、支持がないことは減点しない。** 上位のない生のバイナリも確定できるようにするためです。
- **「未知の同期シリアル」は、既知の規則で説明できない分だけを根拠にする。** 既知の方式の仮説を先に置き、ピンが重なる未知の仮説はそれに勝たせません。

### 3.4 どこまで主張するか

- **上位の解釈は、下位の結果を置き換えずに重ねる。** 上位が外れても、下位は正しいまま残ります。
- **自動で上がるのは、検算できる証拠がある段まで**（チェックサム、CRC、要求と応答の対応、標準の識別子）。
- **機種は、識別の証拠が出たときだけ主張する。** 識別子の値や CRC の一致がない「アドレスだけの一致」は主張せず、候補の一覧として出すだけです。I²C のアドレスは多くの機種が共有しているためです。命令表が同じで証拠で区別できない機種は、まとめて 1 つの主張にします（例 `SHT30 | SHT31`）。
- デバイスの定義は、データシートの書き方に合わせた型で書きます: コマンド表、レジスタ表、メッセージの枠（[`decl/devices/`](../src/wireskein/decl/devices/README.ja.md)）。

### 3.5 出力とヒント

- **出力は後段に合わせて選ぶ。** `--mode final`（主張ごとの最上位の解釈。CLI、スクリプト、AI 向け）、`all`（全段をサンプル位置付きで。GUI の注釈向け）、`select`（パスで段と項目を選ぶ）。深さは `--depth transport|frames|protocol|device`。
  - 中間の段は、エンジンがプラグインに渡した型付きのデータへの参照として残すので、プラグインを書く人は何もしなくてよい。
- **時刻はサンプル（刻み）の番号で出す。** 後段は元の記録を読まずに秒へ換算でき、GUI は元の波形へ戻れます。
- **ヒント（方式、ピンごとの方式・役割・ボーレート、除外するピン、デバイスの定義の選択）は、試す範囲を絞るだけ。** ヒントだけで結論は決めず、プラグインの検査はそのまま行います。

## 4. 照合（`wireskein verify`）

- **照合は推定ではない。** 試験がピンと役割と期待を渡し、指定した役割で復号して比べます。自動判定に頼らないので結果が安定し、1 回だけの短い通信（発見の証拠としては弱い）も照合できます。
- **検査できなかったもの（`unchecked`）は、既定で失敗にする。** 多くは試験の書き間違いか、配線・キャプチャの抜けだからです。測るだけと頼んだもの（`measured`）は失敗にしません。
- **許容誤差は名前で相対か絶対かが分かるようにする**（[記録の形式](run-format.ja.md) §2.3）。
- **UART のボーレートは、期待から独立に測る。** 1 文字の中の同じ向きのエッジどうしの間隔からビットの幅を最小二乗で求め、期待の値は候補を選ぶのにだけ使います。期待で切った窓で測ると、期待がずれたときに測定値もずれるためです。
- **キャプチャの時間軸の乱れは隠さない。** プローブが遅れを報告したとき（`time_base_slipped`）や、エラーの文字だけエッジが格子からずれているときは、判定は変えずに NG の理由に添えます。受信器の誤りと、ソフトで歩調を取るサンプラーの停止を区別するためです。
- **1 つの乱れは 1 件と数える。** UART でフレームエラーの後は、次の 1 文字分の idle まで読み直しを待ちます。
- **要約のチャンネル（`interval-any`、`interval-latch`）では、要約から確かに言えることだけを答える。** 決まらないものは未検査です。

## 5. ファイルと時刻

ファイル形式の規則と、それぞれの理由は [ファイル形式](wireskein-format.ja.md) §1 にあります。要点:

- 独自の形式（`.wireskein`）を持ち、各チャンネルを自分のレートのまま、取ったサンプルだけで持つ。
- ADC の値は生のまま保存し、電圧への換算や補正は分析のときに選ぶ。
- プローブが返す時刻は推定値として記録し、分析で求めた合わせ込みは別の添付に入れる。

### 5.1 パラレル出力の ADC（まだ実装しない）

パラレル出力の高速 ADC をプローブのデジタルの入力につないで取る形は、**プローブは ADC を知らず、ビットから値に戻すのは分析側**とします。

- プローブは普通のロジアナとしてデータのピンと CLK を取るだけにすれば、OEP でも sigrok でも同じ基板と同じ変換が使えます。
- 基板の知識（ピンの並び、符号の形、パイプラインの遅れ、入力範囲）は基板についてくるもので、プローブに持たせると基板を替えるたびにプローブを変えることになります。
- プローブで値にしても帯域は減らず、生のビットがあれば符号の形や遅れの誤りを分析のときに直せます。
- 戻した値は今の `analog` の encoding で持てます。基板の記述は、そのチャンネルの `acquisition` に入れます。

## 6. 評価

- 推定の正しさは、正解付きのコーパス（`corpus/`）で測ります。チャンネル名を `D0…Dn` に置き換えて並びも入れ替え、正解（`truth.json`）は推定器から見えない所に置きます。
- 調整に使ったシードと使っていないシード、ノイズの条件（グリッチ、途中開始、低いサンプリング、ジッター、速度の変化）を分けて測り、過学習とノイズへの弱さを確かめます。
- 評価のスクリプトは [`research/`](../research/README.ja.md) にあります。
