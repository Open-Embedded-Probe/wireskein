# WireSkein — ユースケースと得たい結果

[ビジョン](project-concept.ja.md) と [共通の使い方](workbench-model.ja.md) を具体的な調査で確かめるための事例である。各例は最初の版の対応一覧や実装方式を定めるものではない。

ロジックアナライザの調査では、「何が流れたか」「期待とどこが違うか」「いつ、何をきっかけに起きたか」「どの条件で起きたか」を知りたい。コマンド、タイミング、制御線、マーカー、アナログ値のうち、問いに必要な情報を取り出し、その後の判断へつなぐ。

## 1. 正体の分からない信号線を調べ始める

四つの線を取得し、電源と GND は分かるが、残りの二つが何を運んでいるか分からない。まず活動区間、周期、線同士の連動、おおよその速度を見る。独立したクロックで同期する通信か、UART のように一定のビット速度で読むものか、赤外線のように搬送波を含むものか、見当を付けたい。

得たいのは、UART、I²C、SPI、SWD などの候補、チャンネルの役割の候補、その根拠、まだ分類できない範囲である。利用者が「この線はクロック」「この程度の速度」と指定して候補を絞ったり、推定を修正したりできるようにしたい。

UART の候補が読めた後は上位も調べる。例えば候補の階層は次のようになる。

~~~text
信号
└─ UART候補
   ├─ SCPI候補
   │  └─ 機器固有のコマンド候補
   └─ Modbus候補
~~~

各段階で、一致率や規則に合う範囲、合わない位置、未解釈を確認する。SCPI の構文がすべて合っても、機器固有のコマンドが既知とは限らない。一段の一致率を調査全体の正しさとは扱わず、次に試す候補や区間を選べることが必要である。数値の定義と評価方法は検証で決める。

## 2. 速くなった通信をノイズと誤認せず、解析を改善する

構想のきっかけとなった RVSWD の調査では、V203 の信号の一部をノイズが多い区間と見なしたが、実際には途中で通信が速くなっていた。取得レートを 50 Msps から 100 Msps に上げて取り直すことで分析が進んだ。独自解析がノイズとして落とした成分が重要な信号だった例もある。

まず知りたいのは IN/OUT のコマンド列である。その上で、周波数がどこで変わったか、未知の信号がどこにありどんな特徴を持つか、前処理で何を除いたかを確認したい。詳細なエッジ列は必要なときに取り出す。

元の記録と解析条件へ戻り、ノイズ判定を変える、取得レートを見直す、未知の区間を手掛かりにプラグインを修正する、同じ記録を再実行する、という調査を支える。解釈できたコマンドを利用しながら、未解釈の区間を置き去りにしないことが目的である。

## 3. 既知の通信を必要な情報に絞って読む

SCPI のように既知の通信では、通常は「いつ、何を送り、何が返ったか」の時系列だけで十分なことがある。別の問いでは、個々の内容よりプロトコルとの整合、応答時間、ジッターの概況を見たい。

同じ分析から、例えば次の出力を使い分ける。

| 問い | 必要な出力 |
| --- | --- |
| どの操作が行われたか | 送受方向とコマンド・応答の時系列 |
| 通信の状態に問題があるか | 一致状況、タイミングの指標、例外の区間 |
| 正常な実行と何が違うか | 時刻や毎回変わる CRC などを省いたコマンド列 |
| 機器固有の命令まで理解できたか | 既知のコマンドと未対応のコマンドの区別 |

正常時との差分や試験の合否は外部の後工程で判断する。コアは同じ条件・項目の出力を作り、比較に必要な素材を渡す。時刻や CRC の異常自体を調べる場合は、その項目を残す。

SPI の一部で1ビットずれが疑われる場合などは、不一致の区間とその前後を取り出して条件を変えたい。規則から外れた通信なのか、解析条件の誤りなのかを、候補と元波形から調べられる必要がある。

## 4. 目的に合わせてフィルターを選ぶ

ボタン信号の物理的なチャタリングを調べるときは、細かい変化を残す。ソフトウェアのチャタリング防止後の動作を調べるときは、その挙動に合うフィルターを適用して操作イベントを見たい。

搬送波のある信号も、搬送波自体を見る場合と、除去して変調された内容を見る場合がある。ノイズゲートや補正も目的ごとに条件と有効・無効を選ぶ。入力段に加え、解析途中や解析後に情報を絞る用途もある。

処理前後と適用条件を確認でき、標準のフィルターで足りなければ自分で追加できることを目指す。フィルターで除いたものを元の観測から消したことにはしない。

## 5. 長回しに実験の区切りを付け、必要な区間だけ取り出す

外部の試験ツールが「実験1」「電圧5V」「負荷ON」と順にマーカーを出し、条件を変えるときに次のマーカーを出す。キャプチャは止めずに続ける。後から「実験1の電圧5V・負荷ON」だけを選んで分析できれば、取得のたびにファイルを分けたり、波形から時刻を探し直したりする手間を減らせる。

負荷ON/OFFが独立の試験なら区間ごとに処理し、必要な実データを別ファイルへ取り出す。切り替わり前後の連続変化を見るなら電圧5V全体を処理し、子のマーカーをイベントとして使う。[マーカー階層の例と範囲](workbench-model.ja.md) に共通の振る舞いを示す。

予期しない信号について、直前にどの機器・処理・操作のイベントがあったかを調べる使い方もある。マーカーは原因を断定するものではなく、調べる場所と実験の文脈を与える。

## 6. アナログ波形と低頻度の測定値を結び付ける

LDO やトランジスタの特性を測るため、外部の自動計測が電源や電子負荷の設定を変え、電圧・電流・温度を数秒から数分ごとに記録する。マーカーには設定値と試験段階を入れる。WireSkein は条件と観測値を対応付け、後工程が再集計しやすい構造で出す。この用途では通信プロトコルの復号を使わなくてもよい。

例えば次のような対応が得られれば、後工程のスクリプトは条件ごとの集計や特性の計算に集中できる。列名や形式は例である。

| 区間 | 電源設定 | 負荷状態 | 出力する観測 |
| --- | --- | --- | --- |
| 実験1／電圧5V／負荷ON | 5V | ON | この範囲の電圧・電流・温度と測定時刻 |
| 実験1／電圧5V／負荷OFF | 5V | OFF | この範囲の電圧・電流・温度と測定時刻 |

別の場面では、デジタルの制御信号やコマンドの前後に、電圧低下や電流ピークがあるかを調べる。異なる機器の記録は共通イベントなどで時間を合わせる。5分間隔の測定で許せる数秒のずれが、高速な信号の前後関係でも許せるとは限らない。時間精度の違いを隠さずに調べたい。

## 7. 繰り返しの実験をバッチ処理し、エビデンスを残す

pytest などで機器を動かし、各回のキャプチャを同じプロジェクトへ追加する。GUI で作ったフィルター・復号・出力の処理を、CLI から別の記録やマーカー区間へ適用する。どの回が成功・失敗かは外部の試験ツールが知っており、調査対象も呼び出す側が指定する。

一回の処理で簡易レポート、詳細なコマンド列、対象区間の実データを出す。最初は簡易レポートを見て、解釈がおかしければ処理を直して再実行する。確認できた結果と、必要なら .sr のような元の記録形式で出した区間データを、エビデンスとして別の場所へ保全する。

後工程は各回の出力から差や例外を探し、必要な回・区間の詳細へ進む。ファイル数が増えても設定をやり直さず、保全したデータと条件から対応する結果を再現できることが目標である。一部を切り出しても再現できる条件は実験で確かめる。

## 8. 大量の記録を、人や AI が段階的に調べる

長い記録の全サンプルや全イベントを初めから読む代わりに、簡易 Analyze で活動区間、値や周期の分布、変化点、未解釈の位置を知る。その情報から、関心のある信号・区間のコマンドや測定値、さらに必要なら元の波形へ進む。

変化の少ない記録も、まず概況を読み、変化した部分だけ詳しく調べたい。概要・詳細を両方あらかじめ出しても、要求した範囲を後から出してもよい。情報量と AI のトークン消費を抑えながら、まれな異常や未解釈が概要から消えないことが重要になる。保存量を減らすために元データを捨てるかは別の判断とする。

## 9. 手近な取得環境を使い、必要な機能を足す

Arduino のシリアル出力のようなカンマ区切りの数値を受信し、GUI でプロットし、保存後にも見直す。イベント用の文字列も一緒に記録できれば、数値の変化と操作を追いやすい。専用の機器アダプタがない場面でも利用したい。

未対応の計測器、独自形式、独自プロトコルやフィルターを容易に追加し、同じプロジェクトと処理の流れへ取り込めることを目指す。簡単にビルドできる環境も拡張の選択肢とする。複数アダプタによる同時取得の保存単位、ブラウザ対応、具体的な追加方法は検証計画で扱う。
