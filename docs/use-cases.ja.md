# WireSkein の目的とユースケース（検討用）

この文書は、製品として何を可能にしたいかを整理するためのたたき台である。機能の採用、優先順位、内部構造、実装方法はまだ決めない。

## 目指す体験

異なる機器や形式から得たデジタル信号、アナログ波形、測定値、メッセージ、操作記録を一つの作業の中で見渡し、現象が起きた場所を見つけ、その前後に何があったかをたどれる分析環境を目指す。

利用者は必要に応じてデータにラベルを付け、複数の記録の位置を合わせ、既知の条件を指定できる。アプリはデータの特徴や関係から解釈の候補を提示し、その根拠を確認できる。記録時に用途を決め切らなくても、後から別の観点で調べられることを重視する。

ロジックアナライザの解析は重要な出発点だが、対象をデジタル信号だけに限定しない。

## 利用場面

### 1. 未知のデジタル通信を調べる

ESP32-P4 を使ったロジックアナライザの記録や既存の `.sr` ファイルを開く。利用者は通信方式や速度を知らない状態から、信号の変化、通信の区切り、あり得るプロトコルを見つけたい。候補が複数ある場合は根拠を比べ、必要なら条件を指定して調べ直したい。途中で通信条件が変わる記録も対象になる。

**得たい結果:** 波形のどこに何が流れたかを、元の信号までたどって説明できる。

### 2. デジタル信号とアナログ波形を一緒に見る

制御信号や通信と同時に、電圧、電流などのアナログ波形を記録する。コマンドの前後で電圧が落ちたか、特定のイベントに電流のピークが対応するかを調べたい。

**得たい結果:** 種類の違う波形と解析結果を同じ作業画面で行き来し、関係する箇所を見つけられる。

### 3. 複数の計測器で特性を取る

SCPI などを使って計測器や電子負荷を操作し、設定を変えながら、電圧・電流・温度などを数秒から数分ごとに収集する。測定値だけでなく、その時点の設定値や操作、実験の段階も残し、条件ごとの差や時間による変化を分析したい。既存の自動計測で行う実験を、記録から分析まで一つの流れとして扱いたい。

**得たい結果:** 複数機器の記録を一つの実験として扱い、設定と測定結果の対応を後から追える。この場面では、数秒の時刻ずれが問題にならない場合もある。

### 4. 手軽なデータ送信をそのまま記録する

Arduino などがシリアルへ送るカンマ区切りの値を受け取り、リアルタイムにプロットし、後で同じデータを見直す。専用の機器アダプタがなくても、小さな実験をすぐ始めたい。

**得たい結果:** データの受信から可視化、保存、再表示までつながる。

### 5. 実験中にイベントと階層を付ける

機器や制御スクリプトから UART などでマーカーを送り、試験の開始・終了、条件の変更、段階の切り替えにラベルを付ける。試験、条件、手順のようにマーカーを階層的に整理できると、後からイベントごとに記録を見たり、目的の手順へジャンプしたりしやすい。

**得たい結果:** 波形や測定値だけでは分からない実験の文脈を、記録と一緒に残せる。マーカーの記法や階層の表現方法は未定。

### 6. 長回し記録を実験ごとに取り出す

ロジックアナライザなどで取得を続けながら、UART などで「次に行う実験」や条件変更をマーカーとして記録する。後からマーカー間の区間を取り出し、互いに独立した実験なら別々のデータとして保存・分析したい。連続的な変化を追う実験なら、区間を分けずに記録全体を分析したい。

**得たい結果:** 一度の長い取得から、目的に応じて区間の切り出しと全体分析を選べる。切り出した区間を元の記録やマーカーとどう結び付けるかは未定。

### 7. 長時間の記録から変化した箇所を見つける

長時間データを流し続け、普段と異なる値やイベントが現れた場所を見つけたい。変化の少ない区間は簡潔に扱い、気になる区間を後から詳しく調べたい。

**得たい結果:** 長い記録でも全体像と注目箇所を見失わない。保存量を減らす場合、後からどこまで再分析できるかは別途決める。

### 8. 別々に得た記録を合わせて調べる

ロジックアナライザ、計測器、シリアルログなどが別々に記録したデータを同じ実験として開く。共通のイベントや特徴的な変化を手掛かりに位置を合わせ、必要なら手動で調整したい。

**得たい結果:** 厳密な同期が必要な場面も、多少のずれを許容できる場面も扱える。必要な精度は利用場面ごとに考える。

### 9. 新しい機器や分析方法を追加する

利用したい計測器や独自のデータ形式、解析方法が標準で用意されていない。利用者や第三者が追加し、ほかの記録・表示・分析機能と組み合わせたい。

**得たい結果:** 新しい機器や分析方法を過度な手間なく追加できる。ビルドの要否を含む具体的な拡張方式は未定。

### 10. GUI と CLI から同じ記録を扱う

波形を見ながら対話的に調べるときは GUI を使い、収集や繰り返しの分析を自動化するときは CLI を使う。どちらでも同じ記録と解析結果を扱い、GUI を別のものに替えても分析の仕組みを利用し続けたい。

**得たい結果:** 共通の分析機能を複数の操作方法から利用できる。各操作方法が提供する体験や機能の完全な一致は求めない。ブラウザでの利用も候補だが、それによって主要な利用場面を制限するかは後で判断する。

## ユースケースに共通する要望

- **取り込む:** ライブ取得と既存ファイルの両方を扱う。
- **関連付ける:** 種類や記録元の異なるデータを、一つの調査や実験の中で扱う。
- **見つける:** 変化、イベント、通信、異常や興味深い区間を探す。
- **解釈する:** 自動分析の候補とその根拠を示し、利用者の知識も反映できる。
- **たどる:** 集計値や高次のイベントから、元の記録と周辺状況へ戻れる。
- **残す:** データに加え、ラベル、条件、解析結果、利用者の判断を後から使える形で保存する。
- **区切る:** 一続きの記録を、必要に応じて区間ごとに取り出し、また全体としても調べられる。

## これから確認したいこと

1. 最初に強く支えたい利用場面はどれか。出発点のロジック解析と、複数計測器による実験の位置付けをどうするか。
2. 「一つの実験」として、どこまでのデータや作業をまとめたいか。
3. 自動分析に最初に期待するのは何か。通信方式の候補提示、変化点の発見、記録同士の関係の発見などの優先度。
4. 長時間記録で、元データの保持と保存量の削減をどう選びたいか。
5. 解析アプリとして誰が主に使うか。機器開発者、試験担当者、趣味の電子工作利用者などで求める操作が変わる。
6. マーカーによる区間の切り出しを、どの利用場面で最も必要とするか。元の記録と切り出した記録の関係をどう残したいか。
