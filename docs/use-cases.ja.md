# WireSkein の目的とユースケース（検討用）

この文書は、製品として何を可能にしたいかを整理するためのたたき台である。機能の採用、優先順位、内部構造、実装方法はまだ決めない。

## 目指す体験

異なる機器や形式から得たデジタル信号、アナログ波形、測定値、メッセージ、操作記録を入力し、分析結果を後続の分析にも使える形で出力する。その上で、これらを一つの作業の中で見渡し、現象が起きた場所とその前後をたどれる分析環境を目指す。

利用者は必要に応じてデータにラベルを付け、複数の記録の位置を合わせ、既知の条件を指定できる。アプリはデータの特徴や関係から解釈の候補を提示し、その根拠を確認できる。記録時に用途を決め切らなくても、後から別の観点で調べられることを重視する。

ロジックアナライザの解析は重要な出発点だが、対象をデジタル信号だけに限定しない。

## 利用場面

### 中心: データを分析し、結果を次の分析へ渡す

ファイルやライブ入力などからデータを受け取り、利用目的に合った結果を取り出す。通信内容を知りたいなら送受方向とコマンド・応答の時系列、通信の安定性を知りたいならプロトコルとの整合やジッターなどを選べる。エッジ、パルス、周期などは、詳しく調べる場合や未知の信号を解釈する場合に利用する。得られた結果を別の観点で調べたり、さらに上位の意味へ解釈したりする際には、元のデータを毎回読み直して手作業で変換せず、分析結果を次の入力として使いたい。操作は CLI からでも GUI からでも始められる。

**得たい結果:** 分析の出力が画面上の表示に閉じず、独自スクリプトなどの後工程に渡せる。情報量を抑えた結果から、必要に応じて元データの位置と分析時の条件も追える。入力形式、出力形式、分析をつなぐ方法は未定。

### 自動テストの記録を後工程で調べる

pytest などの自動テストで機器を動かし、その間の信号や測定値をキャプチャする。WireSkein で記録を読み、分かる範囲のコマンドと応答を取り出す。周波数が途中で変わるなら、その位置と前後の周波数候補も示す。解釈できない信号は位置と観測した特徴を残す。これらの結果をテスト固有のスクリプトや AI を使った分析に渡し、期待した動作との照合や原因調査を進めたい。

**得たい結果:** テスト固有の分析を作るたびに記録形式の読み込みや基本的な特徴抽出を実装し直さずに済む。必要な箇所では元の記録を確認でき、共通の前処理で何を行ったかも分かる。AI に渡す場合は、関係する情報を選ぶことで入力するデータ量を抑えられる。

### 多数の記録から差と例外を探す（候補）

自動テストや繰り返しの実験で複数の記録を得る。正常時、異常時、設定変更の前後、ソフトウェア更新の前後を比べ、コマンドの欠落や追加、順序や時間の変化、未知の区間が現れた回を見つけたい。すべての記録を順番に開く前に、どの回のどこが異なるかを知りたい。

**得たい結果:** 多数の記録を簡潔に見渡して調査対象を選び、差のある箇所から個々の分析結果と元データへ進める。比較の基準や「異なる」の判断方法は未定。

### 大きな記録を段階的に調べる

長い記録を人や AI が調べるとき、最初に全サンプルや全イベントを受け取らず、記録の規模、信号の活動や値の分布、条件の変化、未解釈の区間を概観する。関心のある時間帯や信号を選び、その範囲のコマンド列、異常、さらに必要なら元の波形へ進む。

**得たい結果:** 調査に使う情報量を段階ごとに抑え、AI に渡す場合のトークン消費も減らせる。概観の段階で、未知の信号や例外的な変化を見落とさないことが重要。

### 1. 未知のデジタル通信を調べる

ESP32-P4 を使ったロジックアナライザの記録や既存の `.sr` ファイルを開く。たとえば四つの線のうち電源と GND は分かるが、残る二つが何の信号か分からない。まず、どの線が動くか、線同士がどう連動するか、同期クロックや一定のビット速度、搬送波らしい周期があるかを知りたい。その上で UART、I²C、SPI、SWD などの候補と、おおよその速度・周波数を見たい。候補が複数ある場合は根拠を比べ、必要なら条件を指定して調べ直したい。途中で通信条件が変わる記録も対象になる。

**得たい結果:** 最初は信号の種類と次に調べるべき線・区間の見当が付き、分析が進めば波形のどこに何が流れたかを元の信号までたどれる。分類できない部分も残る。

#### ロジックアナライザの記録で調べたいこと（候補）

- **何が行われたか:** コマンド、応答、状態遷移、処理の順序を知る。仕様を知らない通信では、その構造から探る。
- **期待どおりだったか:** 送ったはずの信号の欠落、余分な信号、応答の違い、プロトコルから外れたやり取りを見つける。
- **いつ起きたか:** 信号間の順序、応答までの時間、待ち時間、周期、ばらつき、途中の速度変更を調べる。
- **何と連動したか:** コマンド、制御線、マーカー、別の計測値の前後関係を見て、動作のきっかけを探る。
- **誰が、いつ始めたか:** 予期しない通信や信号変化の直前に、どの機器・処理・操作からイベントが出たかを探る。分からない場合も、候補と根拠を追えるようにする。
- **どんな条件で起きたか:** まれな失敗が出る直前の記録や、長回し中の特定の区間を取り出して調べる。
- **何が変わったか:** 正常時と異常時、設定変更の前後、ソフトウェアの版の違いを比べる。

これらは、動作を理解する、期待した動作を確かめる、異常の原因を絞るという目的にまたがる。必要な出力も、コマンド列、タイミング、未解釈区間、元の波形などで異なる。

### 解釈できない区間を再分析する

RVSWD のような通信を記録した場合、まず IN/OUT などの送受方向とコマンドを時系列で見たい。周波数がどこで変わったか、解釈できない信号がどの区間にあり、どんな特徴を持つかも知りたい。未知の区間を手掛かりに解析プラグインを修正し、同じ記録を再度解析して、分かるコマンドを増やしていく。

**得たい結果:** 既知のコマンド列を利用しながら、未解釈の区間を見失わずに改善と再解析を繰り返せる。前回と今回の解釈をどう管理するかは未定。

### ノイズと見なした変化を見直す

未知の通信を低めのサンプリングレートで取得し、短い変化をノイズとして除外して解析したところ、実際には途中で通信が速くなった区間を見落とした。より高いレートで取り直すと解釈が進んだ。解析中も、除外した変化がどこにどの程度あったか、短いパルスが十分なサンプル数で捉えられているかを確認したい。

**得たい結果:** 取得条件やノイズ判定による見落としの可能性に気付ける。必要なら取得レートを上げて取り直し、前処理の条件を変えて再分析できる。高いレートで得た記録を、十分な詳細が残る範囲で軽い表示や出力へ変換することも候補とする。元の記録がある場合は、それを失わずに確認できる。

### 2. デジタル信号とアナログ波形を一緒に見る

制御信号や通信と同時に、電圧、電流などのアナログ波形を記録する。コマンドの前後で電圧が落ちたか、特定のイベントに電流のピークが対応するかを調べたい。

**得たい結果:** 種類の違う波形と解析結果を同じ作業画面で行き来し、関係する箇所を見つけられる。

### 3. 複数の計測器で特性を取る

SCPI などを使う自動計測で、計測器や電子負荷の設定を変えながら、電圧・電流・温度などを数秒から数分ごとに取得する。WireSkein では測定値と、その時点の設定値や操作、実験の段階をまとめて記録し、条件ごとの差や時間による変化を後から分析したい。実験の進行そのものは、利用者や外部の自動計測の仕組みが担ってもよい。

**得たい結果:** 複数機器の記録を一つの実験として扱い、設定と測定結果の対応を後から追える。この場面では、数秒の時刻ずれが問題にならない場合もある。

### 既知のコマンド通信を時系列で追う

SCPI のように通信方式が分かっている記録では、主に知りたいのは、いつどのコマンドを送り、どの応答が返ったかである。通常の調査では個々のエッジやビット列を読む必要はない。通信が欠けたり解釈に失敗したりした箇所では、元の信号へ戻って確認したい。

**得たい結果:** 少ない情報量の時系列からやり取りを追え、問題のある箇所だけ詳細を調べられる。

### 既知の通信の状態だけを確かめる

既知のプロトコルで通信している装置について、個々のコマンド内容よりも、どの程度プロトコルに整合しているか、ジッターや応答時間が普段と違うかを知りたい。異常がなければ簡潔な結果を受け取り、気になる変化があれば該当区間とコマンド列へ進む。

**得たい結果:** 問いに必要な指標だけを受け取り、詳細が必要なときは根拠となるやり取りや信号へ戻れる。整合性や「正常」の判断基準は今後定める。

### 4. 手軽なデータ送信をそのまま記録する

Arduino などがシリアルへ送るカンマ区切りの値を受け取り、リアルタイムにプロットし、後で同じデータを見直す。専用の機器アダプタがなくても、小さな実験をすぐ始めたい。

**得たい結果:** データの受信から可視化、保存、再表示までつながる。

### 5. 実験中にイベントと階層を付ける

機器や制御スクリプトから UART などでマーカーを送り、試験の開始・終了、条件の変更、段階の切り替えにラベルを付ける。予期しない信号が見つかったときには、その前後のマーカーから、どの機器・処理・操作がいつ始まったかを調べたい。試験、条件、手順のようにマーカーを階層的に整理できると、後からイベントごとに記録を見たり、目的の手順へジャンプしたりしやすい。

**得たい結果:** 波形や測定値だけでは分からない実験の文脈を、記録と一緒に残せる。発生源を断定できない場合も、近くのマーカーを手掛かりに調査を進められる。マーカーの記法や階層の表現方法は未定。

### 6. 長回し記録を実験ごとに取り出す

ロジックアナライザなどで取得を続けながら、UART などで「次に行う実験」や条件変更をマーカーとして記録する。後からマーカー間の区間を取り出し、互いに独立した実験なら別々のデータとして保存・分析したい。連続的な変化を追う実験なら、区間を分けずに記録全体を分析したい。

**得たい結果:** 一度の長い取得から、目的に応じて区間の切り出しと全体分析を選べる。切り出した区間を元の記録やマーカーとどう結び付けるかは未定。

### 7. 長時間の記録から変化した箇所を見つける

長時間データを流し続け、普段と異なる値やイベントが現れた場所を見つけたい。変化の少ない区間は簡潔に扱い、気になる区間を後から詳しく調べたい。

**得たい結果:** 長い記録でも全体像と注目箇所を見失わない。保存量を減らす場合、後からどこまで再分析できるかは別途決める。

### 8. 別々に得た記録を合わせて調べる

ロジックアナライザ、計測器、シリアルログなどが別々に記録したデータを同じ実験として開く。共通のイベントや特徴的な変化を手掛かりに位置を合わせ、必要なら手動で調整したい。

**得たい結果:** 厳密な同期が必要な場面も、多少のずれを許容できる場面も扱える。必要な精度は利用場面ごとに考える。

### 9. 新しい機器や分析方法を追加する

利用したい計測器や独自のデータ形式、解析方法が標準で用意されていない。特定の高価な製品に依存せず、手近な機器からの記録も同じ分析の流れへ取り込みたい。利用者や第三者が必要な機能を追加し、ほかの記録・表示・分析機能と組み合わせたい。

**得たい結果:** 新しい機器や分析方法を過度な手間なく追加できる。ビルドの要否を含む具体的な拡張方式は未定。

### 10. GUI と CLI から同じ記録を扱う

波形を見ながら対話的に調べるときは GUI を使い、収集や繰り返しの分析を自動化するときは CLI を使う。どちらでも同じ記録と解析結果を扱い、GUI を別のものに替えても分析の仕組みを利用し続けたい。

**得たい結果:** 共通の分析機能を複数の操作方法から利用できる。各操作方法が提供する体験や機能の完全な一致は求めない。ブラウザでの利用も候補だが、それによって主要な利用場面を制限するかは後で判断する。

## ユースケースに共通する要望

- **取り込む:** ライブ取得と既存ファイルの両方を扱う。
- **関連付ける:** 種類や記録元の異なるデータを、一つの調査や実験の中で扱う。
- **見つける:** 変化、イベント、通信、異常や興味深い区間を探す。
- **解釈する:** 自動分析の候補とその根拠を示し、利用者の知識も反映できる。
- **たどる:** 集計値や高次のイベントから、元の記録と周辺状況へ戻れる。
- **残す:** データに加え、ラベル、条件、解析結果、利用者の判断を後から使える形で保存する。
- **区切る:** 一続きの記録を、必要に応じて区間ごとに取り出し、また全体としても調べられる。

## これから確認したいこと

1. 最初に強く支えたい利用場面はどれか。出発点のロジック解析と、複数計測器による実験の位置付けをどうするか。
2. 「一つの実験」として、どこまでのデータや作業をまとめたいか。
3. 自動分析に最初に期待するのは何か。通信方式の候補提示、変化点の発見、記録同士の関係の発見などの優先度。
4. 長時間記録で、元データの保持と保存量の削減をどう選びたいか。
5. 解析アプリとして誰が主に使うか。機器開発者、試験担当者、趣味の電子工作利用者などで求める操作が変わる。
6. マーカーによる区間の切り出しを、どの利用場面で最も必要とするか。元の記録と切り出した記録の関係をどう残したいか。
