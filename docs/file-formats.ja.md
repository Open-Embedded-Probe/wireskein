# ファイル形式の検討

作成 2026-09-30。次の 3 つの問いについて、調べたことと実験の結果をもとに案を出します。

1. `.sr` 以外の形式を読み書きするか。
2. 独自の形式を持つか。
3. チャンネルごとにサンプルレートが違うキャプチャ（P4 の間引き）を、取ったままの解像度で保存できるか。

## 1. 今の状態

| 向き | 形式 | 使っている場所 |
| --- | --- | --- |
| 読み | sigrok の `.sr`（`_engine/srio.py`） | `wireskein analyze` |
| 読み | fixture（`capture.json` と `edges.npz`、`_engine/fixture.py`） | `corpus/`、研究用 |
| 読み書き | 記録（`run.json` と `c0001.bin`、1 サンプル 1 バイト、ビット k がチャンネル k） | `wireskein.runlog`、`wireskein verify` |
| 書き | JSON（復号の結果） | `wireskein analyze` |

解析の中のモデルは、チャンネルごとのエッジ列です。エッジの位置はサンプル番号で表し、レートはキャプチャ全体で 1 つです（`Capture.rate`）。

## 2. P4 の間引きの形（前提）

wch-protocols の E106 と E121 で試した codec は、ブロックごとに、全速のチャンネルと間引いたチャンネルを別々に詰めます。

- 間引いたチャンネルの値は、D サンプルごとの **その時刻の 1 点の値**です（`hold`）。区間の平均や論理和ではありません。
- 構成の例:
  - 8 ビット: 全速 3 本と、D = 64 の 5 本
  - 16 ビット: 全速 3 本、D = 8 の 1 本、D = 64 の 12 本
- 間引き率はチャンネルごとに違い、1 つのキャプチャの中で混ざります。
- レートは分数で表します（oep-client の `Fraction`）。間引いたチャンネルのレートは、基準のレートの 1/D です。
- oep-spec の logic-capture §0.1 と §3.2 では、チャンネルごとの間引きは基本の形の外（別の定義）に置かれていて、まだ書かれていません。

間引いたチャンネルを基準のレートに水増ししても（同じ値を D 回繰り返しても）、**エッジの時刻は変わりません**（D の倍数の位置に立つ）。失われるのは、次の 2 つだけです。

- **そのチャンネルの分解能**: エッジは本当は、最大 D サンプル前のどこかで起きています。
- **取ったデータの記録**: 水増しした形は、プローブが実際に送ったデータそのものではありません。

## 3. 外部の形式

| 形式 | 時間の表し方 | チャンネルごとのレート | 読む道具 | 備考 |
| --- | --- | --- | --- | --- |
| sigrok `.sr`（srzip v2） | デバイスごとに 1 つのレート、サンプルを詰めて並べる | 仕様では、デバイス（`[device N]`）ごとにレートを持てる。**実際には使えない**（§4.1） | PulseView、sigrok-cli | 今の標準の見せ方。zip なので、知らないファイルを同梱できる（§4.2） |
| VCD | 変化点の時刻（`$timescale` の整数倍） | 表せる（変化点だけを書くので、レートという考えがない）。分解能の情報はない | GTKWave、sigrok（入出力）、シミュレーター、Saleae などの書き出し | テキストなので、変化の多い信号では大きい |
| Saleae Logic 2 のバイナリ書き出し | チャンネルごとのファイル、変化点の時刻を秒の double で持つ | 表せる | Saleae のスクリプト（Logic 2 に読み込む口は、自分の `.sal` だけ。机上、未確認） | 他社の道具から持ち込む口としての価値 |
| CSV | 行ごとに時刻と値 | 形しだい | 表計算、sigrok の入力、多くの道具の書き出し | 大きい。取り込みの口として |
| DSView `.dsl` | sigrok 系、1 つのレート | 持てない | DSView | `.sr` と同じ位置づけ |
| FST、HDF5、Parquet | — | 表せる | GTKWave（FST）、汎用 | 書くには依存（C ライブラリや大きな package）が要る |

## 4. 実験（2026-09-30、sigrok-cli 0.7.2 / libsigrok 0.5.2）

### 4.1 レートの違うデバイスを 2 つ持つ `.sr`

- 作ったもの: `[device 1]`（100 MHz、3 本、3200 サンプル）と、`[device 2]`（3.125 MHz、5 本、100 サンプル）を持つ `.sr`
- 結果: `sigrok-cli --show` は、`Event source ... already exists` のエラーを出しました。表示は、2 つめのデバイスの名前とレートに、1 つめのサンプル数（3200）を組み合わせたものでした。VCD に変換した結果も、どちらのデバイスとも合いません。
- libsigrok の `session_file.c` は、`device ` の節をすべて回して読みます。しかし、1 つのセッションとして流すところで壊れます。
- **判断: `.sr` は 1 つのレートで書く。** レートの違うチャンネルは、基準のレートに水増しします。

### 4.2 `.sr` に独自のファイルを同梱する

- 作ったもの: `metadata` と `logic-1-1` に加え、`wireskein.json` を入れた `.sr`
- 結果: sigrok-cli は `wireskein.json` を無視し、普通に読みました（`--show` と VCD への変換）。PulseView も同じ libsigrok で読むので、無視されるはずです（GUI では未確認）。
- **判断: 水増しした `.sr` の中に、チャンネルごとの本当の分解能を残せる。** WireSkein で読み直すときは、分解能を戻せます。

### 4.3 大きさ

条件は、0.1 秒分のキャプチャです。

- 100 Msps のチャンネル 3 本: SPI の SCK（10 MHz、途切れる）、MOSI、25 MHz のクロック
- 1/32 に間引いたチャンネル 5 本: UART、I2C の SDA、PWM、止まった線 2 本

| 形 | 圧縮前 | deflate（`.sr` と同じ圧縮） |
| --- | ---: | ---: |
| `.sr`（水増し、1 サンプル 1 バイト） | 10.00 MB | 0.14 MB |
| チャンネルごとに自分のレートで、1 ビット 1 サンプル | 3.95 MB | 0.06 MB |
| チャンネルごとのエッジ（間隔を uint32 で） | 21.79 MB | 0.07 MB |
| チャンネルごとに、小さい方（ビットかエッジ） | — | 0.06 MB |

- 合成の信号は規則的なので、実際より圧縮が効いています。差の比（2〜2.5 倍）を見てください。
- 圧縮前の差は、ホストのメモリと、圧縮にかかる時間の差になります。100 Msps で 1 秒取ると、水増しした形は 100 MB です。
- 変化の多いチャンネル（常に動くクロック）はビットの方が、変化の少ないチャンネルはエッジの方が小さくなります。

**大きさは決め手ではありません（2 倍程度）。決め手は、分解能を正しく持てることと、取ったデータのまま残せることです。**

もう 1 つの理由は、見せ方です（2026-09-30 の議論）。GUI でサンプルの点を出すと、水増しした形では、実際には取っていない D − 1 個の値が、取った値と同じ点で並びます。CLI の解析の結果は変わりませんが、**存在しないデータを存在するように見せない**ため、元の解像度のまま持ちます。

## 5. 案

### 5.1 解析のモデル: 共通の刻みと、チャンネルごとの刻みの幅

- 時間の基準は、キャプチャで 1 つの **刻み**（tick）です。刻みの周波数は、分数の Hz で持ちます。
- エッジの位置は、今と同じく刻みの番号（整数）で表します。
- チャンネルには **`step`**（刻み何個ごとに 1 サンプル。既定 1）を足します。必要なら `phase`（最初のサンプルの刻み）も足します。
- 今の解析は、エッジの位置をそのまま使うので、ほとんど変わりません。手を入れるのは、1 サンプルの幅を前提にしている次の箇所です。このチャンネルの 1 サンプル（`step` 刻み）を使うよう直します。
  - グリッチ（1 サンプルのひげ）の判定と除去: `kernels.deglitch`、`typed`、`exclude`
  - クロックとの一致の判定（1 サンプル以内）: `survey.pair_relation` の `coincide`
  - 方形波のデューティー比の分解能: `markers._periodic`、`verify.check_square`
  - UART のサンプル数とエッジのずれの閾値: `verify.check_uart`
  - 単位の推定で量子化の誤差を見込む所: `features.estimate_units`
- 照合の結果には、チャンネルごとの分解能を出します。測定値の誤差の見積もりに使えるようにするためです。

### 5.2 独自の形式を作る（キャプチャのファイル）

作ります。理由は 4 つです。

- 分解能を正しく持つため。
- 取った形のまま残すため。
- GUI で、取ったサンプルだけを点で見せるため（水増しした値を見せない）。
- 今の記録の `.bin`（1 サンプル 1 バイト、1 つのレート）を置き換えるため。

**書くのは WireSkein のモジュールだけにします**（2026-09-30 の議論）。取ったデータを持つ側は、データを WireSkein の Python モジュールに渡して保存してもらいます。形式の細部を知っているのは WireSkein だけで、ほかのプロジェクトが同じ形式を実装し直すことはしません。

- 書く口: 標準ライブラリだけで動くモジュール（`wireskein.runlog` と同じ約束）。
  - 受け取るのは、チャンネルごとの、そのチャンネルのレートのサンプル列と `step`、それに取得の情報です。
  - 今の 1 つのレートの形（1 サンプル 1 バイト、ビット k がチャンネル k）もそのまま受け取ります。
- 転送の形（P4 の間引きの codec など）を解くのは、その形を知っている側（oep-client）です。WireSkein は解いた後のチャンネルごとのサンプル列を受け取ります。
- oep-client は WireSkein に依存しない方針なので、oep-client のキャプチャを WireSkein に渡すのは、両方を使う側です（ch32rv の pytest プラグインや bench の試験）。

案:

- **入れ物**: zip です（`.sr` と同じく、Python の標準ライブラリの `zipfile` だけで読み書きできる）。
  - `wireskein.runlog` は標準ライブラリだけで動く約束なので、runlog からも書けます。
  - numpy は要りません。oep-client のように WireSkein に依存しないものでも、同じ形を書けます。
- **中身**:
  - `capture.json`:
    - 形式の名前と版
    - 刻みの周波数（分子と分母）と、刻みの数
    - チャンネルの一覧（名前、`step`、`phase`、最初のレベル、データの形、ファイル名）
    - 取得の情報（`start_us`、`time_base_slipped`、プローブ、間引きの構成）
  - チャンネルごとのデータ: 次のどちらかを、チャンネルごとに選びます。
    - `bits`: そのチャンネルのレートで 1 ビット 1 サンプル
    - `edges`: エッジの間隔（整数）
  - 圧縮は zip の deflate です。
- **拡張子**: `.wsc`（WireSkein capture）とします。
- **読む口**: チャンネルごとのサンプル列（標準ライブラリだけ）と、解析のモデル（numpy）の 2 つを持ちます。
- **記録（run）での扱い**: `rec.capture()` がチャンネルごとの `step` を受け取れるようにし、キャプチャを `.wsc` で書きます。
  - 記録の形式は `wireskein-run/1` に上げます。**`/0`（`.bin`）は読みません**（2026-09-30 の決定。利用者がまだいないので、過去の形式を抱えない）。
- corpus の fixture（`capture.json` と `edges.npz`）も、同じ形に寄せられます（別の作業）。

### 5.3 `.sr`

読み書きの両方を持ちます。PulseView で見るための形です。

- **書き**: 1 つのレートで書き、間引いたチャンネルは基準のレートに水増しします。`wireskein.json` を同梱し、チャンネルごとの `step` を残します（§4.2）。PulseView では、水増しした値も取った値と同じ点で見えます。`.sr` は見るための書き出しと割り切り、保存の本体は `.wsc` にします。
- **読み**: `wireskein.json` があれば、`step` を戻します。なければ、今までどおりすべてのチャンネルを step 1 として読みます。
- oep-client の `to_sr` は、今のまま使えます。WireSkein から `.sr` を書く口を足すのは、`.wsc` から PulseView に渡すためです（`wireskein convert x.wsc x.sr`）。

### 5.4 VCD

読み書きの両方を持ちます。**ただし後回しにします**（2026-09-30 の決定。先に `.wsc` の仕様を固める）。

- **書き**: 変化点だけを書くので、水増しは要りません。レートの違うチャンネルも、そのまま GTKWave で見られます。分解能は `$comment` に書きます。
- **読み**: Saleae、DSView、シミュレーター、FPGA の道具から持ち込む口です。
  - 刻みは `$timescale` にします。
  - チャンネルの分解能は分からないので、`step` は 1 とします。
  - 読むときに `step` を指定する option を持たせます。

### 5.5 そのほか（後回し、要望が出たら）

- **CSV の読み**: Saleae の変化点の CSV と、sigrok の CSV。
- **Saleae のバイナリの読み**: Logic 2 から持ち込む口。
- **生のバイナリの読み**: 1 サンプル 1 バイトなど（レートとビットの割り当てを option で与える）。記録の `.bin` と同じ形です。
- **作らないもの**: FST、HDF5、Parquet（依存が要る）、DSView の `.dsl`（`.sr` と同等）。

### 5.6 P4 の今の方針（水増しして `.sr`）との関係

- **当面は、今のままでも解析の結果は同じ**です（エッジの時刻が同じ）。違いは分解能だけで、今のところ照合の結果には効いていません。
  - 分解能が効くのは、間引いたチャンネルとの時間の関係を測る場面です（例: CS を間引いた線に置いた SPI、間引いた線どうしの時間差）。
- 移るときの流れ:
  1. oep-client が、間引きの形を解いてチャンネルごとの配列と `step` を返す（OEP 側の担当）。
  2. 両方を使う側が、それを runlog の `capture()` に渡し、WireSkein が `.wsc` で書く。
  3. PulseView で見るときは、`.sr` に変換する（§5.3）。

## 6. 順番（案）

1. 解析のモデルに `step` を足し、1 サンプルの幅を前提にした箇所を直す（§5.1）。合成の多重レートのキャプチャで、水増しした場合と同じ結果になり、分解能が出ることを確かめる。
2. `.wsc` の読み書きと、`wireskein convert`（`.wsc` と `.sr` と VCD の相互変換）を作る（§5.2〜5.4）。
3. runlog の `capture()` をチャンネルごとの `step` に対応させ、記録の形式を `wireskein-run/1` に上げる。
4. 要望が出たら、CSV、Saleae、生のバイナリの読み込み（§5.5）。

## 7. 決めてほしいこと

1. （決定、2026-09-30）独自の形式を作る。拡張子は `.wsc`。
2. （決定、2026-09-30）記録の形式を `wireskein-run/1` に上げ、`/0` には対応しない。
3. （決定、2026-09-30）保存は WireSkein のモジュールに渡して行う。oep-client は `.wsc` を自前で書かない。
4. （決定、2026-09-30）VCD の読み書きは後にする。
5. 受け渡しの形（チャンネルごとのサンプル列の型、`step` と `phase` の出どころ、ストリーミングの追記、アナログの場所）: oep-client、ArduinoCore-CH32、ch32rv のセッションに相談中（2026-09-30）。
