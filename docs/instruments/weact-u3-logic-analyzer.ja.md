# WeAct の U3 ロジックアナライザー（CH32H417）

[English](weact-u3-logic-analyzer.md)

WeAct Studio の Logic Analyzer V2（CH32H417、USB 3.0、200 MHz × 16 本）と、その PC 側のアプリ U3LogicAnalyzer を調べた結果です。WireSkein で読めるか、どう組み合わせるかを決める材料にします。

調べたもの:
- アプリ: [WeActStudio.U3LogicAnalyzer](https://github.com/WeActStudio/WeActStudio.U3LogicAnalyzer)（commit 54a6d9b、2026-10-28）。
- 本体: [WeActStudio.LogicAnalyzerV2](https://github.com/WeActStudio/WeActStudio.LogicAnalyzerV2)（commit 2d10d93、2026-11-10）。

実機ではまだ試していません。下の内容は、ソースと README から読んだものです。

## 要点

- アプリは sigrok（libsigrok、libsigrokdecode、PulseView）の改変版で、GPL-3.0-or-later でソースが公開されています。
- 保存は sigrok の普通の `.sr`（srzip）です。WireSkein はそれをそのまま読めます。
  - この改変版の形をまねた `.sr` で確かめました。16 本・2 バイトで 187.5 MHz、8 本・1 バイトで 78.125 MHz の 2 つです。
- 本体との通信は単純です。
  - コマンドは 64 バイトのパケットで送り、答えは 32 バイトで返ります。
  - サンプルは、ヘッダーの無い生のバルク転送で流れてきます。
  - そのため、WireSkein から直接取り込む道もあります。
  - ただしストリームには通し番号が無く、途中の欠けはデータからは分かりません。
- 公式の sigrok にこのドライバーは入っていません。
  - sigrok-cli も同梱されていないので、コマンドラインから取り込むには自分で組み立てる必要があります。

## ソース、言語、構成、ライセンス

- PC 側のアプリは公開されています。C（libsigrok）、C++/Qt（PulseView）、Python（libsigrokdecode のデコーダー）で、CMake で組み立てます。
  - 起動するファイルの名前は `U3LogicAnalyzer` です。
- ライセンスは GPL-3.0-or-later です。
  - CH375 版のドライバーと、手を入れていない部分は Q2H2 の著作です（WeAct の改変元）。
  - libusb 版のドライバーは WeAct Studio の著作です。
- ハードウェアのドライバーは 4 つに絞ってあります。
  - `wch-ch32h417`: Windows の CH375DLL / CH375WDM.sys を使います。Windows だけです。
  - `wch-ch32h417-libusb`: libusb を使います。Linux で動き、Windows では Zadig で WinUSB に差し替えれば動きます。macOS では確かめていないそうです。
  - `fx2lafw`: 公式 sigrok と同じものです。
  - `demo`
- 改変は次の所にあります。
  - libsigrok の `src/hardware/wch-ch32h417*/`。
  - `src/output/srzip.c`: 8 本で取ったものを 8 本の幅で保存する直しです。
  - `SR_CONF_LINK_STOP_REASON`、`SR_CONF_ADC_PRECISION`、`SR_CONF_ADC_CHANNEL` などの独自の設定のキー。
  - PulseView の画面。ファームの更新（IAP）の画面もここにあります。
- 本体のファーム:
  - ロジアナのアプリ（slot 0）と、USB シリアル + CMSIS-DAP（slot 1）は、バイナリーだけが公開されています。
  - ソースが公開されているのは、ユーザーのアプリの例（slot 2）だけです。
  - そのため、ファーム側の振る舞いは、ドライバーのコメントから推すしかありません。

## デバイスとの通信

### USB

| 項目 | 値 |
| --- | --- |
| VID:PID（動いているとき） | `1a86:5537`（WCH の VID） |
| VID:PID（ファームの更新） | `1a86:fe17`（HID） |
| インターフェース | 0 番の 1 つ。configuration は 1 |
| EP 0x01 / 0x81 | コマンド。送るのは 64 バイト、答えは 32 バイト |
| EP 0x02 / 0x82 | ロジックのサンプルのストリーム（IN が 0x82） |
| EP 0x03 / 0x83 | ADC のサンプルのストリーム（ADC のある機種だけ） |

- ベンダー独自の control 転送は使いません。すべてバルク転送です。
- SuperSpeed の場合:
  - wMaxPacketSize は 1024、bMaxBurst は 15 なので、1 回のバーストは 16 kB です。
  - ドライバーは、256 kB の転送を 32 本（合わせて 8 MB）出しておいて受けます。
- Linux では、`99-weact-ch32h417.rules` の udev の規則で root 無しで開けるようにします。

### コマンド

送るパケットは `[cmd, len, data…]` で、64 バイトまで 0 で埋めます。答えは `[resp, len, status, payload…]` です。

- `len` が 0 より大きいときは status が付き、0 が成功です。
- payload の長さは `len - 1` です。

| cmd | 答え | 中身 |
| --- | --- | --- |
| `0xA0` ロジックの設定 | `0xB0` | `[幅, 分周の番号]`。幅は `0x08`（1 バイト）か `0x10`（2 バイト） |
| `0xA1` しきい値 | `0xB1` | 2 バイト、上位が先（下を参照） |
| `0xA2` 取り込みの開始 | なし | |
| `0xA3` 取り込みの停止 | なし | |
| `0xA4` / `0xA5` | `0xB4` / `0xB5` | 設定 / しきい値を読む |
| `0xA6`〜`0xAB` | `0xB6`〜`0xBB` | ADC の設定、チャンネル、開始と停止、読み出し |
| `0xAC` 版 | `0xBC` | `[ソフトの版, ハードの版]`。1 バイトだけのファームもあります |
| `0xAE` | | IAP に入る |

分周の番号は、ドライバーの表の位置です。
- USB 3.0 では 25 段あります: 200、187.5、175、162.5、156.25、150、137.5、125、112.5、100、93.75、87.5、81.25、78.125、75、68.75、50、40、30、20、16、12、8、6、4 MHz。
- USB 2.0 では、ファームが番号にずらしを足します（ドライバーのコメントによると `UHSIF_Clock_Set()`）。
  - 16 本: 20〜4 MHz の 6 段。
  - 8 本: 40〜4 MHz の 8 段。
- シリアル番号が `b5` で始まる機種が V2 で、表のすべてが使えます。
  - `01` で始まる機種（ADC のある CH32H417 のボード）では、USB 3.0 で上の 14 段だけ、USB 2.0 で 1 段だけです。

しきい値:
- V2（`b5`）では、画面で選んだ「しきい値」（入力のピンで 0.6〜1.5 V）を「入力レベル」（1.0〜3.3 V）に直して送ります。
  - 0.1 V 単位の値（10〜33）に `0x8000` を足したものです。
  - 0.6 V が 1.0 V に、1.5 V が 3.3 V に当たるように、間を直線で結んでいます（コメントによると実測）。
- `01` の機種では、0〜1024 の DAC の値を送ります。0 がおよそ 3.3 V、1024 がおよそ 1.2 V です。

### サンプルの並び

- EP 0x82 には、サンプルがヘッダー無しで続けて流れてきます。
  - 幅が `0x10` なら 1 サンプルは 2 バイトで、`0x08` なら 1 バイトです。
  - ビット n が Dn です（チャンネル n をビット n に割り当てています）。
  - libsigrok のロジックのデータなので、2 バイトのときは下位のバイトが先です。
- チャンネルの数は 2、4、8、16 から選びますが、送られる幅は 8 本以下が 1 バイト、9 本以上が 2 バイトです。
  - 2 本や 4 本でも 1 バイトです。
  - 選ばなかったチャンネルも、データには入っています。
- D0〜D15 の端子は、PD10〜15、PF0〜2、PC6〜9、PA13〜15 です（本体の README）。
  - UHSIF の PORT16〜31 に当たるという点は、core の調べによります。

### トリガーと止まり方

- 本体にトリガーの回路はありません。
  - トリガーと「pre-trigger」は、PC 側のソフトのトリガー（libsigrok の `soft_trigger_logic`）が、流れてきたデータを見て切り出します。
- サンプルは PC の RAM に溜めます。
  - 上限はおよそ 18 GB と見積もっています（200 MHz・16 本でおよそ 45 秒）。
  - 空きのメモリーが 512 MB を切ると、そこまでを残して止めます。
- USB の帯域が設定したサンプルレートに足りないとき、本体は自分で送るのをやめるとコメントにあります（ファームのソースが無いので確かめられません）。
  - ドライバーは 500 ms データが来なければ止め、`LINK_STOP_NO_DATA` を記録します。
  - 画面はそれを知らせますが、`.sr` にはこの理由は残りません。
  - 途中で止まったキャプチャは、ファイルの上では「短いキャプチャ」に見えます。
- ストリームには通し番号も時刻も無いので、本体の中で一部が捨てられていても PC からは分かりません。
  - 「帯域が足りなければ止まる」という作りなら途中は欠けないはずですが、ファームが非公開なので確かめられません。

## 保存の形式とデコーダー

- 保存（Save / Save As）は sigrok のセッションファイル（`.sr`、zip）です。
  - `metadata` の `samplerate` は `187.5 MHz` のように書かれます。
  - 8 本で取ったものは、`total probes=8`・`unitsize=1` で保存されます。
  - 範囲だけを保存すること、設定だけを保存することもできます。
- 書き出しには、libsigrok の出力（VCD、CSV、binary など）があります。
- 読み込みには、libsigrok の入力（VCD、CSV、Saleae など）があります。
- デコーダーは libsigrokdecode のものが `libsigrokdecode/decoders/` に 132 個あります（`swd` はあり、RVSWD は無し）。
  - 公式の版との差分は見ていません。

## WireSkein から使う道筋

1. **`.sr` を読む（いますぐ使えます）。**
   - U3LogicAnalyzer で取って `.sr` に保存すれば、WireSkein はほかの sigrok のファイルと同じように読みます。
     - チャンネルの名前（D0〜D15）、幅（1 / 2 バイト）、端数のある MHz を読めます。
   - 長いキャプチャも、いまの分割の読み込みが使えます。
   - 欠けを WireSkein から確かめることはできません。
     - 画面で「途中で止まった」と出たキャプチャは、分析に使わないようにします。
     - 設定した時間と、ファイルの長さを比べることもできます。
2. **sigrok-cli を組み立てて、コマンドラインから取り込む。**
   - リポジトリが入れる libsigrok（`install/`）に対して、公式の sigrok-cli を組み立てれば、このドライバーで取れるはずです。
   - 独自のキーを sigrok-cli が扱えるかは確かめていません。
   - 試験の中で自動で取り込みたいときの道です。
3. **本体を WireSkein から直接動かす（`wireskein.sources` に取り込み元を足す）。**
   - 上のとおり通信は単純で、libusb があれば書けます。
   - 気をつける所:
     - 200 MHz・16 本では 400 MB/s です。Python で受けるには、非同期の転送を何本も出しておく必要があります。
     - ストリームに番号が無いので、欠けを見つける手段は「止まらずに予定の数が来たか」だけです。
     - ファームの更新でコマンドが変わっても、それを知るすべがありません（ファームが非公開）。
     - アプリは GPL です。直接動かす取り込み元は、プロトコルの事実から書き、コードは写しません（WireSkein は MIT）。

勧めるのは 1 です。直接の取り込みは、実機で `.sr` の取り込みを試して、帯域と欠けの振る舞いを確かめてから決めるのがよいと思います。

## 分からなかったこと

- ファームの中の振る舞い（ファームが非公開のため）:
  - バッファーの大きさ。
  - あふれたときに止まるのか、捨てるのか。
  - USB 2.0 の分周のずらし。
- 実際のサンプルクロックの正確さ（水晶の精度、PLL から分けるときの誤差）。
  - 187.5 MHz のような端数のある段が、どの基準のクロックをどう分けたものかも分かりません。
- 2 本・4 本を選んだとき、データのどのビットにチャンネルが入るか。
  - ドライバーは幅だけを変え、ビット n をチャンネル n として扱っています。
- 公式の sigrok に取り込まれる予定があるか。
- 実機の `.sr` を WireSkein で読むこと（確かめたのは、この改変版の形をまねたファイルだけ）。
- ADC のモード（`01` の機種だけ。V2 には ADC がありません）。
