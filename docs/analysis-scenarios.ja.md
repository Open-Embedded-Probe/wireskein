# WireSkein — 分析結果を考えるための事例

状態: **検討用の事例**。実際の調査で何を受け取りたいかを確かめるための文書であり、出力形式、必須機能、判断基準は定めない。

各事例で、最初の結果だけで調査が終わるとは限らない。概要から関心のある区間へ進み、必要なら元の記録に戻り、後工程のスクリプトや人が判断する。

## 事例1: 正体の分からない信号線を調べ始める

### 状況と問い

四つの線をまとめて取得した。電源と GND は分かっているが、残る二つの線が何を運んでいるか分からない。UART、I²C、SPI、SWD のような通信か、搬送波を使う信号か、まず大まかな見当を付けたい。

知りたいのは、どの線がいつ動くか、二つの線がどう連動するか、独立したクロックらしい線がありそうか、各線にどの程度の周期性や速度があるかである。

### 最初に受け取りたい結果

- 線ごとの活動区間、変化の多さ、周期性、二つの線の関係
- 同期クロック、一定のビット速度、搬送波などの特徴が見られるかと、速度・周波数の大まかな候補
- 通信方式や線の役割の候補と、その判断材料。複数の候補が残る箇所や分類できない箇所も示す
- 取得レートやノイズのために判断しにくい区間

### 次に行うこと

見込みのある候補を選んで詳しく調べる。たとえば UART の候補なら、フレームを解釈して得たデータから SCPI や Modbus などの上位の候補を調べる。さらに SCPI のコマンドが読めたら、機器固有のコマンド定義に合うかを調べられる。各段階で合わない箇所を残し、別の候補や解析機能の改善へ進む。必要なら線の役割や条件を指定し、記録の一部を拡大する。元の取得では判別しにくければ、取得条件を変えて取り直す。

結果は候補が枝分かれする階層として見られるとよい。たとえば「信号 → UART 候補 → SCPI 候補 → 機器固有のコマンド候補」の各段階で、それぞれ何にどの程度一致したかを確認する。別の枝として、同じ UART の結果から Modbus の候補を試すこともできる。

**確認したい点:** 最初の段階でどこまで自動的に候補を絞れるか。上位の候補を試した結果が下位の判断にも役立つか。候補を確定できなくても、利用者が次に調べる線・区間・取得条件を選べるか。

## 事例2: RVSWD の記録で見落とした高速区間を調べる

### 状況と問い

V203 の線上通信を取得した。短い変化をノイズとして除いた解析では一部のやり取りを見落としたが、後でその区間の通信が速くなっていたと分かった。取得レートを上げて取り直すと分析が進んだ。

知りたいのは、送受方向とコマンドが時系列でどう並んだか、どこで通信速度が変わったか、解釈できない信号がどこに残ったかである。

### 最初に受け取りたい結果

- 記録の区間ごとの活動、通信速度の候補、解釈できた部分とできなかった部分
- 送受方向とコマンドの時系列。解釈できない部分は空白にせず、その位置を示す
- 短い変化をノイズと判断した場所と、取得分解能や前処理によって結果が変わり得る箇所

### 次に行うこと

気になる区間の元信号、エッジ、前処理の条件を見直す。必要なら高いレートで取り直す。未知の区間を手掛かりに解析プラグインを改善し、同じ記録を再分析する。後工程では、得られたコマンド列を別経路の記録や期待した操作と照合する。

**確認したい点:** コマンドを短く出しても、除外した変化と未解釈の区間に気付けるか。再分析時に元記録と前回の解析条件へ戻れるか。

## 事例3: 既知の SPI 通信で一部の解釈が合わない

### 状況と問い

SPI らしい通信は読めるが、ある区間だけ既知のプロトコル定義に合わない。ビットの位置が一つずれている、通信条件が変わった、または機器が規則から外れた可能性を調べたい。

### 最初に受け取りたい結果

- 試した解釈候補ごとの、解釈できた範囲と規則に合わない範囲
- 合わない箇所の位置、前後の通信内容、候補間で結果がどう変わるか
- 元の信号と取得条件へ戻る手掛かり

### 次に行うこと

合わない区間だけを取り出し、ビット位置や通信条件の候補を変えて再分析する。規則違反なのか解析条件の誤りなのかは、詳細な結果と元信号を見て判断する。

**確認したい点:** 全体を一つの「マッチ率」だけで示すより、どの規則がどの区間で合わないかを見せるほうが調査に役立つか。

## 事例4: 既知の SCPI 通信を調べる

### 状況と問い

計測器との通信は既知で、主にコマンドと応答のやり取りを追いたい。同じ記録でも、通信内容を確認したい場合と、応答時間やジッターが普段どおりかだけを確かめたい場合がある。

SCPI の構文は読めても、機器固有のコマンドの意味までは分からない場合がある。対応する機器のコマンド定義を追加し、その段階でどのコマンドが分かり、どれが未知のままかを調べたい。

### 最初に受け取りたい結果

- 内容を追う場合: 時刻順のコマンドと応答、対応しなかったやり取り
- 状態を確かめる場合: プロトコルとの整合やタイミングの概況、例外が起きた区間
- 機器固有の解釈を行う場合: 分かったコマンドと未知のコマンド。SCPI 自体の解釈状況とは区別する

### 次に行うこと

気になるやり取りだけ詳細を取り出す。入力が生信号なら必要に応じてその位置へ戻る。既に文字列のログであれば、そのログの該当箇所へ戻る。

**確認したい点:** 同じ入力から、問いに応じてコマンド列と指標のどちらも選べるか。SCPI の構文がすべて読めても、機器固有のコマンドに未知が残ることを区別できるか。簡潔な結果でも、欠落や解釈できなかった部分が隠れないか。

## 事例5: 自動テストの多数の記録から例外を探す

### 状況と問い

自動テストで複数回キャプチャした。正常な回と失敗した回、あるいはソフトウェア変更の前後で、何が変わったかを調べたい。各回の全波形や全コマンドを初めから読むのは負担が大きい。

### 最初に受け取りたい結果

- 各回の短い概観と、他の回との目立つ差
- コマンドの欠落や追加、順序・時間の変化、未解釈区間、取得上の問題が出た回
- 調べるべき回と区間への手掛かり

### 次に行うこと

例外のある回を選び、コマンド、指標、元記録へ順に進む。後工程のテストや独自分析が期待値と照合し、最終的な判断を行う。

**確認したい点:** 多数の記録を短く見せても、珍しい失敗や取得不良が埋もれないか。比較する基準を誰がどう与えるか。

## 事例6: 遅い測定値とイベントを一緒に見る

### 状況と問い

LDO やトランジスタの特性を調べるため、電圧、電流、温度を定期的に記録し、設定値や試験段階をイベントマーカーで残す。測定値とイベントは機器ごとに異なる時間精度で記録された。どの設定で値が変化したかを知りたい。この用途では通信プロトコルの復号は必要ない。

### 最初に受け取りたい結果

- 試験段階ごとの測定値の変化や分布、目立つ変化の時期
- 設定変更と測定値の対応。時刻合わせが不確かな箇所はそのまま示す
- 関心のある段階と元の測定記録への手掛かり
- マーカーから読んだ設定値と測定値を結び付け、後工程のスクリプトが読める定まった構造のデータ

### 次に行うこと

必要な段階の測定値を取り出し、後工程のスクリプトで集計方法を変えて特性を計算したり、別の条件と比較したりする。

**確認したい点:** 高速な信号と低速な測定値を、同じ「概観から絞って詳細へ進む」流れで扱えるか。時間精度の違いを隠さずに済むか。後工程が依存する出力形式を安定して提供できるか。

## 事例から見える共通の問い

1. 未知の入力で、どの線・区間・信号の種類を次に調べるべきかをどう示すか。
2. 最初の概要に何を載せれば、次に調べる区間や記録を選べるか。
3. コマンド列、指標、測定値、未知の区間のうち、利用者が求めたものだけをどう取り出すか。
4. 短い結果でも、未解釈、取得不足、前処理で除外した変化をどう知らせるか。
5. 結果から元記録、分析条件、別の粒度の結果へどう戻るか。

これらの答えを先に考え、共通の概念や具体的な出力形式はその後で決める。
