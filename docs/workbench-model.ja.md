# WireSkein — ワークベンチの使い方と共通概念

ここでは、[ビジョン](project-concept.ja.md) を実際の作業として説明する。以下は目指す振る舞いであり、製品上の名称や内部形式は未決定である。方式上の未決定事項は [今後の検証計画](next-plan.ja.md) にまとめる。

## 一連の作業

1. プロジェクトを作り、実験を繰り返しながらキャプチャや測定記録をソースとして追加する。
2. フィルター、プロトコル解析、測定値の整理、出力などを組み合わせた処理を定義する。ソースを追加する前に定義しておいてもよい。
3. ソース全体や区間を指定して処理を実行し、まず簡易レポートから概況と例外を見る。
4. 気になる箇所を詳細結果や元データで確認し、必要なら処理条件や解析プラグインを修正して再実行する。
5. 結果を確認できたら、詳細レポートと対応する実データをエビデンスとして別の場所へ保全し、後工程へ渡す。

これは一つの作業例である。簡易・詳細・実データを毎回まとめて出して読む側で使い分けても、用途別に処理を複製してもよい。出力を段階ごとに切り替える操作は必須にしない。成果物の保全先の管理や実験の合否判断は、利用者や外部ツールが担う。

## プロジェクトとソース

プロジェクトは、記録、再利用する処理条件、途中の試行、結果との関係を残し、再び開いて作業を続ける単位である。動画・音声編集のように、元データを共有したまま条件違いの試行を残せることを目指す。

ソースにはデジタル波形、アナログ波形、間欠的な測定値、通信ログ、文字列、イベントを含められる。既存ファイルとライブ取得の両方を想定する。取得中の末尾が増えることと、分析設定の変更で既存データを書き換えることは区別する。

次の対象を、処理を呼び出す側から共通の方法で扱えるようにする。

| 対象 | 例 | 使い方 |
| --- | --- | --- |
| 元のソース | 一回のキャプチャ、計測器の記録 | 全体を分析する |
| マーカーで分かれた子区間 | 実験1の電圧5V・負荷ON | 必要な実験段階だけを分析する |
| 合成ソース | 波形と別の機器のイベントログを時間上で合わせたもの | 合わせた全体やその子区間を分析する |

子区間は親の一部を指すものとして扱い、区間を作るだけで実データを複製する前提にはしない。別ファイルへ実データを切り出す出力とは区別する。

## マーカーで長い記録を実験の文脈に結び付ける

機器や外部の試験ツールが、これから行う操作、設定変更、実験の開始・終了などを文字列で送る。例えば UART のログへ見出しに似たマーカーを流し、その間の信号や測定値と一緒に記録する。具体的な記号は例として示す。

~~~text
# 実験1
## 電圧5V
### 負荷ON
### 負荷OFF
## 電圧4V
### 負荷ON
### 負荷OFF
~~~

この記録は「ソース → 実験1 → 電圧5V → 負荷ON」のような階層として選べる。通信ログや測定値は各区間の中にあり、データ自体を見出しと混同しない。

| 選ぶ対象 | 分析する範囲 | 役立つ場面 |
| --- | --- | --- |
| 実験1 | 電圧5Vと4V、負荷ON/OFFを含む全体 | 実験全体の連続変化を追う |
| 実験1／電圧5V | 負荷ONからOFFまでを含む5Vの範囲 | 負荷の切り替わり前後を調べる |
| 実験1／電圧5V／負荷ON | 5Vかつ負荷ONの区間 | 条件ごとに独立して分析・出力する |

親を対象にしたときは子の実データを含む全範囲を扱い、子のマーカーはイベントとして見える。子を対象にしたときはその区間を扱う。これにより、長回しを止めずに実験を重ね、後から独立した実験を切り出す使い方と、連続変化を全体で調べる使い方を両立できる。

マーカーは、予期しない信号の直前にどの操作が始まったかを探す手掛かりにもなる。GUI で該当箇所へ移動したり、外部ツールがマーカーを指定して必要な実データを取得したりできる。LDO などの特性測定では、マーカー内の条件と測定値を対応付け、再集計用のデータに整える。

区間の扱いは次の方向とする。

- 同じ階層または上位の次の見出しで区間を閉じる。名前のない同階層のマーカーは終了を表し、新しい子区間は作らない。その後のデータも親ソースには残る。
- 同じ親の直下で同名が重なった場合は、コアが連番などを付けて区別する。元のマーカー文字列を保持する。
- 別ソースや別の親の同名マーカーは重複としない。元ソースと階層を含めて対象を特定する。

実際の記法、マーカーの抽出方法、連番の表記、壊れた階層の扱いは検証して決める。

## 複数ソースを合わせる

別の取得元の記録を合わせる場合、ソースごとにオフセットや時間倍率を指定し、一つの合成ソースとして扱う。例えばイベントマーカーだけを送るログと、別のロジックアナライザの波形を合わせれば、マーカーで波形の対象区間を選べる。合成ソースにも子区間を持たせられる。

時間軸や精度の扱いは合成側が担い、その後の処理は通常ソースと同様に実行する。元の時刻、合成後の時刻、合成条件、元ソースとの関係を追えるようにする。同期ラインや共通イベントを使う場合も、手動で合わせる場合も考える。

高速な通信の順序を調べる精度と、5分間隔の測定で数秒のずれを許容する精度は異なる。異なるサンプリング間隔を扱うことは、観測していない詳細を補えるという意味ではない。具体的な同期・補正方法は検証事項とする。

複数アダプタで同時取得する機能については、その記録を一つのソースにするか、時間を合わせたグループとして保持するかをまだ決めない。

## 処理を定義し、対象へ適用する

ここでいう「処理ファンクション」は、条件を持つタスクの組み合わせの仮称である。チャンネルの有効・無効、フィルターの条件、復号の条件、出力する項目や形式などを設定して繰り返し使う。出力タスクにはファイル名などを指定する使い方を考える。直列・分岐などの内部構造は未決定である。

フィルター、特徴抽出、復号、上位プロトコルの解釈は、一つの処理の中でつながる。前段の条件を変えれば、後段の解釈もその条件でやり直す。段階的な復号のために、保存結果を新しいソースとして登録し直す操作を要求しない。

対象は名前や階層で指定する。例えば次のように、同じ処理を一つの区間にも、複数の区間にも適用する。表記は説明用である。

~~~text
SCPI確認(記録A.実験1.電圧5V) → その区間の結果
SCPI確認(記録A.*)            → 選ばれた区間ごとの結果
簡易Analyze(記録B)           → 全体の概況と候補
~~~

複数対象を指定した場合は個別に処理し、対象名と結果の対応を返す。呼び出す側がどの区間を選ぶか決め、コアは指定された処理を実行する。チャンネルの自動判定も、必要ならこの処理の中で使う。

## 成果物とエビデンス

| 成果物 | 使い方 |
| --- | --- |
| 概況・簡易レポート | 活動、分布、一致状況、未解釈や例外の場所を見て、詳しく読む対象を選ぶ |
| 構造化された詳細結果 | コマンド・応答、指標、測定値と条件の対応などをスクリプトで扱う |
| 加工した波形や測定値 | フィルター後の状態を確認し、目的に合う情報量で利用する |
| 対象区間の実データ | 元の観測を検証し、対応する結果を再現するために保全する |

結果の行・区間を絞ることと、出す項目を選ぶことの両方を支える。例えば正常時との差分には時刻や毎回変わる CRC を省いたコマンド列、遅延や CRC エラーの調査にはそれらを含む結果を出す。差分計算や用途固有の判断は後工程で行う。

一回の処理から複数の成果物を取り出せることを目指す。ファイル出力を主な使い方として考え、コンソールへの短い出力も候補とする。すべてを毎回出すか、処理を複製して分けるかは固定しない。

エビデンスには解釈済みの文章だけでなく実データを使う。取り出したデータ、合成・分析条件、使用した分析機能がそろえば、対応する結果を再現できることが目標である。加工後のデータを元の観測と取り違えないよう、何を取り出したかを明らかにする。まずマーカー区間を基準とし、前後の無変化部分を削るかは別途検証する。

## 試行を残し、持ち運んで再開する

GUI でフィルターあり・なしや別の解釈候補を試し、途中の条件を残せるようにする。試行を増やすために元データを複製せず、結果のキャッシュがなくても必要な入力・条件・分析機能から再計算できることを重視する。

再現性には、元データ、対象範囲、適用した補正やフィルター、分析機能の版などが関わる。取得中の暫定結果と、取得後や条件変更後の結果も区別できる必要がある。

プロジェクトをコピーして別の環境で再開できるようにしたい。取り込み時はプロジェクト内へコピーすることを基本案とし、大きなデータの外部参照も選択肢とする。持ち運びに必要な依存がそろっているか、不足すると何を再現できなくなるかを分かるようにする。保存形式やプラグインを含める方式は検証計画で扱う。

表示・出力だけを短くすること、縮小版のソースを保存すること、元ソースを除くことは別の操作である。コマンド列だけを残せば後工程で通信内容を比較できても、元波形がなければビットずれやノイズを調べ直せない。同じ結果の再計算と、将来の別の問いへの再分析を区別する。

## GUI と CLI

GUI はソースを管理し、波形や候補を見ながら入力側の条件から試せるワークベンチとなる。CLI は同じプロジェクトと保存した条件で処理を実行できる。プロジェクトを使わず、入力と条件をすべて指定する一回の実行も扱いたい。

結果に影響する条件は両方で共有し、画面配置など表示だけの状態は GUI 側で扱う。図表の表示と出力データの生成の責務を分け、GUI を差し替えても分析を利用できる構成を目指す。

ソースとマーカーの階層は「どこを調べるか」、処理のつながりは「どう調べるか」、解釈候補の階層は「何として読めるか」を表す。それぞれを同じ単位に押し込める前提は置かない。
