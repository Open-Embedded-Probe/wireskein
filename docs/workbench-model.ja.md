# WireSkein — 分析ワークベンチの概念案

状態: **ここまでの議論を照合するための案**。以下の「共有した方向」と「保留」を分けて扱う。名称、記法、内部形式、最初の版の範囲は決めない。

## 核となる使い方

同じ実験で得た記録を一つのプロジェクトへ追加していく。利用者や外部ツールが**処理ファンクション**と**対象ソース**を指定し、WireSkein は結果を返す。簡易 Analyze や通信方式の自動判定も、選んで実行する処理の候補である。新しいソースが追加されたことだけを理由に、コアが処理を選んで実行する前提は置かない。

GUI は波形や結果を見ながらフィルターや復号の条件を試すワークベンチとなり、条件や途中の試行をプロジェクトに残す。CLI は同じプロジェクトと条件を使って処理を実行できる。プロトコルの段階的な復号は処理の連鎖内で扱い、保存した復号結果を再入力して続けることを中心要求には置かない。

## 共通のソースと階層

プロジェクトには、取得・取り込みしたソースが増えていく。ソースはデジタル波形、アナログ波形、測定値、文字列、イベントなどを共通の枠組みで扱う。元の実データを、分析条件の変更で書き換えない。

ソースにはマーカーで区切られた子区間を持たせる。親全体も子区間も分析対象に指定できる。親を指定したときは子区間の実データを含む全範囲を扱い、子のマーカーは区間内のイベントとして見える。子を指定したときは、その区間のデータを扱う。子はまず親の時間範囲への参照として考え、物理的な複製を前提にしない。

```text
プロジェクト
├─ 記録A
│  └─ 実験1
│     ├─ 電圧5V
│     │  ├─ 負荷ON
│     │  └─ 負荷OFF
│     └─ 電圧4V
└─ 記録B
   └─ 実験1 → 電圧5V → 負荷ON ...
```

マーカーは Markdown の見出しに似た階層を表す。同階層または上位の次の見出しで現在の区間を閉じる。名前が空の同階層マーカーは現在の区間を閉じ、新しい子を作らない。区間外のデータも親ソースには残る。同じ親の直下でマーカー名が重なった場合は、コアが出現順に連番を付けて区別する。別ソースや別の親の同名マーカーは重複とみなさず、元のマーカー文字列も保持する。通信内容などのデータは、区間の見出しとは区別して、その時点の区間に属する。

## ソースの合成

複数のソースを組み合わせるときは、ソースごとにオフセットや時間倍率を指定し、一本の**合成ソース**を作る。合成側が時間軸と精度を扱い、次の処理は合成元を意識せず通常ソースと同じように操作する。合成ソースにもマーカーによる子区間を作れる。元ソースと合成条件の関係を残す。基準時刻、補正方法、物理的な保存方法は後で決める。

## 処理対象の指定と結果

処理ファンクションにはソースの名前または階層パスを渡す。ソース名だけなら全体、子のパスならその区間を対象にする。`記録A.*` のような指定なら、選ばれた区間ごとに同じ処理を実行し、対象名を伴う結果の配列を返す。`*` が直下だけか下位全体か、実際の記法は後で決める。元ソース、合成ソース、子区間で呼び出し方を変えない。

```text
処理("SCPI確認", "記録A.実験1.電圧5V") → 指定区間の結果
処理("SCPI確認", "記録A.*")            → 区間ごとの結果の配列
処理("簡易Analyze", "記録A")           → 記録全体の結果
```

処理ファンクションの設定項目、実行時の上書き、結果の詳細構造はこの段階で決めない。チャンネルの自動判定が必要なら、選んで実行する処理の中で扱えるようにしたい。

## 処理を組み立てるイメージ

処理ファンクションは、対象の入力を用意し、利用者が追加したタスクを順に適用するバッチ処理として考えられる。フィルターのタスクには条件を設定し、プロトコル解析のタスクには解析条件を設定し、出力のタスクには成果物の形式やファイル名などを設定する。GUI でタスクを組み立てて保存し、同じ定義を CLI からも実行する使い方を想定する。画像編集のバッチ処理や BI・CI ツールは、作業を組み立てて繰り返し実行する体験の参考例であり、その仕組みを採用する決定ではない。

概念上は、入力の準備 → 設定したタスクの適用 → 加工後の波形・測定値と分析結果の取得、という流れになる。出力タスクは途中または最後の状態から複数の成果物を作れると便利である。分析結果を後続タスクが使う場合は同じ処理の中で受け渡し、保存済みの結果を新たなソースとして取り込み直す前提にはしない。直列のタスクだけで足りるか、途中の分岐や合流が必要かは利用場面で確かめる。

## バッチ処理を使った作業例

一つのプロジェクトにキャプチャを追加していき、繰り返し使う処理を定義する。処理の定義とキャプチャの追加は、どちらが先でもよい。処理にはフィルターやプロトコル解析に加え、必要な出力を複数指定できるようにしたい。例えば同じ実行で、最初に確認する簡易レポート、詳細レポート、対象区間の実データをそれぞれ取り出す。元の記録の形式で区間を出力する使い方もある。ファイルとして残すのが主な使い方だが、短い結果をコンソールで確認する使い方も候補に残す。

利用者はまず簡易レポートを読み、期待と違う点があれば処理の条件を直して再実行する。納得できる結果になったら、詳細レポートと実データを別の場所へ保全する。このとき、どのソース、区間、処理条件から各成果物が作られたかをたどれることが重要である。保全先の管理や実験の合否判定は外部の作業として考える。

簡易結果から詳細結果へ出力を切り替えることや、毎回すべてを出すことは利用者の構成次第とする。一つの処理に複数の出力を設定しても、処理を複製して用途別に分けてもよい。どちらかを標準の手順には定めない。

## 分析結果とエビデンス

出力には、後工程が使える構造化された分析結果に加え、対象区間の**実データをエビデンスとして取り出す**使い方がある。エビデンスは解釈済みのテキストだけに限定しない。目標は、取り出した実データと保存された分析条件から、対応する結果を再現できることである。合成ソースの場合も、時間合わせと元ソースとの関係が再現に必要になる。

まずはマーカーで定まる区間をエビデンスの範囲として考える。前後の無変化部分を削るか、さらに何を省けるかは別途検討する。元データを縮小・削除する場合は、同じ結果の再計算と、将来別の問いで元データを調べ直すことを区別して扱う。

## 製品の境界

外部の試験ツールは実験を進め、条件や成功・失敗を知っている。そのマーカーや記録を WireSkein に渡し、実験固有の判断、正常時との差分、テキスト分析を後工程で行う。WireSkein は指定されたソースに指定された処理を適用し、必要な結果とエビデンスを渡す分析ワークベンチとなる。GUI のグラフや表は、人が試行錯誤や結果の確認をするための機能である。

キャプチャは分析へ入力を供給する別の役割として考える。複数アダプタから同時に取得したデータが、一つの記録ファイルと一つのソースになるか、時間を合わせたグループとして複数ソースを保つかは決めない。これは取り込み済みの別記録を後から合成する操作とは別の問いである。どちらでも、分析側から指定できるソースとその時間・取得元の関係が分かることを目指す。

## 引き続き保留すること

- 「シーン」「ビュー」「処理ファンクション」などの製品上の名称と、GUI の画面単位との関係
- マーカーをどの取得元からどう抽出し、データの塊をどう表現するか
- `*` の選択範囲、同名への連番の表記、欠けたマーカーの扱い
- 合成ソースの時間合わせの具体的な規則と、プロジェクト設定・個別設定の置き場所
- エビデンスの具体的な形式、再現性の判定方法、無変化部分のトリミング
- 処理ファンクションの設定構造、出力形式、保存方式、プラグインの管理方法
- 複数成果物の具体的な指定方法、コンソールへ出す範囲、実行ごとの成果物の管理方法
- タスクを直列以外に分岐・合流させる必要性と、途中のデータ・結果をどこまで使えるようにするか
- 複数アダプタによる同時取得を一つのソースとするか、複数ソースのグループとするか

## 文書間の整合性を確認した結果

- 以前の「ソースごとにシーンを作り、シーン内で複数記録の時間を合わせる」説明は、今回の「合成ソースを作り、処理と対象を指定する」流れに合わせて修正した。分析条件を保存する単位と、適用先を記録した試行の単位が同じかは保留する。
- マーカーは単なる表示用ラベルだけでなく、親全体と子区間をどちらも処理対象にできるソース階層とした。親を処理したときに子の実データが消えないため、連続変化の分析とも矛盾しない。
- プロトコルの段階的な復号と、保存済みの分析結果を再入力することは別である。前者は一つの処理の連鎖で行い、後者をコアの基本操作にはしない。
- 「結果の再現」は、エビデンスとなる実データ、合成条件、処理条件、必要な分析部品がそろう範囲に限る。軽い結果だけ残した場合に将来の別条件でも再分析できるとは扱わない。

残る検証点は、合成ソースのマーカーが複数の入力にまたがる場合の区間、`*` で選ぶ対象の範囲、エビデンスを取り出した後に対応する結果を再計算できる条件である。いずれも利用場面で確かめてから規則を決める。
