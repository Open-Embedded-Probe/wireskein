# WireSkein — コア構想の整合性レビュー

状態: **検討用レビュー**。入力・処理・出力を用途別に組み合わせ、取得中と取得後に利用する構想を前提に、[構想案](project-concept.ja.md)、[ユースケース](use-cases.ja.md)、[分析事例](analysis-scenarios.ja.md)、ルートの既存メモを照合した。ここでは要求の衝突と不足を整理し、内部設計は決めない。

## 現時点で矛盾しない核

プロジェクトで共有するソースから、シーンごとに必要なフィルター、解析、集計を選び、問いに合う結果を後工程へ出す。元ソースは試行によって書き換えず、シーンを増やしても複製しない。プロトコルの連鎖は一つの分析処理の中で扱い、同じ観測から複数の結果を取り出せる。GUI は対話的に探索し、CLI は繰り返し可能な処理と安定した出力を重視する。どちらもプロジェクト、シーン、共通の分析結果を利用できる。

この核は、未知の通信の階層的な解析にも、マーカーと測定値を結び付ける特性測定にも使える。複数の利用場面を一つの固定手順へ押し込む必要はない。

構成の一例として、同じ入力から複数の道筋を作れる。

```text
ライブ入力・既存記録・以前の分析結果
  ├─→ 元の信号を確認する結果
  ├─→ フィルター → 通信候補 → 復号 → コマンド列・概況
  └─→ マーカーと測定値の対応付け → 再集計用の結果

それぞれの結果 → GUI・CLI・後工程・AI 用に必要な部分を選ぶ
```

これは利用体験を確かめるための例であり、処理の内部構造を決めるものではない。

## 区別が必要な三つの構造

1. **処理のつながり** — シーン内でソース、フィルター、解析、集計、出力の選択をどう組み合わせるか。同じ入力から分岐し、複数入力を合わせる場合もある。
2. **解釈候補の階層** — 信号から通信方式、上位プロトコル、機器固有の意味へ進む候補と、段階ごとの一致状況。利用者にはツリーとして見せられる。
3. **マーカーの階層** — 実験、条件、手順など、利用者や機器が記録に与えた文脈。

これらを同じ「ツリー」や「セッション」と呼ぶと、フィルターの分岐、候補の比較、実験の区切りの意味が混ざる。既存メモの Decoder Graph は 1 のうちデコーダーの連鎖を中心に考え、その候補が 2 の階層を作る。現在の構想では 1 にフィルター、集計、複数入力、用途別の出力も含めて考える必要がある。

プロジェクトはソースとシーンを共有・保存する単位であり、これら三つの構造そのものではない。シーンは処理と出力の選択を残す単位と考える。詳しくは [プロジェクトとシーンの概念案](project-model.ja.md) に記す。

## 修正が必要な前提

| 論点 | 現在の記述と衝突 | 整理する方向 |
| --- | --- | --- |
| 時間の基準 | メモの Capture は一つの sample rate と sample index を基本とする。現在の構想には、別々の機器、アナログ波形、間欠的な測定値がある | 各記録に固有の時間位置を持たせ、記録間の対応とその不確かさを別に扱う。具体的な表現は後で決める |
| Event の発生元 | メモでは Event を主に Decoder が生成する。現在は UART などから送るマーカーや利用者のラベルも必要 | 観測されたマーカー、利用者の注記、解析で見つけたイベントを区別し、同じ調査で使えるようにする |
| 拡張する部品 | メモでは Adapter と Decoder が中心。現在は入力形式、入力側・後段の Filter、集計、用途別出力も求めている | 追加できる処理の種類と、それぞれが扱う入力・結果を整理する |
| 数値の意味 | メモの Confidence、各層の「一致率」、解釈できた割合、取得の品質が混ざりやすい | 少なくとも「試した範囲」「規則に合った範囲」「未解釈」「候補の確からしさ」を区別する。計算式は後で決める |
| 取得中の結果 | メモはライブ解析と取得後の結果モデルを共通にしたい。取得中の候補は追加データで変わり得る | 暫定的な結果、確定した結果、再分析で更新した結果を後工程が区別できるようにする |

## まだ足りない約束

### 用途別の構成

どの部品を利用者が選び、どれを自動検出が候補として提案するかが未定である。同じ観測をフィルターあり・なしへ分岐し、GUI には波形、CLI にはコマンド列、AI には短い概観を出す場合、処理の共有と出力の選択を概念として整理したい。複数データ源を合わせる場合と、別々に解析して並べる場合も区別する。

### 情報を減らす際の意味

表示や出力を短くすること、フィルターで信号を変えること、元の記録を保存しないことは影響が異なる。現在の文書は元データへの参照を重視しているが、どの場合に再分析できなくなるかは未定である。未知の信号、誤り、ノイズ判定で除いた変化を、短い結果でもどう知らせるかを決めたい。

### 後工程が依存する結果

計測値とマーカーの対応、コマンド列、階層的な候補、概観などは利用方法が異なる。どの結果を安定した構造で取得できるようにするか、その意味と変更時の扱いを決めたい。GUI の表示形式と、スクリプトが依存する結果の形式は分けて考える。具体的なファイル形式は後で決める。

### 記録と区間の関係

プロジェクト、ソース、シーンの方向は [概念案](project-model.ja.md) に記した。一度の長回し取得から切り出した区間、複数機器の記録をまとめた調査、マーカーで表した実験段階の関係は引き続き未定である。物理的な切り出しと、元ソースの一部を参照するだけの区間も区別する。

複数ソースのサンプリング条件はそれぞれの記録に属する一方、ソース間の位置合わせは解釈として調整できる必要がある。共通の位置合わせやマーカーをプロジェクトに置く場合、シーンでどこまで上書きできるか、上書きした結果をどう見分けるかが未決定である。

### ソースの取り込みとプロジェクトの持ち運び

プロジェクト内へのコピーを基本にしたいが、高速・長時間の記録では容量が大きくなる。外部参照を選んだプロジェクトは、その外部ファイルが移動・変更されると再現できなくなる可能性がある。取り込み方法、ソースの同一性の確認、依存ファイルが見つからないときの扱いを整理したい。

大量の小さなファイルを伴う保存方式は、コピー漏れや失敗を招きやすい。単一のデータベースやアーカイブは検討候補だが、保存形式だけでは大きな記録の容量問題は解けない。分析中だけのダウンサンプリング、縮小版ソースの作成、元ソースの削除を区別し、後から再分析できる範囲を示す必要がある。

復号した通信の時系列や測定値の列など、波形より軽い結果をプロジェクトに保存する案もある。元データを残す間は再生成できても、元データを除いた後は保持すべき結果になる。これを後工程へ渡す出力とし、一時キャッシュとは区別する。プロトコルの連鎖は内部処理で扱い、保存結果を再入力する仕組みは中心要求に置かない。

### プラグインとシーンの再現性

シーンの条件を保存しても、使ったプラグインの内容が変われば結果は変わる。版やハッシュは識別には使えるが、プラグイン本体を復元する方法にはならない。標準プラグインと独自プラグインについて、何をプロジェクトに含め、何を外部の依存として明示するかを決めたい。シーンを増やしたときの設定量と結果キャッシュの増加も分けて考える。

### 取得と分析の境界

ライブ入力を受け取ることはコアの利用形態だが、計測器の設定変更や実験の進行は中心目標ではない。入力部品が取得のために必要な操作と、外部の自動計測が担う操作の境界を明確にしたい。

### 解析コストと結果の規模

候補やフィルターを無制限に試すことも、全結果を一度に AI や CLI へ渡すことも現実的ではない。まず軽い概観を作り、関心のある部分を詳しく調べる構想はあるが、どの処理を要求時に行い、どの結果を再利用するかは未整理である。具体的な性能目標は後で決める。

## 次に決める順番

1. **共通の言葉:** プロジェクト、ソース、シーン、区間、処理結果、候補、マーカー、用途別の出力を区別する。
2. **処理のつながり:** シーンでの分岐・合流・フィルターの位置と、自動提案と利用者指定の関係を利用場面で確かめる。
3. **結果の約束:** 後工程へ渡す結果の種類、元データとの関係、未解釈や取得不足、暫定・更新の扱いを決める。
4. **時間と区間:** 各データ源の時間、記録間の対応、マーカー、切り出しを整理する。
5. **拡張と操作方法:** 追加できる部品、GUI・CLI 固有の操作、安定した出力の対象を決める。
6. **技術方式:** 内部の接続方法、保存形式、API、具体的な一致率や同期方法を検討する。
