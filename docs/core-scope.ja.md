# WireSkein — コア、CLI、GUI、後工程の境界案

状態: **責務を検討するための案**。まず CLI で再実行できる分析の範囲からコアを定め、GUI による条件の作成・試行と可視化を加える。CLI のコマンド体系や GUI の画面構成はまだ決めない。

## 境界の基準

コアの責務は、共有できる分析条件を保持し、データから再実行可能な構造化結果を作ることである。CLI は保存した条件や明示的に指定した条件で、画面なしに分析を実行する入口と考える。GUI は同じ分析とプロジェクトを使い、入力側のフィルターや復号条件、時間合わせを試しながら設定を作り、結果を確認する。GUI の機能がすべて CLI の操作と一対一で対応する必要はない。

| 担当 | 主な責務 | 例 |
| --- | --- | --- |
| コアと CLI から使う分析機能 | 入力と対象の指定、時間合わせ、フィルター、プロトコル復号の連鎖、測定値とマーカーの整理、結果の項目選択、構造化出力、条件と来歴の記録 | 記録と分析条件を指定し、送受方向・コマンド・未解釈区間を出す |
| GUI の付加価値 | ソースや試行の管理、フィルター・復号・時間合わせ・出力条件の対話的な設定と比較、波形・グラフ・表・候補の階層の表示 | フィルター前後の波形を見て条件を変え、採用した設定をプロジェクトに保存する |
| 外部の後工程 | 出力された結果を使った用途固有の判断や追加分析 | 正常時との差分、テキスト分析、テストの合否判定、報告書の作成 |

GUI で決めたフィルター、復号、時間合わせ、出力項目が分析結果に影響するなら、その設定は共通のプロジェクト条件として残す。CLI はそれを読み、同じ処理を繰り返し実行できる。画面の配置や表の見た目など、人への表示だけに関わる状態は GUI 側の事項として扱う。出力する項目を選ぶことはコアの責務であり、GUI の表で列をどう配置するかとは区別する。

典型的な流れは、GUI で波形や中間結果を見ながらフィルターと復号条件を試す → プロジェクトに採用した条件を保存する → CLI で同じ条件を別の記録や自動テストの記録へ繰り返し適用する、というものである。試行の途中経過を残す単位や、別の記録へ条件を適用する方法は今後整理する。

グラフ化や表への表示は、構造化結果を人が調べるための後工程と考える。GUI に含める場合も、結果を作るコアの責務とは分ける。

## コアの範囲を確かめる例

1. デジタル記録からフィルターと復号の連鎖を実行し、通信候補、コマンド、未知の区間を構造化して出せる。前段の条件を変えた場合は、影響を受ける後段の結果を再計算できる。
2. 複数の記録の時間位置を指定して、測定値と設定マーカーを対応付け、後工程が再集計できる結果を出せる。
3. 同じ通信結果から、時刻と CRC を含む詳細な出力と、それらを省いた比較用の出力を選べる。比較そのものは外部の後工程が行う。
4. GUI で試して保存したプロジェクトのフィルター・復号・出力条件を CLI で再実行し、必要な入力やプラグインが欠けた場合は、それが分かる。

これらはコアの候補を評価する例であり、最初の版にすべて含める決定ではない。

## コアが担当しないこと

- 波形の描画、グラフ化、表のレイアウト、画面操作。これらは GUI の付加価値として検討する。
- 出力したコマンド列のテキスト分析や、正常時との汎用的な差分計算。比較しやすい出力を作るところまでをコアとする。
- テストの合否判定、実験手順の進行、汎用ノートブックや報告書の作成。これらを行う外部ツールへ結果を渡す。
- 保存した復号結果を新たなソースとして登録し直してプロトコル解析を続けること。プロトコルの段階的な解析は処理の連鎖内で扱う。

軽い結果をプロジェクトに保存することは検討対象に残す。これは後工程への受け渡しや持ち運びのためであり、元記録を除いた場合の再復号可能性とは分けて説明する。
