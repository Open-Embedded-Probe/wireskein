# WireSkein — 今後の検証計画

ここにある方式や候補は未採用である。[ビジョン](project-concept.ja.md) と [ワークベンチの振る舞い](workbench-model.ja.md) を満たす方法を、[ユースケース](use-cases.ja.md) の実データで確かめてから決める。検討対象があることと、最初の版へ搭載することは区別する。

## 実験の進め方

次の順番を出発点とする。実験ごとに入力、試した条件、成果物、得られた効果、残った制約を残し、その結果から方式や優先度を決める。実験用の仕組みをそのまま製品の構造にする前提は置かない。

| 順番 | 試すこと | 判断したいこと |
| --- | --- | --- |
| 1 | 同じ処理を複数キャプチャとマーカー区間へ適用し、簡易・詳細・実データを出す | 処理の再利用と対象の選択が自然か。取り出したデータと保存した条件・分析機能で対応する結果を再現できるか |
| 2 | 未知・既知・一部不正な通信を、フィルターの有無や取得レートを変えて調べる | 候補と例外の説明が役立つか。重要な変化をノイズとして隠していないか |
| 3 | アナログ波形、低頻度の測定値、別取得のマーカーを合わせる | 時間精度の違いと区間の境界を扱えるか。条件付きの測定値を後工程が再集計できるか |
| 4 | 後工程のスクリプトや AI へ必要な出力だけ渡す | 出力構造が使いやすいか。情報量を減らしても同じ調査対象を見つけられるか |
| 5 | 独自のフィルター・解析を追加し、プロジェクトを別の環境へ移す | 追加の負担、持ち運びやすさ、依存を含む再現性を確認できるか |

最初の対応機器・形式・プロトコル、ライブ処理と取得後処理の優先度、性能目標は、この結果を使って決める。AI 向けの効果は出力量やトークン数だけでなく、見落としや追加の調査回数も確かめる。

実データによる最初の確認と再実行手順は [初回の成立性調査](../experiments/initial-feasibility/README.ja.md)、[追加検証](../experiments/initial-feasibility/extended-findings.ja.md)、[基礎分析の検証](../experiments/initial-feasibility/foundations.ja.md)、[未知信号から上位解析までのワークフロー調査](../experiments/initial-feasibility/workflow-findings.ja.md) に記録する。

候補の探索、ビット列への変換、基本・上位プロトコルの検査、警告、必要な情報だけの出力を一連の作業として試す。ペア機器の送受成功とは独立に、線上の規則違反や操作後の信号状態を確認する。候補の点数だけで確定せず、説明できた範囲、実施した検査、未解釈、取得品質を別に残す。実機の異常例と未知方式の正解付き記録を増やし、見落とし・誤警告・保留を測ってから初期仕様を決める。

### 初期実験で確認する正確性と再現性

実験ごとに、入力記録と期待する結果を先に用意する。期待値は送信した既知の内容や手作業で確認した区間などを根拠にし、解析機能自身の出力だけで正しさを判断しない。

| 確認項目 | 合格を判断する材料 |
| --- | --- |
| 既知の記録を正しく解釈できる | 期待する送受方向、データ・コマンド列、対象区間と復号結果が一致する。測定値や時間の比較が必要な場合は、入力の精度と目的に応じた許容差を先に決める |
| 未解釈・除外部分を隠さない | 意図的に含めた未知・不正な区間と、フィルターで除外した区間を識別し、それぞれの位置と元データを確認できる。正常に解釈した範囲と区別できる |
| 必要な情報を後工程へ渡せる | 選んだチャンネル・区間・項目が欠けず、指定した形式で外部スクリプトが読める。情報を省いた出力からも、対応する詳細や元データを特定できる |
| 同じ条件で結果を再現できる | 同じ入力・条件・分析機能で再実行し、解析内容、対象区間、元データとの対応が一致する。実行日時などの付随情報と解析結果を分け、数値の許容差が必要なら比較前に明示する |
| 切り出したエビデンスから再現できる | 保全した区間データと条件・分析機能で、その区間の結果を再現できる。区間外のデータや処理状態が必要なら、不足する条件を明らかにする |

これらは初期実験の確認項目とする。具体的な記録、期待値、許容差、結果の比較方法は実験ごとに定め、製品全体の精度保証や初期対応範囲は検証結果を踏まえて決める。

## 1. ソース、時間、マーカー

**確かめること:** 元ソース、合成ソース、マーカー区間を同じ対象指定で使い、元の観測と時間の関係を追えるか。

- 各ソースのサンプル位置・サンプリング条件と、共通の時間位置の関係。単一のサンプルレートだけを全入力の前提にせず、不規則な測定値やアナログも含める。
- オフセット、時間倍率、同期ライン、共通イベント、手動補正の使い分け。基準時刻、時計のずれ、同期精度、元時刻と補正後時刻をどう示すか。補間・再サンプリングの要否もここで判断する。
- マーカーを通信やログから抽出する段階。UART の復号後にマーカーが分かる場合、区間を選ぶ前の準備をどう行うか。
- 見出し、終了マーカー、通信内容などのデータ部分を区別する記法。欠けた終了、階層の飛び、途中から取得した記録、ライブ取得中の未確定区間をどう扱うか。
- 同じ親の重複名へ連番を付ける表記と安定性。元の文字列、外部試験の識別子、ソースと階層をどう対応付けるか。
- 合成元の複数のマーカー系列が重なる場合の規則。合成後も元の出所を追い、必要な区間を選べるか。
- 名前やパス、ワイルドカードの具体的な記法と選択範囲。直下と下位全体、対象順序、存在しない対象の扱い。

既存のマーカー、利用者の注記、分析で発見したイベントは由来が異なる。区間や結果を整理するときに、それぞれの意味を失わない表現を試す。

## 2. タスクの組み合わせと結果の表現

**確かめること:** 条件を持つ処理を再利用し、前段を変更した影響が後段まで正しく反映されるか。

| 検討する案 | 試す内容 |
| --- | --- |
| 直列のタスクと処理グラフ | フィルター→復号→出力で足りる場面と、複数チャンネル、複数候補、フィルター前後の出力で分岐・合流が必要な場面を比較する |
| 型を持つ中間データ（Typed Stream） | デジタル信号、ビット、バイト、フレーム、行、コマンド、測定値などを段階間で渡す。受け付ける型から接続できる案を試す |
| 取得方法と上位解析の分離 | 同じコマンド解析が、波形から復号した内容と既存の通信ログの双方に使えるか確かめる |
| 構造化イベントと表示用注釈の分離 | 同じ分析結果から GUI、CLI、データファイル、レポートを作る。表示文字列を後工程が再パースしなくて済むか |
| 結果の来歴 | 上位のコマンドから、下位のフレーム、元チャンネルと区間、適用したフィルター・条件へたどれるか |

イベントには対象範囲、種別、値や内容、生成元、判断根拠などを持たせる案がある。どの入力・結果にも同じ項目を要求するかは、アナログや測定値も使って確かめる。

中間データを保存済みソースへ登録し直すことは、プロトコルを連鎖させる基本操作にしない。内部で結果を再利用する仕組みと、外部へ渡す成果物の保存を分けて検討する。

プロジェクト共通の条件、処理ごとの条件、実行対象、実行時の上書き、GUI の表示状態の置き場所も確かめる。「シーン」「ビュー」「処理ファンクション」などの名称や保存単位は、その役割が分かってから決める。

## 3. 候補の探索、一致率、条件変化の追跡

**確かめること:** 未知から始めても次に調べる場所が分かり、既知の通信では合わない場所を見つけられるか。

検出・復号を分け、特徴抽出→候補生成→候補の検証へ進む案がある。特徴の候補は、エッジ位置と間隔、パルス幅分布、デューティ比、無変化時間、周期性、変化密度、バースト、チャンネル間の関係、周波数である。共通の特徴を複数の解析から使う効果も測る。

仮説には対象区間、チャンネルの役割、通信方式、パラメータ、判断根拠を持たせる案がある。以下を実データで確認する。

- 同じ信号について複数の配線・速度・形式の候補を残すことと、候補を絞る条件。自動で処理の連鎖を提案する場合も、指定された分析の中で行う。
- 上位プロトコルが読めたことで下位の候補を再評価する方法。例えば UART の二つの形式候補を、その上のコマンドの整合から比較する。
- 利用者が分かっている線の役割や速度を与え、探索を絞る方法。推定値と利用者の上書き値を区別して残す。
- 通信途中の速度・モード・ビット順などの変化を区間で表す方法。周波数変化、位相、タイミング誤差、ドリフト、ジッターをどこまで追うか。公称値へ丸めた表示と実際の推定値も区別する。
- 特徴、候補の評価、型の互換性、計算コスト、以前の結果を使って探索量を制御する方法。低い評価の候補も必要なら再評価できるか。

一致率、解析できた範囲の割合、候補の確からしさ、取得品質は同じ数値ではない。0〜1 の Confidence を共通に持たせる案も含めて、何を分母・根拠とするかを検証する。まだ試していない部分、規則違反、未対応の命令、データ不足を分け、単に「100%」で調査全体の正しさを表さない。

## 4. フィルター、出力、エビデンス

**確かめること:** 情報量を減らした出力から必要な詳細へ戻り、保存したエビデンスで分析を再現できるか。

- ノイズゲート、搬送波除去、チャタリング除去、補正をどの段階に置くか。有効・無効、順序、条件変更、入力と結果へのフィルターを試す。
- 短い変化が通信速度の変更や未知の成分だった例で、除外箇所と取得不足の可能性をどう知らせるか。取得レートを上げる判断や、十分な精度まで下げる判断を支援できるか。
- 概況、コマンド列、指標、測定値と条件、未解釈区間の出力構造。行・区間の絞り込みと項目選択、JSON・CSV・時系列テキストなどの形式、複数レポート、コンソール出力、ファイル名や保存先を検討する。
- 構造の変更や解析機能の更新後も、外部スクリプトが何を前提にできるか。元データとの対応、除外した項目、実行条件を成果物と結び付ける。
- マーカー区間の実データを取り出し、同じ処理で再計算する。区間の前で始まったフレームやフィルターの状態など、境界をまたぐ情報が必要な例も試す。合成した時間軸や元の時刻も再現対象に含める。
- 前後の無変化部分のトリミング、ダウンサンプリング、差分・変化部分を中心に保存する案。何を減らすと同じ結果や将来の再分析を失うかを確かめる。

解析上の問題には、データ不足、時刻の不確かさ、フレーム・チェックサムの誤り、未対応の機能、解釈の曖昧さ、プロトコル違反、解析機能自体の失敗がある。正常に読めた部分を利用しながら問題の範囲を識別できる表現を検討する。

## 5. ライブ取得、部分処理、性能

**確かめること:** 高速・長時間の記録でも、指定した範囲と詳しさで処理できるか。

- 機器の検出、設定、取得開始・停止、データ受信を担うアダプタの範囲。取得に必要な操作と実験手順の制御との境界。
- 複数アダプタから同時取得した結果を、一つのソース・ファイルにする案と、時間補正したグループとして扱う案。
- チャンネル、区間、解析方法を指定する部分処理。境界に必要な前後データと、出力対象の範囲をどう区別するか。
- 取得中の追記を逐次処理する案。フレーム、行、上位の再構成などの途中状態を保持し、取得後の処理と結果の意味を合わせられるか。
- 暫定結果、確定した結果、追加データや条件変更で更新した結果を、後工程がどう区別するか。
- 特徴や中間結果の再利用、キャッシュ、影響範囲だけの再計算。キャッシュの有無で意味が変わらず、必要なメモリ・保存量・待ち時間に収まるか。

API を考える段階では、取得、ソースとチャンネルの列挙、対象の指定、条件の設定、候補や波形・結果の取得、再実行を GUI 固有の概念から切り離す。ここでは具体的なコマンドや API は決めない。

## 6. プロジェクトの保存と持ち運び

**確かめること:** 保存容量を抑える選択をしても、残した情報で何を再現できるかが分かるか。

| 選択肢 | 検証する点 |
| --- | --- |
| プロジェクト内へコピー／外部参照 | コピーを基本にした場合の容量と利便性。外部ファイルの移動・変更・消失の検出、同一性の確認、持ち運ぶときに必要な依存 |
| SQLite のような単一データベース／ZIP などのアーカイブ | コピー漏れを避けやすいか。大きな記録、追記、部分アクセス、更新、破損時の影響を扱えるか |
| 表示・分析時だけのダウンサンプリング | 元記録から別条件で調べ直せることと、処理負荷を減らす効果 |
| 切り詰め・間引きした縮小版ソース | 元との対応と失われた区間・時間・振幅の分解能。同じ結果を再現できる範囲 |
| 軽い分析結果のみを保存 | コマンド比較や測定値の再集計には足りても、元波形からの再復号はできないことの表現 |
| キャッシュの削除 | 元データ、条件、必要な分析機能が残る場合の再計算。保全すべき成果物との区別 |

例えば時刻・送受方向・コマンドだけで後工程に足りる場合、波形や無関係なマーカーを残さない選択も考えられる。どの問いに足りるかを示し、軽い結果を元ソースの代替として無条件に扱わない。

## 7. 拡張機能と再現性

**確かめること:** 新しい取得元や分析方法を過度な負担なく追加でき、使ったものを後から特定・再利用できるか。

- アダプタ、ファイル入力、フィルター、検出・復号、集計、出力を追加する単位と手順。
- 識別子、名称、版、受け付ける入力・生成する結果、設定項目、検出能力などを宣言する案。型の宣言で接続候補を作る案との関係。
- 簡単なビルドで追加する方式と、実行時に読み込む方式。開発・配布・導入・更新の負担を比較する。
- 標準の分析機能を版やハッシュで記録する案、独自の機能をプロジェクトへ埋め込む案。識別情報だけで本体を再入手できない場合を含める。
- 本体・依存が欠けた場合に、どの処理が再現できないか分かること。更新前後の結果と条件を混同しないこと。

## 8. GUI、CLI、実行環境

GUI で条件を試して保存し、CLI で同じ処理を再実行する一連の作業を確かめる。分析条件と表示状態、試行の保存単位、プロジェクトなしの一回実行、GUI の差し替えを検討する。

ブラウザでの利用は候補だが、取得機器への接続や大量データの扱いを制限する場合は PC での利用を優先できる。Rust は実装言語の有力候補として残す。言語、ライブラリ、プラグイン API、配布方法は利用場面と要求が確認できてから比較する。

## 参考にする体験と資料

| 参考 | WireSkein で検証したい性質 |
| --- | --- |
| SAS や R のような分析基盤 | 入力、条件、結果を対応付けて再実行し、後工程につなぐ |
| OBS Studio | 共有ソースから用途別の構成を作り、試した構成を残す |
| 動画・音声編集アプリ | 元データを保って区間を選び、共通イベントを手掛かりに時間を合わせる |
| 画像編集のバッチ処理、BI・CI ツール | 条件付きのタスクを組み合わせ、別の入力へ繰り返し適用する |
| Wireshark | 記録を絞り、出す項目を選んで後工程へ渡す |
| Audacity のプロジェクト保存 | 大量の小さなファイルを扱う負担を減らし、データと設定を持ち運ぶ |

方式を調べる際の資料として、Wireshark の [表示フィルター](https://www.wireshark.org/docs/man-pages/wireshark-filter.html)、[表示列](https://www.wireshark.org/docs/wsug_html_chunked/ChUsePacketListPaneSection.html)、[TShark の項目指定](https://www.wireshark.org/docs/man-pages/tshark)、Audacity の [プロジェクト保存](https://manual.audacityteam.org/man/audacity_projects.html) と [用語集](https://manual.audacityteam.org/man/glossary.html) を参照する。これらの製品の構造や保存形式を採用することは決めない。
