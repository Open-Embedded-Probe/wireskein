# 長いキャプチャ

[English](long-captures.md)

キャプチャは、すぐに GB の大きさになります。OEP のプローブは 40 MB/s で流すので 1 分で 2.4 GB、USB の
SuperSpeed のアナライザなら、その 10 倍の速さで溜まります。WireSkein は、そのようなキャプチャをブロックごとに
読み、区切って分析します。長さによらず、メモリは決まった量で済みます。区切りが復号したものは持ち（または書き出し）、
変化点は捨てます。

## 1. 流れ

1. **まず見る**: `wireskein survey CAPTURE` が 1 回読んで、それぞれの線が全体でどう動くかを示します（§2）。
2. **要るものだけ残す**: `wireskein convert IN OUT --from S --to S --pins A,B` で、一部の時間や一部の線を
   WireSkein のファイルに書きます（§5）。ロジックの `.sr` は、どんな長さでもブロックごとに変換します。
3. **区切って復号・分析する**: `decode` と `analyze` は、変化が `max_edges` より多い区間を区切り（§3）、1 つずつ
   読みます。`--items FILE` で、復号したものを読みながらファイルに書き出します（§4）。

変化が `max_edges` 以下のキャプチャは、今までどおり全体を一度に読みます。

## 2. survey

```sh
wireskein survey long.sr                       # 読むための行
wireskein survey long.sr --json --plan         # 文書（wireskein-survey/1）と、区切ったときの区切り
```

ブロックごとに 1 回読みます（1 つの区間の WireSkein のファイルと、ロジックの `.sr` はファイルから直接。ほかは先に
読み込みます）。線ごとに:

| キー | 意味 |
| --- | --- |
| `edges` | 変化の数 |
| `activity` | 時間を `bins`（既定 1000）等分した、それぞれの変化の数 |
| `intervals`、`high`、`low` | 変化の間隔、high と low の長さを、2 のべきのビン（tick）で |
| `longest_still` | いちばん長く止まっている所の上位 `top`（既定 10）: `s`、`e`、`seconds` |
| `short_share` | 1〜2 tick の間隔の割合。フローティングで震える入力や、縁で揺れる線で高い |
| `usual_interval_s` | 間隔の中央値 |
| `free_running` | 止まらない線（いちばん長い間隔が、いつもの 4 倍以内）: `period_s`、`freq_hz`、`duty` |

全部の線について、`all_still`: どの線も動かない、いちばん長い所。`trembling`: `short_share` が 0.3 を超える線。
`--plan` で、`pieces`: §3 で区切ったときの区切り。

## 3. 区切り

変化が `max_edges` より多い区間は、読みながら区切ります。先頭から `max_edges` までの変化を窓にし、その中で、線が
静かな所で切ります。

- 線ごとに、窓の中の間隔の中央値を、いつもの間隔とします。その `gap_min` 倍止まっていれば、静かです。`noise_max`
  tick 以下のパルスは数えません（反射の揺れ、短い震え）。
- 窓の中で一度も止まらない線（止まらないクロック、PWM、I2S の WS）は、フレームの終わりを示さないので除きます。
  フレームの間で止まるクロック（SWCLK、SPI の SCK、I2C の SCL）は除きません。止まる所が切れ目になります。
- 残りの線が同時に静かな所のうち、窓の `search_from` より後のものが候補です。いちばん長いものの真ん中で切り、
  その `similar` 倍以上の長さのものでも切ります。どの区切りも `min_edges` 変化以上にします。
- 窓に止まらない線があると、静かでもフレームの途中のことがよくあります（データがしばらく同じ値）。その切れ目は
  `data_quiet` です。
- 候補が 1 つも無いとき（止まらない線だけ、または休まないストリーム）は、窓の終わりで `forced` として切ります。
- どの切れ目も、両側の区切りが `overlap_edges` 変化越えて読みます。静かな所でもフレームの途中のことがあるためです
  （プロトコルの折り返し。LinkE が SDI を見張るときのように、フレームが続き、その間の隙間が折り返しより長くない）。
  二度読んだ項目は、その始まりが自分の tick に入る区切りが持ちます。

最後の切れ目より後ろは、次の窓に持ち越します。decode では、spec のバスの線と `lines` で静かな所を探します。
`analyze` は、すべての線で探します。

`analyze` は、役割（confirmed か likely の主張）のある最初の区切りで役割を決め（先頭から `roles_from` 個まで試す）、
すべての区切りをその役割で decode します。見つからなければ、`split.no_roles` がそう言います。
フレームをまたぐ状態（RISC-V Debug Module）は、区切りをまたいで 1 つとして読みます。

### 3.1 オプション

`analyze` と `decode` の `--split KEY=VALUE,...`（Python では `split=`、decode の spec の `"split"`）。
`--split off` は、どんなに長くても全体を一度に読みます。

| オプション | 意味 | 既定 |
| --- | --- | --- |
| `max_edges` | これより変化が多い区間を区切る。窓の大きさ | 1 000 000 |
| `search_from` | 窓のこの割合より後で、切れ目を探す | 0.5 |
| `gap_min` | いつもの間隔のこの倍止まっていれば静か | 4 |
| `similar` | いちばん長い静かさのこの割合以上のものでも切る | 0.5 |
| `min_edges` | 区切りの変化の下限 | 50 000 |
| `overlap_edges` | どの切れ目も、両側で越えて読む変化の数 | 10 000 |
| `noise_max` | この tick 以下のパルスは、線を忙しくしない | 1 |
| `noise_share` | 間隔のこれより多くがその短さの線を、震えている線として知らせる | 0.3 |
| `watch=A;B` | この線でだけ静かさを見る | spec の線、または全部 |
| `ignore=A;B` | この線では見ない | |
| `cuts=T1;T2` | 探さずに、ここ（tick）で切る | |
| `workers` | 区切りを、このプロセス数で同時に decode する（同時に抱えるのは 2 倍まで） | 1 |
| `roles_from` | `analyze`: 役割を探すのに、先頭から試す区切りの数（先頭はバスより前のことがある） | 3 |
| `reanalyze` | 疑わしい区切りを、それだけでも analyze し、見つけたものを `doubtful[].holds` に出す（0: しない） | 1 |

既定値は、WCH-LinkE の SDI の見張りの 2 秒（850 万変化）で測って決めました。区切りが 50 万〜100 万変化のときに
いちばん速く軽く、25 万では強制で切る所が出ました。

### 3.2 区間に出るもの

区間に `split` が付きます。

| キー | 意味 |
| --- | --- |
| `options` | 使ったオプション |
| `pieces` | `[{"s", "e", "edges", "cut", "ratio"?, "read"?}]`: 区切りの自分の tick、変化の数、どう終わったか（`quiet`、`data_quiet`、`forced`、`given`、`end`）、静かさがいつもの間隔の何倍だったか、自分の範囲を越えて読んだときの読んだ tick |
| `trembling` | 1〜2 tick の間隔が多い線: 名前 → 割合（知らせるだけで、外さない） |
| `doubtful` | 役割での読みが悪い区切り（バスが読めない、当てはまりが 0.3 未満、または自分の tick の中でよく読めたものが無い）と、その場所、それだけで analyze して見つかったもの（`holds`: confirmed か likely の主張）。途中で様子が変わったのかもしれない（別のバス、別の速さ） |

バスごとに `uninterpreted_summary`: `count`、`edges`、`sizes`（2 のべきのビン）、`largest`。長いキャプチャには、
小さな読めない区間（フレームの間で動く線）がたくさんあり、意味のあるものは少しです。`fit` は、いちばん悪い区切りの
もので、`fit.pieces` にすべての区切りの点数があります。区切って読むときは、spec に無い線の主張（claims）は
出しません。

## 4. 項目の書き出し

長いキャプチャが復号するものは、メモリに収まりません（LinkE の 38 秒で、DMI のアクセスが 128 万）。`--items FILE`
（Python では `items=`）で、読みながら書き出します。1 行に 1 つの JSON です。

```json
{"bus": 0, "layer": "dmi", "s": 5512646, "e": 5524342, "op": "R", "addr": 4, ...}
```

`bus` は spec のバス（または主張）、`layer` は結果の層（`dmi`、`dm`、`transactions`、`uninterpreted` など）、
残りは [analysis-format](analysis-format.ja.md) §3.2 のとおりの項目で、tick は区間のものです。文書では、バスごとに
`result.items`: `{"file", "counts"}` になります。

## 5. 要らない線

フローティングで震える入力や、バスと関係の無い線を一緒に取っていることは、よくあります。勝手には外しません。
survey と区切りが知らせ、どうするかは利用者が決めます。

1. 分析はそのまま進みます。1〜2 tick のパルスは、静かな所を隠しません。
2. 知らせます。`survey` が `short_share` と `trembling` を、区切って読んだ区間が `split.trembling` を出します。
   休まずに震える線は止まらない線として扱われ、切れ目が `data_quiet` になります（`split.pieces` で分かります）。
3. 確かめます: `wireskein states CAPTURE --pin X`、またはビューア。
4. 分析から外します: `--split ignore=X`（静かさを見ない）、`--pins A,B,...`（この線だけを読む）。
5. データから消します: `wireskein convert IN OUT --pins A,B,...`（この線だけを書く）、`--from` / `--to`（その時間
   だけを書く）。

## 6. 速さ

LinkE の SDI の見張りの 38 秒（25 MHz、1.6 億変化、`.sr` で 950 MB）の RVSWD を、`--split workers=4 --items` で
decode して 6 分 54 秒、530 MB（元のプロセス）。その `.sr` の WireSkein のファイルへの変換は 13 秒、180 MB。
