# WireSkein — プロジェクトと分析作業の概念案

状態: **コアの概念案**。GUI と CLI が共有する作業の単位を整理する。ファイル構造、内部形式、プラグインの配布方法はまだ決めない。

**用語について:** 以前の議論で「シーン」と呼んだものには、分析条件、対象への適用、試行の保存、表示状態が含まれていた。これらを一つの単位にするかは未決定であり、名称も後で決める。「ビュー」も表示画面や表示方法など別の意味と混ざり得る。

ソース階層、合成、処理対象の指定について共有した外形は [分析ワークベンチの概念案](workbench-model.ja.md) にまとめる。この文書はプロジェクトの保存や設定の置き場所を検討する資料とする。

## 参考にする考え方

プロジェクトは試行の再現性を重視する。そのため、次の分野の使い方を参考にし、WireSkein で必要な性質を検討する。個々の製品の構造をそのまま採用するという意味ではない。

| 参考 | 確かめたいこと |
| --- | --- |
| SAS や R のような分析基盤 | 入力、分析条件、結果の関係を残し、処理を再実行して後から別の分析へ進めること |
| OBS Studio | 共有するソースから用途別の構成を複数作り、構成を切り替えながら試すこと |
| 動画・音声編集アプリ | 元データを保ったまま区間や処理を組み替え、複数ソースを時間上で位置合わせすること |
| Wireshark | 取得データをフィルターで絞り、表示する列や取り出す項目を選んで後工程へ渡すこと（[表示フィルター](https://www.wireshark.org/docs/man-pages/wireshark-filter.html)、[表示列](https://www.wireshark.org/docs/wsug_html_chunked/ChUsePacketListPaneSection.html)、[TShark の項目指定](https://www.wireshark.org/docs/man-pages/tshark)） |

保存方式の参考例として、Audacity 3.x の `.aup3` は、音声データや編集情報を一つの SQLite データベースに収めるプロジェクト形式である（[保存内容](https://manual.audacityteam.org/man/audacity_projects.html)、[SQLite 形式](https://manual.audacityteam.org/man/glossary.html)）。旧形式のように一つのプロジェクトが大量の小さなファイルに分かれると、コピーや受け渡しが難しくなる。WireSkein でも、元データ、設定、結果キャッシュをどこまでまとめるかを検討する。ただし、単一ファイルや SQLite の採用はまだ決めない。

## 基本の流れ

利用者は保存して再び開けるプロジェクトを作り、取得済みファイルや計測器からの記録を **ソース** として追加していく。元ソース、合成ソース、マーカーで分けた子区間は共通の枠組みで分析対象に指定できる。元データは分析の試行錯誤によって書き換えない。分析条件と途中の試行もプロジェクトに残す。物理的に単一ファイルにするか、複数ファイルのまとまりにするかは後で決める。

```text
Project
├─ Sources
│  ├─ 記録A → マーカーによる子区間
│  ├─ 記録B
│  └─ 合成ソース（複数ソースと時間合わせの条件）→ 子区間
└─ 保存した分析条件と試行

指定した処理ファンクション + ソース名／子区間のパス → 結果と必要な実データ
```

これは利用体験の例であり、実際の保存形式や処理の接続方法を指定しない。

## ソース

ソースは取得したデータや取り込んだ記録を保持する。デジタル信号、アナログ波形、間欠的な測定値、マーカー、機器の通信ログなどを含められる。複数ソースから作った合成ソースも、元ソースと同じように分析対象に指定できる。マーカーで分けた子区間もソース階層の一部として指定し、親全体も引き続き使える。

取り込み時には、プロジェクト内へコピーして保持することを基本案とする。容量や既存の保管方法に応じて、外部ファイルを参照する選択肢も検討する。プロジェクトがどこまで単体で持ち運べるか、外部ソースが移動・変更・消失したときにどう知らせるかは未決定である。

取得中のソースはデータが増えていく可能性がある。既に取得した部分を分析設定の変更で書き換えないことと、取得中に末尾が増えることを区別する。

## 持ち運びやすさとデータの縮小

プロジェクトは、別の場所へコピーして開き直し、保存した分析を再実行できることを目指す。大量の小さなファイルが散らばっていると、コピー漏れや途中失敗に気づきにくい。一方で、大きな記録をすべて持ち運ぶと容量が問題になる。必要なデータと分析条件がそろっているかを確認できることも、持ち運びやすさの一部と考える。

保存方式の候補には、SQLite のように一つのデータベースへまとめる方法や、プロジェクトを ZIP などのアーカイブにまとめる方法がある。コピーのしやすさに加え、大きなソースの扱い、取得中の追記、必要な区間へのアクセス、破損時の影響も比較する。外部参照を使う場合は、単体で持ち運べる状態とは区別する。

容量を減らす操作は、後からできる分析への影響で分ける。

| 操作 | 元データへの影響 | 再分析できる範囲 |
| --- | --- | --- |
| 表示・分析時のダウンサンプリングフィルター | 元のソースを残す | 元データから別の条件でやり直せる |
| 区間の切り詰めやダウンサンプリングで縮小版ソースを作る | 元のソースを残すか、明示的に除くかを選ぶ | 元を残せば全体を、除けば縮小版に含まれる情報だけを再分析できる |
| 復号・集計した軽い結果を保存する | 元のソースを残すか、明示的に除くかを選ぶ | 外部の後工程には結果を渡せる。元を除くと波形からの再復号はできない |
| キャッシュを削除する | 元データと分析条件を残す | 必要な部品があれば再計算できる |

ソースを切り詰める機能も検討する。元のソースを除く場合は、失われる区間や時間・振幅の分解能を明示し、どのソースにどの処理を施した縮小版なのかを残す。縮小版だけで再現できる結果と、元のソースがないと再現できない結果を区別する。これは分析中のフィルターとは異なる、プロジェクトの保管内容を変える操作として扱う。

波形やマーカーが必要かどうかは、後で答えたい問いによって変わる。例えば、UART のコマンドの順序や内容だけを調べるなら、時刻、送受方向、テキストやバイト列を残し、波形を除いても足りる場合がある。マーカーがその問いに関係しなければ、縮小版に含める必要はない。一方、デコード条件の誤り、タイミング異常、未知の信号を調べ直すには波形が必要になり得る。測定値の再集計には、設定条件と測定値の列だけで足りる場合もあるが、瞬間的な変化を再調査するには元のアナログ記録が必要になる。

復号・集計した軽い結果を、プロジェクトに保存する案も検討する。これは後工程へ渡す出力や、元ソースを除いた場合にも残したい記録に相当する。プロトコルの次の段階を解釈する処理はフィルターやデコーダーの連鎖内で行い、保存結果を新しいソースとして登録し直すことを前提にしない。再生成できる一時キャッシュと、元ソースを除いた後にも保持する結果は区別する。軽い結果が何からどの条件で作られ、どの情報を残しているかを確認できるようにしたい。役割の整理は [コアの境界案](core-boundaries.ja.md) に記す。

## 分析条件と試行単位（「シーン」は仮称）

GUI で条件を試し、途中経過を残せるようにしたい。処理ファンクションにはソース名や子区間のパスを渡して実行する。保存した分析条件と、あるソースに適用して得た試行結果を同じ単位に含めるかは未決定である。記録しておきたい内容の候補は次のとおり。

- 適用したソース名・子区間のパスと、チャンネルの有効・無効
- 利用者による分析上の補正や指定
- フィルターの選択、順序、有効・無効、条件
- 試すプロトコルや分析、候補の選択、手動の補正
- GUI での表示と、CLI や後工程向けに取り出す結果

同じソースに対する試行を増やしても、元データを複製せずに条件の違いを残せることを目指す。保存した条件を別のソースや子区間に適用する使い方もある。フィルターあり・なし、複数のプロトコル候補、以前の試行を後から再開できるようにしたい。表示だけの一時的な操作との境界は今後決める。

処理は一つの直列手順に限定しない。同じソースから複数の分析を試したり、合成したソースを分析したりできる構成を想定する。概念上は次のような流れになる。

```text
指定したソース／子区間 → フィルターや解析条件を適用する
                       → 特徴抽出・プロトコル分析・測定値の整理など
                       → 構造化結果と必要な実データを出力する
```

処理の途中から別の分析へ分岐したり、分析後の結果にフィルターをかけたりする場合もある。試行を複製して条件を変えられれば、分岐と比較がしやすい。具体的な接続方式は後で決める。

## 設定を置く場所と合成ソースの時間軸

複数のソースを合わせるときは、オフセットや時間倍率を指定して一本の合成ソースにする。サンプリング間隔や時刻表現の違いを含む時間軸の扱いは合成側の責務とし、その後の分析は通常ソースと同じように行う。必要な精度は、通信波形を照合する場合と低頻度の測定値を比較する場合で異なる。

合成の条件には、元ソースとその時間上の対応を残す。どのソースを時刻の基準にするか、同期信号やイベントをどう使うかは後で決める。ソースごとの元の時刻と合成後の時刻は区別して扱う。

設定の置き場所は、まず次のように分類して検討する。

| 種類 | 例 | 現時点の扱い |
| --- | --- | --- |
| ソースの事実 | 元データのサンプリング条件、記録時刻、チャンネル、記録された同期信号 | ソースとともに保持し、分析条件の変更で書き換えない |
| 合成ソースの条件 | 合成元、オフセット、時間倍率 | 合成ソースとともに保持する方向。具体的な規則は未決定 |
| 分析の条件 | 対象の選択、チャンネルの有効・無効、フィルター、復号、出力項目 | 保存して再利用する候補。設定単位の境界は未決定 |

プロジェクトで共通にする条件と個別の試行で変える条件の境界は引き続き検討する。結果を出す際には、実際に使った合成ソースと分析条件を確認できる必要がある。

## 結果とキャッシュ

プロジェクトには、分析結果そのものだけでなく、結果を再計算できる条件を保持する。結果をキャッシュして表示や繰り返し処理を速くしてもよいが、キャッシュの有無で分析の意味が変わらないことを目指す。多くの試行を残せるよう、設定と大きくなり得る結果キャッシュを分けて考える。

取得中の暫定結果、取得後の結果、プラグインを更新して再計算した結果は異なり得る。後工程へ結果を渡すとき、どの状態の結果か分かるようにする。

## 再現性に必要な情報

同じ結果を作り直すには、少なくとも対象ソースと区間、使用したフィルターと分析機能、合成の条件、利用者の補正を特定できる必要がある。プラグインも、名前だけでなく実際に使った版を区別する。

標準で提供されるプラグインは版や内容の識別情報を記録し、独自のプラグインはプロジェクトに含める案がある。ただし、ハッシュや版の記録だけではプラグイン本体を再入手できるとは限らない。どの状態を「再現可能」と呼ぶかと、必要な部品が見つからない場合の扱いは今後決める。

## GUI と CLI

GUI はプロジェクト内のソース階層や試行を見渡し、フィルター、復号、合成の時間合わせ、出力項目などを試し、採用した条件を保存する。波形や結果の表示は、その試行を助ける。CLI は同じプロジェクトのソース名または子区間のパスと処理ファンクションを指定して実行できる。GUI で保存した条件も利用できる。CLI でプロジェクトを使わず、ソースと条件をすべて指定して一回の分析を行う使い方も候補に残す。

GUI と CLI が共有するのは、ソースの意味、保存した分析条件、結果である。操作方法や画面上の状態を同じにする必要はない。GUI の表示画面と、ここで仮に「シーン」と呼ぶ単位が一対一で対応するかも未決定である。

CLI で再実行できる分析と構造化出力を先にコアの基準として整理し、GUI による条件の作成・試行、表示、探索操作を付加価値として考える。詳しくは [責務の境界案](core-scope.ja.md) に記す。

## 次に決めること

1. プロジェクトに保存する分析条件、試行の途中経過、表示状態の境界。共通設定の上書き範囲も含める。
2. 元データをプロジェクト内へコピーする既定動作と、外部参照を選ぶときの約束。
3. プロジェクトを持ち運べる単位と、保存方式を比較するときの条件。縮小版ソースだけを残す場合の再現範囲も含める。
4. プラグインを後から再利用できる状態と、版・内容をどう特定するか。
5. 取得中に増えるソースと暫定結果を、保存した分析条件と後工程がどう扱うか。
6. キャッシュを消して再計算したとき、同じ結果とみなす条件。
