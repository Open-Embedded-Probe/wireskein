# WireSkein — プロジェクトとシーンの概念案

状態: **コアの概念案**。GUI と CLI が共有する作業の単位を整理する。ファイル構造、内部形式、プラグインの配布方法はまだ決めない。

**用語について:** この文書の「シーン」は、分析対象・条件・出力を保存して試行を残す単位を指す仮称であり、製品で使う名称は後で決める。「ビュー」も表示画面や表示方法など別の意味と混ざり得るため、この単位の正式名称とはしない。名称を決める際には、保存する分析設定と GUI の表示状態が同じ単位かどうかも確認する。

## 参考にする考え方

プロジェクトは試行の再現性を重視する。そのため、次の分野の使い方を参考にし、WireSkein で必要な性質を検討する。個々の製品の構造をそのまま採用するという意味ではない。

| 参考 | 確かめたいこと |
| --- | --- |
| SAS や R のような分析基盤 | 入力、分析条件、結果の関係を残し、処理を再実行して後から別の分析へ進めること |
| OBS Studio | 共有するソースから用途別の構成を複数作り、構成を切り替えながら試すこと |
| 動画・音声編集アプリ | 元データを保ったまま区間や処理を組み替え、複数ソースを時間上で位置合わせすること |

保存方式の参考例として、Audacity 3.x の `.aup3` は、音声データや編集情報を一つの SQLite データベースに収めるプロジェクト形式である（[保存内容](https://manual.audacityteam.org/man/audacity_projects.html)、[SQLite 形式](https://manual.audacityteam.org/man/glossary.html)）。旧形式のように一つのプロジェクトが大量の小さなファイルに分かれると、コピーや受け渡しが難しくなる。WireSkein でも、元データ、設定、結果キャッシュをどこまでまとめるかを検討する。ただし、単一ファイルや SQLite の採用はまだ決めない。

## 基本の流れ

利用者は保存して再び開けるプロジェクトファイルを作り、取得済みファイルや計測器からの記録を **ソース** として追加する。ソースはプロジェクト全体で共有し、分析の試行錯誤によって元データを書き換えない。そこから複数の **シーン** を作り、同じソースを異なる目的と条件で調べる。物理的に単一ファイルにするか、複数ファイルのまとまりにするかは後で決める。

```text
Project
├─ Sources
│  ├─ logic capture
│  ├─ analog measurements
│  └─ event log
├─ Scene: 未知の信号を概観する
│  └─ source と channel を選択 → 特徴抽出 → 候補を見る
├─ Scene: 通信を詳しく調べる
│  └─ 同じ source → filter と解析条件を選択 → command / unknown 区間
└─ Scene: 特性を再集計する
   └─ measurements と marker → 条件付き測定値の出力
```

これは利用体験の例であり、実際の保存形式や処理の接続方法を指定しない。

## ソース

ソースは取得したデータや取り込んだ記録の原本に相当する。デジタル信号、アナログ波形、間欠的な測定値、マーカー、既存の分析結果などを含められる。シーンはソース全体または必要な区間を参照する。

取り込み時には、プロジェクト内へコピーして保持することを基本案とする。容量や既存の保管方法に応じて、外部ファイルを参照する選択肢も検討する。プロジェクトがどこまで単体で持ち運べるか、外部ソースが移動・変更・消失したときにどう知らせるかは未決定である。

取得中のソースはデータが増えていく可能性がある。既に取得した部分を分析設定の変更で書き換えないことと、取得中に末尾が増えることを区別する。

## 持ち運びやすさとデータの縮小

プロジェクトは、別の場所へコピーして開き直し、保存した分析を再実行できることを目指す。大量の小さなファイルが散らばっていると、コピー漏れや途中失敗に気づきにくい。一方で、大きな記録をすべて持ち運ぶと容量が問題になる。必要なデータと分析条件がそろっているかを確認できることも、持ち運びやすさの一部と考える。

保存方式の候補には、SQLite のように一つのデータベースへまとめる方法や、プロジェクトを ZIP などのアーカイブにまとめる方法がある。コピーのしやすさに加え、大きなソースの扱い、取得中の追記、必要な区間へのアクセス、破損時の影響も比較する。外部参照を使う場合は、単体で持ち運べる状態とは区別する。

容量を減らす操作は、後からできる分析への影響で分ける。

| 操作 | 元データへの影響 | 再分析できる範囲 |
| --- | --- | --- |
| 表示・分析時のダウンサンプリングフィルター | 元のソースを残す | 元データから別の条件でやり直せる |
| 区間の切り詰めやダウンサンプリングで縮小版ソースを作る | 元のソースを残すか、明示的に除くかを選ぶ | 元を残せば全体を、除けば縮小版に含まれる情報だけを再分析できる |
| 復号・集計した軽いデータを追加する | 元のソースを残すか、明示的に除くかを選ぶ | 軽いデータを入力とする後段の分析は続けられる。元を除くと波形からの再復号はできない |
| キャッシュを削除する | 元データと分析条件を残す | 必要な部品があれば再計算できる |

ソースを切り詰める機能も検討する。元のソースを除く場合は、失われる区間や時間・振幅の分解能を明示し、どのソースにどの処理を施した縮小版なのかを残す。縮小版だけで再現できる結果と、元のソースがないと再現できない結果を区別する。これは通常のシーン内フィルターとは異なる、プロジェクトの保管内容を変える操作として扱う。

波形やマーカーが必要かどうかは、後で答えたい問いによって変わる。例えば、UART のコマンドの順序や内容だけを調べるなら、時刻、送受方向、テキストやバイト列を残し、波形を除いても足りる場合がある。マーカーがその問いに関係しなければ、縮小版に含める必要はない。一方、デコード条件の誤り、タイミング異常、未知の信号を調べ直すには波形が必要になり得る。測定値の再集計には、設定条件と測定値の列だけで足りる場合もあるが、瞬間的な変化を再調査するには元のアナログ記録が必要になる。

分析済みの軽いデータを、別の分析やシーンから参照できる入力としてプロジェクトに追加する案も検討する。このデータを「ソース」に含めるか、保存する「分析結果」として別に扱うかは未決定である。元データから再生成できるキャッシュと、元データを除いた後も保持する必要がある入力は区別する。どちらの場合も、軽いデータが何からどの条件で作られ、どの情報を残しているかを確認できるようにしたい。

## シーン

シーンはソースから何をどう調べ、何を取り出すかを記録する作業単位である。候補となる内容は次のとおり。

- 使うソース、区間、チャンネルと、それぞれの有効・無効
- 記録間の位置合わせ、マーカーや利用者の指定
- フィルターの選択、順序、有効・無効、条件
- 試すプロトコルや分析、候補の選択、手動の補正
- GUI での表示と、CLI や後工程向けに取り出す結果

同じソースからシーンを増やしても、元データを複製せずに条件の違いを残せることを目指す。フィルターあり・なし、複数のプロトコル候補、以前の試行をそれぞれ残し、後から再開できる。シーンが保存する範囲と、表示だけの一時的な操作の境界は今後決める。

シーン内の処理は、一つの直列手順に限定しない。同じソースから複数の分析を試したり、複数のソースを合わせて見たりできる構成を想定する。概念上は次のような流れになる。

```text
共有ソース → シーン内で対象・区間・チャンネルを選ぶ
          → 必要な位置合わせやフィルターを適用する
          → 特徴抽出・プロトコル分析・測定値の整理などを行う
          → 用途別の表示・構造化出力を得る
```

処理の途中から別の分析へ分岐したり、分析後の結果にフィルターをかけたりする場合もある。シーンを複製して条件を変えられれば、試行の分岐と比較がしやすい。具体的な接続方式は後で決める。

## 設定を置く場所と複数ソースの時間軸

複数のソースを同じシーンで扱う場合、サンプリング間隔や時刻表現の違いはコアが扱い、共通の時間軸で表示・分析できるようにしたい。ただし、記録開始時刻のずれはデータ形式だけでは分からない場合がある。一定間隔の測定なら数秒のずれを許せることもあり、通信の前後関係を調べるならより正確な位置合わせが必要になる。

位置合わせには、利用者が指定するオフセットのほか、共通に記録された同期信号やイベントを手掛かりにする方法が考えられる。動画のカチンコに相当するイベントや、ロジックアナライザーの同期用ラインがその例である。長時間の記録では開始時刻のずれだけでなく、各ソースの時計の進み方の違いも起こり得る。ソースごとの時刻と、位置合わせ後にシーンで使う時刻は区別して残す。

設定の置き場所は、まず次のように分類して検討する。

| 種類 | 例 | 現時点の扱い |
| --- | --- | --- |
| ソースの事実 | 元データのサンプリング条件、記録時刻、チャンネル、記録された同期信号 | ソースとともに保持し、シーンから書き換えない |
| プロジェクトで共有したい解釈 | 複数ソース間の基準となる位置合わせ、チャンネルの名前や役割、共有マーカー | 共通設定の候補。どこまで置くかは未決定 |
| シーン固有の解釈 | 対象区間、チャンネルの有効・無効、フィルター、分析条件、特定の仮説を試すための位置合わせ | シーンに保存する候補 |

共通の位置合わせをプロジェクトに置いて各シーンが引き継ぐ方式と、各シーンが独立して指定し共通の設定を再利用する方式の両方が考えられる。プロジェクト設定をすべてシーンで上書き可能にするかも含めて未決定である。どちらの方式でも、結果を出す際には実際に適用された位置合わせと、その根拠や手動調整を確認できる必要がある。

## 結果とキャッシュ

シーンは分析結果そのものだけでなく、結果を再計算できる条件を保持する。結果をキャッシュして表示や繰り返し処理を速くしてもよいが、キャッシュの有無で分析の意味が変わらないことを目指す。多くのシーンを追加できるよう、シーンの設定と大きくなり得る結果キャッシュを分けて考える。

取得中の暫定結果、取得後の結果、プラグインを更新して再計算した結果は異なり得る。後工程へ結果を渡すとき、どの状態の結果か分かるようにする。

## 再現性に必要な情報

同じ結果を作り直すには、少なくとも元のソース、シーンの設定、使用したフィルターと分析機能、各条件、記録間の位置合わせ、利用者の補正を特定できる必要がある。プラグインも、名前だけでなく実際に使った版を区別する。

標準で提供されるプラグインは版や内容の識別情報を記録し、独自のプラグインはプロジェクトに含める案がある。ただし、ハッシュや版の記録だけではプラグイン本体を再入手できるとは限らない。どの状態を「再現可能」と呼ぶかと、必要な部品が見つからない場合の扱いは今後決める。

## GUI と CLI

GUI はプロジェクト内のソースやシーンを見渡し、条件を試しながら結果を比べる。CLI は同じプロジェクトとシーンを指定して分析や出力を繰り返し実行できる。CLI でプロジェクトを使わず、ソースと条件をすべて指定して一回の分析を行う使い方も認める。その場合も、後から同じ処理を行うために必要な条件を結果と一緒に確認できるようにしたい。

GUI と CLI が共有するのは、ソース、保存した分析設定の意味、分析条件、結果である。操作方法や画面上の状態を同じにする必要はない。GUI の表示画面と、ここで仮に「シーン」と呼ぶ単位が一対一で対応するかも未決定である。

## 次に決めること

1. プロジェクトとシーンが保持する情報の境界。特にマーカーや位置合わせを共有するか、シーンごとに変えられるか。共通設定の上書き範囲も含める。
2. 元データをプロジェクト内へコピーする既定動作と、外部参照を選ぶときの約束。
3. プロジェクトを持ち運べる単位と、保存方式を比較するときの条件。縮小版ソースだけを残す場合の再現範囲も含める。
4. プラグインを後から再利用できる状態と、版・内容をどう特定するか。
5. 取得中に増えるソースと暫定結果を、シーンと後工程がどう扱うか。
6. キャッシュを消して再計算したとき、同じ結果とみなす条件。
