# WireSkein — ビジョンとコアの方向性

この文書は、製品が解決する課題と目指す振る舞いを示す。最初の版の範囲や実現方式は、[今後の検証計画](next-plan.ja.md) に沿って判断する。

## 目指すもの

WireSkein は、観測データを受け取り、共通の下調べや解釈を行い、後工程で使いやすい結果とその根拠を取り出す分析ワークベンチを目指す。

出発点はロジックアナライザによる調査だが、デジタル信号、アナログ波形、低頻度の測定値、通信ログ、イベントを扱う。特定の取得機器や記録形式に依存せず、手近な機器を使った環境でも利用できる、MIT ライセンスの開かれた基盤とする。

出力の後には、独自スクリプト、外部の試験環境、人、AI による分析や判断が続く。大量の記録から問いに必要な情報を取り出し、詳しく調べる必要があれば元の観測へ戻れることを重視する。波形を見て調査が終わる使い方も、後工程へ渡す中間素材を作る使い方も支える。

## 解決したい課題

### 記録の種類や機器ごとに分析が分断される

デジタル通信、アナログ波形、計測器の値、操作ログが別々に記録され、同じ実験で何が起きたかを追うために形式変換や転記を繰り返している。高速な信号と数分間隔の測定では必要な時間精度も異なる。用途に必要な精度で結び付け、共通の作業として扱いたい。

### 情報が多すぎる一方、重要なものを除いてしまう

全波形や全イベントを人や AI が毎回読むのは負担が大きい。活動や値の分布、変化点、未解釈区間を概観し、必要な場所だけ詳しく調べたい。AI に渡す情報量とトークン消費の削減も、この流れによって目指す。

ただし、短い信号をノイズと判断した結果、通信速度が変わった区間を見落とすことがある。情報を減らす際も、未知の信号、異常、除外した変化、取得不足の可能性を後から調べられる必要がある。

### 共通の下調べと設定を何度も作り直している

独自の分析をするたびに、ファイルの読み込み、エッジや周期の抽出、復号、区間の整理まで実装し直すのは負担が大きい。同じ実験の記録ごとにフィルターを設定し直す手間もある。共通処理を再利用し、実験固有の問いに集中できるようにしたい。

### 拡張や受け渡し、再現に手間がかかる

新しい機器・形式・分析方法を容易に追加でき、得た結果を外部で扱いやすい形にしたい。プロジェクトを別の環境へ持ち運ぶ場合や分析方法を更新する場合も、どの記録と条件から結果が得られたかを確認できる必要がある。

## コアとして提供する価値

| 方向性 | 利用者ができること |
| --- | --- |
| 柔軟な入力と再利用できる処理 | 記録全体、マーカー区間、複数記録を合わせたソースに同じ処理を適用する |
| 必要な粒度への整理 | コマンド列だけ、状態の指標だけ、詳しい信号など、問いに必要な結果を選ぶ |
| 未知からの段階的な調査 | 信号の特徴から通信方式、上位プロトコル、機器固有の意味へ候補を進める |
| 判断材料の保持 | 候補ごとの合致・不一致、未解釈の場所、元データ、適用条件をたどる |
| 繰り返しと再現 | 一度作った条件で別の記録も処理し、条件を修正して同じ記録を調べ直す |
| 外部へつながる成果物 | スクリプトが読める安定した構造の結果と、検証に使う実データを取り出す |

自動判定も、利用者や外部ツールが選んで実行する処理である。対象と処理を決めるのは呼び出す側であり、ソースを追加しただけでコアが実験固有の分析を自律的に進める前提は置かない。

未知の通信は複数候補と各段階の一致状況を示し、利用者の知識や手動指定も反映できるようにする。既知の通信なら短いコマンド列や指標で足りる場合がある。測定値の整理ではプロトコル解析を経ず、条件と値を結び付けた出力だけを作る場合もある。

## 大切にする性質

- **情報量と検証可能性を両立する。** 概要や省略した出力から、必要な区間と詳細へ進める。未解釈を解釈済みとして扱わず、見ていない部分も区別する。
- **元データを保って試せる。** フィルターや解析条件を変えても元の記録を書き換えず、試行を残すためだけに大きな記録を複製しない。
- **再現性と持ち運びやすさを両立する。** 必要なデータ、条件、分析機能を追えるようにし、不足があれば再現できる範囲を把握できる。
- **異なる時間精度を尊重する。** すべての記録へ一律に厳密な同期を要求せず、時間を合わせた根拠と限界を残す。
- **拡張しやすくする。** 取得元、形式、フィルター、解析、出力を過度な手間なく増やせる。簡単なビルドを含む拡張方法も選択肢とする。
- **操作方法から独立させる。** CLI と GUI が同じ分析条件と結果を使え、GUI を替えても分析の仕組みを利用できる。

短い出力を作ること、信号にフィルターを適用すること、元データを削除することは、それぞれ後の分析への影響が異なる。無条件に情報が失われないとは扱わず、目的に必要な情報と再分析の可能性を確認できるようにする。

## コアと周辺の役割

| 担当 | 役割 |
| --- | --- |
| コア | 対象ソースと処理条件を受け取り、分析・整理・出力を行う。条件と結果の関係を保持する |
| CLI | 保存したプロジェクトや明示した条件でコアを実行し、バッチ処理や外部ツールにつなぐ |
| GUI | 取得元や対象を選び、フィルター・解析・時間合わせ・出力条件を試す。波形、表、グラフ、候補を表示し、条件を保存する |
| キャプチャ機能 | 機器やストリームから取得・記録し、分析へ入力を供給する |
| 外部の試験・分析ツール | 実験の進行、成功・失敗の判断、正常時との比較、用途固有の分析、実験全体の報告を行う |

コアの範囲は、まず CLI から画面なしで実行できる分析を基準に定める。GUI は結果表示に加えて入力側の試行錯誤も担う。GUI と CLI の操作の完全な一致は求めない。

実験全体を制御する環境や汎用ノートブック、あらゆる未知信号を必ず正しく自動判定する仕組みを中心目標にはしない。コアが作る簡易・詳細の分析レポートは、後工程が判断するための成果物とする。

具体的な作業と合意した振る舞いは [ワークベンチの使い方](workbench-model.ja.md)、調査で何を得たいかは [ユースケース](use-cases.ja.md) にまとめる。
