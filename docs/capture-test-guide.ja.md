# キャプチャで確かめるテストの作り方

CH32 向け Arduino コアの動作確認テストに、ロジックアナライザのキャプチャでの検証を加えるためのガイドです。

## 前提

- テストは pytest で自動実行します。
- ESP32-P4 がプローブです。CH32 ボードのできるだけ多くのピンと直結し、次の役割を兼ねます。
  - 全ピンのキャプチャ
  - RVSWD での書き込み
  - SPI・I2C のデバイス側のスタブ
- pytest から CH32 にコマンドを送り、周辺機能を動かします。

WireSkein は本来、未知の信号から方式を推定する道具です。このガイドの用途はそれとは違い、**意図した信号どおりに出ているかを確かめる**ものです。そのため、次の2点を前提にします。

- **期待をテストが持つ。** 方式・ピン・パラメータ・許容誤差は、テストから解析側に渡します。解析側は推定ではなく照合をします。WireSkein のヒント（`protocols`、`pins`、`baud`）と時間窓（`--window`）が、この用途の入口です。
- **区切りと静かな区間をテストが作る。** どこからどこまでが、どの期待に対応するかを、マーカーで示します。

## 1. どんな不具合をキャプチャで見るか

今のペアテスト（CH32 と P4 で値を受け渡して、OK か NG かを見る）で見つかるのは、主に値の不一致です。キャプチャは、値は合っているのに波形が仕様から外れている不具合を見つけるために使います。

| 分類 | 例 | ペアテストで見えるか |
| --- | --- | --- |
| 後始末 | I2C の後に SDA や SCL が High に戻らない。SPI の CS が High に戻らない。`end()` の後もピンが出力のまま | 見えない（次のテストで初めて壊れる） |
| 始まりの乱れ | `begin()` でピンの機能を切り替えるときのグリッチ。UART の初期化で出るゴミの1文字 | 受け側が捨てれば見えない |
| 時間のパラメータ | PWM の周波数やデューティー比の誤差、ボーレートの誤差、I2C の tLOW・tHIGH、SPI の CS からクロックまでの時間 | 受け側の許容範囲内なら見えない |
| 形式 | SPI のモード（CPOL/CPHA）、ビット順、ストップビットの数、I2C の Repeated Start | 受け側がたまたま同じ設定だと見えない |
| 余計な動き | 別のピンが動く（リマップの誤り）。余計なクロックが出る。更新時に PWM が欠ける | 見えない |
| 受け手のいない送信 | RGB LED（WS2812）、tone()、MCO のクロック出力 | P4 側で解析するのが面倒 |

特に効くのは**「このステップで動いてよいピン以外は、全部静止していること」**という検査です。全ピンを直結しているので、リマップの誤りや、ピンの初期化漏れを一度に見つけられます。

## 2. マーカー

マーカーの書式と区間の規則は、[ワークベンチのモデル](workbench-model.ja.md) の「マーカーで長い記録を実験の文脈に結び付ける」に従います。
この節では、それを pytest のテストにどう当てはめるかを決めます。区間に分ける処理はプロトタイプに実装済みです（`ws.py segments`、`wsproto/markers.py`、方言の定義は `prototype/decl/markers/heading.toml`）。

### 2.1 書式: 見出し型

マーカーは、行頭の `#` の数を階層とする1行の文字列です。pytest から、CH32 のコマンド用 UART（PC → CH32）に流します。

```text
# test_pwm_duty            ← 階層 1: テスト
PING                       ← マーカーではない行（イベント）
PONG                       ← CH32 → PC の線の行（イベント）
## freq=1000 duty=25       ← 階層 2: ステップ（1 つの条件）
PWM PA1 1000 25            ← コマンド（イベント）
OK
PWM PA1 STOP
OK
##                         ← 名前のない同じ階層: ステップを閉じる
## freq=2000 duty=50
...
##
#                          ← テストを閉じる
```

| 規則 | 内容 |
| --- | --- |
| 階層 | `#` の数。テスト、ステップ、フェーズの 3 段を目安にする（深さに上限はない） |
| 閉じ方 | 同じ階層または上の階層の次の見出しで閉じる。名前のない見出し（`##` だけ）は閉じるだけで、新しい区間を作らない |
| 同じ名前 | 同じ親の下で名前が重なると、`freq=1000 duty=25[0]`、`[1]` のように連番を付けて区別する。元の文字列は残す |
| 区間の範囲 | 見出しの行の送信が終わった時点から、それを閉じる行の送信が始まる時点まで。マーカー自体の UART の通信は区間の外になる |
| 親と子 | 親の区間を選ぶと、子の区間も含む全範囲を扱う。子の見出しは、親の中のイベントとして見える |

### 2.2 テスト側の規則: `#` の行はコメントとして無視する

マーカーはコマンド用の UART を PING/PONG やパラメータと共有するので、CH32 のテスト用ファームウェアに次の規則を入れます。

- **`#` で始まる行はコメントとして捨てる。** 応答も返さず、エコーもしない。応答を返すと、マーカーの前後に余計な通信が入り、静かな区間が崩れます。
- **コマンドの行は `#` で始めない。** `#` で始まる行はすべてマーカーとして読まれます。
- **改行で終える。** 解析側は、改行までを1行として読みます。

### 2.3 マーカーでない行はイベント

`#` で始まらない行（`PING`、`PONG`、`PWM PA1 1000 25`、`OK` など）は、区間の中のイベントとして扱います。イベントは時刻・ピン・文字列を持ちます。

- マーカーと同じ線（PC → CH32）の行だけでなく、CH32 → PC の線の応答も、同じ時間軸でイベントになります。
- これで、「どのコマンドをいつ渡し、いつ応答が返り、その間に波形がどう動いたか」が区間の中で分かります。
- **イベントは主に GUI 向けです。** CLI の出力には既定で含めません（`--events` で含める）。GUI 向けの全層出力（`--mode all`）では常に含めます。

### 2.4 静かな区間を区間の中に置く

1 つのステップの中は、次の形にします。

```text
## <条件>
   前の静かな区間   初期状態を確かめる（ピンのレベル、動いているピンがないか）。1 ms 以上、または対象の信号の 3 周期
   コマンドと動作   CH32 にコマンドを送り、周辺機能を動かす
   後の静かな区間   終了状態を確かめる（戻し忘れ、余計な動き）。ドライバの最長のタイムアウトより長く、目安 10 ms 以上
##
```

- 静かな区間がないと、「戻し忘れ」と「次のステップの始まり」を区別できません。
- 閉じる行（`##`）を省いて次の見出しで閉じることもできます。ただし、その場合は後の静かな区間が次の見出しの直前までになります。**終了状態を確かめるステップでは、`##` で明示的に閉じます。**
- 周波数を止めずに変えるなど、切り替わり自体を試すときは、切り替わりを別のフェーズ（`###`）にします。

### 2.5 区間ごとに分かること

`ws.py segments CAPTURE` は、区間の木と、区間ごとに次の情報を出します（`--results` で復号結果の中身、`--events` でイベントも出す）。

| 項目 | 内容 | 使いみち |
| --- | --- | --- |
| `activity.moved` | 区間の中で動いたピンと変化の回数（マーカーの線を除く） | 動いてよいピン以外が動いていないか |
| `activity.levels` | 各ピンの、区間の始まりと終わりのレベル | 初期状態と戻し忘れ（例: I2C の SDA が 1 → 0 のまま） |
| `activity.quiet_head_s` / `quiet_tail_s` | 区間の始まりから最初の変化まで、最後の変化から終わりまでの時間 | 静かな区間が取れているか |
| `activity.periodic` | 規則的に動くピンの周波数・デューティー比・周期のばらつき・分解能 | PWM、tone()、クロック出力の照合 |
| `decoded` | 区間の中の復号結果（I2C のトランザクション、SPI の転送など）の件数 | 期待した通信が区間の中にあるか |
| `issues` | 階層の飛び（`#` の次に `###`）、対応する見出しのない閉じ、書式に合わない行 | マーカーの送り方の誤りや取りこぼし |

1 つの区間だけを解析するときは `ws.py analyze CAPTURE --segment "test_pwm_duty/freq=1000 duty=25"` です（パスは glob。`[` は連番として文字どおりに扱う）。

合成データでの確認（`prototype` の作業用スクリプト）では、次のことが区間ごとに出ました。

- 2 kHz を指令したステップで PWM が 2.1 kHz になっていたこと
- I2C のステップの後で SDA が Low のまま残ったこと

実データ（I2CDeviceDB の記録）では、`INPUT` の命令 `0x2400` と、同じ区間の I2C の書き込み `2400` が対応しました。

### 2.6 マーカーの時刻の精度

pytest から USB-UART で送るマーカーは、USB のフレームの都合で数 ms の遅れと揺らぎがあります。マーカーは区間を選ぶ目印として使い、測定の境界は区間の中の信号の変化点から解析側が決めます。マーカーと動作の間には、この揺らぎより長い余白を取ります。

時刻の精度を上げる方法として、次の 2 つがあります。

- **P4 のキャプチャに印を直接付ける。** OEP には、UART や console のストリームに付ける `mark`（host が値 u8 を付ける。位置はストリームのバイト位置、時刻は ms）があります。ただし、キャプチャの時間軸に付ける印は、今の `oep.if.capture` にはありません。付ける場合は OEP の仕様への追加提案になります。
- **P4 がマーカー用のピンを動かし、それもキャプチャする。** ピンを 1 本使いますが、サンプル単位で揃います。文字列のマーカーとは、並べて使えます（文字列で名前を、パルスで正確な時刻を示す）。

### 2.7 期待値はマーカーに書かない

見出しの名前は、人が読めて区間を特定できれば十分です（`freq=1000 duty=25` など）。期待値（ピン、周波数、デューティー比、許容誤差）は、pytest が区間のパスをキーにして別ファイル（マニフェスト）に書き出します。見出しを長くすると、送信に時間がかかって区間の余白が増えます。

```json
{"path": "test_pwm_duty/freq=1000 duty=25",
 "active_pins": ["PA1"],
 "expect": [{"pin": "PA1", "kind": "pwm", "freq_hz": 1000, "duty": 0.25, "tol": {"freq": 0.02, "duty": 0.01}}],
 "idle_before": {"PA1": 0}, "idle_after": {"PA1": 0}}
```

## 3. テストの組み方

### 3.1 1つの条件を1ステップにする

PWM で周波数とデューティー比を複数試すときは、組み合わせごとに `##` の見出しでステップを作り、`##` で閉じます。テスト全体を1つの区間にすると、どの条件で外れたかが分かりません。

複数の周辺機能を同時に動かすテストでは、1ステップの期待に全部を書きます。`active_pins` には、そのステップで動いてよいピンを全部並べます。解析側は、ピンの組ごとに照合します。

### 3.2 ピンの対応表は1か所に置く

CH32 のピン名、P4 のキャプチャのチャンネル、P4 の役割（スタブの SPI など）の対応を、ボードごとに1つのファイルに書きます。テストと期待値は、CH32 のピン名（`PA1`）で書きます。

### 3.3 最初にキャプチャ系の自己テストを入れる

セッションの最初に、P4 自身が既知の信号（決まった周波数の方形波など）を出し、それをキャプチャで測ります。サンプルレートや配線の誤りを、CH32 の不具合と取り違えないためです。

### 3.4 許容誤差の決め方

- **発振源の誤差を含める。** CH32 を HSI で動かすと、周波数は ±1〜2% ずれます。HSE（水晶）を使うテストと分けるか、許容誤差に含めます。
- **サンプルレートから決まる分解能を含める。** 1 周期が N サンプルなら、デューティー比の分解能は 1/N です。デューティー比を 1% で見るなら、1 周期に 100 サンプル以上必要です。周波数は、多くの周期の平均で測れば分解能が上がります。
- **目安**: 測る信号の周波数を、サンプルレートの 1/10 以下にします（時間のパラメータを測る場合）。P4 のキャプチャの最大サンプルレートと、同時に取れるピン数を先に確認しておくと、試せる上限が決まります。

## 4. 周辺機能ごとの検査項目

| 周辺機能 | 定常の区間で測る | 静かな区間・境界で確かめる |
| --- | --- | --- |
| GPIO | レベル、トグルの時間（`digitalWrite` の連続など） | ほかのピンが静止していること |
| PWM（analogWrite、TIM） | 周波数、デューティー比、周期ごとの揺らぎ、複数チャンネルの位相、相補出力のデッドタイム、極性 | 最初のパルスが欠けないこと、更新で欠けたり伸びたりしないこと、停止後のレベル |
| tone() | 周波数、持続時間 | 終了後のレベル |
| UART | ボーレートの誤差、データビット・パリティ・ストップビット、文字間の間隔、内容 | 初期化でゴミが出ないこと、アイドルレベル、`end()` の後のピンの状態 |
| I2C（Wire、P4 がスタブ） | SCL の周波数、tLOW と tHIGH、START・STOP・Repeated Start、ACK と NACK、クロックストレッチへの追従、内容 | 終了後に SDA と SCL が両方 High（戻し忘れ）、SDA が Low に張り付かないこと |
| SPI（P4 がスタブ） | モード（CPOL/CPHA）、ビット順、クロック周波数、内容、CS から最初のクロックまでと最後のクロックから CS までの時間 | 取引の間に CS が High、余計なクロックがないこと、アイドル時の MOSI |
| WS2812（RGB LED） | T0H、T1H、1 ビットの周期、バイトの順序（GRB）、LED の数 | リセットの Low（50 µs または 280 µs 以上）、送信後のレベル |
| 割り込み・pulseIn | P4 が入力を出し、CH32 が応答のピンを動かす。その遅れと揺らぎ | 応答のピン以外が静止していること |
| スリープ | スリープ中のピンの状態 | 復帰後のピンの状態 |

WS2812 と tone() は受け手がいないので、キャプチャでの解析を主な判定にします。I2C と SPI は、P4 のスタブでの値の照合（ペアテスト）と、キャプチャでの波形の照合の両方で判定します。

## 5. 判定の流れ

```
pytest
  ├─ マニフェスト（期待）を書き出す
  ├─ ステップごとに: "## <条件>" → 静かな区間 → CH32 にコマンド → 待つ → 静かな区間 → "##"
  ├─ キャプチャを P4 から取り出す（.sr など）
  └─ 解析: マーカーで区間に分ける（ws.py segments）→ 区間ごとに期待と照合 → 項目ごとの OK/NG と測定値
        └─ pytest の assert、または JUnit XML として出す
NG のステップのキャプチャは、PulseView で見られる形で保存する
```

pytest からの呼び出しは、次のような形を想定しています。

```python
def test_pwm_duty(dut, probe, capture, freq, duty):
    with capture.step("pwm_duty", active=["PA1"],
                      expect=[pwm("PA1", freq, duty, tol_freq=0.02, tol_duty=0.01)],
                      idle_before={"PA1": 0}, idle_after={"PA1": 0}):
        dut.cmd(f"pwm PA1 {freq} {duty}")
        probe.wait_ms(20)
        dut.cmd("pwm PA1 stop")
    # capture.verify() がステップごとの結果を返す（キャプチャを止めた後にまとめて）
```

## 6. WireSkein 側の対応状況

| 機能 | 状態 |
| --- | --- |
| 見出し型のマーカーで区間の木を作る。連番、名前のない見出しでの閉じ、階層の飛びなどの問題の記録 | 実装済み（`ws.py segments`） |
| マーカーでない行をイベントにする（すべての UART の行、時刻付き） | 実装済み（CLI は `--events` のとき、GUI 向けの全層出力は常に） |
| 区間ごとの動いたピン、始まりと終わりのレベル、静かな時間、周期的な信号の周波数とデューティー比 | 実装済み |
| 区間を選んだ解析（`analyze --segment`） | 実装済み |
| マニフェストの期待と照合して、項目ごとの OK/NG を出す（`ws verify`） | 未実装 |
| I2C の tLOW と tHIGH、SPI の CS のタイミング、WS2812 のビットの幅などの時間の測定 | 未実装 |
| マーカーをパルスやキャプチャの印から読む | 未実装（OEP のキャプチャの仕様に印がない） |
