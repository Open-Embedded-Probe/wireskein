# キャプチャで確かめるテストの作り方

CH32 向け Arduino コアの動作確認テストに、ロジックアナライザのキャプチャでの検証を加えるためのガイドです。

## 前提

- テストは pytest で自動実行します。
- ESP32-P4 がプローブです。CH32 ボードのできるだけ多くのピンと直結し、次の役割を兼ねます。
  - 全ピンのキャプチャ
  - RVSWD での書き込み
  - SPI・I2C のデバイス側のスタブ
- pytest から CH32 にコマンドを送り、周辺機能を動かします。

WireSkein は本来、未知の信号から方式を推定する道具です。このガイドの用途はそれとは違い、**意図した信号どおりに出ているかを確かめる**ものです。そのため、次の2点を前提にします。

- **期待をテストが持つ。** 方式・ピン・パラメータ・許容誤差は、テストから解析側に渡します。解析側は推定ではなく照合をします。WireSkein のヒント（`protocols`、`pins`、`baud`）と時間窓（`--window`）が、この用途の入口です。
- **区切りと静かな区間をテストが作る。** どこからどこまでが、どの期待に対応するかを、マーカーで示します。

## 1. どんな不具合をキャプチャで見るか

今のペアテスト（CH32 と P4 で値を受け渡して、OK か NG かを見る）で見つかるのは、主に値の不一致です。キャプチャは、値は合っているのに波形が仕様から外れている不具合を見つけるために使います。

| 分類 | 例 | ペアテストで見えるか |
| --- | --- | --- |
| 後始末 | I2C の後に SDA や SCL が High に戻らない。SPI の CS が High に戻らない。`end()` の後もピンが出力のまま | 見えない（次のテストで初めて壊れる） |
| 始まりの乱れ | `begin()` でピンの機能を切り替えるときのグリッチ。UART の初期化で出るゴミの1文字 | 受け側が捨てれば見えない |
| 時間のパラメータ | PWM の周波数やデューティー比の誤差、ボーレートの誤差、I2C の tLOW・tHIGH、SPI の CS からクロックまでの時間 | 受け側の許容範囲内なら見えない |
| 形式 | SPI のモード（CPOL/CPHA）、ビット順、ストップビットの数、I2C の Repeated Start | 受け側がたまたま同じ設定だと見えない |
| 余計な動き | 別のピンが動く（リマップの誤り）。余計なクロックが出る。更新時に PWM が欠ける | 見えない |
| 受け手のいない送信 | RGB LED（WS2812）、tone()、MCO のクロック出力 | P4 側で解析するのが面倒 |

特に効くのは**「このステップで動いてよいピン以外は、全部静止していること」**という検査です。全ピンを直結しているので、リマップの誤りや、ピンの初期化漏れを一度に見つけられます。

## 2. マーカー

### 2.1 Start と End の両方を出す

結論: **Start と End の両方を出し、その間に静かな区間を置きます。**

| 構成 | できること | できないこと |
| --- | --- | --- |
| Start だけ | 区間の始まりが分かる | 終わりが分からない。「戻し忘れ」と「次のテストの始まり」を区別できない |
| Start と End | 区間が閉じる。区間の外の動きを「余計な動き」として検出できる | 静かな区間がないと、初期状態と終了状態を測れない |
| Start、静かな区間、動作、静かな区間、End | 初期状態の確認、アイドルレベルの推定、終了状態（戻し忘れ）の確認ができる | —（推奨） |

1ステップの形は次のとおりです。

```
START(id, seq)
  ├─ 前の静かな区間  … 初期状態を確かめる（ピンのレベル、動いているピンがないか）
  ├─ 動作            … CH32 にコマンドを送り、周辺機能を動かす
  │    ├─ 過渡の区間 … 周波数を変えた直後など。ここは測らない（測るなら別の検査にする）
  │    └─ 定常の区間 … ここで周波数・デューティー比・ボーレートを測る
  ├─ 後の静かな区間  … 終了状態を確かめる（戻し忘れ、余計な動き）
END(id, seq)
```

### 2.2 静かな区間の長さ

- **前の静かな区間**は、次のうち長い方にします: 1 ms、または対象の信号の 3 周期（UART なら 3 文字分）。アイドルレベルを推定し、初期状態を確かめるための区間です。
- **後の静かな区間**は、ドライバの最長のタイムアウトより長くします。I2C の STOP が遅れて出る場合や、割り込みの後始末などを取りこぼさないためです。目安は 10 ms 以上です。「戻し忘れ」は、この区間の最後のレベルで判定します。
- **ステップの間**にも静かな区間を置きます。連続して切り替わること自体を試す場合（PWM の周波数を止めずに変える、など）だけは、その切り替えを「過渡の区間」として明示します。

### 2.3 マーカーの時刻は測定に使わない

pytest から USB-UART でマーカーを送ると、USB のフレームの都合で数 ms の遅れと揺らぎが出ます。マーカーは「どの区間か」を示す粗い目印として使い、測定の境界は区間の中の信号の変化点から解析側が決めます。そのため、マーカーと動作の間には、揺らぎより長い余白（数 ms）を取ります。

時刻の精度を上げる方法は3つあります。精度の高い順です。

1. **P4 がキャプチャのデータ自体にイベントを書き込む。** pytest は P4 に「マーカーを入れて」と頼むだけにします。ピンを使わず、時刻はサンプル単位で正確です。P4 のファームウェアを自作しているなら、これが一番です。
2. **P4 がマーカー用のピンをパルスで動かし、それもキャプチャする。** ピンを1本使います。時刻の精度はサンプル単位です。
3. **pytest からマーカー用の UART に文字列を送る。** 今のやり方です。ずれは数 ms あります。CH32 のテスト対象の UART とは、必ず別の線にします。

### 2.4 マーカーの中身は短くする

マーカーには ID と通し番号だけを載せます。期待値（方式・ピン・パラメータ・許容誤差）は、pytest が別のファイル（マニフェスト）に書き出します。UART のマーカーが短いほど区間の余白が短く済みます。通し番号があれば、マーカーの取りこぼしも分かります。

```
@S 0042 pwm_duty
@E 0042
```

```json
{"seq": 42, "test": "test_pwm[1kHz-25%]", "step": "pwm_duty",
 "active_pins": ["PA1"],
 "expect": [{"pin": "PA1", "kind": "pwm", "freq_hz": 1000, "duty": 0.25,
             "tol": {"freq": 0.02, "duty": 0.01}}],
 "idle_before": {"PA1": 0}, "idle_after": {"PA1": 0}}
```

## 3. テストの組み方

### 3.1 1つの条件を1ステップにする

PWM で周波数とデューティー比を複数試すときは、組み合わせごとに START と END を出します。全体を1組のマーカーで囲むと、どの条件で外れたかが分かりません。

複数の周辺機能を同時に動かすテストでは、1ステップの期待に全部を書きます。`active_pins` には、そのステップで動いてよいピンを全部並べます。解析側は、ピンの組ごとに照合します。

### 3.2 ピンの対応表は1か所に置く

CH32 のピン名、P4 のキャプチャのチャンネル、P4 の役割（スタブの SPI など）の対応を、ボードごとに1つのファイルに書きます。テストと期待値は、CH32 のピン名（`PA1`）で書きます。

### 3.3 最初にキャプチャ系の自己テストを入れる

セッションの最初に、P4 自身が既知の信号（決まった周波数の方形波など）を出し、それをキャプチャで測ります。サンプルレートや配線の誤りを、CH32 の不具合と取り違えないためです。

### 3.4 許容誤差の決め方

- **発振源の誤差を含める。** CH32 を HSI で動かすと、周波数は ±1〜2% ずれます。HSE（水晶）を使うテストと分けるか、許容誤差に含めます。
- **サンプルレートから決まる分解能を含める。** 1 周期が N サンプルなら、デューティー比の分解能は 1/N です。デューティー比を 1% で見るなら、1 周期に 100 サンプル以上必要です。周波数は、多くの周期の平均で測れば分解能が上がります。
- **目安**: 測る信号の周波数を、サンプルレートの 1/10 以下にします（時間のパラメータを測る場合）。P4 のキャプチャの最大サンプルレートと、同時に取れるピン数を先に確認しておくと、試せる上限が決まります。

## 4. 周辺機能ごとの検査項目

| 周辺機能 | 定常の区間で測る | 静かな区間・境界で確かめる |
| --- | --- | --- |
| GPIO | レベル、トグルの時間（`digitalWrite` の連続など） | ほかのピンが静止していること |
| PWM（analogWrite、TIM） | 周波数、デューティー比、周期ごとの揺らぎ、複数チャンネルの位相、相補出力のデッドタイム、極性 | 最初のパルスが欠けないこと、更新で欠けたり伸びたりしないこと、停止後のレベル |
| tone() | 周波数、持続時間 | 終了後のレベル |
| UART | ボーレートの誤差、データビット・パリティ・ストップビット、文字間の間隔、内容 | 初期化でゴミが出ないこと、アイドルレベル、`end()` の後のピンの状態 |
| I2C（Wire、P4 がスタブ） | SCL の周波数、tLOW と tHIGH、START・STOP・Repeated Start、ACK と NACK、クロックストレッチへの追従、内容 | 終了後に SDA と SCL が両方 High（戻し忘れ）、SDA が Low に張り付かないこと |
| SPI（P4 がスタブ） | モード（CPOL/CPHA）、ビット順、クロック周波数、内容、CS から最初のクロックまでと最後のクロックから CS までの時間 | 取引の間に CS が High、余計なクロックがないこと、アイドル時の MOSI |
| WS2812（RGB LED） | T0H、T1H、1 ビットの周期、バイトの順序（GRB）、LED の数 | リセットの Low（50 µs または 280 µs 以上）、送信後のレベル |
| 割り込み・pulseIn | P4 が入力を出し、CH32 が応答のピンを動かす。その遅れと揺らぎ | 応答のピン以外が静止していること |
| スリープ | スリープ中のピンの状態 | 復帰後のピンの状態 |

WS2812 と tone() は受け手がいないので、キャプチャでの解析を主な判定にします。I2C と SPI は、P4 のスタブでの値の照合（ペアテスト）と、キャプチャでの波形の照合の両方で判定します。

## 5. 判定の流れ

```
pytest
  ├─ マニフェスト（期待）を書き出す
  ├─ ステップごとに: START マーカー → CH32 にコマンド → 待つ → END マーカー
  ├─ キャプチャを P4 から取り出す（.sr など）
  └─ 解析: マーカーで区間に分ける → 区間ごとに期待と照合 → 項目ごとの OK/NG と測定値
        └─ pytest の assert、または JUnit XML として出す
NG のステップのキャプチャは、PulseView で見られる形で保存する
```

pytest からの呼び出しは、次のような形を想定しています。

```python
def test_pwm_duty(dut, probe, capture, freq, duty):
    with capture.step("pwm_duty", active=["PA1"],
                      expect=[pwm("PA1", freq, duty, tol_freq=0.02, tol_duty=0.01)],
                      idle_before={"PA1": 0}, idle_after={"PA1": 0}):
        dut.cmd(f"pwm PA1 {freq} {duty}")
        probe.wait_ms(20)
        dut.cmd("pwm PA1 stop")
    # capture.verify() がステップごとの結果を返す（キャプチャを止めた後にまとめて）
```

## 6. WireSkein 側で必要になるもの（未実装）

- **`ws verify CAPTURE --manifest steps.json`**: マーカーで区間を切り、区間ごとに期待を照合して、項目ごとの結果を出す。推定は使わず、ヒントを全部与えた状態で復号します。
- **マーカーの読み取り**: UART の文字列、パルス、キャプチャ内のイベントの3種類に対応する。
- **静止していることの検査と、終了状態の検査**: 区間ごとの「動いてよいピン」と「区間の最後のレベル」を見る。
- **時間のパラメータの測定**: PWM、I2C の tLOW と tHIGH、SPI の CS のタイミング、WS2812 のビットの幅など。
