# 未知信号から上位解析までのワークフロー調査

2026-09-27。これは実記録で分析のつながりと失敗の見え方を調べた結果であり、候補スコア、API、初期対応プロトコルの製品仕様ではない。[初回調査](README.ja.md)、[追加検証](extended-findings.ja.md)、[基礎分析](foundations.ja.md)を踏まえる。

## 再実行と資料

リポジトリのルートから実行する。既存の `.sr`、`.jsonl`、`.ndjson` は読み取りのみで使い、出力 JSON は Git に含めない。Python と NumPy は[初回調査](README.ja.md)の固定環境を使う。上位の UART/I²C 復号には `sigrok-cli` 0.7.2、RVSWD/SWIO には wch-protocols の既存解析器を使う。

~~~sh
uv run --offline --project experiments/initial-feasibility python experiments/initial-feasibility/i2c_wire_audit.py > experiments/initial-feasibility/i2c-wire-audit-result.json
uv run --offline --project experiments/initial-feasibility python experiments/initial-feasibility/hypothesis_chain_probe.py > experiments/initial-feasibility/hypothesis-chain-result.json
~~~

両スクリプトは `--i2c-root` と、後者は `--wch-root` で参照元を指定できる。I²Cの線上判定は既存の取引デコーダとは別に元サンプルを読む。解析器の独立実装どうしの一致まで示すものではない。

## 実記録で分かったこと

| 段階 | 試した資料と観測 | この観測が示さないこと |
| --- | --- | --- |
| 入力と基本特徴 | I2CDeviceDB の4記録は各8 MHz、活動線は UART_TX/SCL/SDA の3本。匿名の D0/D1/D2 として扱っても、試作の I²C 線ペア順位は D1=clock、D2=data が4件とも最上位 | 別速度、未知配線、多数の候補線でも同じ順位になること |
| 基本プロトコル候補 | I²CのSTARTは合計227件、STOPは173件、繰り返しSTARTは54件。4記録とも開いたままの取引はなく、最後はSCL/SDAともHIGH。試作のペア順位は正しい組が0.9999〜1.0、次点が0.442〜0.562。RVSWD記録をI²Cと仮定した場合も0.267/0.424の候補ができた | 数値はこの標本で順位を試すための重み付き値で、確率でも適合率でもない。線の終端がHIGHでも駆動の解放や電気特性は分からない |
| ビット列の来歴 | I²Cの最初のSTART後、SCL立ち上がりでSDAを読む試行は、4記録とも最初の境界まで10ビット相当を得た。各ビットのサンプル位置を残した。RVSWDでは最初のフレーム候補のビット列とクロック位置を残した | I²Cの10回目の立ち上がりをそのまま次のデータビットとみなせない。境界とACK等を読む状態機械が必要 |
| UART候補から上位文法 | 8N1の形だけの一致率は、真のUART_TXが約0.719〜0.720、SCLをUARTと仮定した方が約0.941〜0.985。UART復号後にCASEマーカー文法を試すと、UART_TXでは4記録すべて開始・終了が対応し、SCLでは一致しない | 上位文法が無い未知UARTを棄却してよいこと。今回はマーカー語彙が分かっている |
| I²C取引から機器固有解析 | SHT30 の2記録で各6件の測定応答を候補として選べ、各記録12件のCRC検査がすべて一致。出力は元の取引行番号を保持する。既存の[追加解析](sht30_crc_extension.py)は1バイト反転をCRC不一致として検出 | CRCがない上位形式、誤りがCRCにも整合する場合、機器固有の全命令の正しさ |
| RVSWDからメモリアクセス | L103の`target_info`は334/334フレームを形として認識、V203の50 MHzは310/328、別回の100 MHzは328/328。読めた部分からchip IDのメモリアクセスへ進める。50 MHzの18件は未解釈として残る | 100 MHzにすれば常に直ること。既存解析器は短いフレームのパリティだけを検査し、長いフレーム等の正しさは未確認 |
| SWIOから上位へ | V003の`target_info`では既存解析器が1,503パルス群中40を既知フレーム形として認識し、6件のメモリアクセスを組み立てた | 残り1,463群をプロトコル違反と呼ぶこと。解析器の対象外形式、境界の切り方、ノイズの内訳は未確認 |

I²Cの生波形監査では、QMP6988の2記録それぞれで、取引の外にSCL立ち上がりが1件ある。いずれも同じ操作の近くで、保存済み取引デコーダは前後の取引を正常に出している。この時点では**調査を促す観測**であり、原因や適否は確定していない。記録をメモリ上だけで加工し、最後のSTOPを消してSDAをLOWのままにした場合は未完了・待機状態不一致を、STOP後にSCLパルスを足した場合は取引外の活動増加を4記録すべてで検出した。これは警告の検出経路の試験であって、実機の故障検出率ではない。

## 試すべき一連の処理

1. **入力の品質を記録する。** 取得元、チャンネル、レート、実サンプル範囲、欠落と同期の根拠を残す。欠落情報がない入力は「欠落なし」としない。現行のI2CDeviceDB `.sr` には取得経路の完全性を独立に判定する情報がない。
2. **プロトコル名を付けずに特徴を出す。** 活動区間、エッジ、ラン幅、線の組み合わせ、速度の変化、収録の前後の待機状態を、サンプル位置と一緒に保持する。短いパルスを最初から捨てない。
3. **チャンネル役割とビット列の候補を列挙する。** 線の組、極性、速度、サンプル位相、クロックの使い方を仮説として作る。ビット列には元のサンプル範囲と抽出条件を付け、複数候補を残す。活動の多い線をクロックと決め打ちしない。
4. **基本プロトコルの候補を検査する。** I²CならSTART/STOPとACK、UARTならフレーミング、RVSWDならフレーム境界と検査ビットのように、候補ごとに適用可能な規則を明示する。認識数、未解釈区間、検査を実施した範囲と失敗数を別々に出す。
5. **上位解析を条件付きで試す。** 対応するバイト列や取引列へ、マーカー文法、CRC、機器固有の命令などの解析を接続する。上位の整合が下位候補を支持・反証しても、元の候補と失敗位置を消さない。上位解析器が無い場合は未評価のまま残す。
6. **必要な成果物を選ぶ。** 候補一覧、検査の範囲、警告一覧、必要なコマンドや値だけを先に出し、各項目からフレーム・ビット列・元波形へ戻す。短い出力に省略した項目と未評価範囲を添える。
7. **条件を保存して再実行する。** 元ファイルのハッシュ、入力アダプタ、解析器の版、チャンネルの役割、フィルター、候補選択、対象区間を保持する。同じ条件の再実行で結果の意味と元範囲が一致するか確かめる。

### 候補の点数と保留

候補を一つの「正解率」で表すと、未実装の検査を成功と誤認する。まず次を別々の数値・状態として保持する。

| 項目 | 分母・意味 |
| --- | --- |
| 説明できた範囲 | 観測した活動区間・エッジ・フレーム候補のうち、その仮説で扱った範囲。何を分母にしたかを明示 |
| 規則への整合 | 実際に検査したフレームやフィールドのうち適合した数。未実装の検査は分母に入れない |
| 反証 | パリティ・CRC・フレーミング・タイミング等の不一致の件数と位置。取得不足か実際の違反かを区別 |
| 上位からの支持 | 既知マーカー、機器ID、チェックサム、期待操作との対応。上位解析器が無ければ未評価 |
| 取得品質 | サンプル不足、区間欠落、時刻の不確かさ、フィルターによる除外。仮説自体の点数と分ける |

今回の `rank_score_trial` はI²Cの**線の組を並べるだけ**の重み付き値であり、閾値や共通尺度には使わない。UARTの形だけの高得点がSCLに出たこと、SWIOの既存解析器が多くの群を扱わないことが、単一数値を製品仕様にできない理由である。候補を棄却する条件、順位の更新、計算量の上限は正解付きの多様な資料で測る。どの候補も十分な根拠を持たないときは**不明**を返す。

### 警告、エラー、ヒント

| 種類 | 例 | 最初の扱い |
| --- | --- | --- |
| 取得上の問題 | 欠落が報告された、レートが速い区間に対して不足、区間境界の前後が無い | 解析結果の限界として表示。根拠のない「正常」は出さない |
| 解析の未完了 | 未解釈フレーム、未対応の上位命令、候補同士が拮抗 | 未評価の位置と次に試せる条件を示す |
| 規則との不一致 | 検査したCRC/パリティの失敗、フレームの不正な形 | 規則、実測位置、前後データを示す。取得不良の可能性も残す |
| 追加調査のヒント | 取引外のSCLパルス、操作後に線が待機レベルへ戻らない | まず警告候補とする。試験の期待状態・十分な後置収録・取得品質がそろえば、試験側で失敗条件にできる |
| 解析器の失敗 | クラッシュ、未対応入力、結果の矛盾 | 他の候補や既知の正常区間まで「不正データ」と扱わない |

各項目に、発見した段階、元ソースのサンプル範囲、使った規則、解析条件、確定／暫定の状態を持たせる。フィルター後に消えた警告も、フィルター前の観測と一緒に比較できる必要がある。[NXPのI²C仕様](https://www.nxp.com/docs/en/user-guide/UM10204.pdf)はSTART/STOP、繰り返しSTART、データの安定条件を定義している。ただし、デジタル8 MHz収録では125 nsより短い変化の検出を保証できず、電圧・立ち上がり時間、どの機器が線を駆動したかは判定できない。電気的適合性には別の観測が要る。

## 仕様判断に必要な次の実験

| 必要な資料 | 具体的な試験 | 判断すること |
| --- | --- | --- |
| 正解付きの実SPI、UART、I²C、RVSWD/SWIO | ラベルを隠し、配線候補・速度・極性を入れ替えて列挙。正常、別速度、途中開始、静的線、無関係な活動線を混ぜる | 候補の順位、保留率、見落としと誤警告。SPIは現状生成波形のみ |
| 上位解析の正例・反例 | 既知ペイロードに加え、CRC不一致、未知命令、双方の機器が許容する形式違反を混ぜる | 基本プロトコルだけでは見えない問題を上位で発見できるか。上位の失敗で下位候補をどう再評価するか |
| 実機の状態異常 | 同じ通信の前後も収録し、選択線を戻さない、I²CのSTOPを出さない、操作後に線を保持する例を別に用意する | ペア間の送受成功後でも警告を出せるか。後置収録が足りないときに保留できるか |
| 取得品質を変えた対 | 同一刺激を異なるレート・チャンネル数・取得器で収録し、取得側の欠落も記録する | プロトコル違反、フィルターの誤り、取得不足を取り違えないか |
| 複数取得元と出力選択 | 共通イベントを同時収録し、簡易一覧から指定範囲の詳細と実データを再取得する | 時間合わせの精度、元位置の保持、短い出力の見落としと再現性 |

各資料に、**想定する結果とその根拠を分析器とは別に**付ける。ペアテストのログは期待操作やペイロードの根拠になるが、線上の適合性の正解そのものにはしない。正常例だけでなく、意図的に壊した実機キャプチャと解析器の既知の取りこぼしを含める。警告の強さ、候補スコアの尺度、初期対応範囲は、この行列の見落とし・誤警告・保留を測ってから決める。

現環境では `/run/board-identify/by-id` と USB デバイスが見えておらず、新しい実機キャプチャは取れていない。今回確かめられたのは保存済み記録とメモリ上での異常注入までである。
