# 実データを用いた追加検証

2026-09-27。対象は [初回調査](README.ja.md) と同じ I2CDeviceDB / wch-protocols の参照記録。既存の解析器と固定した `uv` 環境を使い、入力ファイルは読み取りのみとした。以下の数字は、この標本と解析条件で得られた結果である。

## 再実行

リポジトリのルートで、[初回調査](README.ja.md) の `uv sync` と `sigrok-cli` の準備後に実行する。各スクリプトは `--i2c-root` または `--wch-root` で参照元を変更できる。出力 JSON は Git から除外し、スクリプトで再生成する。

~~~sh
uv run --project experiments/initial-feasibility python experiments/initial-feasibility/extended_probe.py > experiments/initial-feasibility/extended-result.json
uv run --project experiments/initial-feasibility python experiments/initial-feasibility/overview_probe.py > experiments/initial-feasibility/overview-result.json
uv run --project experiments/initial-feasibility python experiments/initial-feasibility/features_probe.py > experiments/initial-feasibility/features-result.json
uv run --project experiments/initial-feasibility python experiments/initial-feasibility/extension_probe.py > experiments/initial-feasibility/extension-result.json
uv run --project experiments/initial-feasibility python experiments/initial-feasibility/mixed_time_probe.py > experiments/initial-feasibility/mixed-time-result.json
uv run --project experiments/initial-feasibility python experiments/initial-feasibility/portability_probe.py > experiments/initial-feasibility/portability-result.json
~~~

## 既知のデータで復号結果を照合する

WCH の V203、100 MHz の `flash_pattern4k.sr` を RVSWD として読んだ。独立に保存されている4 KiBの既知パターンと、線上の書き込みに現れる連続1024ワード、読み戻しの64バーストから組み立てた1024ワードの**双方が一致**した。9,416フレームのうち9,414を既存の解析器が形として認識し、残る2フレームは162.7014 msと162.8590 ms付近に未解釈として残った。認識された短いフレームにも、ヘッダーまたはデータのパリティ検査で失敗したものが39件ある。パターンの一致は既知データ部分の強い確認になるが、すべての通信が正常だった証明ではない。

別方式の V003 / SWIO の `flash_pattern4k.sr` でも、1 KiBに相当する256ワードの書き込み列が4区間あり、読み戻しの4 KiB全体が既知パターンと一致した。この解析器は15,542のパルス群のうち11,186をフレームとして認識した。残り4,356の群を一括して通信エラーとは呼べない。フレームにしていない群、正規の別形式、ノイズなどの内訳は未検証であり、**解析器が認識した割合とプロトコルの正しさは別の指標**になる。

SHT30 の保存済み I²C 取引には、6バイトの測定応答が2記録で計12件ある。[試作の追加解析](sht30_crc_extension.py)を別ファイルとして読み込むと、温湿度の生値12組が既存 observation の値と一致し、温度・湿度それぞれ12件の CRC が一致した。元の取引の行番号を残したまま結果を得られ、試料の1バイトを反転すると CRC 不一致を検出した。これは既存の取引表現から機器固有の分析を足せる例であり、拡張機能の配布・権限・版管理まで成立したことは示さない。

## フィルターとサンプリングの影響

V203 の `target_info.sr` を、短いパルスを受け入れる保持サンプル数 `k` を変えて処理した。`k_frame` はフレーム境界判定用の値である。

| 入力 | `k` / `k_frame` | 全フレーム | 未解釈 |
| --- | --- | ---: | ---: |
| 実測50 MHz | 1 / 3 | 354 | 40 |
| 実測50 MHz | 3 / 3 | 328 | 18 |
| 実測100 MHz | 1 / 3 | 328 | 0 |
| 実測100 MHz | 3 / 3 | 328 | 15 |

フィルターを強くすると未解釈数が減る場合と増える場合の両方がある。100 MHz の `k=1` では読めた短いフレームが、`k=3` では失われる。50 MHz と100 MHz は別回の取得なので、この比較だけでは取得レートの効果を切り分けられない。

そこで**同じ100 MHz波形**から偶数番・奇数番サンプルをそれぞれ残して、50 MHz相当の試料を一時的に作った。`k=1` では未解釈が43件と50件、`k=3` では22件と19件になった。間引く位相とフィルター条件で結果が変わり、失ったサンプルから元の波形を復元できない。実測160 MHzの別記録は取得欠落が7か所と記録されており、レートを上げること自体も完全性を保証しない。

100 MHz の `target_info.sr` の短いフレーム126件をフレーム内のクロック周期で見ると、15件は中央値0.5 µs未満で、125.60–129.37 ms に集まった。その15件の中央値は0.1 µsである。全体を単一周波数として要約すると、この高速区間が隠れる。周波数候補は**対象区間と根拠のフレーム**を伴って示す必要がある。

## 未解釈の箇所を切り出す

V203 の4 KiB記録の未解釈2フレームを含む部分を実データのまま一時 `.sr` に切り出した。前後100 µsを付けた試料では元の2件を再現できたが、切り出し境界に由来する未解釈が1件増えた。前後500 µsでは元の2件だけを再現できた。前後幅の値はこの標本に限る。**保全する範囲と、結果として報告する範囲を分ける**ことが、境界に起因する偽の例外を避ける手掛かりになる。[初回調査](README.ja.md) の I²C 子区間では、さらに親マーカーの文脈も必要だった。

## 短い出力から詳細へ戻る

I²C の4記録には詳細の JSONL が合計61,064バイトある。実マーカーに沿う26区間について、元 `.sr` と詳細ファイルの名前、マーカー名、サンプル範囲、詳細行範囲、件数などを持つ概況を作ると合計4,122バイトだった。全227行が26区間のいずれかに**重複なく**対応し、概況にある行範囲から詳細を選び直せた。これは出力サイズで約93%の削減であり、AI の実トークン数や調査精度を測った結果ではない。

同じ機種の2記録で時刻とデータ値だけを伏せ、アドレス・方向・ACK・バイト数・順序を比べた。QMP6988 の58件同士は構造が一致した。SHT30 の54件と57件には、後者の `polling-low` 区間でアドレス `0x44` への読み取り試行が3件多い差が残った。値を伏せた一致は、値や CRC に異常がないという意味ではない。比較目的ごとに項目を選び、伏せた項目を明らかにする必要がある。

WCH の4 KiB記録では、既存解析器の時系列テキストは9,417行・361,550バイトだった。元 `.sr`、解析条件、認識数、未解釈2区間のサンプル範囲、既知パターンの照合結果を含めた概況 JSON は338バイトとなった。詳細や別条件の再解析は元記録から行える。この概況だけで未表示の通信をすべて検証したとは言えない。

## チャンネル候補と複数ソース

I²C の4記録では、各8ビット中、UART_TX・SCL・SDAの3線が変化し、5線は無変化だった。SCL の局所的な立ち上がり間隔の中央値は4記録とも80サンプル、8 MHz なので約100 kHzに相当する。ただし**エッジ数が最多なのは4記録とも UART_TX**だった。活動量だけでクロック線を選ぶ方法はこの実例で外れる。RVSWD は2線、SWIO は1線が活動しており、信号の特徴は候補を絞る材料になる。数件の既知記録で未知プロトコルの自動判定精度は測れない。

WCH の `target_info` では、L103 と V203 の双方で、USB 応答中の chip ID と線上で読んだ chip ID が値として一致した。これは別記録を同じ操作として結び付ける手掛かりになる。一方、両取得元に共通の時刻マーカーやクロックはないため、転送と線上フレームを厳密な時刻で一対一に対応させる根拠にはならない。

## 生成データによる時間軸と保存の試行

実 SHT30 記録のマーカー順序と境界だけを使い、時間を6,000倍に引き延ばした**生成実験**を作った。アナログの電圧・電流・温度値は生成値であり、機器の測定精度は評価していない。測定元の時計に3秒のずれと倍率1.0002を与え、割り当てには±2秒の不確かさを付けた。44測定のうち、12件は一つのマーカー区間内と明確に判断でき、32件は境界または区間外との重なりで保留した。時刻補正を使わずに割り当てると17件で生成時の区間と異なった。異なる時間精度を扱う場合、値を無理に一つの区間へ押し込まない表現を試す価値がある。

小さい SHT30 の元 `.sr` 30,780バイト、結果13,621バイト、来歴442バイトを一時的に ZIP と SQLite へ格納し、別の場所で開き直した。両方ともハッシュ照合と、**外部にある同じ解析器を使った**再デコードが一致した。今回の ZIP は約12 KB、SQLite は約53 KBだった。この標本は小さく、追記・部分読み出し・破損・大きな記録は試していない。解析器自体も格納していないため、保存方式の選定や完全な自己完結性を示す結果ではない。

## 残る検証

| 残る問い | 今回の制約 |
| --- | --- |
| 実機のアナログ波形と低頻度計測を同じ仕組みで扱えるか | 提示された参照先に、この用途の実測組がない。時間実験は生成値のみ |
| 未知信号の候補と一致率をどう評価するか | 既知の I²C / RVSWD / SWIO 標本だけで、未知方式の正解付き標本がない |
| 複数機器の厳密な同期と実験マーカーの合成 | WCH の USB / 線上記録に共通時刻マーカーがない |
| ライブ取得、長時間の追記、GUI 操作、ブラウザでの処理 | 保存済みファイルのオフライン実験では確認できない |
| プロジェクト保存形式とプラグイン方式の選定 | 実験規模が小さく、独自機能の導入・更新・移動まで比較していない |

今回の結果から進められるのは、元ソースと結果の対応、区間・未解釈の位置、解析条件と依存機能を保持する最小の実験用モデルである。どの形式や API を正式に採用するかは、残る標本と利用手順で確かめる。
