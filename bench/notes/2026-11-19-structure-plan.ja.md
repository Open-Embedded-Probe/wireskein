## 1. 追い込みで分かった構造の限界（事実）

### 1.1 雑音の除き方が段と方式ごとに散らばっている

同じ「短いパルスを除く／跳ねをまとめる」が、少なくとも 9 か所に別々にある:

| 場所 | 何をしているか |
| --- | --- |
| `survey.gated_view` / `collapse` | クロックの周期の 1/4 で変化をまとめる（線の関係を測るため） |
| `survey._debounced_clock` | 跳ね・1 サンプルのパルスを除いてクロックの特徴を測り直す |
| `survey._despiked_select` | 選択線の 1 サンプルのパルスを除いて枠を測り直す |
| `staged.glitch_views` | 同期のバスの見え方（幅 2・3・5・k_rel、遅い所だけ）と重複除き |
| `staged.single_views` | 非同期の線の見え方（スパイク、跳ね: 対かどうかで使い分け） |
| `analyzers/pulse.py` | 1-Wire・LED・NEC それぞれの除き方と跳ねの見え方 |
| `timing.i2c_input` | I2C の入力の見方（t_SP、ヒステリシス） |
| `typed.sample_edge_for` | 縁が決まらないとき、跳ね・クロストークを除いて測り直す |
| `typed.frames_select` | 選択線の区切りの前に変化をまとめる |

その結果（2026-11-18〜19 に実際に起きたこと）:

- 「跳ねは最初の変化にまとめる」を 5 か所に別々に入れた。まとめる窓が 8 と 5 で食い違い、直したのは下調べの 1 か所
  だけ（ほかの 2 か所を合わせると差し引きなし）。
- UART にだけ跳ねの見え方を入れて、1-Wire・LED の線が UART に取られた（CI 6ac0857、c342502 で後から直した）。
- 見え方は方式ごとに作り直す。重複を除き、覚えを入れて、ようやく時間を戻した。

### 1.2 下調べの証拠と、方式が読む線が違う

下調べ（クロックらしさ、周期、データ線の寄り、選択線らしさ）は取ったままの線で測る。方式は見え方で読む。
食い違いで起きたこと:

- 見え方では正しく読めるのに、下調べの寄り（0.33）で点数が下がる。
- 跳ね・クロストークでクロックの周期を読み違え（10 を 53、32 を 13）、グループ自体ができない。
- スパイクがクロックのバーストを記録全体に広げ、UART が「同期のデータ」と見られる。

どれも下調べの側に個別の見直しを足して埋めた（`_debounced_clock`、ゲートでの `sync_with_clock` など）。

### 1.3 バスを 1 つずつ別に決めている

役割はクロックごとに独立に決まり、「1 本の線は 1 つのバス」の制約がない（再検討 §10 の 2）。2 つの SPI が同時に
動くと、片方の CS がもう片方のデータになる（heldout 1031・1042）。「完全な選択線は別のクロックのデータにしない」
規則で一部を防いだが、規則を緩めると別の組で同じ数だけ悪くなった。

### 1.4 そのほか

- 点数: 方式ごとの掛け算の項。同点が多い（縁の CPHA の拮抗、実行ごとに結果が変わった不具合 0882067 の元）。
- 評価: outcome は役割と速さだけ。読みの一致（decode）を見ない（LED を全部 1 と読んでも ok だった）。
- 粗い記録（1 ビット 4〜6 サンプル）: ビットの中央で読む作りでは、1 サンプルの雑音がビットの 1/4〜1/6 になる。

## 2. あるべき形

再検討 §6 の段に、今回の限界を当てはめる:

```text
L0 取った記録            書き換えない
L1 線の質と見え方         線ごとに一度だけ: 雑音の種類（スパイク・跳ね・クロストーク・リンギング）を見分け、見え方の
                          候補を作る（そのまま／スパイク除き／跳ねまとめ／短い Run 除き）。各見え方に、除いた変化の
                          数と種類（きれいな記録 §10 の 8 の元）。方式を知らない
L1' 下調べ               見え方ごとに、線の特徴・クロック・周期を測る（いまの survey）。どの見え方で測ったかを持つ
L2 エピソード             どの線がいつ一緒に動くか
L3 グループ               エピソードの中で、クロック・データ・選択の関係を測る（見え方を選んで）
L4 型付きの層と読み        方式は L1 の見え方から選んで読む（自前で除かない）。どの見え方で読んだかを証拠に
L5 説明を詰める           線 × 時間を重ねない最良の組（全部のバスを一度に）
L6〜L8                    再検討のまま
```

決まりごと:

- **雑音の除き方は L1 に 1 つ。** 方式・段は L1 の見え方を名前で選ぶ。窓や幅の決まりは L1 の定数だけ。
- **証拠は、読んだ見え方で測ったものを使う。** 下調べの値を見え方ごとに持ち、方式の点数はその見え方の値で。
- **割り当ては L5 で全体を一度に。** 各方式は候補（線・時間・点数）を出すだけで、持ち主を決めない。
- **同点は決まった順で解く**（線の名前、見え方、縁の順）。結果は実行ごとに変わらない。

## 3. 段（それぞれ測ってから次へ）

| 段 | すること | 測るもの | 次へ進む条件 |
| --- | --- | --- | --- |
| A | L1 の見え方の層を作る。いまの 9 か所の除き方を、L1 の見え方の名前と定数に寄せる（出力は変えない: 同じ見え方を同じ定数で作るだけ） | 56 の記録と雑音の 236 件でバイトまで同じ、時間 | 同じ。時間が増えない |
| B | 方式の除き方を L1 から選ぶ形にする（1-Wire・LED・NEC・UART の自前の除き方をやめる） | 速い組、雑音の組、pulse・ir・uartlike | 悪化なし（入れ替えで変わる所は理由を書く） |
| C | 下調べを見え方ごとに（L1'）。方式の点数は読んだ見え方の値で（1.2 の個別の見直しを消す） | 雑音の組、確認用の洗い出し（今 101・0） | 読めたもの・誤りとも良くなるか同じ |
| D | 同点の決まった順と、点数の尺度（方式をまたいで比べられる形）を決める | 拮抗の数、確定の数、誤り | 拮抗が減り誤りが増えない |
| E | L5: 全体の割り当て（線 × 時間）。再検討 §12 の段 (c)(d) と一緒に | spimulti・spimultimix、heldout の取り違え（1031・1042）、時間 | 取り違えが規則なしで消える |
| F | 評価: outcome に読みの一致を入れる（下限を決める）。読めるはずの印（UNDER_PERIOD、NOISE_REACH）を見直す | 印の付け替えで数がどう動くか（調整の前に印を決める） | 印を決めてから F 以降の調整に使う |
| G | 粗い記録の読み方（変化の位置から読む等）を試す（測定台の試しの方式として） | 1 ビット 4〜6 サンプルの I2C・SPI（今の残り 101 の大半） | 試しの方式が主の方式に勝つ |

- A は出力を変えない作り替え（2026-11-18 の最適化と同じやり方: バイトまで同じを確かめる）。ここで散らばりを
  なくすのが、B 以降の変更を 1 か所で済ませる前提。
- B と C は出力が変わる。CI（main で回し、悪ければ戻す）で全スイートを確かめる。
- E は再検討の L2・L3・L5 そのもの。段 (c) エピソードを先に入れると、関係を範囲の中で測れて C とも噛み合う。
- F は評価の側の変更なので、数字の意味が変わる。台帳には印の版を残す（suites の定義は変えず、新しい印で数え直す）。

## 4. 測り方（今回うまくいったもの）

- 速い組（330 件、約 4 分）と pytest（約 2 分）を毎回。
- 56 の記録の出力の比べ（バイトまで）。作り替えの段（A）はこれで合否。
- 確認用の組の洗い出し（heldout 0〜99 × 12 の変換、方式ごとの「読めるはずで読めない」と誤り）。段ごとの基準にする
  （今: 101・0）。
- 変更の前後を同じ組で並べて回す（前の版のコードを写して PYTHONPATH で）。時間は前後を交互に 2 回ずつ。
- 全スイートは main の CI（gate は自動で飛ぶ）。

### 8.x 段 C の続き（e4db38b と次のコミット、2026-11-19）

調整用の組のスパイクとクロストーク（tuning[0:100] の spike 0.1/0.3、xtalk 0.05/0.3、820 本）で、読めるはずで読めない
48 → 21。ほかの 2127 件（広い組）は 読めた +20、確定 +34、失ったものなし、誤った主張は同じ。i2cbench は同じ。

効いたもの:
- glitch views を、クロックがきれいでもデータ線・選択線の短いパルスから作る（SCL はきれい、SDA にクロストーク）。
- I2C の縮んだクロックは、両側の Low の長い方が普通の 4 倍以下のときだけ（取引の間の長い Low のクロストークを
  クロックとして残していた。実機の遅い立ち上がりは最大 2.9）。
- 1 周期 4〜8 サンプルのクロックに、1 サンプルのパルスを除いた見え方（下調べと同じ条件）。クロックの典型的な Run を、
  4 刻み未満を除いた Run から取るのは、ほとんど残らない所ではやめる（速いクロックで 3 が 220 になっていた）。
- 長さ 3 の Run の中のパルス（1 サンプルの Run が 3 つ）は真ん中を除く。ただし速い見え方のクロック線だけ。
  全体に入れると、CS に乗ったクロストークのパルスの列で選択線の測り方が悪くなる（D6 の選択線 0.76 → 0.46）。
- SPIKE_BROKEN 0.5 → 0.35（50 MS/s の xtalk 0.3 が 0.48。実機の速いクロックは 0.136 と 0.546）。

残り（調整用の組）:
- CS の線がほとんどクロストークのパルスで、2 つの SPI の CS が入れ替わる（mixed-171 xtalk 0.3）。写しの見分けが要る。
- 雑音のない記録でも決まらないもの（mixed-183 の D9: バイト数個でビット順が決まらない）: 段 D。
- crop:0:0.25 の 34 件: 多くは取引が 1 つだけで「あいまい」（I2C 6 語で 0.49）。証拠の下限をどこに置くか（段 F と同じ判断）。
- spivar の uncaptured（CS を取っていない相手がいる、種の 10 分の 1）: CS で選ばれた相手と、その外の残りを CS のない相手

### 8.m sigrok との中身の突き合わせ（CAN・1-Wire・DMX512・NEC）と CAN FD（2026-11-21）

- sigrok-test の設定で sigrok-cli（0.7.2）を走らせ、CAN・1-Wire（onewire_network）・NEC の注釈を正解として比べた。
  0.7.2 の dmx512 は UART に重ねない単独のデコーダで、sigrok-test の設定（uart に重ねる）では動かないので、単独で
  読ませた。0.7.2 の ir_nec には extended のオプションがなく、拡張アドレスの記録はアドレスの誤りで止まる（コマンドの
  正解なし。wireskein の読みはアドレスが sigrok と同じで、コマンドの反転の照合が通る）。
- 見つかったものと直したもの（どれも合成波形のテストを足した）:
  - DMX512: 17 本中 3 本しか読めていなかった。全部 0・0x55・0xff の試験の並びは線から速さが出ず（下調べにはクロック）、
    0 のスロットが続くと待機のレベルも時間では決まらない。DMX+ と DMX- の対はクロックとデータの組（RVSWD・SWIO・SPI
    のあいまい）になっていた。ブレークのある線を規格の 250 kbaud でも読む、変化ごとに一緒に変わる 2 本は組にしない、
    短い記録の 1 パケットも数える、で 15 本（残り 2 本は 1 ビット 2 サンプル）。DHT の線（50 µs の Low）を DMX の 0 の
    スロットと読む穴を、テストで見つけてふさいだ（スロットの Low は 9 ビットまで、ブレークは 22 ビットから。その間の
    Low は枠の誤り）。ma_lighting などの 1 秒の記録は sigrok 0.7.2 のほうが読み違える（長い High をブレークと読む）。
  - CAN: 負荷をかけた 4 本は sigrok と完全に同じ。同じメッセージをくり返すだけの 2 本が、周期的な線の判定
    （degenerate）で落ちていた: CRC のあるフレームは違うものごとに 1 回数える（can.toml の `repeats = "once"`）。
    NMEA2000 の記録は sigrok の側が同期を外している（125 中 109 が一致、違うものは wireskein の側の CRC が通る）。
  - CAN FD: 対応した（8 本すべて）。CRC-17 / CRC-21 の多項式を最上位の項込みで書いて最後の値がずれる誤りを、実物で
    見つけた。データの最後の 5 ビットが同じときの送り手の扱いは資料で確かめられず、両方で読んで CRC で決める。
  - 1-Wire: Overdrive Match ROM（0x69）の後をオーバードライブで読んでいなかった（SoCkit）。空のメモリ（0xff の連続）を
    同じ値ばかりの線とみなしていた（DS1985 のメインメモリ）。ds2408 の 4 本はアナログだけの記録（--threshold の話）。
    owfs の 2 本は末尾のバイトが sigrok より多い（読み出しスロットの続き。sigrok の network 層が出さないだけとみる）。
  - SPI（TODO にあった adesto_at25sf041）: CS の候補は作られていたが、記録の終わりに CS がクロックと一緒に切り替わる
    区間があり、1 ビットのフレームが 16 できて長さの合う割合が 0.4 になっていた。1 ビットの窓はフレームにしない。
- CI 2dd2e95（gh44833873103、全スイート、エラー・時間切れ 0）: 24fa5bb より全体に良く、誤った確定 19 → 4、誤った有力
  40 → 16（全スイートの和）。24fa5bb・76842b9 より悪いのは noise-holdout xtalk:0.3 の誤った有力 0 → 1（synth-mixed-1066:
  I2C と UART の記録で MDIO を有力）だけ。holdout なので合わせない。real-i2c の誤った有力 3 は前から。
- 広い組（調整側 2127 件）で 2 つの悪化を見つけて直した（誤り 1 → 4、取りこぼし 40 → 47 だった）:
  - DMX512: 長い Low をはさんだクロックのバースト（mixed:nack:54 の D3）を、クロックに見える線にも試す DMX の読みが確定に
    した。文字の長さを Run に一番合う 8 ビット（6 データビット）で読み、7 ビットの Low が「0 のスロット」になっていた。
    DMX のスロットは常に 11 ビットで読む（そう読むと 0xC0 で、スタートコードが 0 にならない）。
  - 1-Wire: 乱数のデータでリセットの 1 バイト目が 0x3C / 0x69 になると、オーバードライブに切り替えてその後を読み違えて

    短いか、すべて 16 µs 以下で 2 µs の両側にある）ときだけにした。SoCkit はスロットの間隔が 66 µs で、前者だけでは

- RC-5、RC-6、SIRC、ほかの IR は、決めたとおり本体に足さない（todo-ir-protocols）。読めないものが SPI・sync_unknown の
