# 拡張点の仕様（2026-11-23、案）

v1 で約束する拡張点を、ここに決めた範囲だけにする。組み直しはこの仕様の範囲で行う。もとにした決定は v1 の B7、B9、B10、
B11（エンジンの境目）、B12（拡張を 3 つに分ける）、B13（名前空間）。案の部分は、決めてもらってから直す。

## 1. 段と、拡張が差し込まれる所

```text
記録（capture.Part の変化で持つ見方）
  │
  ├─ 判定のエンジン（本命: 今のエンジン）      ─┐
  ├─ 付け足しのエンジン（register_engine）      ├─ 主張（出口の形式の claims）
  │                                              ┘
  ├─ 合わせる段: 本命の主張を土台に、付け足しのエンジンの主張を決まりで足す（§3.2）
  │
  ├─ 上の段: 主張の出口の層の上で読む
  │     組み込みの上の層（行、NMEA、Modbus RTU、SCPI、UART の組）
  │     自前のプロトコル（register_protocol）
  │     機器パック（devices/）、マーカーの方言（markers/）
  │     チェックが合えば、下の主張の確かさを上げる（§3.3）
  │
  └─ 出口（wireskein-analysis/1）
```

入出力の拡張（検査 register_check、ファイル形式 register_format、取り込み元 register_source）は、この流れの外側で、
すでに `wireskein.plugins` にある（B9）。

## 2. 名前（B13）

- 組み込みは名前空間なし（`uart`、`i2c`、`spi`、`lines`、`nmea` …）。組み込みの名前はリポジトリの台帳 1 つ
  （§4）にだけ置く。
- 外からの名前は `持ち主.名前`（英小文字で始まる英数字と `_`、`.` で 1 段）。持ち主はパッケージや組織の名前。
  当てはまるもの: 自前のプロトコル、付け足しのエンジンとそれが読むプロトコル、マーカーの方言、検査の種類、ファイル形式。
- 取り込み元の名前は URI の scheme なので、名前空間を付けない（組み込みの `oep`、`sigrok` を断るだけ）。（案）
- 機器パックの機器は部品の名前（`SHT30`）で、名前空間を付けない。同じ部品のパックが 2 つあれば、後から足した方を使う。（案）

## 3. 拡張点

### 3.1 上の拡張（約束する）

| 拡張 | 入口 | 読むもの | 出すもの |
|---|---|---|---|
| 自前のプロトコル | `plugins.register_protocol(obj)`、EP `wireskein.protocols` | `over` に名付けたバスの、出口の形式の dict（§4 の台帳の層） | `messages`、`checks_passed`、`checks_failed` |
| 機器パック | 定義のディレクトリの `devices/<bus>/...`（`wireskein-device/1`） | I2C の取引、SPI の転送 | 機器の特定とレジスタの読み |
| マーカーの方言 | 定義のディレクトリの `markers/*.toml`（`wireskein-marker-dialect/1`） | UART の行 | 区間 |

- `over` に書けるのは、台帳にあるバスの名前（`uart`、`spi`、`i2c`、`uart_pair`、`can`、`lin`、`dmx512` …）と、
  付け足しのエンジンが申告したプロトコルの名前。
- 上の拡張は、下の主張の役割も判定（confirmed / likely …）の言葉も変えない。チェックが合えば、確かさ（score）を
  決まった式で上げるだけ（§3.3）。

### 3.2 付け足しのエンジン（約束する）

- 入口: `plugins.register_engine(name, engine, protocols=[...])`、EP `wireskein.engines`。`name` と `protocols` は
  `持ち主.名前`。
- `engine(view, hints) -> claims`: 入口と出口はエンジンの境目の約束（B11）のとおり。`claims` の `protocol` は申告した
  名前だけ。出口の層の形は、その名前の台帳（§4）の申告に合わせる。
- 合わせる段の決まり:
  - 付け足しのエンジンの主張は、本命が説明しなかった線（主張なし、unknown-sync、ambiguous の線）にだけ足す。
  - hints の `protocols` がそのプロトコルを名指ししたときは、そのエンジンの主張を本命より先にする。
  - 付け足しのエンジンどうしがぶつかったら、点数の高い方。同点は名前の順。
- 本命のエンジンを替えるのは拡張点ではない（エンジンの入れ替えは WireSkein の中の作業。ベンチのポートフォリオで比べる）。

### 3.3 確かさの上げ方（上の段）

- 子（上の層、自前のプロトコル、機器パック）のうち、いちばん確かなものの点数を `support` として、
  `score = s + 0.5 (1 − s) · support · s`（今のエンジンの式と同じ）。
- 判定の言葉は、上げた後の点数と元の差（margin）で決め直す（今のエンジンの verdict と同じしきい値）。

### 3.4 約束しないもの

- 判定のエンジンの中の作り（下調べ、見方、ビットの層、点数、定数）。
- 線そのものの上のプロトコルの定義（decl/*.toml）、`[score] terms`、`reframe`: 今のエンジンの一部（B12）。
- エンジンの入れ替えの口（`_engine.methods`）: ベンチの道具。

## 4. 組み込みの名前の台帳

- 置き場所: `src/wireskein/registry.toml`（案）。機械が読む形。
- 1 つのプロトコルにつき: 名前、種類（`bus` / `upper`）、役割の名前、出口の層の名前と、分析の形式の節、読むエンジン
  （今は `main`）。
- テストで確かめること:
  - 本命のエンジンが出す `protocol` が、すべて台帳にあること。
  - 出口の層の名前が台帳と合うこと。
  - 外からの名前が名前空間を持ち、台帳の名前とぶつからないこと。

## 5. 組み直しの順

1. 台帳を作り、本命のエンジンの出力と突き合わせるテストを入れる（出力は変えない）。
2. 名前空間を必須にする（B13）。今の例（demo_link、demo_cmd、demo_telemetry、demo_settle、saleae_csv）は
   `examples.xxx` などに直す。
3. 上の段をエンジンの外に移す（出力はバイトまで同じ: 今の式のまま）。組み込みの上の層、自前のプロトコル、機器パック、
   マーカーの方言をこの段へ。
4. 付け足しのエンジンの口と、合わせる段を作る（ポートフォリオの宣言型エンジンを付け足しとして挿して試す）。
5. 文書（extending、protocols、analysis-format）を、この仕様に合わせて英日で書き直す。
