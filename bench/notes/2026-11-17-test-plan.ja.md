# テスト計画（たたき台、2026-11-17）

ベンチの目的は、WireSkein の品質を上げること。速いテストではない。この計画は「何が良くなれば品質が上がったと言えるか」を
先に決め、ベンチはそれを測るためにだけ回す。

## 1. 品質の目標（優先の順）

| | 目標 | 利用者から見て |
|---|---|---|
| G1 | **黙って誤らない** | 確定と言ったものは正しい。読めなかった所は「読めなかった」と言う（黙って落とさない） |
| G2 | **読めるものは正しく全部読む** | 取引・フレーム・バイトが、外の正解と一致する |
| G3 | **自動で見分ける** | ヒントなしで、プロトコル・線の役割・速さが当たる |
| G4 | **読めない条件を知らせる** | 速さ不足・ノイズ・配線の問題を、理由と取り直し方つきで知らせる |
| G5 | **実用の時間とメモリで終わる** | 長い取り込み（数百万の変化）も、待てる時間と手元のメモリで読める |

## 2. 指標・データ・正解・合格の線

| 目標 | 指標 | データ（スイート） | 正解（WireSkein の外） | 向き |
|---|---|---|---|---|
| G1 | 誤った確定（`false_confirmed`） | 全部 | 生成の真値、実機の記録 | 少ないほど良い（実機で 0 を目指す） |
| G1 | **黙った取りこぼし**（新設）: 正解にあるのに、読みにも「読めなかった区間」にもないもの | linke-l103-core、ebdd-50m、i2cbench | ch32rv の DmiOp と read.bin、ファームの出力 | 少ないほど良い |
| G2 | 読みの一致（`decode_mean`、ケースごとの最小も） | 実機のスイート全部と、その間引き | 同上 | 高いほど良い |
| G3 | 見分け（`ok`、`confirmed`） | noise、stress、real、ebdd-50m、linke | 生成の真値、記録の配線 | 高いほど良い（確認用で確かめる） |
| G4 | 読めない条件での確定（`false_confirmed_hard`）と知らせ（notice）の有無 | size、rate、間引きの 5 MHz 以下 | 物理（サンプル数）と正解 | 確定は少ないほど、知らせは漏れなく |
| G5 | 時間とメモリ（`cost-real`、変化 100 万あたり） | cost-real | ― | 短いほど、少ないほど良い |

合格の線は置かない。どの指標もどこまでも良くし、比べた中で一番良いものを採る（ほかの指標を下げない範囲で）。
`ok` は実機のデータでほぼ 1.000 に張り付き、品質の差を示さない。実機のスイートの見出しは G1 の取りこぼしと G2 の一致にする。

## 4. 進め方

- **変更は仮説から**: どの穴を、どの指標でどこまで動かすかを先に書く。確かめは手元で、関係するスイートを名前で指定し、
  ケースは `cases.py`（遅い・誤ったケースを明細から選び、そのまま再現）で。
- **Actions のフルのベンチは区切りで**: 方式を選ぶとき（試行が増えたとき）と、製品に入れる前の「下がっていないか」の確認。
  結果は前の区切りと `cases.py diff` で比べ、notes に判断と実行 ID を残す。
- **データは穴ごとに**: 穴を測れるデータがなければ取りに行く（b の V003、ほかに V203、SPI / UART の実機）。

## 5. 順番

まず取れない信号を取れるようにし、それから悪いデータで粘る。

1. **取れない信号を取る**
   - f → a: 黙った取りこぼしの指標を足し（実機のスイートの見出しにする）、RVSWD の BURST の消失を直す。
   - b: V003 のデータを取り、SWIO の区切り（隙間の詰まったフレーム）を直す。
2. **悪いデータで粘る**
   - d: 誤った確定を減らす combo を、遅い取り込みでも悪くならない形にして製品に入れる。
   - c: 遅い取り込みの I2C を、読むか、読めないと知らせるかのどちらかにする。
3. **時間とメモリ**（e）: いつも最適化を続ける。線は置かない。
