# 構造の実験（2026-11-22〜）

正解率を追い込む段階ではない。判定の構造を、いろいろな向きに入れ替えたときに何がどう変わるかを、粗い試作で数値にして
比べ、メリット・デメリットと方向を見る（ユーザー、2026-11-22）。実験は手元の写し（scratchpad の exp/）で、製品は変えない。

## 物差し

| 軸 | 何で測るか |
|---|---|
| 確度 | UART・I2C・SPI の本物のバスを、プロトコルと役割で見つけた数。役割の合わない主張は誤り |
| 計算量 | CPU 時間（参考。あとで何とかできる可能性があるので、判断の主な軸にしない） |
| シンプルさ | 経路の上の規則と定数の数、行数 |
| 拡張性 | プロトコル 1 つを足すときに書く所と量、ほかのプロトコルを巻き込むか |
| 難しさの段 | L0 確実（ノイズなし）、L1 少しノイズ（spike 0.02、bounce 0.1、xtalk 0.05、間引き 2）、L2 ノイズ多め（spike 0.3、bounce 0.5、xtalk 0.3 とずれ 0〜1、間引き 4） |

## 仮説と試作

| 案 | 中身 | 仮説 |
|---|---|---|
| E1 総当たり（brute） | 下調べなし。役割の割り当てを総当たりし、役割を与えた小さな読み手（UART・I2C・SPI、各 40〜60 行）の合い方の点数で選ぶ | 規則がほぼ消え、プロトコルは「読み手 + 合い方」で足せる / 遅い。点数の尺度がそろわないと選べない |
| E2 最低条件（gate） | E1 に、プロトコルごとの最低条件（I2C の SCL は SDA より多く変わる、SPI のデータはクロックより少なく変わる、など）で読む割り当てを絞る | 速く、条件をプロトコル側に置けば差し込みやすい / 条件を外すノイズで取りこぼす |
| E3 見方を次元に（gate_views） | 決まった見方（そのまま、1 サンプルのパルス除き、跳ねまとめ）すべてで読み、候補ごとに最高点 | ノイズの種類を推し量る規則が消える / 見方の数だけ読む |
| E4 軽いエンジン | E1〜E3 の読み手そのもの（約 250 行、3 プロトコル） | 今の大きなエンジン（共通の層 約 5900 行）が何を稼いでいるかの物差し |
| E6 全体の割り当て | 候補を点数順に、線を重ねずに取る | 「1 本の線は 1 つのバス」が規則なしで守られる / 点数の比べやすさに頼る |
| E8 相関を先に（corr） | 線を「いつ動くか」で 2000 に区切り、一緒に動く線のグループの中だけで候補を作る（プロトコルに依らない） | プロトコルを足しても直す所がない / 別々のバスが同時に動くとまとまる |
| cascade | 軽いエンジンで読み、確か（どの主張も 0.85 以上で、動く線の 8 割以上を説明）なら採り、そうでなければ今のエンジン | 易しい記録を速く済ませ、難しい記録は今の確度 / 「確か」の判定が外れると誤りが通る |
| E9 層の積み重ね | (a) 今: 共通のビットの層 → フレーム → プロトコル、(b) プロトコルごとに端から端（E4）、(c) 共通は「クロック同期のビット列」と「非同期の文字列」の 2 つだけ | 足す量と巻き込みの釣り合い |

## 結果

### 組を広げた比べ（tuning 100 件 × きれい・xtalk 0.3:01・bounce 0.1・間引き 4、spivar 40 件）

見つけた / バス、誤り、CPU 秒。

| | 今のエンジン | gate | brute |
|---|---|---|---|
| きれい（207） | 207、0、36 | 170、22、7.8 | 170、22、120 |
| xtalk 0.3:01（207） | 201、0、104 | 16、30、13.5 | 20、28、242 |
| bounce 0.1（207） | 192、0、126 | 1、42、9.7 | 1、43、120 |
| 間引き 4（207） | 164、0、34 | 139、18、7.0 | 139、18、102 |
| spivar（50） | 45、4、8.3 | 28、13、1.3 | 28、13、15 |

- 軽い読み手は、きれいな記録の 8 割を 5〜8 倍の速さで読む。間引きにもそこそこ強い。
- ノイズには極めて弱い（bounce 0.1 でほぼ全滅）。生の辺を数えるので、1 つの跳ねで文字や取引の数が崩れる。今のエンジンの
  共通の層の多くは、このノイズへの備え。
- 最低条件で絞っても、総当たりと同じ結果で 15 分の 1 の時間。絞り方は確度をほとんど損ねずに計算量を減らせる。
- 点数で全体を選ぶ形は、誤りが多い（22）。軽い読み手の点数が、まだ本物と偽物をよく分けていない（最初の版では、ゆるい
  UART の読みがクロックの線を取り、本物の I2C・SPI を押しのけた: プロトコルをまたいだ点数の尺度が要の論点）。

### E9 (c) 共通の層 2 つ（layered）と、選び方の重み（E6b）

共通の層を「クロック同期のビット列」と「非同期の文字列」の 2 つだけにし、各層で線自身の長さ（クロックの半周期、
ビットの時間）の 0.3 倍より短い Run を除く。固定の幅や、ノイズの種類を推し量る規則は使わない（約 200 行）。

| | 今のエンジン | gate | layered | layered + 線の数の重み |
|---|---|---|---|---|
| きれい | 207、0 | 170、22 | 170、23 | 170、23 |
| xtalk 0.3:01 | 201、0 | 16、30 | 74、59 | 79、54 |
| bounce 0.1 | 192、0 | 1、42 | 64、62 | 79、46 |
| 間引き 4 | 164、0 | 139、18 | 138、18 | 139、17 |

- 線自身の長さに対して短い Run を除くだけの薄い共通の層で、ノイズのある記録の見つけた数が数倍になった（16 → 74、1 → 64）。
  ノイズへの備えは、プロトコルごとではなく共通の層に置くと、少ない量でよく効く。
- 誤りは増えた。多くは SPI のデータ線を UART と読んだもの（1 本だけ説明する読みが、点数の高い順で先に線を取る）。
  選ぶ重みを「点数 × 説明する線の数」にすると、少し良くなった（プロトコルに依らない一般の決まり）。
- 残る誤りは、軽い読み手の点数の弱さ。ここを磨くのは調整になるので、方向の確認としてはここまで。

### E5 選び方を学習する（layered_learned）、E10 説明できた辺（explain）、E11 その両方

候補（layered の読み手）の特徴から、正しい読みである確率をロジスティック回帰で学ぶ。学ばせるのは tuning だけ、
確かめは set:heldout と spivar[1000:]。見つけた / 880、誤り。

| | 調整用 | holdout |
|---|---|---|
| 手の点数（layered + 線の数の重み） | 495、153 | 458、145 |
| E5 学習した確率（0.5 以上） | 363、4 | 331、9 |
| E10 説明できた辺の割合 | 542、365 | 527、384 |
| E11 学習（説明できた辺も特徴に）+ 説明できた辺の多い順 | 352、12 | 330、11 |
| 今のエンジン | — | 818、5 |

- 学習した選び方は、誤りを手の点数の 1/15 にし、調整用と holdout の差も小さい（合わせすぎていない）。慎重になり、
  見つけた数は減る（しきい値で動かせる）。
- 「説明できた辺の割合」はプロトコルに共通の尺度になるが、それだけでは本物の形か見分けられない（データ線やおとりの線も
  UART として自分の辺を説明する）。見つけた数は軽い形の中で最多、誤りも最多。
- どの形でも、見つけた数は読み手の力で頭打ちになる（選び方では越えられない）。

### E12 今のエンジンの読み手を残し、選び方だけ学習に（rearb）

今のエンジンのすべての主張（mode all、次点つき）を候補にし、その数字（点数、差、判定、ぶつかる主張の数、次点の有無、
プロトコル: 13 個）から正しさの確率を学ぶ。tuning（6 組 600 件）で学び、heldout（600 件）で確かめる。

| | 調整用（1160 本） | holdout（1159 本） |
|---|---|---|
| 今の判定（確定・有力） | 1014、9 | 1036、12 |
| 学習（0.5 以上） | 1018、11 | 1038、16 |
| 学習（0.7 以上） | 1000、10 | 1023、13 |

- ほぼ同じ。今の選び方は読み手の限界の近くまで合わせてある。手で決めた判定の決まりを、小さな学習モデルで同じ確度の
  まま置き換えられる（プロトコルを足すときに確定のしきい値を手で合わせなくて済む可能性）。
- 今のエンジンは 1 本の線に候補をほぼ 1 つしか出さない（主張 1064、正しいもの 1036）。見つけた数は読み手で決まる。

### 難しさの段ごと（見つけた / バス、誤り、CPU 秒）

| 段 | gate | gate_views | corr | cascade | 今のエンジン |
|---|---|---|---|---|---|
| L0 確実（257） | 198、35、10 | 198、37、26 | 168、58、56 | 248、8、41 | 252、4、42 |
| L1 少しノイズ（828） | 331、120、39 | 601、150、85 | 294、146、282 | 805、2、309 | 807、0、246 |
| L2 ノイズ多め（1035） | 171、88、74 | 719、247、138 | 149、109、756 | 894、2、488 | 895、0、375 |

- cascade で軽いエンジンだけで済んだのは L0 21%、L1 5%、L2 3%。「確か」の目安が誤りを通し（L0 で誤り 4 → 8）、
  時間も減らない。軽いエンジンがもっと強くならないと、難しさで段を分ける cascade は割に合わない。

- 見方を次元にする形（E3: 3 つの決まった見方をすべて読み、候補ごとに最高点）で、ノイズのある段の見つけた数が大きく
  伸びた（L2 で 171 → 719）。ノイズの種類を推し量る規則なしで。今のエンジンの散らばったノイズの規則の多くを、この形で
  置き換えられる見込み。
- 相関で先にグループにする形（E8: 時間の区切りで一緒に動く線）は、別々のバスがまとまり、同じバスの線が分かれて悪化。
  粗い相関だけでの決め打ちは向かない。

### プロトコルの近さ（CI cba29df、bench/confusion.py）

癖のある時間の形を持つプロトコル（SWIO、RVSWD、SWIM、J1850、SENT、Wiegand、SD）は、取られた・拮抗したがほぼ 0。混ざるのは
形のありふれた一群（I2C 取られ 86、SPI 17、UART は取る側で拮抗 31、sync_unknown）。遠いものを先に厳しく読んで線を押さえ、
残りを念入りに見分ける順番（プロトコルの近さで段を分ける cascade）が考えられる。

### 今のエンジンの量（E9 の (a)）

- 定義ファイルのプロトコル: 1 つ 21〜70 行（SPI 21、I2C 33、RVSWD 70）。その下の共通の層が約 5900 行（survey、taxonomy、
  typed、declarative、timing、views、kernels、staged）。定義ファイルは、共通の層が名前で用意する点数の項や区切り直しに頼る。
- Python のプロトコル: 1 つ 66〜450 行。

## 記録の仕組み

- bench/confusion.py: CI の実行から、取り違えたプロトコルの組と拮抗した組を数える（cba29df から記録）。どのロジックで、
  どのプロトコルとの見分けに気を配るかの物差し。

### E3 を今のエンジンの中で（fixedviews）、E13 プロトコルの近さで 2 回に分ける（twotier）

今のエンジンの読み手と点数はそのままに、glitch_views / single_views（見方を作る規則）を、決まった 3 つの見方（そのまま、
1 サンプルのパルス除き、跳ねまとめ 5）を毎回作る形に替えた。見つけた、誤り。

| 段 | 今のエンジン | 見方を固定 |
|---|---|---|
| L0（257） | 252、4 | 241、3 |
| L1（828） | 807、0 | 775、0 |
| L2（1035） | 895、0 | 861、15 |

減ったのは主に間引き（-26、-27）: 間引いた本物の信号の 1 サンプルの Run を除いた見方の方が、形がそろって点数が高く、
誤った見方が選ばれる。跳ね 0.5 では見つけた数は増え、誤り 15。「線の辺の 25% より多くを消す見方は、その線を残す」を
足すと、きれい・間引きは今と同じに戻り（207、203、164）、跳ね 0.5 は 123 → 95 に落ちた（ノイズ自体が 25% を超える）。

- 消した量だけでは、重いノイズと本物の短い Run を分けられない。跳ね（辺の隣に対で）と間引き（規則正しく並ぶ）の形の
  違いが要る。今のエンジンの見方の規則の複雑さは、この違いを個別に扱っているため。
- 一般の形にするなら、点数の側で「見方は消した辺の分だけ不利」（E10 の説明できた辺の数え方）にするのが筋。今の点数の
  作りに手を入れる必要があり、試作が大きい。

E3b / E3c: 見方の固定で落ちた間引きの記録を、一般の決まりで戻せるか試した。「掃除した見方の読みは、消した辺の割合だけ
点数を下げる」（λ 0.5、1.0）、「取ったままの見方の、同じプロトコル・同じ役割の読みより 0.05 を超えて高いときだけ数える」。
どちらも結果は変わらなかった。落ちた事例（synth-mixed-1、間引き 4）を見ると、決め手は見方の点数ではなく、取ったままの
見方の中で、同じバスが立ち上がりと立ち下がりの両方で読まれ、ほぼ同点（0.9279 と 0.9274）になったことだった。今のエンジンでは
立ち上がりだけで読まれる。見方を作る関数が、どちらの辺で読むかの決定にも影響している。

- 今のエンジンの見方の層は独立した部品になっておらず、辺の決定などほかの段と絡み合っている。見方だけを入れ替える実験が
  素直にいかないのは、このため。層を入れ替えられる形にするには、段どうしの受け渡し（見方 → 辺 → ビット → フレーム）を
  はっきりさせ、ある段の出力が別の段の決定を黙って変えないようにする必要がある（エンジンの境目の考え方を、エンジンの中の
  段にも当てはめる）。

E13: 癖のある形のプロトコルを先に読み、確定した線を押さえてから、残りをありふれた一群で読む（今のエンジンの hints で
2 回）。protomix 60 件（きれい、xtalk 0.3:01）と tuning 40 件の 390 本で、1 回 386（117 秒）、2 回 375（141 秒）、誤りは
どちらも 0。今のエンジンは癖のあるプロトコルを 1 回で見分けている。先に絞ると、競う候補どうしの比べが欠けて落ちる。

### E15 線の役割を学習で、E16 線どうしの関係を学習で

E15: 線 1 本の特徴（features の点数 5 つ、周期、デューティ、Run の分布、バースト）から、役割（クロック、データ、選択、
非同期、その他）を one-vs-rest のロジスティック回帰で学ぶ。tuning（きれい、xtalk 0.3:01、bounce 0.1、間引き 4）で学び、
heldout で確かめる。

| | 学習 | 点数の最大で決める規則 |
|---|---|---|
| 調整用（2508 本） | 76.2% | 41.5% |
| holdout（2456 本） | 73.4% | 42.3% |

- 規則はもともと線 1 本で役割を決めない作りなので、比べは規則に不利。線 1 本でも学習で 7 割強を当て、holdout でも落ちにくい。
- 当てられないのは UART の線とデータの線（223 本）、おとりの止まらないクロックとバスのクロック。どちらも線 1 本では決まらず、
  線どうしの関係が要る（今のエンジンが関係を重く見るのは正しい）。

E16: 下調べの関係の数字（一緒に動く割合、辺への寄り方、同時の変化、選択の枠、バーストあたりの変化、data_score、クロック
らしさ）から、「このクロックのデータか、選択か、無関係か」を学ぶ。

| holdout（13138 組） | 学習 | 規則（data_score ≥ 0.5、枠 ≥ 0.5） |
|---|---|---|
| データ（748 組）を当てた / 取りこぼし | 738 / 10 | 723 / 24 |
| 無関係をデータと誤った | 66 | 147 |
| 選択（296 組）を当てた | 3 | 293（無関係も 1229 組拾う） |

- データの関係は学習の方がきれい（取りこぼしも誤りも規則の半分以下、調整用 0.977 と holdout 0.972 で差が小さい）。
- 選択は少数（2%）なので「確率の最大」では無関係に負ける。役割ごとのしきい値で拾う形にすれば戻せる見込み。規則の選択は、
  後の段で絞る前提のゆるい候補。

## ここまでの方向（2026-11-23）

1. 力を入れるべきは選び方ではなく、読み手と見方。選び方を学習に替えても確度はほぼ同じ（E12）で、見つけた数は読み手で
   頭打ちになる（E5、E11）。
2. ノイズへの備えは、プロトコルを仮定して線自身の長さで取る薄い共通の層（E9 c）と、決まった見方をすべて読んで最高点を
   採る形（E3）が、少ない規則でよく効く。今のエンジンの散らばったノイズの規則を置き換えられる見込み。
3. 選び方は、線の数で重みを付ける一般の決まり（E6b）や、小さな学習モデル（E5、E12）で、手の判定の決まりを置き換えられる。
   プロトコルを足すときの調整が減る見込み。
4. 粗い相関で先にグループにする（E8）、難しさで段を分ける cascade、プロトコルの近さで段を分ける（E13）は、今の形では割に
   合わない。全体を一度に比べる今の形の方がよい。
5. 下調べの手の規則（線の役割、線どうしの関係）も、同じ数字を材料にした小さな学習で、同じか少し良い当たり方になり、
   holdout でも崩れない（E15、E16）。少数の役割（選択）の扱いは別に要る。
6. 今のエンジンの段（見方、辺の決定、ビット、フレーム、点数）は絡み合っていて、1 つの段だけを入れ替えにくい（E3b、E3c）。
   入れ替えの実験を進めるには、段どうしの受け渡しをはっきりさせる作り替えが先に要る。

次の実験の候補:
- 段どうしの受け渡しをはっきりさせた小さなエンジン（軽いエンジンの形）に、今のエンジンの強い読み手（I2C の入力の見方、
  SPI の辺の決定など）を 1 つずつ移し、確度と量を比べる。今のエンジンを外から入れ替えるより、組み立て直す向き。
- 共通の層（E9 c）と見方の次元（E3）を、その小さなエンジンの前段に置く。

## エンジンのポートフォリオ（bench/engines、2026-11-23〜）

採用は別にして、方向の違うエンジンを並べて追い込み、互いの苦手を見る（ユーザー、2026-11-23）。どれもベンチの e2e の試行
（bench/algos/e2e/engines.py）で、本命と同じ組・同じ採点（evaluate.judge）。CI では Bench の algorithms に engine と
書くと全部の組で回る。

| エンジン | 方向 |
|---|---|
| 今のエンジン（本命） | 調整型: 拡張の仕組みは持たず、微調整したパラメーターと多数のプロトコルの競い合いで識別 |
| light | 軽量型: 独立した読み手（UART・I2C・SPI、仮定の長さで掃除）、最低条件の候補、線の数で重みを付けた選び方 |
| views | light を決まった 3 つの見方すべてで読み、候補ごとに最高点 |
| declarative | 宣言型: プロトコルを TOML の表で宣言し、1 つの解釈器で読む。候補・ノイズ・出口は宣言だけから |

### 開いた世界の仕組み（「どの知っている形にもよく合わない」）を 2 つ（2026-11-23）

軽量型の誤りの大部分は、UART でない線を UART と読むこと（34dccdd の light の誤り 2462 件のうち、UART が約 2100 件:
LED、1-Wire、IR、DMX・LIN、おとり）。そこで 2 つの方向を views の上に試した。

- nulled（帰無の比べ、`bench/engines/nulled.py`）: 同じ読み手を、構造を壊した代わりの線（1 本なら区間の幅を並べ替え、
  複数なら 2 本目から時間をずらす）にかけ、その合い方を超えた分だけを残す（`fit · (fit − null) / (1 − null)`）。
  どのプロトコルの名前も持たない、読み手に共通の仕組み。
- open（形の説明、`bench/engines/shapes.py`）: 「各レベルの区間が 1〜2 種類の幅しか取らない線」（パルスの符号: LED、
  1-Wire、IR）を、プロトコルの名前なしの説明として候補に入れる。最良の組の中で読み手の主張と競い、勝てば線を取って表に
  出さない。

調整用（gen:pulse・uartlike・ir・spivar の [0:30]、set:tuning[0:30]、バス 222 本）と holdout（同じ [1000:1030]、
set:heldout[0:30]、225 本、1 回だけ測った）、読めた本数と誤り（確定 + 有力）:

| エンジン | 調整用 読めた | 調整用 誤り | holdout 読めた | holdout 誤り |
|---|---|---|---|---|
| views | 98 | 125 | 109 | 134 |
| nulled（差のまま） | 49 | 25 | | |
| nulled（余地に対する割合） | 93 | 99 | | |
| open（形の点 0.9、読み手の後） | 98 | 100 | | |
| open（形の点 1.0、読み手より先） | 96 | 76 | 108 | 98 |

- 帰無の比べは UART に効かない。並べ替えた線でも UART の読み手は 0.5〜0.6 合う（ビット幅に揃った区間なら何でも
  ある程度 UART になる）。本物の UART も LED も 1.0 対 0.55 前後で、区別がつかない。読み手の特異さが低いのが根で、
  ゲートの掛け方では直らない。
- 形の説明は効く（holdout で誤り −27%、読めた数 −1）。どの線を取るか: UART の線 0/39、LED 22/23、IR 17/30、
  1-Wire 12/27、ほかの線は SCL 1/16・SPI のクロック 1/41・無関係の線 4/190。失った 1 本はクロックの線を形が取ったもの。
- 残りの誤りの多くは DMX512・LIN（物理的には UART: 名前の付け方の問題で、上の層で読むもの）と、形が拾えなかった
  IR・1-Wire。
- わかったこと: 閉じた世界の誤りは、点数の足切りでは減らず、「別の説明」を競わせると減る。今のエンジンが多数の
  プロトコルの競い合いで満たしているのと同じ仕組みを、名前なしの形（パルスの符号、クロック、…）でも作れる。軽い
  エンジンの開いた世界は、形の小さな辞書で持てる見込み。

### 形の説明を 2 段に（2026-11-23）

形を「各レベルの区間の幅が 1〜2 種類（90%）」の少数アルファベットに広げた（間を切る閾値 GAP はやめた: 1-Wire の
リセットや IR のリーダーを間として切り、取りこぼしていた）。1 種類を入れると、搬送波で変調した IR とクロックも形になる。
そのまま候補に混ぜると、クロックの線の形が SPI・I2C の主張の対抗になり、差が負で ambiguous になった（読めた 42）。そこで
2 段にした: 形を入れた最良の組で「形が取る線」を決め（SPI のクロックは、線を多く説明するバスが先に取るので形にならない）、
残りの線の読みだけで主張と差を作る（形は対抗にならない）。
