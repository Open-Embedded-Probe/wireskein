# 追加データの依頼（2026-11-16）

判定の見直し（[2026-11-16-detection-review.ja.md](2026-11-16-detection-review.ja.md)）で、今のデータでは測れない
ことが分かったものの一覧です。別のセッションで作ってもらうための依頼書として書きます。優先度の高い順です。

## 0. どのデータにも共通の決まり

- **正解は WireSkein の外から取る。** ファームウェアの側の記録（EmbedBench の `capture/` の `CaptureWire` /
  `CaptureSPI` / `CaptureSerial` / `CaptureLines`、テストのスケッチの出力）、確立した別の道具（ch32rv の読み出しの
  結果、sigrok の復号器、wch-protocols の参照の復号器）、送った内容が分かっているもの（書き込んだファイル）。
  WireSkein の復号を正解にしない（`eval/README.md`）。EmbedBenchDeviceData の `c0001.i2c.json` も WireSkein の復号。
- **取り込みは、プローブで取れる最速で取る**（ESP32-P4 の OEP プローブで 160 MS/s）。遅い取り込みは、測定台で
  間引いて作れる（`decimate:K`）。逆はできない。間引きは同じ回の同じ信号なので、正解をそのまま使える。
- **同じ回の記録と正解を組にする**（別の回の記録は、状態の読み出しの値などが回ごとに違い、正確な正解の代わりに
  ならない: V203 の 100 / 160 MS/s の書き込みは、アクセスの数は同じでも中身の一致は 0.83）。
- **形式**: `wireskein-run/1`（run.json ＋ キャプチャ ＋ 目印のログ）。チャンネルの名前は役割が分かるもの
  （SCL、SDA、SWCLK、SWDIO、MOSI ...）。測定台は読むときに D0、D1 ... に付け替えて隠す。
- **確認用（holdout）を、作った時点で取り分ける。** ケースの名前のハッシュで半分を確認用にし、中身を見ない。
  今の確認用（`real-i2c`）は、何度も結果を見たので価値が下がっている。
- **読めないはずの条件も、外さずに残す**（測定台がラベルを付けて別に数える）。読めない記録で「自信を持って誤る」か
  どうかを測るのに必要。

## 1. RVSWD / SWIO を 160 MS/s で、同じ回を間引く前提で（最優先）

- **なぜ**: V203 の速い転送のクロックは、High が約 20 ns（Low 約 75 ns、周期約 100 ns）。50 MS/s では High が 1 サンプル
  になり、本物のクロックがひげに見える。50 MS/s の WireSkein は DMI のアクセスの約半分を取りこぼし（4184 対 8808）、
  wch-protocols の参照の復号器も V203 はほとんど読めていない（`.dmi.txt` の読めないフレームが最大 884 行）。100 / 160 MS/s
  では、同じ操作でアクセスの数が一致する（8808）。
- **何を**: V203、L103（RVSWD）、V003（SWIO）。可能なら V103（長い形式）と H417 も。操作は wch-protocols の fixture と同じ
  12 種（`target_info`、`read_ram_256`、`read_flash_4k`、`flash_pattern4k`、`verify_pattern4k`、`dbg_halt`、`dbg_regs`、
  `dbg_step`、`dbg_resume`、`reset`、`erase_all`、`flash_sketch`）と、`extra/` の LinkE の速度 low / medium / high の 3 種。
- **取り方**: 160 MS/s、LinkE 側で分岐（fixture と同じ。target 側の分岐は LinkE が target を見失う）。ch32rv の
  `--capture <op>.ndjson`（USB の往復）と、コマンドの出力（`<op>.json`）、読み出しの結果（`read_*.bin`）を一緒に。
- **正解**: ch32rv の読み出しの結果と、書いた pattern（`pattern-4k.bin`）から、DMI の読み書きの値を照合する。160 MS/s の
  WireSkein の復号を、局所的なゲートなしで読み、ch32rv の結果と矛盾がないことを確かめてから、その DMI の列を「同じ回の
  間引き」の正解に使う（間引いた記録の採点用。160 MS/s 自体の採点には使わない）。
- **測定台での使い方**: `wchfix:` と同じ形の元を足し、`decimate:2,4,8,16`（160 → 80 → 40 → 20 → 10 MS/s）のスイート。
  「どの速さまで DMI が読めるか」を、エンジンの改良と取り込みの推奨値の両方に使う。

## 2. 実機の I2C を、ファームウェアの側の全部の取引と一緒に、速く

- **なぜ**: EmbedBenchDeviceData の 35 本で、正しいプルアップの普通の I2C が得られ、NACK の多い使い方で本命が確定
  できないことが分かった（27 / 35 → 試行で 34 / 35）。ただし (a) 取り込みが 2 MS/s だけ（400 kHz は 1 周期 5 サンプル）、
  (b) 正解がファームウェアの出力の一部（読んだバイト、戻り値）だけで、取引の全部の一覧がない。
- **何を**: EmbedBenchDeviceData の同じケース（`sht30-modes`、`sht30-ready`、`qmp6988-modes`、`wire-scan`、
  `wire-absent-address`、`esp32p4-i2c-nack-answers`、`sht30-stretch-wait` ...）を、
  - 取り込み 20 / 50 MS/s（間引けば 2 MS/s も作れる）
  - I2C の速さ 100 kHz / 400 kHz / 1 MHz
  - **EmbedBench の `CaptureWire` を有効にして**、ファームウェアの側から全部の取引（アドレス、読み書き、バイト、
    ACK / NACK、戻り値）を同じ時計で記録する
- **あると嬉しい**: 同じバスに複数の機器（ENV ユニットに別の I2C 機器を足す）、クロックストレッチの長いもの、
  repeated start の多いもの、10 ビットアドレス。
- **測定台での使い方**: `ebdd:` の正解を「読んだバイト」から「全部の取引」に広げる（`eval/evaluate.py` の
  `expect.transactions` の形にできる）。

## 3. 弱いプルアップ・遅い立ち上がりの I2C を、プルアップの値を振って

- **なぜ**: 実機の遅い立ち上がり（h417_slow）は 1 台のボード、1 種類の取引、プルアップ 1 種類（プローブの 45 kΩ）だけ。
  合成の `odslow` がどこまで現実的かを確かめられない。
- **何を**: 同じボードと、もう 1〜2 種類のボード（X035、V205 など、`tests/data/i2c_bench` にあるもの）で、プルアップを
  1 kΩ / 4.7 kΩ / 10 kΩ / 47 kΩ（外付け）に振る。I2C 100 / 400 kHz。取り込み 160 MS/s。ACK のある取引も（今は全部 NACK）。
- **正解**: ファームウェアの側の取引（`CaptureWire`）と `endTransmission()` の戻り値。

## 4. 実機の SPI、UART、CAN を、ファームウェアの側の記録と一緒に

- **なぜ**: 今の実機の正解付きの記録は I2C と RVSWD / SWIO だけ。SPI、UART、CAN は合成だけで、点数の付け方の改善が
  これらに効くか・害がないかを実機で確かめられない。
- **SPI**: SPI フラッシュ（W25Q など）、SD カード、ディスプレイ。SPI の速さ 1 / 4 / 10 / 20 MHz、モード 0 と 3、CS あり。
  取り込み 160 MS/s。正解は `CaptureSPI` の MOSI / MISO のバイト列。
- **UART**: 9600 / 115200 / 1 Mbaud、パリティあり・なし、途中で速さを変えるもの（ブートローダーの速さの切り替え）。
  正解は `CaptureSerial` と、相手の機器の受信のログ。
- **CAN**（機材があれば）: 125 k / 500 k / 1 Mbps、トランシーバーの RX の線。正解はコントローラーの送受信のログ。

## 5. ノイズのある実機の環境

- **なぜ**: 頑張るモード（全体の前処理）は、合成の刻みのノイズでは一番効いたが、実機では効かなかった。振り分けの
  規則（観測で振り分ける）を、実機のノイズで確かめる必要がある。合成のノイズのモデル（spike、bounce、xtalk、pspike、
  pbounce）が現実的かも分からない。
- **何を**: 上の 2〜4 と同じ通信を、モーター・PWM・スイッチング電源の近く、長い配線（1〜2 m）、GND の取り方を変えて。
  ノイズの源のオン・オフの組。取り込み 160 MS/s。
- **あると嬉しい**: 同じ場所でアナログ（オシロスコープ）の波形も 1 本。ノイズの実際の形（幅、どの線に、どのタイミング）
  を合成のモデルに戻せる。

## 6. 複数のバスと、おとりの線が一緒に写っている実機の記録

- **なぜ**: 合成では、複数のバスと、おとり（PWM、連続したクロック、ランダムな線）が一緒に写っている。実機の記録は
  ほとんど 1 つのバスだけで、グループ分け（どの線とどの線が組か）と、おとりへの誤った主張を実機で測れない。
  合成で見つかった誤確定（25 MS/s で取った 12 MHz のおとりのクロックを I2C と読む）が実機で起きるかも確かめたい。
- **何を**: I2C ＋ SPI ＋ UART を同時に動かすボード、近くに PWM（LED の調光、モーターの駆動）と、水晶の出力（連続した
  クロック）。取り込みは 160 MS/s と、エイリアスが起きる遅い速さ（間引きで作れる）。

## 7. 長い記録

- **なぜ**: 速さの区間（RVSWD の接続と転送、UART の速さの切り替え）と、コスト（2 乗で遅くなる方式がないか）。
  今日の V203 の書き込みは 100 万エッジで 30〜77 秒。
- **何を**: 数秒〜数分、数百万〜数千万エッジ。RVSWD の書き込みの一連、I2C の機器の長いポーリング、UART のログ。

## 9. 作ったデータを測定台に入れる手順

1. 記録と正解を、リポジトリの外（EmbedBenchDeviceData か wch-protocols のような、データのリポジトリ）に置く。
2. `bench/wsbench/data.py` に、読み方（`ebdd:`、`wchfix:` と同じ形）を足す。正解は、その場で外の記録から作る。
   チャンネルの名前は付け替えて隠す。
3. `bench/suites.toml` に、調整用（tune）と確認用（holdout）のスイートを分けて足す。読めない条件のラベル
   （`data.hardness`）が付くかを確かめる。
4. 本命だけで一度走らせ、正解の作り方の誤り（今日の V203 の `.dmi.txt`、SWIO の参照の復号器の消失、BURST の扱い）がないかを
   確かめてから、試行と比べる。
