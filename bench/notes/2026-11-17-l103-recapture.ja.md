# L103 の LinkE の取り直し（2026-11-17）

[追加データの依頼](2026-11-16-data-requests.ja.md) §1 のうち、L103（RVSWD）を取り直した。データは
`bench/data/l103-linke-2026-11-17`（切り出しと正解）、生の記録は wireskein-captures。スイートは `linke-l103`、
`linke-l103-holdout`、`linke-l103-rate`、`linke-l103-rate-holdout`。

## 取ったもの

- 160 MS/s で 103 操作: LinkE の速さ high / medium / low × 14 操作と、high の追加 61 操作。撮り直しは 3 回
  （P4X の HS の USB の切断 2 回と、操作が窓から外れた 1 回）、取れなかった操作はない。
- 取り込みの速さを振った組: 4 操作 × 26 種（160 MHz〜627 kHz、整数分周 15、分数分周 11）。撮り直しなし。
  測定台には 6 種（160、133.3、50、10、8、5 MHz）の 24 本だけ入れ、ほかは生の記録の側にだけ置く。
- 収録の後、L103 の flash とオプションバイトを収録の前と同じに戻した（読み戻して一致）。

## 正解と 160 MS/s の読み

- ch32rv の DmiOp（USB の往復のうち `81 08 06`、1 つが線上の DMI の 1 フレーム）は、207 本すべてで 160 MS/s の
  WireSkein の読みの中に順に全部見つかった。
- 読み出しの中身（`read.bin`）との一致は、ほぼすべて 1.000。**例外は LinkE の速さ low（クロックの周期 2.1 µs）の
  長い読み出しと、133.3 MHz の取り込みの low の読み出し**: 自動実行の連続読み出し（BURST、15 回）が 1 塊まるごと
  読みから消える（`low/read_flash_4k` 0.985、`low/read_pattern4k` 0.81、`rate/133p333M/low_read_ram_256` 0.77）。
  その区間の線には、隣の正常な塊と同じだけクロックの縁がある（SWCLK 1186 対 1188）。復号器はそこをフレームとしても、
  読めなかった縁（`uninterpreted`）としても出していない。黙って落としている。medium / high では起きない。
  → 製品の不具合。測定台で直し方を比べてから入れる（読みの質の段の最初の題材）。
- 接続の遅い区間の 85 クロックのフレーム（どの操作も 202 個）は「応答なし」として数えられる。前回の fixture から
  未解読のまま。

## 取り込みの速さ（`rate/`、4 操作）

| 速さ | 読み |
|---|---|
| 160〜10 MHz | ch32rv の DmiOp を全部読む（整数分周と分数分周で差はない） |
| 8 MHz | 読み出しの中身が抜け始める（`read_flash_4k` 0.49） |
| 5 MHz 以下 | high の速いクロック（周期 425 ns、High 約 167 ns）が読めない |

- SWDIO のリンギングとして数えられる変化の割合は、速さで大きく変わる: 160 MHz で 0.16〜0.25、80 MHz 前後で最大
  （0.36〜0.45）、25 MHz 前後で 0.04〜0.08。クロックのひげは 0.01 以下。
- **本物の遅い取り込みは、160 MS/s の記録を遅く取り直したもの（`resample` / `decimate`）と同じに読める**
  （150〜8 MHz で、DmiOp の割合、応答のあったフレームの数、ひげとリンギングの割合が数 % 以内で一致。
  `tools/rate_compare.py`）。分数分周は、160 MHz の刻みの上に不揃いに並んだサンプルとして作れば合う。4 MHz 以下は
  どちらもほとんど読めず、残った数件の当たり外れで値がぶれる。
  → 遅い取り込みは 160 MS/s から作ってよい。`linke-l103` は 160 MS/s の記録を 133.3 / 50 MHz（分数分周）と
  80〜5 MHz（整数分周）に取り直して使う。

## 取り込みの環境

- P4X の HS の USB（3-4）が 2 回切れて再列挙した（07:07:05、07:47:59）。2 回とも、LinkE が L103 に強めの操作
  （64 KiB の読み出し、違う SKU での接続）をしている間。プローブは再起動しておらず（boot_id が同じ、[oep] が確認）、
  LinkE と P4X の間は SWD の 2 本と GND だけ（電源はつながっていない、ユーザーが確認）。原因は未定（GND の揺れ、
  ホストやハブの側）。[oep] が LinkE を動かさない流し続けで切り分ける。
- 切れた直後は ModemManager が新しい CDC を 15〜20 秒探るため、その間の取り込みは遅く、欠ける。`capture.py` は
  切れたら 25 秒待ってから撮り直す。
- 取り込みの開始から最初のサンプルまで 0.8〜2.1 秒ばらつく（リンクを開く、configure、start）。3 秒待ってから
  操作し、取り込みの時計の記録で窓に収まったかを確かめる。

## 最初の Actions の実行（20261117T005331Z-42ad7b1-gh43991262660）

- 2 時間 30 分かかった。20 の分割のうち 14 は 12〜31 分、6 は 123〜149 分。遅い 6 はどれも
  `high/x_read_flash_64k`（64 KiB の読み出し）を間引いたもの（decimate:2 / 4 / 16 / 20 / 32、resample:50M）を 1 本ずつ
  持っていた。その 1 本が 113〜135 分。
- 遅かったのは線の組を多く試す試行: `combo.clear_gated`、`combo.clear_gated_select`、`refit.uart_combo_select` が
  1 本 30〜43 分、`inject.gated`、`select.w4_sparse_gated` が 5〜7 分。本命とほかの試行は 1 分以内。160 MS/s のままと
  decimate:8、resample:133M では、どれも 1 分程度。
- 原因は製品の I2C の入力の見え方（`timing.i2c_input`）: 間引いてリンギングの増えたデータ線（変化 180 万）を I2C の SDA
  として試すと、START らしい変化が何十万もでき、`i2c_restore` が START ごとに SCL の縁を全部なめていた（2 乗）。
  `local_period` の np.percentile も重かった。線の組を多く試す試行ほど、この見え方を何度も作る。
  → 製品で直した（`bf99aa7`、結果はビットまで同じ）: 見え方 1 回が 20〜42 秒から 6 秒。
- 長い取り込みの解析は、メモリも GB 単位で使う（このケースの解析 1 回で 6.4 GB、仮想 24 GB。手元の N100 では
  ほかの処理と重なって OOM になった）。→ 製品の課題: 長い取り込みでのメモリの使い方。手元では回さず Actions で測る。
- 分割の配り方（ケースを順に配る）は変えない: 台帳の時間（データセットごとの中央値）×ケースの大きさで見積もって
  重い順に配る案を、この実行の実際の時間で比べると、一番遅い分割が 223 分から 303 分に延びた（中央値では極端な
  1 本を見積もれない）。全体の時間は極端に重い 1 本で決まるので、その 1 本を速くする。

## 2 回目の Actions の実行（20261117T051644Z-d4984ee-gh44022950674、`bf99aa7` の後）

- e2e の点数は前回とすべて同じ（速くした直しは結果を変えない）。本命（current、wireskein）はどの段も同じ。
- 前回と値が違ったのは試行の 3 つだけ（clean の hybrid.r2 / r3 の 34 行、lineclass の rhythm.g3ns の 1 行、どれも
  小数第 4〜5 位）。原因は bench の `kit.comb_unit` の `np.argsort(cnt)[::-1]`: 同じ回数の候補の並びが CPU で変わる
  （numpy 2 の argsort は AVX-512 の CPU で x86-simd-sort を使う。Actions のランナーは AMD EPYC と Intel Xeon が
  混ざる）。→ `np.argsort(-cnt, kind="stable")` にした（回数が同じなら短い間隔から）。どの CPU でも同じになる。
- 遅い分割は残った: 前回の 6 つが 88〜160 分（前回 123〜149 分）、ほかは 10〜32 分。I2C の入力の見え方の 2 か所の
  ほかにも、線の組を多く試す試行に重い所がある。明細で方式ごとの時間を見て、次に直す所を決める。
