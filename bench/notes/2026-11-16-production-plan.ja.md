## 1. 線どうしの関係を、クロックの周期でゲートして測る（最初に入れる）

- **何を**: `survey.pair_relation` を、クロックごとに「T/4 より近い変化を 1 つにまとめた見え方」の上で測る（T はその
  クロックの周期）。元のエッジは消さない（見え方は関係を測るときだけ）。
- **元のコード**: `bench/algos/grouping/gated.py` の `collapse`、`_view`、`engine`（差し込みの形。`w=4`）。
- **入れる場所**: `src/wireskein/_engine/survey.py` の `survey()`（今は `methods.get("pair_relation", pair_relation)` で
  呼んでいる所）。クロックごとに見え方を 1 回作り、そのクロックの全部の相手に使う。
- **根拠**（Actions の実行 20261116T094947Z、e2e の `inject.gated`）:

  | | 本命 | gated |
  | --- | --- | --- |
  | noise の誤確定 | 41 | **19** |
  | noise の ok | 0.602 | 0.640 |
  | rate の ok | 0.819 | 0.839 |
  | 確認用（real、real-i2c） | | 変わらず |
  | 誤有力（noise / rate） | 55 / 24 | 61 / 29（少し増える） |

- **懸念**: コストを測っていない（見え方を作るのは、線の数 × エッジ数）。誤有力が少し増える。周期の 1/4 という幅は、
  合成のデータで決めた（w8 も試し、ほぼ同じ）。
- **やらないこと**: 全体の前処理として線そのものを書き換えること（実機の I2C の、切り詰められた本物のクロックを消す）。

## 2. I2C の点数を、証拠で数える

- **何を**: I2C の点数（`declarative.frame_score` の I2C の場合）を次の形にする。
  - 長さの規則（9n＋1）に合った取引の割合を、偶然（規則の確率 2/9）を超えた分にする: `(fit − 2/9) / (1 − 2/9)`
  - 量の項を、語の数ではなく、取引の数 n と合った数 k から: `1 − P(Binomial(n, 0.5) ≥ k)`
  - ACK / NACK を検査から外す（どちらも I2C の正しい動作）
  - クロックらしさと相関の掛け方を弱める: `(0.75 + 0.25 × x)`
  - 証拠の項を掛ける: **START / STOP が SCL の変化から、その辺りの SCL の半周期の 15% 以上離れている割合**、
    **STOP から次の START まで SCL が動かない（2 変化まで）割合**、**取引の中の SCL が 5 MHz（UM10204 の上限）を
    超えたら 0**
- **元のコード**: `bench/algos/e2e/score.py` の `_tail`、`clearance`、`bus_free`、`scl_hz`、`_binomial`（取り込む候補は
  `_binomial(0.5, 0.25, clear=True, free=True, above_chance=2/9, max_hz=True)`、試行の名前 `binomial.rule_clear_free_hz`）。
- **入れる場所の案**: `src/wireskein/decl/i2c.toml` の `[score]` に数え方と項の名前を書き（例:
  `count = "binomial"`、`above = "rule"`、`check_weight = 0`、`soft = 0.25`、
  `terms = ["startstop_clearance", "bus_free", "max_clock_hz"]`、`max_clock_hz = 5e6`）、`declarative.py` の
  `frame_score` が、項を名前でコアの関数として呼ぶ（今の `select_boundary` や `degenerate` と同じ形。定義に式は書かない:
  `docs/design.md` 3.2 節）。ほかの方式（SPI、SWD、CAN、RVSWD）の点数は変えない。
- **根拠**:

  | | 本命 | 新しい点数（＋ gated の combo） |
  | --- | --- | --- |
  | 実機 I2C、弱いプルアップ（real-i2c、壊れていない 31 本）の確定 | 0 | **30**（combo） |
  | 実機 I2C、EmbedBenchDeviceData（real-ebdd、35 本）の確定 | 27 | **34** |
  | 合成 nack の確定（読めるはずのバス） | 0.438 | 0.738 |
  | 復号（前から見つけていたバス） | | 変わらず |
  | 誤確定 | | rate で +1（エイリアスのおとりのクロック: 2.5 節） |

- **懸念**:
  - エイリアスの誤確定 1 件（サンプルからは区別できない。取り込みの速さ不足として L7 で扱う: 4 節）
  - 壊れた取り込み（プローブのフィルタが固まった実機）で、読めていないのに確定するものが 4 本（L7 で扱う）
  - stress の読みにくいバス（freqhop の速いフレーム）で、確定が少し下がる（0.689 → 0.533〜0.644）
  - 二項分布の裾の計算は、取引の数に比例する。取引が数万の記録でのコストを確かめる

## 4. 読みの質（L7）を判定に入れる（設計から）

- **なぜ**: 識別（どのプロトコルか）が正しくても、中身が読めていない記録を「確定」とするのは誤解を招く（壊れた実機の
  記録の確定 4 本）。サンプルからは区別できない誤り（エイリアス）も、「取り込みが遅すぎる」と言えれば防げる。
- **分かっていること**: キャプチャ全体の観測（ノイズの量、細かさ）では、読めないバスを当てられない（精度 0.3、
  再現率 0.5〜0.8）。**バスごとの読みの検査**が要る: パリティ・CRC・ACK の位置などプロトコルの不変条件が破れている割合、
  `reading.stopped` / `oscillating`（既にある）、クロックの半周期のサンプル数（既に警告がある）。
- **案**: これらを判定の上限にする（例: 不変条件の破れが一定以上なら確定にしない、取り込みが遅すぎるなら有力まで）。
  `methods` の `verdict` は今 `(total, margin)` しか受け取らないので、主張（Node）を渡す形に広げてから試す。
- **測定台で先にやること**: e2e の明細の `claim_list` に、バスごとの読みの検査の値を足し、`calibrate.py` で上限の効果を
  測る。

## 5. 入れないもの（今は）

| もの | 理由 |
| --- | --- |
| 線の分類（`rhythm`） | 段の指標では大きく改善（0.85 → 0.92）、確認用の実機でも改善したが、解析全体には効かない（ok 0.602 → 0.601）。L0 / L1 の部品として、区間分けと一緒に考える |
| 全体の前処理（deglitch、hybrid） | 実機の I2C の復号を悪くし、遅い取り込みで本物を削る。合成の刻みのノイズでは一番効くので、「観測で振り分ける頑張るモード」の候補として、実機のノイズのデータ（`2026-11-16-data-requests.ja.md` 5 節）で確かめてから |
| 速さの区間（局所的なゲート） | UART はひげから守れる（0.606 → 0.899）が、クロックは物理的に限界（半周期 4 サンプル未満）。160 MS/s の RVSWD の記録（依頼の 1 節）が来てから |
| 振り分け（観測で頑張るモードを選ぶ） | 合成では一番安定したが、根拠が合成の刻みのノイズに偏る。実機のノイズのデータが来てから |

## 6. 見つかった、別に直すべき点

- **UART の誤有力**: 実機の I2C の線（プローブのフィルタで壊れた記録）を UART と読み、有力にする（real-i2c で 8〜10 件）。
  どの方式でも残る。UART の点数（`staged.UartPlugin`）にはまだ差し込み口がない。差し込み口を作って、試行（例: ゲートした
  関係で、同期のクロックと強く組む線への UART の主張を下げる、文字の種類の偏り）を測る。
- **eval の固定のコーパスの WCH の正解**: `eval/corpus/real/wch-l103-*` の正解は wch-protocols の `dmi_decode.py` から
  作られていて、読み書きの区別が一部誤っている（番地と値は正しい）。eval の L103 の復号の数字は、そのぶん低く出ている。
  `expect.dmi_ignore_op` を付けて作り直す（`eval/convert_real.py`）。V203 の `.dmi.txt` は参照の復号器が読めておらず
  （V203 の SWCLK の High は約 20 ns で、50 MS/s では 1 サンプル）、正解に使えない。
- **SWIO の参照の復号器**（wch-protocols の `captures/tools/swio.py`）が消えている。eval の V003 の正解を作り直すには、
  別の参照が要る。
- **`staged.verdict` の閾値**は手で決めた値（0.85 / 0.15、0.6 / 0.05）。3 節の較正で置き換える。
- **設計の文書の 3.1 節**「クロックのある方式は速度の変化で分割しない」: RVSWD の V203 では、速さの区間を取れないと
  DMI の半分を取りこぼす（50 MS/s）。分割しない方針は正しいが、取り込みの速さが足りないことを判定と報告に出す
  （4 節）。
