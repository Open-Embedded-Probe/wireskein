## 0. 進め方の決まり

- **1 つずつ、別のコミット（別の PR）で入れる。** 入れる前と後を、測定台で同じスイートで測る。
- **入れたら、測定台の本命（`bench/algos/<段>/current.py`、e2e の `wireskein`）がその動作になる。** 試行のファイルは
  `retired`（reason: 取り込んだ版）にする（`bench/README.ja.md` 1.5 節）。
- **確認すること**（どの手順でも）:
  1. テスト全体（`uv run pytest -q tests`）
  2. eval（`cd eval && uv run python evaluate.py --set heldout`、`--set tuning`、ストレスのセット）で悪くならない
  3. 測定台を Actions で: stages `e2e`、suites は既定の `all`、algos 空。**誤確定が増えない**（`false_confirmed`。
     種類別の `false_confirmed_protocol` / `_roles` / `_params`、エイリアスの `false_confirmed_aliased` も見る）、
     確認用（real-i2c、real-ebdd、real）で悪くならない。WCH の記録（`wch-fixture`、`wch-ladder`）で読み（decode）が
     下がらない
  4. コスト: N100 で `cost` スイート（`bench/README.ja.md` 1.9 節）。本命比と規模に対する伸び
- 製品の文書（`docs/design.md` 3.3 節の判定、`docs/protocols.md` の点数、CHANGELOG）を、日英で合わせて直す。

## 1. 線どうしの関係を、クロックの周期でゲートして測る（最初に入れる）

- **何を**: `survey.pair_relation` を、クロックごとに「T/4 より近い変化を 1 つにまとめた見え方」の上で測る（T はその
  クロックの周期）。元のエッジは消さない（見え方は関係を測るときだけ）。
- **元のコード**: `bench/algos/grouping/gated.py` の `collapse`、`_view`、`engine`（差し込みの形。`w=4`）。
- **入れる場所**: `src/wireskein/_engine/survey.py` の `survey()`（今は `methods.get("pair_relation", pair_relation)` で
  呼んでいる所）。クロックごとに見え方を 1 回作り、そのクロックの全部の相手に使う。
- **根拠**（Actions の実行 20261116T094947Z、e2e の `inject.gated`）:

  | | 本命 | gated |
  | --- | --- | --- |
  | noise の誤確定 | 41 | **19** |
  | noise の ok | 0.602 | 0.640 |
  | rate の ok | 0.819 | 0.839 |
  | 確認用（real、real-i2c） | | 変わらず |
  | 誤有力（noise / rate） | 55 / 24 | 61 / 29（少し増える） |

- **懸念**: コストを測っていない（見え方を作るのは、線の数 × エッジ数）。誤有力が少し増える。周期の 1/4 という幅は、
  合成のデータで決めた（w8 も試し、ほぼ同じ）。
- **やらないこと**: 全体の前処理として線そのものを書き換えること（実機の I2C の、切り詰められた本物のクロックを消す）。
- **3 節（CS）と同じ見え方を使う**ので、続けて入れるとよい。

## 2. I2C の点数を、証拠で数える

- **何を**: I2C の点数（`declarative.frame_score` の I2C の場合）を次の形にする。
  - 長さの規則（9n＋1）に合った取引の割合を、偶然（規則の確率 2/9）を超えた分にする: `(fit − 2/9) / (1 − 2/9)`
  - 量の項を、語の数ではなく、取引の数 n と合った数 k から: `1 − P(Binomial(n, 0.5) ≥ k)`
  - ACK / NACK を検査から外す（どちらも I2C の正しい動作）
  - クロックらしさと相関の掛け方を弱める: `(0.75 + 0.25 × x)`
  - 証拠の項を掛ける: **START / STOP が SCL の変化から、その辺りの SCL の半周期の 15% 以上離れている割合**、
    **STOP から次の START まで SCL が動かない（2 変化まで）割合**、**取引の中の SCL が 5 MHz（UM10204 の上限）を
    超えたら 0**
- **元のコード**: `bench/algos/e2e/score.py` の `_tail`、`clearance`、`bus_free`、`scl_hz`、`_binomial`（取り込む候補は
  `_binomial(0.5, 0.25, clear=True, free=True, above_chance=2/9, max_hz=True)`、試行の名前 `binomial.rule_clear_free_hz`）。
- **入れる場所の案**: `src/wireskein/decl/i2c.toml` の `[score]` に数え方と項の名前を書き（例:
  `count = "binomial"`、`above = "rule"`、`check_weight = 0`、`soft = 0.25`、
  `terms = ["startstop_clearance", "bus_free", "max_clock_hz"]`、`max_clock_hz = 5e6`）、`declarative.py` の
  `frame_score` が、項を名前でコアの関数として呼ぶ（今の `select_boundary` や `degenerate` と同じ形。定義に式は書かない:
  `docs/design.md` 3.2 節）。ほかの方式（SPI、SWD、CAN、RVSWD）の点数は変えない。
- **根拠**:

  | | 本命 | 新しい点数（＋ gated の combo） |
  | --- | --- | --- |
  | 実機 I2C、弱いプルアップ（real-i2c、壊れていない 31 本）の確定 | 0 | **30**（combo） |
  | 実機 I2C、EmbedBenchDeviceData（real-ebdd、35 本）の確定 | 27 | **34** |
  | 合成 nack の確定（読めるはずのバス） | 0.438 | 0.738 |
  | 復号（前から見つけていたバス） | | 変わらず |
  | 誤確定 | | rate で +1（エイリアスのおとりのクロック: 2.5 節） |

- **懸念**:
  - エイリアスの誤確定 1 件（サンプルからは区別できない。取り込みの速さ不足として L7 で扱う: 6 節）
  - 壊れた取り込み（プローブのフィルタが固まった実機）で、読めていないのに確定するものが 4 本（L7 で扱う）
  - stress の読みにくいバス（freqhop の速いフレーム）で、確定が少し下がる（0.689 → 0.533〜0.644）
  - 二項分布の裾の計算は、取引の数に比例する。取引が数万の記録でのコストを確かめる

## 3. 選択線（CS）を、クロックの周期でゲートして読む

- **なぜ**: 今の製品の誤確定の 8 割（49 件中 40 件）は、SPI をクロック・データ線・モード・バイトまで正しく読み、
  **CS の線だけを付け損ねた**もの（CS の線のひげ: 合成のスパイク、クロストーク）。
- **何を**（2 か所）:
  1. `taxonomy.pin_classes` の sparse（CS の候補）を、生のエッジの数ではなく、一番速いクロックの周期の 1/4 より近い
     変化を 1 つにまとめた数で決める（曲線は今と同じ。値が大きくなるときだけ置き換える）。
  2. CS で区切った枠（`typed.frames_select`）を、CS の線をそのバスのクロックの周期の 1/4 でゲートしてから切る
     （元のエッジは消さない。枠を切るときの見え方だけ）。
- **元のコード**: `bench/algos/lineclass/gated_sparse.py`（`classes`）、`bench/algos/grouping/gated_select.py`
  （`select_frames`）。製品の差し込み口は `pin_classes` と `select_frames`（`staged.py` の 2 か所）。
- **根拠**（実行 20261116T115616Z）: combo の上で誤確定 24 → 8（CS の付け損ね 17 → 1）、ok 0.764 → 0.768、
  確定 3630 → 3647。本命の上だけでも（`select.w4_sparse_gated`）誤確定 49 → 7。確認用は変わらない。
- **懸念**: 根拠は合成の刻みのノイズだけ。実機の CS のノイズの記録がない（[追加データの依頼](2026-11-16-data-requests.ja.md)
  の 4 節）。コスト未計測（線ごとのまとめ直しは線の数 × エッジ数）。

## 4. UART の速さを、読めた文字ごとに当てはめ直す

- **なぜ**: 残りの誤確定の多く（本命 8 件、combo ＋ CS で 5 件）は、UART のバイトを正しく読んだうえで、報告した
  速さが 3.6〜4.8% ずれたもの（eval の許容は 3%）。1 ビットの長さを、連続（run）の長さの最小二乗
  （`features.estimate_units`）で決めているため、ひげや跳ね返りで run が割れると偏る。
- **何を**: `staged.UartPlugin` で文字を読んだあと、読めた文字ごとに、文字の中のエッジを「開始のずれ ＋ k × 1 ビット」
  で当てはめ、全部の文字で 1 ビットの長さを求め直す（ビットの格子から 0.3 ビット以上ずれたエッジは除く。2 回）。
  **求め直した長さで文字を読み直し**、報告する速さもそれにする。
- **元のコード**: `bench/algos/e2e/refit.py` の `refit_unit`（測定台では、解析のあとに報告する速さだけを直している）。
- **根拠**: 誤確定の 8 件で、誤差が 0.2% 以内に戻った（ノイズのない記録は変わらない）。スイート全体は実行 `refit-uart`。
- **懸念**: 速さの区間が複数ある UART（baudhop）では、区間ごとに当てはめる。読み直しで文字の数が変わると点数も
  変わるので、解析全体で測り直す。

## 6. 読みの質（L7）を判定に入れる（設計から）

- **なぜ**: 識別（どのプロトコルか）が正しくても、中身が読めていない記録を「確定」とするのは誤解を招く（壊れた実機の
  記録の確定 4 本。**実機の RVSWD の L103 を 6.25 MS/s に間引くと、読み出しが 2〜6% しか合っていないのに 10 本中
  8 本が確定**: レビューの 2.8 節）。サンプルからは区別できない誤り（エイリアス）も、「取り込みが遅すぎる」と言えれば防げる。
- **分かっていること**: キャプチャ全体の観測（ノイズの量、細かさ）では、読めないバスを当てられない（精度 0.3、
  再現率 0.5〜0.8）。**バスごとの読みの検査**が要る: パリティ・CRC・ACK の位置などプロトコルの不変条件が破れている割合、
  `reading.stopped` / `oscillating`（既にある）、クロックの半周期のサンプル数（既に警告がある）。
- **案**: これらを判定の上限にする（例: 不変条件の破れが一定以上なら確定にしない、取り込みが遅すぎるなら有力まで）。
  `methods` の `verdict` は今 `(total, margin)` しか受け取らないので、主張（Node）を渡す形に広げてから試す。
- **測定台で先にやること**: e2e の明細の `claim_list` に、バスごとの読みの検査の値を足し、`calibrate.py` で上限の効果を
  測る。実機の材料は `wch-ladder` の L103 の `decimate:8`（読みの正解は ch32rv の内容）と、`real-i2c` の壊れた記録。

## 8. 見つかった、別に直すべき点

- **UART の誤有力**: 実機の I2C の線（プローブのフィルタで壊れた記録）を UART と読み、有力にする（real-i2c で 8〜10 件）。
  どの方式でも残る。UART の点数（`staged.UartPlugin`）にはまだ差し込み口がない。差し込み口を作って、試行（例: ゲートした
  関係で、同期のクロックと強く組む線への UART の主張を下げる、文字の種類の偏り）を測る。
- **eval の固定のコーパスの WCH の正解**: `eval/corpus/real/wch-l103-*` の正解は wch-protocols の `dmi_decode.py` から
  作られていて、(1) 読み書きの区別が一部誤っている（番地と値は正しい）、(2) **連続の読み出しを数え落とす**（1024 語の
  読み出しを 104 件と出す。WireSkein の正しい読みが 0.487 になった）。eval の L103 の復号の数字は、そのぶん低く
  出ている。作り直すとき（`eval/convert_real.py`）は、`expect.dmi_ignore_op` を付け、読み出しの操作には ch32rv が
  読んだ内容（`<op>.bin`）を `expect.read_bytes` に入れる（eval は既に対応: data0 の読み出しの中に、その語が順に
  見つかる割合）。V203 の `.dmi.txt` は参照の復号器が読めておらず（V203 の書き込みの SWCLK の High は約 20 ns で、
  50 MS/s では 1 サンプル）、DMI の列の正解には使えない（読み出しの操作は `.bin` で測れる）。
- **SWIO の参照の復号器**（wch-protocols の `captures/tools/swio.py`）が消えている。V003 の読み出しの操作は `.bin` で
  測れる（測定台では済み）。ほかの操作の正解には、別の参照が要る。
- **`staged.verdict` の閾値**は手で決めた値（0.85 / 0.15、0.6 / 0.05）。較正では動かす根拠がなかった（5 節）。
- **設計の文書の 3.1 節**「クロックのある方式は速度の変化で分割しない」: RVSWD の V203 では、速さの区間を取れないと
  書き込みの DMI の半分を取りこぼす（50 MS/s）。分割しない方針は正しいが、取り込みの速さが足りないことを判定と報告に
  出す（6 節）。

## 9. 作業の順序の案

1. 1 節（関係のゲート）と 3 節（CS のゲート）。同じ「クロックの周期でゲートした見え方」なので続けて。コストを N100 で

3. 4 節（UART の速さ）。小さく独立しているので、いつでも。
4. 8 節の eval の正解の作り直し（WCH: `dmi_ignore_op` と `read_bytes`）。数字の比較の土台なので、早めに。
5. 5 節の較正を、1〜4 が入った状態でやり直す（閾値を変える根拠が出るかを見るだけ）。
6. 6 節（L7）と、8 節の UART の誤有力。設計から。
