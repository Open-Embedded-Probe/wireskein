# 判定エンジンの境目（2026-11-22、案）

判定のエンジンを丸ごと入れ替えられるように、前後のインターフェースだけを固め、その間（層、見方、点数、拡張の仕方）は
エンジン次第にする。今後も大掛かりな入れ替えや、プロトコルを絞った軽いエンジンを置くことを考え、固める範囲は狭くする。

## 決めたこと（ユーザー、2026-11-22）

- 固める範囲は狭く。出口は「必須を少なく、推奨を厚く」の段に分ける（必須 / 推奨 / 任意）。どの鍵をどの段にするかは、
  下の案をもとに検討する。
- 定義ファイル（TOML のプロトコル、機器パック、マーカーの方言）は、エンジンの側に属するかもしれないので、まだ何も絞らない
  （v1 の約束にするか、エンジンごとのものにするかを含めて未定）。

## 入口

| 段 | 内容 |
|---|---|
| 必須 | 変化で持つ見方: `rate_hz`、`n_samples`、`channels`（`name`、`initial`、`edges`、`step`、`level_at`）。エンジンはこれ以外に触れない |
| 必須 | `hints.protocols`（試すプロトコルの限定） |
| 推奨 | `hints.pins`（ピンの役割、速さ）、`hints.exclude_pins`。知らないエンジンは無視してよい |
| 任意 | `analog`、`hints.devices`（機器パック） |
| 必須 | 役割がわかっているときの `spec`（バス、ピン、パラメーター） |

## 出口（wireskein-analysis/1）

| 段 | 鍵 |
|---|---|
| 必須 | `claims[]` の `protocol`、`roles`、`verdict`、`score`（0〜1） |
| 必須 | 読むと申告したプロトコルの `result` の層の形（UART の bytes / chars、SPI の transfers、I2C の transactions など）。自前のプロトコルと試験の照合がこれを読む |
| 必須 | 役割を指定したときの `buses[]` の `decoded`、`result` |
| 推奨 | `margin`、`params`（速さ、モードなど）、`fit`、`uninterpreted`、`runner_up` |
| 任意 | `evidence`、`layers`（すべて出す形）、`relations`、`devices`、エンジン独自の鍵 |

- 読む側は、知らない鍵を無視する（今の文書の §5 のとおり）。推奨の鍵がないときの扱いを、読む側の各所（verify、annotate、
  ビューア）で決めておく。
- `score` の尺度の意味（どこから確定か）は、エンジンごと。verdict が共通の言葉。

## エンジンの自己申告

- 名前、版、読めるプロトコルの一覧（各プロトコルの役割の名前）。hints と名前の予約、エンジンの選択に使う。
- 軽いエンジンは、少なく申告するだけでよい。

## エンジンに依らない拡張点

自前のプロトコル（出口のバスを読む）、検査（入口の見方を読む）、ファイル形式、取り込み元。

## エンジン次第のもの

- 中の層の作り（survey、グループ、見方、点数）と、その定数。
- 長い記録の分割は、エンジンの外の共通の枠で行い、各区切りでエンジンを呼ぶ（区切りでの役割の受け渡しは、出口の
  `claims[]` の `roles` と `params` だけを使う）。
- 定義ファイル: エンジンの側に属するかもしれない。まだ何も絞らない（上）。

   今のエンジンを境目の後ろに置く。56 の記録と広い組で、バイトまで同じを確かめる。
