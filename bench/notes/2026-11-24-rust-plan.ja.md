# Rust への組み直しの計画（2026-11-24、案）

## 0. 前提（2026-11-24、ユーザー）

- 行き先は Rust だけで動く形。1 つのコアを、ネイティブアプリ、web（wasm）、Python（PyO3）から使う（2026-11-23-ui-directions.ja.md §11）。
- 推定から作る（いちばん試しやすい: 入力はエッジ、出力は主張。正解と台帳がベンチにそろっている）。
- **Python と一致する必要はない。同等以上であればよい。** 2026-11-18 の grand-design の「出力はバイトまで同じ」と「L5 は当面 Python」は、この計画で置き換える。
- **徐々に差し替える。Python の利用者には影響を出さない。**
  - 公開の口（`decode`、`verify`、`runlog`、`capture`、`sources`、CLI）と出力の形式は変えない。
  - 入れるのに Rust の道具は要らない（ビルド済みの wheel）。
  - 読みの変化は、今と同じく CHANGELOG に書く（ベンチで同等以上を確かめたうえで）。

## 1. 「同等以上」の決め方

ベンチの全スイート（Actions の Bench、既定の e2e / all / wireskein）で、Python のエンジンと Rust のエンジンを並べて比べる。合格の線は次のとおり。

| 指標 | 合格 |
| --- | --- |
| 誤確定（false confirmed） | 増えない（セットごとに） |
| 正しい読み（ok）、確定（confirmed） | 合計で減らない。セットごとの減りは、理由を書いて残す |
| ambiguous | 合計で増えない |
| 時間 | Python 以下（スイートの合計と、いちばん長い記録） |
| メモリ | Python 以下 |
| 長い記録（分割読み） | 同じ記録を最後まで読める |

一致は見ない。差の出た記録は、どちらが正しいかを正解で言える形で一覧にする（`bench/engines` のエンジン比べと同じ出力）。

## 2. 差し替えの仕組み

Rust の推定は、まず**ベンチのポートフォリオの 1 エンジン**として入れる。`bench/engines` の light_main_<protocol>（読み手の差し替え）や `*_open` と同じ並びに置く。製品の中では、部分ごとに切り替える口を `_engines` に置く。

```
decode / verify / CLI（Python の口、変えない）
        │
   _engines.main ──┬─ Python の推定（今）
                   └─ Rust の推定（wheel の中の拡張モジュール）
                        部分ごとに切り替え（プロトコルの読み手、候補、選択 …）
```

- **既定はベンチで合格した部分だけ Rust にする。** 環境変数で Python と Rust を切り替えられるようにして、比べと逃げ道に使う（例: `WIRESKEIN_ENGINE=python|rust`）。
- **合格して 1 リリースたったら、その部分の Python 版を製品から消す**（1 つの層に実装は 1 つ）。研究用の写しとして bench に残すかは、§5 で決める。
- **numpy との受け渡しはコピーなし**（エッジの配列）。主張は、分析の形式の辞書で返す（`register_engine` の `engine(view, hints)` と同じ形）。

## 3. 段階

各段は「次に移る条件」で区切る。急がない。

| 段 | すること | 次に移る条件 |
| --- | --- | --- |
| R0 下地 | 下地を作る（下の表）。製品の振る舞いは変えない | 空の Rust エンジンがベンチで回り、全 OS の wheel が作れる |
| R1 縦に 1 本 | 1 つのプロトコルを、下処理から主張まで Rust で通す。UART から（件数が多い。light_main の分解で差の大部分が読み手と分かっている。単線で候補の組が少ない）。比べるのは light_main_uart と main の UART | UART のセットで同等以上 |
| R2 読み手を足す | I2C → SPI → ほかのバス（件数の多い順）。各プロトコルは、まず読み手の差し替え（Python の候補と選択 + Rust の読み手）で比べる | プロトコルごとに同等以上。合格したものから製品の既定を Rust に |
| R3 候補と選択 | 下調べ、線の組の候補、点数、選択、regrade を Rust に（SPI の差は、候補と選択が大部分）。開いた世界（形だけの線）もここ | 全スイートで同等以上。ここで推定の全体が Rust になる |
| R4 推定の周り | 上の段（`_upper`）、書き出し（export）、照合（verify の検査）、ファイル形式（.wireskein / .sr / VCD）、分割読み（split） | 同上。Python の側は口と、標準ライブラリだけの部分（runlog、capture の保存）だけになる |
| R5 Rust だけで動く | CLI を Rust で。Python は PyO3 の薄い口になる | CLI の出力が同等以上。Python を入れずに analyze / verify が動く |
| R6 画面 | ネイティブアプリと web（wasm）を同じコアで。画面の作りは ui-directions §11.1 で並べて試す | — |

R0 の中身:

- 同じリポジトリに crate のワークスペースを置く。PyO3 + maturin、abi3（cp311）、Rust 1.88。rust-core-spike の調べと下書きの workflow を元にする。
- wheel の配布を、ch32rv と同等以上の 5 つにする（Linux x86_64 / aarch64、macOS arm64 / x86_64、Windows x86_64）。Actions で作り、入れたうえで試験する。
- ベンチの道具に Rust のエンジンを呼ぶ口を作り、e2e の engines に `rust` を足す。

R1 の前に要るもの:

- **エッジの見え方とカーネル**: 変化の列、ラン、clean、views、own_short_runs。これは L1・L2 にあたる。どの読み手も使うので、R1 の中で作る。下の層だけを先に全部移すことはしない。縦の 1 本に要る分だけ作る。

## 4. 進め方

- **探索は狙いの組だけ、整合確認は CI でまとめて**（今と同じ）。手元では、そのプロトコルのセットだけを回す。
- **Rust の試験**: crate の中に単体の試験。答え合わせはベンチで（Python の試験は口の試験として残る）。
- **プロトコルの仕様は TOML のまま使えるか**: decl/*.toml は今のエンジンの内部の表なので、Rust で読むか、Rust のコードに書き直すかは、R1 で UART を作るときに比べる。
- **リリース**: Rust の入った最初のリリースは、既定が Python のまま（環境変数で Rust を試せる）。合格した部分から既定を切り替え、CHANGELOG に読みの変化を書く。

## 5. 決めたこと（2026-11-24、ユーザー）

- **実験は Python と Rust の両方で続ける。** どちらで書いたエンジンも、ポートフォリオに並べて同じベンチで比べる。
  - 試しやすい方で書けばよい。よい構造は、製品の言語（Rust）へ写す。
  - 役目を終えたエンジンは引退させる。Python 版も Rust 版も、同じ扱いにする。
  - そのため「ベンチの Python 版エンジンを消すか残すか」は、引退の判断に含める（エンジンごとに、比べの基準として要るかで決める）。
- **wheel のない環境（32 ビットの ARM、musl など）は考えない。** 要望が来たら、wheel の対象を増やす。純 Python の逃げ道は持たない。
- **アプリはフル Rust にする。周辺も並行して Rust 化する。**
  - エンジンは育て続ける。それと並行して、周辺（ファイルの読み書き、verify、上の段、書き出し、split、decode spec、CLI など）も Rust へ移す。
  - 移すときは、Python から呼びやすい部品（`wireskein_core` の関数）として組む。Python の実装と答えを比べながら進め、落ち着いたら wheel の中身を入れ替える。
  - 動きが同じなら、組み込みにくいところは Python の実装を残してもよい。

## 6. 実験で決めること

どちらも机の上では決まらない。段の中で試作して測る。

- **web で wasm の推定はどこまで読めるか**
  - 測るもの: 記録の大きさごとの時間とメモリ。wasm32 は 4 GB まで。memory64 も試す。
  - 比べる形: ブラウザの中だけで読む / 手元のネイティブに読ませて web は表示だけ / 区切って読む。
  - いつ: R1 で UART が通ったら、同じコードを wasm にして最初に測る。R3 の後に、推定の全体で測り直す。
- **拡張の口（Rust だけの形で、外の人がどう足すか）**
  - 候補:
    - wasm のモジュール（ネイティブでも web でも同じものが動く）
    - Rust の crate（足した版を作り直す）
    - 動的ライブラリ
    - 宣言の表（機器パック・マーカーの方言）
    - Python の口を残す
  - 測るもの:
    - 書く手間
    - 速さ（呼び出しの手間）
    - 配り方
    - ライセンスの切り分け
    - 3 つの口（ネイティブ・web・Python）で同じものが動くか
  - 2026-11-24 のユーザーの見立て: エンジンの中の拡張（線そのものの上のプロトコル、`register_engine`）は要らないかもしれない。バスの上に載るものは、テキストで宣言できそう。
    - 試すこと 1: 今の Python のプロトコル（`register_protocol`）の例と、よくある上位のプロトコルを、宣言の表で書き切れるか。
      - 書く中身: フィールド、長さ、区切り、CRC やチェックサムの種類、応答の組、機器パック。
      - 書けなかったものを数える。例: 状態を持つ、分割したものを組み立てる、独自の計算。
    - 試すこと 2: 書けない残りを、逃げ道（wasm など）で持つか、WireSkein 本体に足す要望にするか。
    - 線そのものの上のプロトコルは、今の「本体に提案」の扱いで足りるか。`register_engine` を引退させてよいか。
  - いつ: R2 で、1 つの機器パックか 1 つの読み手を、候補の形それぞれで足してみる。今の Python の口（`register_engine`、機器パック、自前のプロトコル）は、R4 まではそのまま。

## 7. R0 で作ったもの（2026-11-24）

- **配り方の選択**: R0〜R2 の間、Rust は本体と別のパッケージ `wireskein-core`（`crates/wireskein-py`、import は `wireskein_core`）にする。
  - 本体の wheel は純 Python（hatchling）のまま。release.yml も変えない。Python の利用者に影響はない。
  - ベンチだけが `uv run --with ./crates/wireskein-py` で入れる。
  - 部分を既定にする時（R2 以降）に、本体の wheel に入れる（maturin へ移る）。
- **crate の構成**
  - `crates/wireskein-core`: 素の Rust。`View` / `Channel`（線の変化）と `Claim`（分析の形式）、`analyze(view, hints)`。今は主張を返さない。
  - `crates/wireskein-py`: PyO3 0.30、abi3-py311。
    - 線は int64 の配列を借りる（連続でなければ 1 回だけ写す）。
    - 主張は分析の形式の JSON で返す。
    - 計算の間は GIL を外す。
- **ベンチ**
  - `bench/engines/rust.py` を、ポートフォリオの `rust` エンジンとして置いた（e2e の `engine.rust`）。
  - bench.yml は、エンジンを回す時だけ Rust を作る（`engine*`、`rust`、`(status ...)`）。
- **CI**
  - test.yml に `rust` のジョブ: fmt、clippy、コアの試験、最低の Rust（1.88）。
  - wheels.yml（手動だけ）: 5 つのターゲットの wheel と sdist を作り、走らせられるものは入れて呼ぶ。
- **版**: Cargo の版は wireskein と同じ。`tools/prepare_release.py` が Cargo.toml と Cargo.lock も上げる。
- 手元で確かめたこと
  - `cargo test` / `clippy -D warnings` / `fmt --check` が通る。
  - Python から呼べ、誤った線を断る。
  - smoke の組で `engine.rust` が回る（主張はまだない）。

## 8. R1 の途中（2026-11-24）: UART を 1 本

`crates/wireskein-core/src/uart.rs`（`features.rs`、`kernels.rs`、`sync.rs`）。Python の読みを写すのでなく、同じ考えで書き、ベンチで比べる。

- **入れたもの**
  - アイドルの水準、ビットの長さの候補（`estimate_units`、`unit_of`、`_unfold`）
  - ストップビットでの文字の長さ、ビットに丸めた Run からの文字、ビットの長さの合わせ直し、パリティ
  - 雑音を除いた見方（スパイク、バウンス）
  - LIN と DMX512 の枠の検査（UART の点数から引く）
  - クロックに合わせて動く線（同期のデータ線）の判断
    - 位相の集まり × Burst の中の割合 × 数の確からしさ。Python の `data_score` と同じ考えを、小さく書いた。
  - 対立する読み（別のアイドル、3 % 以上違う速さ）との差、確定の規則
- **まだ入れていないもの**
  - 線の中の速さの切り替え（ブロックは 1 つ）
  - 選択線の窓（`tight_windows`）、USB の SE0、CEC
  - クロックのゲートした見方での合わせ方、バウンスを除いた対
- **途中の数字**（smoke + uartlike、本物の UART 79 本）

| | 確定 | ほぼ | 見逃し | 誤った確定 | 誤ったほぼ |
| --- | --- | --- | --- | --- | --- |
| Python | 70 | 5 | 3 | 0 | 0 |
| Rust | 68 | 6 | 4 | 0 | 6 |

  - 誤ったほぼは、SPI・I2C・DMX512 の線を UART と読んだもの。Python では、その線をほかのプロトコルの読みが取る。Rust で SPI や I2C を読むまで（R2）は残る。
  - 時間: Rust は全体で 1.3 秒。Python は全プロトコルを読んでいて 90 秒なので、そのまま比べられない。
- **進め方の気づき**
  - LIN と DMX512 の枠の検査だけで、誤った確定が 74 から 1 に減った。
  - 見方（雑音を除く）で、雑音の入った記録の確定が 48 から 71 に戻った。
  - 同期のデータ線の判断は、Python の重み（co_activity、quantity）が要った。位相だけでは、速さの近い PWM や速いクロックの横の UART を取り違えた。

## 9. wheel とリリース（2026-11-24、案）

ユーザー: 基本はリリースの時だけ。PyPI と Rust のリリースを分けるか一体か。ベンチは使う環境だけビルドして流す。

### 9.1 何を配るか（段ごと）

| 段 | 配るもの | wheel |
| --- | --- | --- |
| R0〜R2（今） | wireskein（純 Python）だけ。Rust の部分はどこも既定でない | 作らない。wheels.yml は手動の確かめだけ |
| 部分が既定になってから | wireskein と wireskein-core（Rust の wheel） | リリースの時に作る |
| R5（Rust だけで動く） | 上に加えて、CLI とネイティブアプリ（cargo のバイナリ、インストーラ）、web（wasm） | それぞれのリリースの時に |

### 9.2 分けるか一体か（候補）

- **A. 一体**: wireskein の wheel に Rust を入れる（maturin へ移る）。版は 1 つ。
  - 利点: 版のずれが起きない。入れるものが 1 つ。
  - 欠点: Python だけの直しでも、毎回 5 つのターゲットの wheel を作る。どれかのランナーが壊れると、Python の直しも出せない。
- **B. 分ける**: wireskein（純 Python、どこでも入る wheel 1 つ）は wireskein-core（Rust の wheel）に依存する。
  - 版はそれぞれが持ち、wireskein は `wireskein-core>=X,<Y` で幅を決める。
  - 利点:
    - Rust を変えた時だけ core を出す。
    - Python の直しは今のまま速く出せる。
    - R5 の CLI・ネイティブ・web も、同じ core の版を指せる。
  - 欠点: 2 つのパッケージ。組み合わせの試験（wireskein の CI は、出ている core と手元の core の両方で回す）。
- **C. 移る間は分け、Python が薄い口だけになったら一体に**（R5 の頃に A へ）。

今の作り（core は別パッケージ `crates/wireskein-py`）は B と C のどちらにもそのまま進める。どれにするかは、部分を既定にする時（R2）に、wheels.yml の実際のビルド時間と失敗の頻度を見て決める。
- 手がかりとして、ch32rv は一体（A）で回っている。
- 推定の研究は両方の言語で続ける。core の変わる頻度が高ければ B の利点が大きい。

### 9.3 いつ wheel を作るか

- **リリースの時だけ**作って出す。
  - B なら core のタグ（例 `core-v0.1.0`）で wheels.yml を走らせ、PyPI に出す。
  - A なら release.yml の中で作る。
- **ふだんの CI（test.yml）**: crate の fmt / clippy / 試験 / Rust 1.88 だけ。wheel は作らない。
- **wheels.yml の手動実行**: ビルドが壊れていないかを、リリースの前やランナーの変わり目に確かめる。

### 9.4 ベンチ

- ベンチは配った wheel を使わない。その commit の Rust を、その場でビルドして使う。比べたいのは今のコードなので。
- ビルドするのは、Rust を使う組（エンジンの組、`engine.rust`、`(status ...)`）の時だけ。
- 1 回のベンチで 1 回だけビルドする。plan のジョブで wheel を作って artifact にし、各 shard はそれを入れる（20 の shard がそれぞれビルドしない）。

## 10. wasm の最初の測り（2026-11-24、§6 の 1 つ目）

`crates/wireskein-core/examples/scale.rs` は、UART の線 2 本（8N1、1 ビット 17 サンプル、ときどき間）を中で作り、大きさを変えて解析する例。ファイルの形式を Rust で読む前なので、記録は使わない。同じものを、ネイティブと `wasm32-wasip1` で動かした。
- node は `bench/rust_wasm_scale.mjs`（WASI）で動かした。
- wasmtime は `bench/rust_wasm_scale_wasmtime.py` で動かした。

| 文字数（変化の数） | ネイティブ | wasm（wasmtime） | wasm（node 22） |
| --- | --- | --- | --- |
| 1 万（12 万） | 0.09 秒、9 MB | — | 0.20 秒、7 MB |
| 10 万（122 万） | 0.95 秒、66 MB | 1.07 秒、73 MB | node が Segmentation fault（8.5 万文字までは動く） |
| 100 万（1224 万） | 12.2 秒、530 MB | 12.4 秒、646 MB | — |

- wasm の速さは、ネイティブとほぼ同じ（wasmtime）。
- メモリは変化 1 つあたり約 45〜55 バイト。wasm32 の 4 GB なら、この形で変化 7000 万前後まで。それより大きい記録は、区切って読むか memory64 にする（まだ試していない）。
- 最初の形は、変化 1 つあたり 210 バイトで、100 万文字に 2.5 GB を使った。原因は 2 つ。
  - 文字ごとの層を JSON の値の木（`serde_json::Value`）で持っていた。
  - 選ばれない見方の読みにも層を作っていた。
  - 層を、選ばれた読みにだけ、JSON の文字列で直接書く形に変えた（`Claim.layers` は `RawValue`）。
- 時間の詰め: `chain` と文字の長さの検査を、二分探索から順に進む形へ。アイドルの水準の上位 20 は、全体を並べ替えずに取る。100 万文字で 21 → 12 秒。変化 1 つあたり約 1 マイクロ秒で、いくつもの処理に分かれていた。Python よりずっと速いので、ここで止めた。
- **node の落ち方は未解決。** V8 のコンパイラを変えても同じ（`--liftoff-only`、`--no-liftoff`）。wasmtime では同じ wasm が最後まで動くので、node の WASI（実験的）の側と見ている。
  - ブラウザも V8 なので、web で使う前に、ブラウザの中で（WASI でなく wasm-bindgen の形で）確かめる。

## 11. R2 の途中（2026-11-24）: I2C と SPI

real + noise + smoke + uartlike の組での、本物のバスの結果（Python は CI 前の手元の回、Rust は 6f4e9f9 以降の手元の回）。

| | 確定 | ほぼ | 見逃し | 誤り | 誤った確定 |
| --- | --- | --- | --- | --- | --- |
| UART（319 本）Python | 291 | 15 | 9 | 0 | 0 |
| UART Rust | 289 | 15 | 9 | 0 | 0 |
| I2C（332 本）Python | 302 | 12 | 11 | 4 | 0 |
| I2C Rust | 301 | 6 | 16 | 6 | 0 |
| SPI（321 本）Python | 288 | 10 | 13 | 3 | 0 |
| SPI Rust | 249 | 16 | 25 | 25 | 0 |

- 時間は、この組全体で Rust 13 秒、Python 約 550 秒（Python は全プロトコルを読む）。
- 誤った主張（ほぼ）は UART 3、I2C 3、SPI 0 まで減った。SPI の線を、SPI の読みが取るようになったため。

**入れたもの**
- **I2C**
  - 2 本の線を時刻の順にたどり、START・STOP・ビットを読む。
  - 9n / 9n+1 の枠を、偶然（0.3）と二項分布の裾で量る（裾は対数で計算。クロックのない START と STOP も枠に数える）。
  - 条件が SCL の辺から離れているか、1 ビット 1〜2 回の変化か、5 MHz まで。
  - 雑音を除いた見方。組は整えた線とアイドルの水準で決める。
- **SPI**
  - クロック、CS（なしも）、データ線（クロックへの合わせ方の上位 1〜2 本）。
  - データが変わる所から遠い辺でサンプルし、モードを決め、MSB から読む。
  - 点数: 窓ごとにバイトにそろうか、クロックの辺が窓の中か、CS が Burst をすべて枠に収めるか、窓がクロックを持つか、窓がぴったりか、1 周期 1 回の変化か、同じ値ばかりでないか、語の数。
  - 線の整え方を 3 つ: 短いパルスを除く、バウンスを 8 サンプル以上でまとめる、短い Run から除く。
- **選ぶ段（全体で 1 つ）**
  - 線が重ならない組み合わせのうち、価値（線の数 ×（点数 − 0.3））の合計が最大のもの（分枝限定）。
  - 差は、その主張を除いた最良の組み合わせとの差を、変わった線の数で割ったもの（Python と同じ）。
- **UART に足したもの**: 選択線の窓（クロックの Burst をぴったり包む窓）を UART から引く。

**残り**
- SPI のバウンスは、クロックの半周期が 6 サンプルほどと速いところで、まだ読めない（数十件）。バウンスの幅が半周期と同じくらいなので、パルスを除く、辺に寄せる、短い Run から除く、のどれでもクロックの数が戻らない。Python はここを確定しているので、その見方の組み合わせ（`own_short_runs` や、クロックの見方ごとの読み）を調べる。
- I2C のアドレスの証拠（`evidence.addresses`）は、まだ入れていない。
- 次のプロトコル（CAN、LIN、DMX512、SWD など）と、上の段（Python のまま、R4）。

## 19. RVSWD の誤り、デバイスパック（2026-11-24）

## 27. SPI の誤った主張と bounce・xtalk、I2C の偶然の読み（2026-11-24、§26 の残りを詰める）

## 28. 周辺を Rust の部品にして Python から呼ぶ（2026-11-24、R4 / R5 の一部）

## 29. 雑音の下の I2C・PS/2・SWD・JTAG・DMX512（2026-11-25、CI e0aa744 の SPI・I2C 以外の差を詰める）

CI e0aa744 で SPI・I2C 以外のスイートに残っていた差（protomix の調整用の組の JTAG・PS/2・SWD、uartlike の DMX512、
smoke の bounce の I2C）を見ると、どれも**雑音の下で、読み手がその線の見え方を 1 つしか持たない**ところだった。
閾値は足さず、SPI がすでに持つ見え方（そのまま、パルス抜き、作り直したクロック）を他の読み手にも並べ、点数で選ぶ形にした。

- I2C（`i2c.rs`）:
  - **SCL を周期から作り直す見え方を足した**（Python の rebuilt views。refused・followed・gridded、SDA は 4 tick の
    bounce をまとめる）。1 MHz を 8 MS/s（半周期 4 サンプル）で取った bounce の I2C は、幅のフィルタのどれでも
    bounce とクロック自身の Run が分けられず、見逃していた。作り直しは、幅の見え方の読みが 0.85 未満の組だけ
    （Python の REBUILD_BELOW）。
  - **変化から一定の窓（7 tick）の中の変化を 1 つの変化とその bounce とする見え方（`kernels::settled`）を足した**。
    `debounce` は前の変化からの間隔でつなぐので、400 kHz を 8 MS/s（半周期 10 サンプル）で取った bounce:0.5 では、
    鳴り続ける bounce が次の本物の変化までつながって消えていた。SCL の半周期が窓より長い組だけ。
    tuning-17+bounce:0.5 で I2C を見逃し、その SDA を UART と読んでいた誤った主張がなくなった。
- PS/2・SWD（`ps2.rs`、`swd.rs`）: **組を、そのままと 1 tick のパルスを抜いた線の 2 通りで読み、良い方を取る**。
  xtalk のパルスを受けたデータ線は、クロックより変化が多くなり（クロックの選び方から外れる）、クロックの中央値の
  半周期もパルスのものになっていた。クロックは、どちらの見え方でも変化の多い方。
- JTAG・SD・I2S（`clocked.rs`）: クロックの見え方に gridded を足した（SPI と同じ）。unknown-sync は gridded の
  見え方を使わない（自分の枠を持たないので、格子がそのクロックのものかを確かめられない。gridded の見え方で
  1 MS/s の bounce の I2C の線に unknown-sync が 0.31 で出ていた）。
- DMX512（`uart.rs`）: **UART の読みのビット時間でも読む**（Python の DmxPlugin は UART の読みのブロックを使う）。
  250 kbaud 固定の読みは、短い Run が 1 割を超える線を読まないので、xtalk の 1 tick のパルスのある線を見逃していた。
  読みのビット時間では、1 tick の Run はビットにならない。
- 試してやめたもの:
  - I2C の点数で、条件（START・STOP）の clearance を Python と同じく丸ごと掛ける（今は 0.25 の重み）。glitch-14 の
    偶然の I2C（clearance 0.4）の誤った主張は消えたが、freqhop の bounce・decimate、lowrate で、本物の I2C の
    確定 → ほぼが 6 件。
  - 枠ごとに、条件が clear なものだけを「合う枠」と数える。同じく glitch-14 は消えたが、確定 → ほぼが 4 件、
    ほぼ → 曖昧 1 件。
  - I2C の作り直しの見え方を、線の時計らしさ（Python の clock_score）で絞る。bounce:0.5 の本物の SCL（0.22）と、
    作り直しで偶然の I2C になった SDA（0.14）が分けられない。
- 突き合わせ（CI e0aa744 の engine.rust と Python とケースごと。holdout は確かめだけで、調整には使っていない）。

## 30. 周辺の Rust 化の 2 回目: 書き出し、states・survey・annotate（2026-11-25、§28 の続き）

方針は §28 と同じ（一致は不要で同等以上、既定の動きと公開の口は変えない、未設定なら wireskein_core を import しない）。

- **作ったもの**
  - `wireskein-io`:
    - `write`（読み手の対）: `write_wireskein`、`write_sr`、`write_vcd`、名前で選ぶ `write`。Python の `fileio.save` / `_fileformat.write`、`srio.write_sr`、`vcdio.write_vcd` と同じ作り。
      - 1 tick 1 サンプルの線は、変化の方が小さければ events、でなければ bits。any_high / any_low は区間のまま、粗い step の events と change_latch もそのまま。アナログは raw か float32。
      - データは level 1 で deflate。先頭 1 MiB が 1 割縮まなければ stored。付属物（attach、notes）はそのまま運ぶ。
      - 部分の事実（start_ns など PART_META）は部分の meta に入れる。id がなければ新しく作る。
    - .sr と VCD の読みを Python に合わせた。
      - .sr: アナログ（raw は `wireskein/analog-K.raw` から、volts は自分の rate で）、extra の acquisition。

## 32. RVSWD の遅れた応答と decode の差、調整用の組の誤った主張（2026-11-25、§29・§31 の残り）

- **RVSWD**（`rvswd.rs`）:
  - long 形式の応答の時刻（Python の `long_answer`）を写した。DMI に `answer_delay`・`answer_delay_ns`、中央値が 1 周期を
    超えると `late`。`test_rvswd_long::test_an_answer_a_clock_late_is_marked` が Rust のエンジンで通る。
  - params に `declared: "rvswd.toml"`（Python の宣言のプロトコルの名）。
  - `bits` の層（Python と同じく clock・data・sample_edge・t・values・deglitch）。spec の `layers: ["bits"]` が読める。
- **SWIO**（`swio.rs`）: `pulses` の層（Python と同じく s・width・short・split）。spec の `layers: ["pulses"]` が読める。
- **ヒントの下の読み**（`lib.rs` の `candidates_of`）: ヒントが名前を挙げたプロトコルが、どれも単独で立つもの（`ALONE`。
  汎用の UART・I2C・SPI と unknown-sync は、他の読みに外されるので含めない）なら、その読み手だけを回す。
  - §31 の L103 x_read_flash_64k（200 万変化）で、RVSWD の `readings` が 40〜48 s → 0.4 s（手元、全体を 1 度）。
    遅さは RVSWD ではなく、同じ線に全部の読み手（UART・I2C・SPI・クロックの組など）を回していたこと。`bits` の層を
    足した後は 1.0 s（90 万の標本の書き出し）。
  - 組（`clocked::groups`）も、JTAG・SD・I2S を読むときだけ作る。読みの結果は変わらない（同じ読み手の同じ出力）。
- **SPI**（`spi.rs`）:
  - **選択の窓の中だけで変わる線もデータ線の候補にする**（クロックの半周期が 3 サンプル以下のときだけ）。1 周期 4
    サンプルの跳ね返るクロックでは、データの変化が集まる位相がぼやけ、正しい MOSI の keeping が 0.497 で DATA_KEEPS
    に届かなかった（tuning-141+bounce:0.1）。どの組を取るかは今までどおり点数。遅いクロックに広げると、I2C の SDA を
    選択とした読みに、その窓の中で変わる別の線が足され、線の数で主張を取った（nack-84+odslow）ので、速いクロックに限った。
  - **Burst の最後の変化が、窓の半周期の余白のちょうど端にあるものも窓の中とする**（`<=`）。跳ね返るクロックの最後の
    変化が CS の立ち上がりの 3 サンプル後に鳴り、select_frames が 2/3 になっていた（baudhop-4+bounce:0.1。CS のない読みが
    likely で取っていた）。

  - note: `notes/NNNN.json` を zip に足すだけ（既存を書き換えない）。時刻は ISO 8601 のローカル時刻と UTC オフセット（Rust の標準にはタイムゾーンがない。`chrono` など依存が要るか、UTC で書くかを決める）。小さい。
  - attach: `attach/NAME` を足す・`--replace` で `markers::put`。名前の検査（`_attach_name`）と、str / dict / bytes の書き方を写す。小さい。
  - capture: 取り込み元（OEP のクライアント、sigrok）が Python。OEP の Rust クライアント（oep-client の側の仕事。担当セッションに頼む）と、ストリームの受け（P4 の 40 MB/s、別プロセス受信の工夫）、損失の扱い（取れた所は保存して失敗とする）、`--trigger` などの解釈と表示の行（`_link_line`・`_fewer`・`_loss_lines`）。大きい。
  - gui: Python の HTTP サーバと web の UI。UI の作り直し（MIT・今風）とまとめて、Rust のサーバ（axum など）か wasm で決める。§6 の wasm と並べて比べる。
- 既存の試験: `tests/test_rust_parts.py` の「Rust にない選択肢は Python に戻る」を、select・alternatives・depth は Rust で行うように直した（devices の指定と知らない depth は Python）。

## 35. 周辺の Rust 化の 6 回目: JSON のキーの順、note・attach、verify の残り、wheel の入れ替えの下ごしらえ（2026-11-25、§34 の続き）

方針は §28・§30・§31・§33・§34 と同じ（一致は不要で同等以上、既定の動きと公開の口は変えない、未設定なら wireskein_core を import しない）。

- **JSON のキーの順**（Rust の CLI と `wireskein_core.analyze_file` / `decode_file`）
  - 比べた案:
    - serde_json の `preserve_order`: cargo の機能はワークスペースで 1 つにまとまる（wheel もベンチも同じ）。wireskein-core の Map の順（層の文字列の順、Map を回す処理）まで変わるので取らない。
    - 文書を最初から `J` で組む: wireskein-analysis の json! と Map が 300 か所ほど。大きすぎる。
    - 出口で並べ直す（取った案）: `wireskein-analysis` の `order`。
  - `order` の決め方:
    - この crate が作る辞書は種類ごとに Python の順（文書、capture、part、claim、bus と分割読みでつないだ bus、reading とつないだ reading、clock_speeds、undersampled、読めなかった区間、undeclared、split など）。
    - 線を名前に持つ辞書（ringing、data_edges、line_changes など）は claim の roles、decode では spec の順。
    - コアが書いたもの（層、項目、params、evidence）は、コアが書いた順。コアの層は手で書く所があり、並べ替わっていない（UART の blocks・chars・breaks・bytes など）。そこで、層を読むときに順を覚えておき（`order::layers`。キーの組ごと）、それに合わせる。
    - analyze が frame に足す `period_ns` と `high_ns` は、コアのキーの後（RVSWD は period_ns をコアが持つので high_ns だけ）。DM のアクセスは Python の上の段の順（s、e、op、addr、value、size）。
    - hints と spec は与えられた順（spec は `Spec::doc_j`）。
  - `--items` の行は `{"part", "bus", "layer", **項目}`（項目のキーはコアの順）。align の項目（find・between）の順は CLI から wireskein-analysis に移し、`wireskein_core.align_*` も同じ順で返す。
  - wireskein-core は触っていない。
  - 比べ: `tests/test_rust_cli.py` の JSON をキーの順まで比べるようにした（stdout、`--out`、`--items` の行）。analyze（例 10 ファイル × 10 通り）、分割読み、decode（3 通りの spec、depth frames と細かい分割、`--out`）が、Python（Rust のエンジン）とキーの順まで同じ。
  - 最初の比べでは、RVSWD と SWIO の dm、UART の層、SPI の frame の period_ns・high_ns、decode の params・undeclared・doubtful.holds が違っていた。上の決め方でそろえた。
- **note と attach**
  - `wireskein-io` の `attach`:
    - `attach`: `attach/NAME` を zip の最後に足す。置き換え（`--replace`）は `markers::put`。名前の検査は `_attach_name` と同じ。
    - `note`: `notes/NNNN.json`。Python の `json.dumps` の既定の区切りで書く。時刻は `chrono` で、Python の `datetime.now().astimezone().isoformat(timespec="seconds")` と同じ書き方。
    - 誤りは Python の例外の種類に分ける（FileExistsError、FileNotFoundError、OSError、BadZipFile、ValueError）。
  - 依存: wireskein-io に `chrono`（default-features なし、clock と std）。Cargo.lock も同じコミット。
  - `wireskein-rs note FILE TEXT [--json] [--kind K]`、`wireskein-rs attach FILE NAME [SRC | --text TEXT] [--replace]`。表示、誤りの文言、終了コードは Python と同じ。JSON の構文の誤りは、頭の `JSONDecodeError:` だけ同じ。
  - `wireskein_core.note` / `attach`。`WIRESKEIN_RUST=note,attach` で `_fileformat.note` / `attach` が通る（`wireskein note`、`wireskein attach`、capture の `--note`、align の保存なども）。attach のデータの書き方（str、dict / list、bytes）は Python の `_encode` のまま。
  - 比べ: 同じ記録の写し 2 つに、Python と Rust で同じ順に note 4 つと attach 5 つ、誤り 6 つを行った。表示・誤り・終了コード、zip の中身（note の時刻を除く）、読み返した線が同じ。`WIRESKEIN_RUST` 経由でも、項目、番号、例外の種類と文言が同じ。
- **verify の残り**（§23）
  - i2c: t_SP が 2 サンプル未満の記録では、入力のビューに加えて、線そのままとグリッチのビューも読む。グリッチのビューの幅は Python の `staged.glitch_views` と同じ決め方（2・3・5 サンプルと、見えたパルスからの幅。SCL の半周期の半分まで）。どのビューも Rust のコアの I2C の読み（`i2c::read`）の点数で比べ、最良を取る（同点なら入力のビュー）。
    - 比べ: 8 MS/s で、両方の線に 1 サンプルのクロストークを入れた記録。Python は ok。前の Rust は、各バイトに余分なビットを読んで ng だった（前の版の wireskein_core で確かめた）。今は Python と同じ status と transactions になる。クロストークなしの 8 MS/s と 50 MS/s も同じ。
  - 定義ディレクトリのない protocol の残り（WireSkein の decl/ に宣言したプロトコルを線から読むもの）: Python は宣言の読み手（Python のエンジン）の frames 層を messages にする。I2C なら {s, e, bits}。Rust のコアの層（I2C の transactions）とは形が違うので、Rust の verify は unchecked のまま残した。
    - その代わり、`WIRESKEIN_RUST=verify` で Rust の報告がこれを unchecked にしたときは、報告全体を Python で作り直す（`_rust.left_to_python`）。unchecked の報告にはしない。
- **wheel の入れ替えの下ごしらえ: `WIRESKEIN_RUST=all` で `pytest -m 'not slow'`**（main 32de9798 に rebase した後。wireskein_core はこの worktree のビルド）
  - 結果: 3 failed、1067 passed、24 skipped。
  - エンジン由来（直さない）: `test_rvswd_long::test_a_frame_no_layout_reads_is_uninterpreted`。Python のエンジンの `rvswd.reframe_startstop` を差し替える試験で、Rust には効かない。
  - 周辺由来（直した）:
    - `test_engine_switch::test_default_is_python` と `test_rust_and_python_agree_on_a_clean_bus`: 試験が `WIRESKEIN_ENGINE` だけでエンジンを選ぶ前提だった（`WIRESKEIN_RUST=engine` があると既定が rust になり、`WIRESKEIN_ENGINE=python` と矛盾して誤りになる）。試験の中で `WIRESKEIN_RUST` を外すようにした。
    - `test_protocols::test_a_declared_protocol_from_outside_is_read`（`WIRESKEIN_ENGINE=rust` で落ちる。エンジンのエージェントの報告）: decl/ の外のプロトコルの表（`staged.PROTOCOL_TABLES`）は Python のエンジンだけが読む。`_engines.analyze` で、それがあるときは Python のエンジンにした（WIRESKEIN_RUST の部品は前から Python に戻していた）。直す前に落ち、直した後に通ることを確かめた。
  - そのほかは、すべての部品を Rust にしても通る。
- 試験の数: `tests/test_rust_parts.py` 243 件（239 通り、4 件は意図した skip）、`tests/test_rust_cli.py` 192 件（184 通り、8 件は spec のない例などの skip）。wheel を作って回した 2 つで 423 通り、12 件 skip。
- 残り
  - 宣言のプロトコル（decl/）を線から読む verify は Python のまま。Rust のコアの層を宣言の frames の形にするか、宣言の読み手を Rust に持つかは、§6 の拡張の口と一緒に決める。
  - コアの辞書の順は、読んだ層から覚える。そのため、層を読む前に作られる辞書（コアの evidence、relations の中身）は serde_json の順（並べ替え）のまま。今の比べでは差が出ていない。
  - capture と gui は §34 の見立てのまま。
