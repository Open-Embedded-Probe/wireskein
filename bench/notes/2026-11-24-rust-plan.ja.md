# Rust への組み直しの計画（2026-11-24、案）

## 0. 前提（2026-11-24、ユーザー）

- 行き先は Rust だけで動く形。1 つのコアを、ネイティブアプリ、web（wasm）、Python（PyO3）から使う（2026-11-23-ui-directions.ja.md §11）。
- 推定から作る（いちばん試しやすい: 入力はエッジ、出力は主張。正解と台帳がベンチにそろっている）。
- **Python と一致する必要はない。同等以上であればよい。** 2026-11-18 の grand-design の「出力はバイトまで同じ」と「L5 は当面 Python」は、この計画で置き換える。
- **徐々に差し替える。Python の利用者には影響を出さない。**
  - 公開の口（`decode`、`verify`、`runlog`、`capture`、`sources`、CLI）と出力の形式は変えない。
  - 入れるのに Rust の道具は要らない（ビルド済みの wheel）。
  - 読みの変化は、今と同じく CHANGELOG に書く（ベンチで同等以上を確かめたうえで）。

## 1. 「同等以上」の決め方

ベンチの全スイート（Actions の Bench、既定の e2e / all / wireskein）で、Python のエンジンと Rust のエンジンを並べて比べる。合格の線は次のとおり。

| 指標 | 合格 |
| --- | --- |
| 誤確定（false confirmed） | 増えない（セットごとに） |
| 正しい読み（ok）、確定（confirmed） | 合計で減らない。セットごとの減りは、理由を書いて残す |
| ambiguous | 合計で増えない |
| 時間 | Python 以下（スイートの合計と、いちばん長い記録） |
| メモリ | Python 以下 |
| 長い記録（分割読み） | 同じ記録を最後まで読める |

一致は見ない。差の出た記録は、どちらが正しいかを正解で言える形で一覧にする（`bench/engines` のエンジン比べと同じ出力）。

## 2. 差し替えの仕組み

Rust の推定は、まず**ベンチのポートフォリオの 1 エンジン**として入れる。`bench/engines` の light_main_<protocol>（読み手の差し替え）や `*_open` と同じ並びに置く。製品の中では、部分ごとに切り替える口を `_engines` に置く。

```
decode / verify / CLI（Python の口、変えない）
        │
   _engines.main ──┬─ Python の推定（今）
                   └─ Rust の推定（wheel の中の拡張モジュール）
                        部分ごとに切り替え（プロトコルの読み手、候補、選択 …）
```

- **既定はベンチで合格した部分だけ Rust にする。** 環境変数で Python と Rust を切り替えられるようにして、比べと逃げ道に使う（例: `WIRESKEIN_ENGINE=python|rust`）。
- **合格して 1 リリースたったら、その部分の Python 版を製品から消す**（1 つの層に実装は 1 つ）。研究用の写しとして bench に残すかは、§5 で決める。
- **numpy との受け渡しはコピーなし**（エッジの配列）。主張は、分析の形式の辞書で返す（`register_engine` の `engine(view, hints)` と同じ形）。

## 3. 段階

各段は「次に移る条件」で区切る。急がない。

| 段 | すること | 次に移る条件 |
| --- | --- | --- |
| R0 下地 | 下地を作る（下の表）。製品の振る舞いは変えない | 空の Rust エンジンがベンチで回り、全 OS の wheel が作れる |
| R1 縦に 1 本 | 1 つのプロトコルを、下処理から主張まで Rust で通す。UART から（件数が多い。light_main の分解で差の大部分が読み手と分かっている。単線で候補の組が少ない）。比べるのは light_main_uart と main の UART | UART のセットで同等以上 |
| R2 読み手を足す | I2C → SPI → ほかのバス（件数の多い順）。各プロトコルは、まず読み手の差し替え（Python の候補と選択 + Rust の読み手）で比べる | プロトコルごとに同等以上。合格したものから製品の既定を Rust に |
| R3 候補と選択 | 下調べ、線の組の候補、点数、選択、regrade を Rust に（SPI の差は、候補と選択が大部分）。開いた世界（形だけの線）もここ | 全スイートで同等以上。ここで推定の全体が Rust になる |
| R4 推定の周り | 上の段（`_upper`）、書き出し（export）、照合（verify の検査）、ファイル形式（.wireskein / .sr / VCD）、分割読み（split） | 同上。Python の側は口と、標準ライブラリだけの部分（runlog、capture の保存）だけになる |
| R5 Rust だけで動く | CLI を Rust で。Python は PyO3 の薄い口になる | CLI の出力が同等以上。Python を入れずに analyze / verify が動く |
| R6 画面 | ネイティブアプリと web（wasm）を同じコアで。画面の作りは ui-directions §11.1 で並べて試す | — |

R0 の中身:

- 同じリポジトリに crate のワークスペースを置く。PyO3 + maturin、abi3（cp311）、Rust 1.88。rust-core-spike の調べと下書きの workflow を元にする。
- wheel の配布を、ch32rv と同等以上の 5 つにする（Linux x86_64 / aarch64、macOS arm64 / x86_64、Windows x86_64）。Actions で作り、入れたうえで試験する。
- ベンチの道具に Rust のエンジンを呼ぶ口を作り、e2e の engines に `rust` を足す。

R1 の前に要るもの:

- **エッジの見え方とカーネル**: 変化の列、ラン、clean、views、own_short_runs。これは L1・L2 にあたる。どの読み手も使うので、R1 の中で作る。下の層だけを先に全部移すことはしない。縦の 1 本に要る分だけ作る。

## 4. 進め方

- **探索は狙いの組だけ、整合確認は CI でまとめて**（今と同じ）。手元では、そのプロトコルのセットだけを回す。
- **Rust の試験**: crate の中に単体の試験。答え合わせはベンチで（Python の試験は口の試験として残る）。
- **プロトコルの仕様は TOML のまま使えるか**: decl/*.toml は今のエンジンの内部の表なので、Rust で読むか、Rust のコードに書き直すかは、R1 で UART を作るときに比べる。
- **リリース**: Rust の入った最初のリリースは、既定が Python のまま（環境変数で Rust を試せる）。合格した部分から既定を切り替え、CHANGELOG に読みの変化を書く。

## 5. 決めたこと（2026-11-24、ユーザー）

- **実験は Python と Rust の両方で続ける。** どちらで書いたエンジンも、ポートフォリオに並べて同じベンチで比べる。
  - 試しやすい方で書けばよい。よい構造は、製品の言語（Rust）へ写す。
  - 役目を終えたエンジンは引退させる。Python 版も Rust 版も、同じ扱いにする。
  - そのため「ベンチの Python 版エンジンを消すか残すか」は、引退の判断に含める（エンジンごとに、比べの基準として要るかで決める）。
- **wheel のない環境（32 ビットの ARM、musl など）は考えない。** 要望が来たら、wheel の対象を増やす。純 Python の逃げ道は持たない。

## 6. 実験で決めること

どちらも机の上では決まらない。段の中で試作して測る。

- **web で wasm の推定はどこまで読めるか**
  - 測るもの: 記録の大きさごとの時間とメモリ。wasm32 は 4 GB まで。memory64 も試す。
  - 比べる形: ブラウザの中だけで読む / 手元のネイティブに読ませて web は表示だけ / 区切って読む。
  - いつ: R1 で UART が通ったら、同じコードを wasm にして最初に測る。R3 の後に、推定の全体で測り直す。
- **拡張の口（Rust だけの形で、外の人がどう足すか）**
  - 候補:
    - wasm のモジュール（ネイティブでも web でも同じものが動く）
    - Rust の crate（足した版を作り直す）
    - 動的ライブラリ
    - 宣言の表（機器パック・マーカーの方言）
    - Python の口を残す
  - 測るもの:
    - 書く手間
    - 速さ（呼び出しの手間）
    - 配り方
    - ライセンスの切り分け
    - 3 つの口（ネイティブ・web・Python）で同じものが動くか
  - 2026-11-24 のユーザーの見立て: エンジンの中の拡張（線そのものの上のプロトコル、`register_engine`）は要らないかもしれない。バスの上に載るものは、テキストで宣言できそう。
    - 試すこと 1: 今の Python のプロトコル（`register_protocol`）の例と、よくある上位のプロトコルを、宣言の表で書き切れるか。
      - 書く中身: フィールド、長さ、区切り、CRC やチェックサムの種類、応答の組、機器パック。
      - 書けなかったものを数える。例: 状態を持つ、分割したものを組み立てる、独自の計算。
    - 試すこと 2: 書けない残りを、逃げ道（wasm など）で持つか、WireSkein 本体に足す要望にするか。
    - 線そのものの上のプロトコルは、今の「本体に提案」の扱いで足りるか。`register_engine` を引退させてよいか。
  - いつ: R2 で、1 つの機器パックか 1 つの読み手を、候補の形それぞれで足してみる。今の Python の口（`register_engine`、機器パック、自前のプロトコル）は、R4 まではそのまま。

## 7. R0 で作ったもの（2026-11-24）

- **配り方の選択**: R0〜R2 の間、Rust は本体と別のパッケージ `wireskein-core`（`crates/wireskein-py`、import は `wireskein_core`）にする。
  - 本体の wheel は純 Python（hatchling）のまま。release.yml も変えない。Python の利用者に影響はない。
  - ベンチだけが `uv run --with ./crates/wireskein-py` で入れる。
  - 部分を既定にする時（R2 以降）に、本体の wheel に入れる（maturin へ移る）。
- **crate の構成**
  - `crates/wireskein-core`: 素の Rust。`View` / `Channel`（線の変化）と `Claim`（分析の形式）、`analyze(view, hints)`。今は主張を返さない。
  - `crates/wireskein-py`: PyO3 0.30、abi3-py311。
    - 線は int64 の配列を借りる（連続でなければ 1 回だけ写す）。
    - 主張は分析の形式の JSON で返す。
    - 計算の間は GIL を外す。
- **ベンチ**
  - `bench/engines/rust.py` を、ポートフォリオの `rust` エンジンとして置いた（e2e の `engine.rust`）。
  - bench.yml は、エンジンを回す時だけ Rust を作る（`engine*`、`rust`、`(status ...)`）。
- **CI**
  - test.yml に `rust` のジョブ: fmt、clippy、コアの試験、最低の Rust（1.88）。
  - wheels.yml（手動だけ）: 5 つのターゲットの wheel と sdist を作り、走らせられるものは入れて呼ぶ。
- **版**: Cargo の版は wireskein と同じ。`tools/prepare_release.py` が Cargo.toml と Cargo.lock も上げる。
- 手元で確かめたこと
  - `cargo test` / `clippy -D warnings` / `fmt --check` が通る。
  - Python から呼べ、誤った線を断る。
  - smoke の組で `engine.rust` が回る（主張はまだない）。

## 8. R1 の途中（2026-11-24）: UART を 1 本

`crates/wireskein-core/src/uart.rs`（`features.rs`、`kernels.rs`、`sync.rs`）。Python の読みを写すのでなく、同じ考えで書き、ベンチで比べる。

- **入れたもの**
  - アイドルの水準、ビットの長さの候補（`estimate_units`、`unit_of`、`_unfold`）
  - ストップビットでの文字の長さ、ビットに丸めた Run からの文字、ビットの長さの合わせ直し、パリティ
  - 雑音を除いた見方（スパイク、バウンス）
  - LIN と DMX512 の枠の検査（UART の点数から引く）
  - クロックに合わせて動く線（同期のデータ線）の判断
    - 位相の集まり × Burst の中の割合 × 数の確からしさ。Python の `data_score` と同じ考えを、小さく書いた。
  - 対立する読み（別のアイドル、3 % 以上違う速さ）との差、確定の規則
- **まだ入れていないもの**
  - 線の中の速さの切り替え（ブロックは 1 つ）
  - 選択線の窓（`tight_windows`）、USB の SE0、CEC
  - クロックのゲートした見方での合わせ方、バウンスを除いた対
- **途中の数字**（smoke + uartlike、本物の UART 79 本）

| | 確定 | ほぼ | 見逃し | 誤った確定 | 誤ったほぼ |
| --- | --- | --- | --- | --- | --- |
| Python | 70 | 5 | 3 | 0 | 0 |
| Rust | 68 | 6 | 4 | 0 | 6 |

  - 誤ったほぼは、SPI・I2C・DMX512 の線を UART と読んだもの。Python では、その線をほかのプロトコルの読みが取る。Rust で SPI や I2C を読むまで（R2）は残る。
  - 時間: Rust は全体で 1.3 秒。Python は全プロトコルを読んでいて 90 秒なので、そのまま比べられない。
- **進め方の気づき**
  - LIN と DMX512 の枠の検査だけで、誤った確定が 74 から 1 に減った。
  - 見方（雑音を除く）で、雑音の入った記録の確定が 48 から 71 に戻った。
  - 同期のデータ線の判断は、Python の重み（co_activity、quantity）が要った。位相だけでは、速さの近い PWM や速いクロックの横の UART を取り違えた。

## 9. wheel とリリース（2026-11-24、案）

ユーザー: 基本はリリースの時だけ。PyPI と Rust のリリースを分けるか一体か。ベンチは使う環境だけビルドして流す。

### 9.1 何を配るか（段ごと）

| 段 | 配るもの | wheel |
| --- | --- | --- |
| R0〜R2（今） | wireskein（純 Python）だけ。Rust の部分はどこも既定でない | 作らない。wheels.yml は手動の確かめだけ |
| 部分が既定になってから | wireskein と wireskein-core（Rust の wheel） | リリースの時に作る |
| R5（Rust だけで動く） | 上に加えて、CLI とネイティブアプリ（cargo のバイナリ、インストーラ）、web（wasm） | それぞれのリリースの時に |

### 9.2 分けるか一体か（候補）

- **A. 一体**: wireskein の wheel に Rust を入れる（maturin へ移る）。版は 1 つ。
  - 利点: 版のずれが起きない。入れるものが 1 つ。
  - 欠点: Python だけの直しでも、毎回 5 つのターゲットの wheel を作る。どれかのランナーが壊れると、Python の直しも出せない。
- **B. 分ける**: wireskein（純 Python、どこでも入る wheel 1 つ）は wireskein-core（Rust の wheel）に依存する。
  - 版はそれぞれが持ち、wireskein は `wireskein-core>=X,<Y` で幅を決める。
  - 利点:
    - Rust を変えた時だけ core を出す。
    - Python の直しは今のまま速く出せる。
    - R5 の CLI・ネイティブ・web も、同じ core の版を指せる。
  - 欠点: 2 つのパッケージ。組み合わせの試験（wireskein の CI は、出ている core と手元の core の両方で回す）。
- **C. 移る間は分け、Python が薄い口だけになったら一体に**（R5 の頃に A へ）。

今の作り（core は別パッケージ `crates/wireskein-py`）は B と C のどちらにもそのまま進める。どれにするかは、部分を既定にする時（R2）に、wheels.yml の実際のビルド時間と失敗の頻度を見て決める。
- 手がかりとして、ch32rv は一体（A）で回っている。
- 推定の研究は両方の言語で続ける。core の変わる頻度が高ければ B の利点が大きい。

### 9.3 いつ wheel を作るか

- **リリースの時だけ**作って出す。
  - B なら core のタグ（例 `core-v0.1.0`）で wheels.yml を走らせ、PyPI に出す。
  - A なら release.yml の中で作る。
- **ふだんの CI（test.yml）**: crate の fmt / clippy / 試験 / Rust 1.88 だけ。wheel は作らない。
- **wheels.yml の手動実行**: ビルドが壊れていないかを、リリースの前やランナーの変わり目に確かめる。

### 9.4 ベンチ

- ベンチは配った wheel を使わない。その commit の Rust を、その場でビルドして使う。比べたいのは今のコードなので。
- ビルドするのは、Rust を使う組（エンジンの組、`engine.rust`、`(status ...)`）の時だけ。
- 1 回のベンチで 1 回だけビルドする。plan のジョブで wheel を作って artifact にし、各 shard はそれを入れる（20 の shard がそれぞれビルドしない）。
