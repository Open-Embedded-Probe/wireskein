# UI と作り方の方向（2026-11-23〜、方向を確かめる段階）

PulseView の代わりになるものを作りたい（ユーザー、2026-11-23）。PulseView はベースとして古く、ライセンス（GPL）も
使いにくい。MIT で今風で使いやすいもの。**最初に決めない。方向は広く並べる。フルスクラッチで組み直すのも、Rust だけで
組み直すのも選択肢。今の構成（Python のコア、wireskein-web）は候補の 1 つで、前提にしない。** この段階では試作も計測も
しない。

## 1. 何を作るか（製品の形）

**作るのは PulseView そのものの置き換え**（ユーザー、2026-11-23）: 機器から取る、見る、プロトコルを読む（下の P2 が軸。
P3・P4 などをどこまで足すかは開いたまま）。**試験の道具は今の形（Python のライブラリ、`verify`、pytest-embedded-wireskein、
CLI・JSON）で育てる。** アプリとは、ファイルの形式（`.wireskein`、試験の記録、解析の出力）で繋ぐ。アプリのプロトコルの
解読に WireSkein のエンジンを使うか、アプリの側で持つかは開いたまま。

| 形 | 中身 |
|---|---|
| P1 波形ビューア | 記録を開いて見る、測る。解析は外の道具 |
| P2 ロジックアナライザのアプリ | 機器から取る、見る、プロトコルを読む（PulseView・Saleae Logic と同じ立ち位置） |
| P3 自動で読むアナライザ | 取ったら方式と線が自動で注釈される。設定なしが売り |
| P4 試験の道具 | 期待と照合し、OK / NG を時間軸で見せる（CI、pytest と繋がる） |
| P5 AI・スクリプトが先の道具 | CLI と JSON が主、画面は確かめ用 |
| P6 ライブラリ・部品 | 他のアプリに組み込む表示の部品、解析の部品 |
| P7 プローブの中の画面 | プローブ（ESP32 など）が Web の画面を出す。PC にインストールなし |

組み合わせてよい（P2 + P3 + P4 など）。

## 5. 拡張のしかた

（§8）、ファイル形式（読み・書き）、測定や表示（周期、アイパターンなど）、書き出し。下の表は書き方の案（組み合わせてよい）。

| 案 | 中身 |
|---|---|
| X1 宣言（表） | TOML / JSON などでプロトコルを書く。コードなし |
| X2 スクリプト言語 | Python、Lua、JS などで書く |
| X3 WASM のプラグイン | どの言語で書いても WASM にして載せる。安全に隔離できる |

## 6. データの扱い

一度に全部メモリに載せる / 必要な所だけファイルから読む / 取りながら流して見る（ライブ） / 圧縮したまま描く。
大きな記録（1 億の変化、数 GB）をどう扱うかは、言語より作りで決まる。

流し続ける機材（ユーザー、2026-11-23）: CH32H417 は使い勝手はかなり悪いが、SS で 8 か 16 ch を 200 MHz で流し続ける
ことに特化していて、それだけなら割といけそう。ただしその量を取り続けると容量がすごいことになる。

| | 毎秒 | 1 分 | 1 時間 |
|---|---|---|---|
| 8 ch × 200 MHz | 200 MB | 12 GB | 720 GB |
| 16 ch × 200 MHz | 400 MB | 24 GB | 1.44 TB |

全部を取っておけないので、取りながら減らす作りが前提になる。減らす方向（組み合わせてよい）:

| 案 | 中身 | 効き方 |
|---|---|---|
| 変化だけ持つ | 変わった時刻だけ | 止まった線・遅い線はほぼ 0。速いクロックはかえって大きい（200 MHz で 10 MHz のクロックは毎秒 2000 万の変化） |
| 線・区間ごとに小さい方 | 区間ごとに生の並びと変化の小さい方 | 今の .wireskein の「bits と events の小さい方」と同じ考え |
| 汎用の圧縮 | zstd など | 中身によらず効く。毎秒 400 MB に追いつく速さが要る |
| 輪のバッファ | 直近の N 秒だけ持ち、トリガ・エラー・マーカーの前後を残す | 長く見張れる。残す条件が要る |
| 取りながら読む | 流しながらプロトコルを読み、結果と怪しい所の生だけ残す | 何時間でも。読み違えた所の生は消える |
| 段階的に持つ | 直近は生、少し前は変化、古い所は読んだ結果だけ | 見返す範囲と量の釣り合い |
| プローブで減らす | 変化への変換、線ごとの間引き（OEP の any_low など）をプローブで | 送る量そのものが減る。プローブの力しだい |
| 見るための粗い層 | 拡大縮小用の粗い要約を別に持つ | 何 TB でも画面はなめらか。容量は増える |

比べる軸に入ること: 毎秒 400 MB を取りこぼさずに受けて減らせるか（速さが要件になる所）、ディスクに書き続けられる速さ、
後から生の波形に戻れる範囲。

## 8. 機材との繋がり

PulseView（sigrok）が対応している機材は便利なものが少なく、最近の機材は PulseView をフォークして独自のアプリで出している
（ユーザー、2026-11-23）。機材の対応は「sigrok の対応表をどこまで引き継ぐか」ではなく、「各社のフォークの機材とどう繋がる
か」の問題。

| 案 | 中身 | 引き換え |
|---|---|---|
| D1 sigrok（libsigrok）経由 | 今の対応機材をそのまま | 古い機材が中心。リンクすると GPL、別のプロセスで（sigrok-cli のように） |
| D2 最近の機材を直接 | 各社のフォーク（公開のコード）を手がかりに通信を実装 | 機材ごとに手間。GPL のコードからの移植にならない書き方が要る |
| D3 機材の対応を差し込みに | ドライバを別のプロセスや WASM の差し込みにして、メーカーや有志が足す | 本体は MIT のまま。差し込みの約束（取り方、流れ）を決める |
| D4 各社のアプリのファイルを読む | DSView、Saleae、KingstVIS などの保存・書き出しを開く | ドライバなし。取るのは各社のアプリ、見るのはこちら |
| D5 共通のプロトコル | SUMP / OLS（安い FPGA や RP2040 の機材に多い）など | まとめて増える。機能は最低限 |
| D6 自前の機材を第一に | OEP のプローブ（ESP32 など）をいちばんよく動く道に | 安く手に入る。仕様を自分で決められる |
| D7 OEP を開いた約束に | 各社・有志が自分の機材に OEP を話させる | 機材の側に頼る。広まれば機材ごとのドライバが要らない |
| D8 各社のアプリや API を外から | Saleae の自動化の API などを別のプロセスで | 動いても各社の都合で変わる |

組み合わせてよい（D3 + D4 + D6 など）。

**ライセンスで配れない機材がある**: USB の FX3 はロジックアナライザを作れるが、ドライバや SDK 自体が GPL での配布を
許さない（ユーザー、2026-11-23）。GPL の PulseView / sigrok には入れられない。本体を MIT にし、機材の対応を差し込みに
すれば、FX3 の SDK を使うドライバやファームウェアは差し込みの側でその条件のまま配れる見込み（どの組み合わせで配れるかは
SDK の条件の本文で確かめる）。PulseView に対する強みになりうる。

ファームウェアを送り込む型の機材（ユーザー、2026-11-23）: FX2 も FX3 も、PC のアプリが繋ぐたびにファームウェアを USB で
送って動かす。そのためアプリ・ファームウェア・メーカーの SDK のライセンスが絡む。FX2 は sigrok が SDK を使わずに作った
ファームウェア（fx2lafw、GPL）があるので扱えている（MIT のアプリが別のプログラムとして送れるかは条件の確認事項）。FX3 は
そうした自由なファームウェアや道具がなく、SDK の条件にそのまま縛られる。

安い開発ボード（ユーザー、2026-11-23）: ESP32-P4、ESP32-S31、CH32H417 などが安く出てきて、ノイジーだが使いやすく値段も
安い。一度書き込めば自分のファームウェアで動き、繋ぐたびの転送も SDK の再配布も要らない（ESP-IDF は Apache-2.0、WCH の
SDK の条件は確認事項）。OEP のプローブとしてすでに使っている（D6・D7）。主な機材にするなら、ノイズに強い読み方が欠かせない
機能になる（WireSkein が力を入れてきた所で、PulseView に対する強みになりうる）。

PulseView（sigrok）の対応機材（sigrok.org/wiki/Supported_hardware と Logic_analyzer_comparison、比べのページは
2023 年の版、2026-11-23 に読んだ）: ロジックアナライザで「対応済み」は 55 件。

| 群 | 例 | 最高のサンプリング | チャンネル |
|---|---|---|---|
| FX2 の Saleae 互換品（いちばん多い） | Saleae Logic、各社の互換品、USBee 互換、Hantek 6022BL | 24 MHz | 8 |
| FX2 系の 16 チャンネル | Braintechnology、Lcsoft Mini Board | 24 / 12 MHz | 8 / 16 |
| Logic16 系 | Saleae Logic16 と互換品、Kingst KQS3506 | 16 ch で 16 MHz、3 ch で 100 MHz | 16 |
| 機材のメモリに貯める型（FPGA 付き） | DSLogic（400 MHz）、Kingst LA2016 / LA5016 / LA5032（200〜500 MHz）、Hantek 4032L、ASIX、ZEROPLUS、Sysclk、ChronoVu | 100 MHz〜1 GHz | 8〜34 |
| その他 | BeagleLogic、GreatFET One、Openbench Logic Sniffer（SUMP）、FTDI、Bus Pirate、PICkit2 | 1〜204 MHz | 1〜32 |

- USB 3.0（SuperSpeed）の機材は一覧にない（USB の速度はページに書かれていない）。DreamSourceLab の USB 3.0 の機種は
  独自の DSView 側と見られる。
- USB 2.0 HS で流し続けられるのは実用で毎秒 40 MB 前後（16 ch なら 20 MHz 程度）。200 MHz 以上の機材は、機材のメモリに
  短く貯める型と見られる（各機材の流し取りの数字はページにない）。
- ESP32-P4 の OEP の目標（欠けなしで毎秒 40 MB）は HS の上限とほぼ同じ所。HS の機材で明確に上なのは、短い時間を速く貯める
  用途だけ（ユーザー: 「基本 HS の USB だと ESP32-P4 とかより明確に高性能のは少ない」）。CH32H417 の SS で 200 MHz・16 ch
  （ユーザー）は、sigrok の対応機材の範囲を超える。
- ページに書かれていないもの: ドライバの名前、USB の速度。Openbench Logic Sniffer は 2 つのページで数字が違う（100 MHz と
  200 Msps）。

**ターゲットは DSLogic や Kingst LA2016 などのシリーズ**（ユーザー、2026-11-23）。HS なので、ライトな使い方は ESP32-P4
で巻き取れそう。置き換えの地図:

| 使い方 | 今の DSLogic / LA2016 | 置き換えの候補 |
|---|---|---|
| ライト（UART・I2C・SPI を数十 MHz 以下で、長めに流して見る） | USB HS の流し取り（実用で毎秒 40 MB 前後） | ESP32-P4（OEP、目標は毎秒 40 MB 欠けなし）で同じ帯 |
| 短く速く（160 MHz まで） | 機材のメモリに貯める型 | ESP32-P4（160 MHz） |
| 160 MHz で足りない所 | 400〜500 MHz で貯める | 400 MHz でも足りないことが多い（ユーザー: 「160 MHz の P4 で足りないことは 400M とかでも足りない時が多い」）。数十 MHz の SPI の取りこぼし、ns のグリッチ、立ち上がりやリンギングは、オシロスコープ（アナログ、GHz 帯）の領域 |
| 長時間の速い流し取り | できない（HS の帯域） | H417（SS、8〜16 ch・200 MHz）。§6 の量の問題が付く |

- 160〜400 MHz の帯を埋めるために DSLogic・LA2016 を直接扱う理由は、思ったより弱い。持ち主の記録を読む（D4）だけでも乗り
  換えの入口になりうる。ただ、持っている機材をそのまま使いたい人は残る。
- 160 MHz を超える所は、ロジックアナライザではなくアナログの波形の話。OEP のアナログのチャンネルや、オシロスコープとの
  連携は別の方向として並べられる。

ここから出る方向（並べるだけ）: OEP のプローブを主な道にする（P4 が HS の帯、H417 が SS の帯: D6）、DSLogic や LA2016 も
直接扱う（今の持ち主がそのまま使える: D2・D3。どちらも FPGA の構成やファームウェアを PC から送り込む型と見られ、FX2・FX3
と同じライセンスの絡み方を確かめる。LA2016 は sigrok でもメーカーのアプリからファームウェアを取り出して使う形だったはずで、
確認事項）、持ち主の記録を読むだけにする（DSView などの記録を開く: D4、乗り換えの入口）。

機材の差し込みの形（ライセンスの切り離し方で）:

| 形 | 中身 | 切り離し | 届く先 |
|---|---|---|---|
| 別のプロセスのドライバ | 別の実行ファイルが機材を扱い、決まった約束でデータを流す | いちばん強い（何のライセンスでも） | ネイティブ |
| 共有ライブラリ（C の ABI） | 本体が読み込む | 本体が MIT なら独自のものも載る。GPL の差し込みとの組み合わせは差し込みの側の問題 | ネイティブ |
| WASM の差し込み + 本体の USB の API | 手順は WASM、USB の読み書きは本体 | 隔離できる（安全も） | ネイティブとブラウザ（WebUSB）で同じ差し込み |
| ファームウェアだけ | 機材のファームウェア（FX3 の SDK で作ったものなど）を差し込みが持ち、通信は共通の約束 | ファームウェアは SDK の条件、本体は MIT | 両方 |

ほかの繋がり: ファイル形式（.sr、VCD、今の .wireskein）、ブラウザの WebUSB /
WebSerial、試験の道具（ファイルの形式で）、AI（CLI・JSON）。

## 11. 2026-11-24 の傾き: 1 つの Rust コアを 3 つの口で

ユーザー:「方向性的には rust で組み直してネイティブアプリと web、python で同じコア使うかな」。決定ではなく傾き。この形の中で、まだ開いているものを並べる（実装はまだしない）。

```
            ┌──────── Rust コア（取り込み・保存・解析・上の段） ────────┐
            │                                                          │
   ネイティブアプリ            web（wasm）               Python（PyO3 の wheel）
   （PulseView の置き換え）    （置かずに開く・共有）     （試験・ベンチ・スクリプト）
```

### 11.1 開いている選択肢

- **コアの範囲**: 解析まで全部 / 取り込み・保存・下処理だけ Rust で、推定は当面 Python のまま（段階的）/ 推定も最初から Rust。
- **画面の共有のしかた**:
  - 同じ Rust の画面をネイティブと wasm の両方へ（egui/eframe、Slint、Iced、Dioxus など）。
  - web の技術の画面を 1 つ書き、ネイティブは殻で包む（Tauri など。コアはネイティブでは Rust、web では wasm）。
  - ネイティブと web で画面を別々に作り、コアだけ共有する。
- **波形の描き方**: GPU（wgpu）で直接 / 画面の部品の描画に任せる / 間引きの段（何段の要約を持つか）をコア側に置くか画面側に置くか。
- **web のコアの置き場**: ブラウザの中で wasm / 手元のネイティブを小さなサーバーにして web は表示だけ / 両方。
- **機器の繋ぎ方**: コアに入れる / 別のプロセス（ライセンスの切り分け、§8）/ web は WebUSB・Web Serial。
- **拡張の口**: Rust の crate として / wasm のモジュール（ネイティブでも web でも同じものが動く）/ Python のプラグイン（今の口を Python 側に残す）/ 宣言の表（§5）。
- **Python の口の形**: 今の API（`wireskein.decode` など）をそのまま保つ / 作り直しに合わせて変える。
- **移し方**: 今のリポジトリで下の層から置き換える / 別に一から作り、今の Python を答え合わせの基準にする。

### 11.2 比べる軸（§9 に足すもの）

- 3 つの口で、同じ記録から同じ主張が出るか（ベンチで確かめられる形か）。
- ネイティブと web で、画面のコードがどれだけ共有できるか。

### 11.4 どこから組むか（2026-11-24、ユーザー:「rust のみで動くようにするのでどこからでもいいけど、逆に推定のところが一番テストしやすいのでは？」）

推定から組む案の利点と注意点。

- **利点**
  - 入力は記録（エッジ）、出力は主張の、状態を持たない関数で、画面にも機材にも依らない。
  - ベンチに正解と台帳がそろっている（e2e で 1 万 2 千件余）。
  - 二重の答え合わせができる。
    - 正解との照合（正しいか）
    - 今の Python の出力との照合（同じか、差分試験）
  - 違いが出たら、どちらがよいかをベンチの数字で言える。Python に合わせる義務はない。
- **注意点**
  - 推定はまだ研究中で、構造の実験を Python で続けている。両方を追うと二重の手間になる。
    - 案 1: 研究は Rust に移す
    - 案 2: Python の今の形を凍結して基準にする
    - 案 3: 区切りごとに写す
  - 浮動小数の順番や同点の扱いで、細かい差が出る。照合は判定と主張の一致で見て、点数の数字そのものは見ない。
  - 前に要るもの: 記録を読む最小限（.wireskein / sigrok の形）と、ベンチの道具から Rust の結果を呼ぶ口（CLI の JSON で足りる）。
