# グランドデザイン（2026-11-18、案）

WireSkein 全体の方向性。急がない。決めるのは方向で、手順は段ごとに測って進める。ユーザーとの相談（2026-11-18）:
JS（wireskein-web）は固まるまで凍結。Rust はできる所から。全体の方向を先に決める。

関連: 使う人と場面、線と時間の考え方は [線のグループと時間のグループの再検討](2026-11-17-lines-and-time-review.ja.md)、
品質の回し方は [テスト計画](2026-11-17-test-plan.ja.md)、v1 の決定はメモ（B1〜B8）。

## 1. 何のための道具か（変えないもの）

- 観測の記録から、問いに要る情報を取り出して後工程（試験、スクリプト、人、AI）へ渡す（docs/concept）。
- 大切にする性質: 未解釈を解釈済みとして扱わない（黙らない）、元のデータを書き換えない、CLI と JSON が基本、呼び出す側が
  対象と処理を決める。
- 渡される知識（K0: 何も 〜 K5: 期待）に関わらず、解析は 1 つの流れで、知識はその段に入り、出力の形は同じ
  （再検討 §2、§10）。analyze・decode・verify は入口の違い。

## 2. 構成（リポジトリと役割）

| もの | 役割 | 方向 |
| --- | --- | --- |
| wireskein（Python のパッケージ） | 公開の口（`capture`、`runlog`、`verify`、`decode`、`sources`: v1 の B7）、CLI、解析 | 口はここに残す。中身は下から順に Rust のコアへ |
| エンジンのコア（Rust、将来） | ファイル形式、エッジの見え方、カーネル、役割を与えた復号、照合 | wireskein の中のクレート。Python からは PyO3、JS からは WASM |
| wireskein-web（JS） | ビューア | **凍結**（不具合の直しだけ）。形式が固まったら、コアの WASM を使う形で再開 |
| pytest-embedded-wireskein | 試験への組み込み | Python のまま |
| oep-client-python / -js | プローブからの取得（B1: 取得の組み立てはこちらへ） | 変えない |
| wireskein-captures | 生の記録（正解の元） | 変えない（きれいな取得だけ） |
| bench/、eval/ | 方式を比べて選ぶ、正解付きの評価 | Python のまま。コアを移すときの照合の基準にもなる |

## 3. 層と、その置き場所

下から上へ。下ほど仕様が固く、速さが効き、ほかの言語と共有したい。上ほど研究中で、試す速さが効く。

| 層 | 中身 | 仕様 | 今 | 行き先 |
| --- | --- | --- | --- | --- |
| L0 ファイル形式 | `.wireskein`、`.sr`、VCD の読み書き、区間、欠損 | wireskein-format（固い） | Python と JS で二重 | **Rust（最初）** |
| L1 エッジの見え方 | 変化の列、ラン、間引いた線、events、アナログ | 同上 | Python | Rust |
| L2 カーネル | グリッチ除去、ゲート（collapse）、サンプリング、ビットの読み、区切り、宣言の定義の解釈器、DMI | 内部（試験とコーパスで固定） | Python（numpy と一部のループ） | Rust |
| L3 役割を与えた復号 | decode（wireskein-analysis）、型付きの層（ビット → フレーム → 語 → 方式） | analysis-format | Python | Rust |
| L4 照合 | verify の検査（run-format の期待） | run-format | Python | Rust（L3 の後） |
| L5 推定 | 下調べ、線の組、時間の区切り、仮説、点数、詰め方、確かさ | 研究中（ベンチで決める） | Python | **当面 Python**。意味が固まってから判断 |
| L6 上位と関係 | デバイス、Debug Module、コマンドと応答、ほかの人のプロトコル（Python） | protocols | Python | 定義（TOML）とほかの人の Python はそのまま。コアの部分は L3 と一緒に |
| L7 口と出力 | API、CLI、JSON、きれいな記録、注釈 | 各形式 | Python | 口は Python のまま |

決まりごと:

- **1 つの層に実装は 1 つ。** Rust に移した層の Python 版は残さない（二重の実装はずれる。今の L0 の二重もなくす）。
- **移す前後で出力はバイトまで同じ。** 評価コーパスと測定台の全部で比べてから置き換える（2026-11-18 の最適化と同じやり方）。
- **拡張の口は保つ。** 方式の定義（TOML）、デバイスの定義、ほかの人の上位のプロトコル（Python）、測定台の差し込み口（methods）。
  L5 を Python に残す間は、methods もそのまま。

## 4. 言語の方針

- **Python**: 公開の口、CLI、推定（L5）、ベンチ、試験への組み込み。標準ライブラリだけで動く所（runlog、capture の保存）は
  そのまま。
- **Rust**: L0〜L4 を下から順に。1 つのクレート（ワークスペース）で、Python には PyO3 と maturin、JS には WASM。
  numpy との受け渡しはコピーなしで。
- **JS**: 凍結。再開するときは、ファイル形式も復号も Rust の WASM を使い、自前の読み書きはやめる。
- **配布**: Rust を入れたら、wheel はビルド済みが必須（Linux・macOS・Windows、x86_64・arm64）。純 Python の代わりは持たない
  （二重の実装になるため）。
- design §2「ネイティブ実装を作るなら別リポジトリ」は、**並べて別の実装を作る**前提の決定だった。コアを入れ替える形にするなら、
  同じリポジトリ・同じ版にする方が、版のずれと二重の仕様をなくせる。変えるのは計画が決まってから（v1 の方針）。

## 5. 仕様が先

- ファイル形式、記録の形式、分析の形式、events は、言語に依存しない仕様として持ち、番号はリリースまで 1（メモ）。
- 実装の正しさは、仕様と、評価コーパス（eval/corpus）、測定台のデータ（bench/data: 実機の正解付き）で決める。
  正解は WireSkein や DUT から取らない（メモ）。
- Rust に移す順番は、仕様の固さの順（L0 → L1 → L2 → L3 → L4）。L5 は、分析の形式（範囲、バスと相手、覆い:
  再検討 §10）が固まってから。

## 6. 品質の回し方（今のやり方を続ける）

- テスト計画（目標 → 指標 → データ → 合否の線はなく、いちばん良いものを採る）。順番は「取れない信号を取れるように」→
  「悪いデータで粘る」。
- 方式の比べ合いは測定台（多くの方式は Actions で、1 つの方式の詰めは手元）。製品へは段を分けて、測ってから。
- 2026-11-18 時点の数字（手元、58 のデータセット）: 誤確定 110 → 7、読めたバス 4950 → 5315、確定したバス 3481 → 4355。

## 7. 段階（急がない。移る条件で区切る）

| 段 | すること | 次に移る条件 |
| --- | --- | --- |
| 0（今） | Python で推定を詰める。線 × 時間のモデル（再検討）をどこまでできるか測る。v1 の仕様（events、分析の形式）を決める | events と分析の形式が v1 として決まる |
| 1 | Rust のクレートを作り、L0（ファイル形式）と L1 を移す。Python は中で呼ぶ。wheel の配布を整える | コーパスと測定台で出力が同じ、配布が全 OS で通る |
| 2 | L2（カーネル）と L3（役割を与えた復号）、L4（照合）を移す。速さを測る | 同上。長い記録の時間が目標に入る |
| 3 | wireskein-web を再開（WASM で、Python なしに開く・復号する） | ビューアの要件が決まる |
| 4 | L5（推定）を移すかを判断（研究の速さと、ブラウザでの解析の要否で） | — |

## 8. 決めること（計画を決めるとき）

1. Rust のコアを wireskein のリポジトリの中に置くか（推奨）、別のリポジトリにするか。design §2 の書き換え。
2. wheel の対象（OS、CPU、Python の版）と、Rust の最低の版。
3. 段 1 を始める時期（events と分析の形式が決まった後を推奨）。
4. L5（推定）を将来も Python に置くか（研究の道具として Python のまま、製品の推定だけ Rust、という分け方もある）。
5. wireskein-web を再開する時期と、それまでの凍結の範囲（不具合の直しだけ、でよいか）。
