# アプリの画面をゼロから検討する（2026-11-25〜、方向を確かめる段階）

ユーザー（2026-11-25）:
- 今ある web（wireskein-web）は簡易表示なので使わない前提。
- 大幅に手を入れるので、ブラウザベースかネイティブかをゼロベースで検討する。
- PulseView ではなく、Saleae Logic（Logic 2）を超える使い勝手を目指す。
- かなりの作り込みと描画が要る想定。

このノートでは、要る要素と環境（画面の作り・言語・描画・届く先）を並べる。前のノート bench/notes/2026-11-23-ui-directions.ja.md（製品の形 P1〜P7、言語、画面の作り G1〜G7、機材、拡張）を土台にし、そこで開いていた「画面の共有のしかた」「波形の描き方」をこの前提で掘り下げる。**最初に決めない。案は広く並べ、§7 の試作で数字を取って比べる。**

## 0. 前提（決まっていること）

- アプリはフル Rust（コアは Rust。bench/notes/2026-11-24-rust-plan.ja.md §5）。画面の言語は開いている（Rust だけ、TS と組む、ほか）。
- 解析・取り込み（OEP のクライアントも wireskein の中）・ファイルの読み書きは、Rust の部品としてそろいつつある（rust-plan §28〜§37）。画面はそれを呼ぶ。
- 試験の道具は今の形（Python のライブラリ、verify、CLI・JSON）で育てる。アプリとはファイルの形式で繋ぐ。
- ライセンスは MIT で配れること（同梱物を含めて）。

## 1. 越える相手: Logic 2 の今

Logic 2（Electron の上に作られたアプリ。機材は Saleae の Logic 8 / Pro 8 / Pro 16 と、新しい Logic MSO）が使いやすいと言われる所と、越えられそうな所を並べる。機能の細部は版で変わるので、試作の前に今の版を触って確かめる（確認事項）。

**よい所（最低でもここまでは要る）**
- 開いた瞬間から波形が動く。拡大・移動がなめらかで、ホイールとドラッグだけで迷わない。
- デジタルとアナログを同じ時間軸に並べる。
- プロトコルの解析を足すと、波形の上に注釈が載り、右のパネルに表（データテーブル）が出る。表と波形が連動する。
- 測定: 線にマウスを載せると幅・周期・周波数が出る。区間を選ぶと統計が出る。タイミングマーカー（2 点の差）。
- 検索（解析の結果の中を）。
- トリガの設定、取りながら見る（取り込み中も波形が流れる）。
- 拡張: Python の High Level Analyzer（解析の結果の上にさらに読む）、測定の拡張、マーケットプレイス。
- 自動化の API（外のプログラムから取る・書き出す）。
- 見た目が今風で、ダーク / ライト。

**越えられそうな所（WireSkein が既に持っている力と重なる）**
- **設定なしで読む:** Logic 2 は線ごとに解析を手で足す。WireSkein はバスと役割を自動で推定し、確からしさまで出す（P3）。
- **ノイズに強い:** 安いプローブ（ESP32-P4 など）の汚れた線でも読める。読めなかった区間・疑わしい所を見せられる。
- **試験と繋がる:** 期待と照合した OK / NG を時間軸に出す（P4、verify・run の記録）。
- **大きな記録・長い流し取り:** Logic 2 は記録をメモリに載せる作りで、長い取り込みはメモリで頭打ちになると言われる（確認事項）。こちらは変化で持つ・要約の層・分割読みを既に持つ。H417 の SS（毎秒 200〜400 MB）も視野。
- **機材が開いている:** 自前の OEP のプローブが第一。各社の記録も読める。
- **重さ:** Electron のアプリは起動とメモリが重い。ネイティブなら軽くできる。
- **上の段:** UART の行、Modbus、SCPI、デバイスパック、RISC-V の DM など、バスの上の意味まで読む。
- **比べる:** 2 つの記録を並べて合わせる（align）、差を見る。
- **AI・スクリプト:** CLI と JSON が最初からある。

| 要素 | 中身 | |

### 2.7 速さの目標（試作で測る数字の候補）

- 開いてから最初の絵まで: 1 億の変化の記録で 1 秒以内、10 億で 2 秒以内（全部を読み終わる前に、要約から描く）。
- 拡大・移動: どの倍率でも 60 fps を落とさない（120 Hz の画面では 120 fps を目指す）。
- 取りながら: 毎秒 40 MB（P4X）を落とさずに描き続ける。毎秒 400 MB（H417）は受けて残すのが先で、描くのは間引いてよい。
- メモリ: 記録の大きさに比例させない（要約と見えている所だけ）。

## 3. 描画の作り（画面の作りに依らない部分）

どの環境を選んでも、重い所の作りはほぼ同じになる。ここは Rust のコアの部品として先に作れる（画面なしで試験できる）。

- **要約の層（LOD）:** 線ごとに、時間の区切り（2 の冪の幅）ごとの「最初と最後の水準、変化の数、最小・最大」の段を持つ。どの倍率でも、1 ピクセルあたり 1〜2 区切りを読めば描ける。アナログは最小・最大・平均。
  - 開くときに作るか、ファイルに持つか（.wireskein の付属物として）。
  - 取りながら足していけること。
- **注釈の層:** 解析の項目を時間で引ける形（区間木や、区切りごとの索引）に持つ。倍率ごとに、どの段を描くか、収まらない文字を畳むかを決める。
- **タイル:** 見えている範囲を、倍率ごとのタイルにして GPU に置き、移動のたびに作り直さない。
- **GPU で描く:** 線と四角はインスタンス描画、文字はアトラス。1 フレームで数十万の図形を描ける作りにする。
- **非同期:** 重い読み（ファイル、解析）は別スレッドで、描画を止めない。読み終わった所から細かくなる。

この層を `crates/` の部品にしておけば、ネイティブでも wasm でも、どの画面の作りからも使える。各案を比べるときも、この部分は共通にできる。

## 4. 環境の案

### 4.1 届く先

| 届く先 | よい所 | 引き換え |
|---|---|---|
| ネイティブのアプリ | USB を直に、ファイルを直に、メモリの上限なし、軽い、オフライン | 配布（署名・更新）、OS ごとの差 |
| ブラウザ | 置かずに開く、共有のリンク、どの OS でも | 下の §4.2 の制約。USB は WebUSB（Chromium 系のみ）、大きなファイルの扱い |
| 両方 | 使い分け | 作りによっては二重の手間 |

### 4.2 ブラウザの今の制約（2026-11 時点で確かめたもの）

- **WebGPU:** Chrome / Edge は 113（2023）から。Safari は 26（2025）から macOS・iOS など。Firefox は Windows で 141、Apple シリコンの macOS で 145 から。**Linux の Firefox と Intel の Mac はまだ途中**。WebGL2 は全部で使える。
- **wasm のメモリ:** 32 ビットの wasm は 4 GB まで（実際はもっと手前）。64 ビット（memory64）は Chrome 133・Firefox 134 から。**Safari はまだ**。記録を全部載せる作りは、ブラウザでは数 GB で止まる。要約と見えている所だけにする作り（§3）が前提になる。
- **USB:** WebUSB は Chromium 系だけ（Firefox・Safari にはない）。ブラウザから取り込むなら Chrome / Edge に限られる。
- **ファイル:** 大きなファイルを開くのは File API で読めるが、保存して書き戻す（File System Access）は Chromium 系だけ。
- **スレッド:** wasm のスレッド（SharedArrayBuffer）は、配信の側で COOP / COEP の見出しが要る。

### 4.3 画面の作りの案

| 案 | 中身 | ネイティブ | ブラウザ | 描画の自由 | 部品（表・木・入力） | 気になる所 |

| E2 宣言型の Rust の GUI | iced、Slint、Xilem / Masonry（Vello）、Makepad、Dioxus（ネイティブの Blitz）、GPUI の派生 | ○ | 案による（iced・Slint・Makepad・Dioxus は wasm も） | 案による | 案による | 成熟度がまちまち。Slint はライセンス（GPL / 独自 / 商用の 3 つ）を確かめる。GPUI は Zed の中で育っていて、単体の版は 1.0 前で派生が分かれている |

| E6 Qt | C++ / QML（Rust からは cxx-qt）。PulseView・DSView と同じ型 | ◎ | △ | ○ | ◎ | 言語が混ざる。LGPL の扱い。前のノートで遠ざけた方向 |
| E7 Flutter + Rust | 画面は Dart、コアは flutter_rust_bridge | ◎ | ○（CanvasKit） | ○ | ◎ | 言語が 2 つ。wasm のコアとの繋ぎ |

### 4.4 案ごとの「Logic 2 を越える」への効き方

- **描画の上限:** どの案でも、波形の面を GPU で自前に描けば、上限は §3 の作りで決まる（E3 の WebGPU、E1・E5 の wgpu は同じ道具の上）。差が出るのは、パネル・表・文字の作り込みの手間と、ブラウザの制約。
- **軽さ:** E1・E2・E5 がいちばん軽い。E3 の Tauri は OS の webview なので Electron よりは軽い。E4 は重い。
- **今風の見た目と作り込み:** E3・E4・E7 は部品と作り方の蓄積が多い。E1 は見た目を詰めるほど手間が増える。
- **ブラウザで同じものが動くか:** E1・E3・E4 は同じコードで動く。E2・E5 は案による。E6 はほぼ別。
- **レイアウトの自由さ:** web の技術にはドッキングの部品があり、egui にも egui_dock がある。別の窓への切り離しは、ネイティブなら OS の窓をそのまま使える。ブラウザは別の窓を開いて窓どうしで状態を受け渡す作りになる（手間と制約は確認事項）。宣言型の Rust の GUI は案ごとに差が大きい。
- **ネイティブの力（USB を直に、大きなファイル、メモリ）:** E1・E2・E5・E6・E7 は直に使える。E3・E4 は殻（Tauri / Electron）の側の Rust を通す。

## 5. 比べる軸

前のノートの §9・§11.2 に足すもの:

- §2.7 の速さの数字（最初の絵、fps、取りながら、メモリ）。
- 注釈の文字が多い所の速さと読みやすさ（文字の描画の質、日本語）。
- 部品の作り込みの手間（表 1 万行のスクロール、木、検索の入力、設定のフォーム）。
- レイアウトの自由さ（§2.6）: ドッキング、別の窓への切り離し、同じ種類のパネルを複数、保存と切り替えが、どれだけの手間でできるか。ネイティブの複数の窓とブラウザの別の窓（ポップアップと窓どうしの受け渡し）の差も。
- ネイティブとブラウザで共有できるコードの割合。
- 起動の速さ、配る物の大きさ、メモリ。
- Linux（作る人の主な環境）・Windows・macOS での動き。とくに Linux のブラウザと webview。
- IME とアクセシビリティ。
- 作る人の数と言語の数（Rust だけで済むか）。
- 依存の寿命（成熟度、1.0 前か、作っている所が続くか）。

### 9.2 数字（Xvfb の上。fps はソフトウェア描画なので参考にならない）

  ただし 10 億の要約が全部できるのは 15.6 s 後（2 スレッド）。そこまでは右の方が「要約 n%」。

  GPU のある画面の fps はまだ測っていない（この機械の Xvfb は DRI3 がなく llvmpipe。1600×960 を CPU で塗って 10〜20 fps）。

  GUI では最初の絵はすぐでも、一覧が出るまで 2 分待つ。**大きな記録では解析の速さとメモリが先の問題**（GUI の描画ではない）。

### 9.4 詰まった所・気になった所

- **文字:** ネイティブは日本語のフォントを自分で探して足す（Noto Sans CJK の .ttc を読む）。web に同じ見た目を求めるなら数 MB の
  フォントを持つことになる。egui 0.37 は harfrust で字形を組むので文字の質は前より良いが、等幅の数字列の見た目はまだ詰めていない。
- **IME:** この環境（Xvfb、入力メソッドなし）では確かめられていない。検索の欄に日本語の言葉（「書き込み 0x72」）を入れた検索は通り、欄にも正しく出る（引数から入れた。キーボードからの変換は未確認）。fcitx / ibus での
  変換中の表示は利用者の画面で確かめる（確認事項）。
- **egui の API の揺れ:** 0.37 で `App::ui(ui)`、`Panel::top`、`Id::new` の非推奨など、版ごとに書き直しが要る（1.0 前）。
- **見た目の作り込み:** 角丸・影・余白・アイコンを今風にするのは自分で一つずつ。標準の見た目は「道具」っぽい。表の行の高さ・
  選択の色・列の並べ替え（未実装）も自前。
- **重なりの多い注釈:** 項目が画素より多い所は「いちばん悪い状態」で塗ったが、50 万項目に 0.5 % の誤りでも全体表示はほぼ全部が誤りの色に
  なる。誤りの割合で塗る・誤りだけ別の細い帯にする、などの工夫が要る。検索に合った項目の枠（2 px）もライトでは見えにくい。
- **解析の層:** "all" の文書でも I2C は transactions だけ、分割読みでは final の層だけになる。3 段（取引・フレーム・ビット）は試作の中で
  クロックの立ち上がりから作った（「(GUI)」の段）。本来はエンジンの文書がフレームとビットの時刻を持つべき（wireskein 側の要件）。
- **メモリの形:** 解析の項目を serde_json の Value のまま 370 万行持ったら 4 GB を超えて落ちた。一覧の行は詰めた形（ビット 1 B、
  バイト 2 B）と、文字を 1 本の String にまとめた索引にして 1.2 GB。画面に要るのは列ごとの詰めた配列。
- **web の制約:** スレッドがないので要約と解析は開くときに止まって作る（1e8 で数秒）。ファイルを開く道（File API）と大きな記録の
  分割読みはまだ。wasm は 13.7 MB（gzip で 4.1 MB）: エンジンと解析を丸ごと持つため。
- **fps の計測:** GPU のある画面で測る道（ヘッドレスで DRI3 のある X か、利用者の画面で `--bench`）がこの機械にない。

### 9.6 1 フレームの内訳を測り、図形を減らした（2026-11-25、試作 1 の改良）

§9.2.1 の「合成 1e8 で 1 フレーム 34〜41 ms なのに波形 CPU は 1.3〜2.2 ms」を分けるため、`--bench` に 1 フレームの内訳を足した
（中身と列の意味は proto/gui/README.md の「--bench の内訳」）。

- **測り方:** egui・eframe・egui-wgpu・wgpu は `profiling` の区間を持つ。`profiling` を tracing の後ろで動かし、自前の小さな subscriber で
  区間ごとの時間を足す（`--bench` のときだけ）。egui の組み立て（`Context::run`）、三角形にする処理（`Context::tessellate`）、バッファの更新
  （`Renderer::update_buffers`）、命令を作る・提出・表示（`get_current_texture` / `Queue::submit` / `present`）が別々に出る。パネルごと
  （波形・ミニマップ・一覧・測定）はアプリが自分で測る。図形・頂点・三角形・描画の単位（prims）は、1 フレームの図形を egui の層から写して
  三角形にして数える。メインスレッドの CPU 時間（Linux）も出す: この機械は他の仕事で混んでいて（load 10〜15）、壁時計の時間は倍ほど揺れる。

     配置からやり直していた）。1 フレーム 1.5〜3 ms → 0。
  3. 注釈の文字を 1 つずつの切り抜き（clip）で描くのをやめ、箱に収まる文字だけを波形の切り抜き 1 つで描く（文字ごとに描画の単位が
     分かれていた）。
  - `--old-draw` で前の描き方に戻せる（同じ機械で前後を比べるため）。
- **やらなかったもの（数で決めた）:** タイルの Mesh の使い回し・egui_wgpu の callback で頂点を GPU に置いたままにする案は、手直しの後で
  三角形にする処理とバッファの更新が合わせて 1 フレーム 1〜3 ms（波形の分はその一部）しかなく、この機械では効く所がない。利用者の
  機械で `upload` / `encode` / `submit` が大きければ次に試す。見えていないパネルは egui_dock がもともと描かない（同じ葉の後ろのタブは
  ui が呼ばれない）ので止める仕事がない。
- **利用者の機械の 34〜41 ms の見立て（確かめる前）:** mixed-1 が `--bench`（vsync を切るつもりの AutoNoVsync）でも 60 fps で頭打ちなので、
  Windows では垂直同期が切れていない（DX12 の窓では Immediate が使えず Fifo に落ちる、など）と見られる。すると 1 フレームの仕事が
  16.7 ms を少しでも越えると 2 つ分の 33.3 ms に丸まり、p50 34〜41 ms と合う。加えて eframe の既定（LOW_LATENCY）は
  `desired_maximum_frame_latency = 1` で、CPU が前のフレームの GPU の終わりを待つ（CPU と GPU が重ならない）。`--latency 2` と
  `--present immediate` を流してもらって、`acquire` / `present` の待ちがどこに出るか、結果の頭の `# gpu:`（API・表示の仕方）と
  合わせて見る。
- **流しの長さ:** 倍率ごとに 24 フレームを超えて 3 秒経てば次へ、掃引は 12 秒まで。合成 1e9 は全体で 85〜90 s（要約を待つのが 18 s、
  この機械で 1 フレーム 150〜300 ms の所が多いので）。GPU のある機械では倍率ごとに 96 フレームで 1〜2 秒ずつ。

#### 9.6.1 ユーザーの機械で流し直した結果（2026-11-25、Windows・Iris Xe・i7-1355U、60 Hz）

| 記録 | 直す前 | 直した後 |
| --- | --- | --- |
| 合成 1e8（16 本） | 24〜30 fps（p50 34〜41 ms） | 54〜60 fps（p50 16.6〜18.5 ms）。最初の絵 135〜251 ms、要約 0.8〜1.4 s |
| 合成 1e9（16 本） | 流せていない | 53〜60 fps。最初の絵 102 ms、要約 8.7 s、RSS 1.3 GB |
| mixed-1 | 57〜60 fps | 54〜59 fps（60 Hz で頭打ち） |
| i2c-controller-400k-nack.vcd | 52〜54 fps | 60〜61 fps。first paint は NaN のまま（直っていない。§14.1） |

- 1e8 の 4 本（通常、`--old-draw`、`--latency 2`、`--present immediate`）はどれも 55〜60 fps。直す前の描き方でも速いので、前の遅さは波形の図形の数でも垂直同期でもなかった。一緒に直したミニマップ（毎フレーム解析の 50 万項目から作り直していた）が残る候補。
- 波形を作る CPU は 1 フレーム 0.5〜1.9 ms。どの倍率でも 60 fps の予算に収まる。

## 10. 試作 2: web の技術（2026-11-25）

proto/gui-web（本番の workspace の外。使い捨て）。中身・起動・速さの測り方の詳細は proto/gui-web/README.md。試作 1 と同じ中身を、
画面は TypeScript、波形は WebGPU（なければ WebGL2）、計算は view-core と wireskein の Rust の部品を wasm にして作った。

### 10.1 作ったもの

- **画面:** TypeScript + Solid 1.9 + dockview-core 8.9（MIT）、ビルドは Vite。中身は試作 1 と同じ: 波形（拡大・移動・慣性・範囲・全体、
  ミニマップ、目盛り、マーカー 2 本、カーソルの測定）、注釈 3 段・確からしさの点・読めなかった区間、波形から独立した結果の一覧
  （仮想の行、列の選択と幅、主張・層の切り替え、連動の入り切り）、検索（日本語の言葉）、次の誤りへ、ドッキング（分ける・タブ・
  大きさ・浮かせる・同じ種類を複数・名前を付けて保存と切り替え）、一覧を別の窓に（2 通り: 下）、ダーク / ライト、ファイルを開く
  （File API とドラッグアンドドロップ、URL）。
- **フレームワークの選び方:** 重い所（波形のキャンバス、何十万行の一覧）は結局どれでも自前の命令的なコードになる。周りの UI は
  細かく何度も変わる（状態の表示、測定、検索の件数）ので、仮想 DOM の差分を取らない細粒度の反応（Solid のシグナル）が合う。
  React はフレームごとに変わる値で再描画を抑える工夫（memo）が要り、配る物も大きい。Svelte 5 も同じ方向の候補（比べてはいない）。
  素の TS は表示の同期を手で書く量が増える。Solid 2.0 は出たばかりで vite-plugin-solid がまだ 1.x しか受けないので 1.9 にした。
  dockview は素の TS の版（dockview-core）があり、別の窓（popout）・浮いた窓・保存（toJSON / fromJSON）を持つので選んだ
  （golden-layout も候補だが古い）。
- **wasm 2 つ:** `wasm/view`（画面のスレッド、152 KB）は view-core の薄い口。`Scene.frame` が見えている所を GPU のインスタンスの列
  （8 個の float: 矩形か太さのある線分、色はパレットの番号）にし、文字は「どこに何を」だけ返す。`wasm/engine`（Worker、2.9 MB、gzip
  0.9 MB）は wireskein-io / -core / -analysis（本番の crates を path で読むだけ）と、試作 1 の model.rs の解析の読み方・フレームとビットの段・
  検索をほぼそのまま移したもの。
- **スレッド:** 画面のスレッドは受け取るだけ。ファイルを読む・要約の段 0 を作る（合成は 2 つの Worker で 16 本を分ける）・解析・
  検索はすべて Worker（型付き配列を移す。コピーしない）。要約の上の段は画面のスレッドで受け取りながら作る（`Lod::append`）。
  注釈の索引は Worker で作ったものを部品のまま渡す（view-core に `Track::parts / from_parts`、`AnalogLine::levels / from_parts`
  を足した。どちらも足しただけで、試作 1 はそのまま）。
- **描画:** 波形の図形は 1 回の draw（インスタンス描画）。WebGPU と WebGL2 で同じ形のシェーダ（WGSL と GLSL、各 40 行ほど）。
  文字は上に重ねた 2D キャンバスにブラウザのフォントで描く（日本語のフォントを持たなくてよい）。目盛りの線は wasm 側で波形の下に敷く。

GPU に渡すまでの CPU の時間（試作 2 は括弧に wasm の分。残りは 2D キャンバスの文字と GPU のコマンド）。メモリは試作 1 がプロセスの RSS、
試作 2 は Chrome のプロセス全部の RSS（ブラウザ・GPU・ユーティリティを含む）と、その中の内訳。

### 10.3 web で良かった所

- **画面が止まらない:** ファイルを読む・要約・解析・検索を Worker に出すのは素直に書けた（Worker 2 種、メッセージは型付き配列を移すだけ）。
  試作 1 の wasm 版は開くときに止まって作っていたが、ここでは 1e9 の要約（24 s）も I2C 10 万取引の解析（200 s）も、その間ずっと
  波形を動かせる。要約は 2 つの Worker で線を分け、作れた所から描く（試作 1 のネイティブの 2 スレッドと同じ形）。
- **wasm が小さい:** 画面の側 152 KB、Worker の側 2.9 MB（gzip 0.9 MB）。試作 1 の wasm 13.7 MB（gzip 4.1 MB）の大半は egui と wgpu。
  JS は main 562 KB（gzip 116 KB。うち dockview が大きい）。
- **見た目の作り込みが速い:** 色・余白・角丸・影・メニュー・ツールチップは CSS で数行ずつ。ダーク / ライトは CSS 変数と、波形は
  GPU のパレット（uniform）の差し替えだけ。試作 1 で「道具っぽい」と書いた所が、同じ時間でずっと今風に寄る。
- **表:** 仮想の行は自前（行の要素を使い回して scroll で埋める。約 360 行）。320 万行（ビットの層）も、要素の高さの上限（Chrome で
  約 3,300 万 px）を越える分は scroll を縮めて読む。列の幅のドラッグ、色の印、当たりの色付けは CSS で簡単。試作 1 の egui_extras と
  同じく見えている行しか作らないので、50 万行・320 万行でも引っかからない。
- **ドッキング:** dockview-core が分ける・タブ・大きさ・浮いた窓・別の窓（popout）・保存（toJSON / fromJSON）を一通り持つ。
  既定のレイアウト 3 つ、名前を付けて保存（localStorage）、同じ種類を複数、がそれぞれ十数行。egui_dock と同じくらいの手間で、
  別の窓まで付いてくる。
- **別の窓（2 通り）:** (1) dockview の popout: パネルの要素ごと別のブラウザの窓に移す。JS の状態は同じものなので受け渡しは要らない
  （ネイティブの egui の `show_viewport_immediate` に近い）。(2) 独立した窓（list.html）: BroadcastChannel で層のデータを写して受け取り、
  選択・検索の当たり・テーマを送り合う。メインの窓を読み直しても残り、つなぎ直す。Tauri や別の画面でも同じ形で動くのは (2)。
- **日本語:** 文字はすべてブラウザが描く（OS のフォント。何も持たない）。検索の欄は普通の `<input>` なので IME の変換もブラウザの
  もの（変換中は composition のイベントで検索を止める）。試作 1 のようにフォントを探して足す処理が要らない。
- **ファイルを開く:** File API とドラッグアンドドロップがそのまま使える（File を Worker に渡すと Worker が読む）。URL でも開ける。
- **測る道具:** ヘッドレスの Chrome（puppeteer-core）で開いて、ベンチの結果・スクリーンショット・Chrome のプロセスのメモリを取れる。

### 10.4 詰まった所・気になった所

- **wasm の境目のコピー:** Worker の wasm と画面の wasm はメモリが別なので、渡すたびに写す。320 万行のビットの層を含む 370 万行を
  画面の側の索引に入れるのに 0.3〜2.3 s 画面が止まった（JS → wasm のコピーと wasm のメモリの伸び）。合成のアナログ 400 万サンプルも
  0.45 s。wasm のスレッド（SharedArrayBuffer に 1 つのメモリ、COOP / COEP は配信の道具で用意済み）にすれば写さずに済むが、Rust は
  nightly の build-std が要る（今は使っていない）。少しずつ受け取る（フレームごとに区切る）手もある。
- **wasm の遅さ:** 同じ Rust でもネイティブより遅い。ファイルを読む（zip の展開と bits → 変化）は 5〜6 倍（i2c 10 万: 0.37 s → 2.4 s、
  h417: 0.2 s → 1.1 s）、要約は 1.5〜2.7 倍、解析は 1.5 倍（136 s → 200 s）。この機械は SwiftShader が CPU を取り合うので割り引いて見る。
  wasm にはスレッドもないので、解析を分けて並べることもできない。
- **wasm のメモリは縮まない:** 解析の Worker は I2C 10 万で 0.95 GB、読む Worker は 0.2 GB のまま。使い終わった Worker は閉じる
  （読む Worker は閉じるようにした）。32 ビットの wasm の 4 GB が上限で、解析を丸ごと（3.5 GB）はブラウザでは無理（分割読みが前提）。
- **dockview-core 8.9.1 の ESM 版に CSS が入っていない:** UMD 版だけが CSS を注入する。Vite のプラグインで UMD 版から取り出した。
  popout の窓では Solid の委譲したイベント（document に付く）が効かないので、開いた窓の document に `delegateEvents` を足した。
  ResizeObserver も要素の窓のものを使う（移った先で付け直す）。
- **Solid 2.0:** 出たばかりで vite-plugin-solid が 1.x しか受けない。1.9 にした。TypeScript は 7（Go 版）がそのまま使えた。
- **ヘッドレスの Chrome:** GPU がないので WebGPU は SwiftShader（CPU）。スクリーンショットに WebGPU のキャンバスが写らない（白い）。
  1 フレームを読み戻して重ねる口を作って撮った。fps は SwiftShader と合成の速さで、GPU の画面の数字ではない（試作 1 の Xvfb と同じ注意）。
- **文字の描画:** 2D キャンバスの fillText は SwiftShader の上では重く、注釈の文字が多い倍率で 1 フレーム 15〜20 ms かかった（wasm は 1.4 ms）。
  GPU の画面では軽いはず。文字を GPU のアトラスで描く案（§3）と比べる余地。
- **2 つの言語:** 解析の読み方（model.rs）と検索は Rust に残したので、TS 側は画面だけ。それでも状態の型（層、列、選択）は両側に要る。

### 10.5 Tauri と WebKitGTK

- **Tauri の殻は作れなかった:** この機械には webkit2gtk-4.1 / javascriptcoregtk-4.1 / libsoup-3.0 の実行用のライブラリはあるが、
  開発用のヘッダ（pkg-config の .pc）がなく、webkit2gtk-sys が通らない（入れるには root が要る）。利用者の機械で
  `libwebkit2gtk-4.1-dev` などを入れれば試せる（確認事項）。
- **代わりに同じ WebKitGTK（2.52.6）の MiniBrowser で同じページを開いた**（Tauri は Linux でこれと同じ webview を使う）:
  - そのまま動いた（Worker、wasm、BroadcastChannel、dockview、Solid）。
  - WebGPU: 2.52 では「unstable」の機能。`--features=+WebGPU` で `navigator.gpu` は現れるが、この機械（DRI なし）ではアダプタが出ず、
    WebGL2 に落ちた。Linux の WebKitGTK の WebGPU は GPU のある機械でも確かめが要る（確認事項）。**Tauri の Linux では WebGL2 で
    描く前提**にしておくのが安全（同じシェーダの WebGL2 版は用意済み）。
  - 例（mixed-1、窓の幅が 768 px で Chrome の半分）: 最初の絵 0.61 s、解析 5.0 s（Worker）、要約 0.06 s。ベンチは 15〜19 fps、
    波形 CPU 2〜6 ms（wasm 0.05〜0.2）。合成 1e8: 最初の絵 0.54 s、要約 6.9 s、作り物の解析 6.0 s。
  - Chrome より llvmpipe の WebGL2 の方がこの機械では速い（Chrome の SwiftShader の WebGPU は 2〜8 fps）。
- Tauri にすると、ファイル・USB・解析は殻の側の Rust（ネイティブ、スレッドあり）で走らせ、画面へは IPC で渡す形になる。今の Worker と
  の境目（型付き配列を渡す）をそのまま IPC に置き換えられるように作ってある。wasm の遅さ（§10.4）とメモリの上限は消える。

- **見立て:** 画面の作り込み（見た目、表、ドッキング、別の窓、日本語）は web が明らかに楽で、Logic 2（Electron）と同じ土俵の見た目に
  寄せやすい。重い所（要約・解析）は Rust のまま共有でき、波形は WebGPU / WebGL2 で同じ設計（§3）が通る。弱いのは wasm の遅さと
  Worker の間のコピー: ブラウザ版はこれを抱え、ネイティブ版（Tauri）は殻の側の Rust で避ける、という分け方が見える（E3）。
  逆に egui は 1 つの言語で全部が書け、ネイティブの速さとスレッドがそのまま使えるが、見た目と部品の作り込みの手間が残る。
- **次に確かめること:** GPU のある画面での fps（両方の `bench`）、Tauri の殻（Linux の WebKitGTK、Windows の WebView2）、
  wasm のスレッド（SharedArrayBuffer に 1 つのメモリ: Worker 間のコピーを消す）、文字を GPU のアトラスで描く案、ファイルの記録を
  区画ごとに渡して最初の絵を早める。

### 11.3 IPC の渡し方の比べ

合成 I2C 10 万（画面へ 240 MB: 線の変化 101 MB、370 万行の解析の層 140 MB ほど）と合成 1e8（88 MB: 要約の段 0 と作り物の 50 万行）。
「止まり」は開いてから要約と解析が来るまでの間の、アニメーションのフレームの間のいちばん長いもの（画面のスレッドが塞がった長さ。
ベンチの待ちの間は描き続けているので、llvmpipe の 1 フレーム 50〜100 ms が下限）。

| 渡し方 | I2C: 最初の絵 | I2C: 解析が殻 → 画面に来るまで | I2C: 止まり | 1e8: 要約 | 1e8: 解析 → 画面 | 1e8: 止まり |
|---|---|---|---|---|---|---|
| wasm の Worker（比べ） | 3.16 s | +1.9 s | 0.39 s | 6.7 s | +4.8 s | 0.37 s |
| json | 6.39 s | +15.2 s（JSON → 型付き配列 1.8 s） | 1.95 s | 19.2 s | +11.4 s | **5.78 s** |
| raw（1 つのバイト列） | 2.50〜2.72 s | +4.8〜5.5 s | **2.96〜3.46 s**（2 回） | 5.0 s | +2.6 s | 0.53 s |
| chunk（1 MiB ずつ） | **1.74 s** | **+1.7 s** | **0.51 s** | 5.8 s | +3.1 s | 0.70 s |
| fetch（scheme から取る） | 2.21 s | +3.3 s | 0.58 s | 7.6 s | +2.9 s | 0.94 s |

- **JSON は使えない:** 数の列の JSON は大きく（1e8 で要約が 19 s、画面が 5.8 s 止まる）、型付き配列に戻す手間も画面に乗る。
- **大きな 1 つのバイト列（raw）は画面を 3 s 止める:** 140 MB の解析の層を 1 つで送ると 3 s 止まる。こちらの復号（型付き配列で見る
  だけ: 0.05 s）と受け取り（view の wasm に写す: 0.2 s）は短いので、止まっているのはその手前、Tauri の channel が大きな中身を画面の
  側から取りに行って ArrayBuffer にする所（WebKit の画面のスレッド）と見ている（中までは測っていない）。
- **1 MiB ずつ（chunk）がいちばん良かった:** 止まりは 0.5 s（wasm の Worker の 0.4 s と同じくらい）、最初の絵も解析の到着も最も早い。
  画面で 1 つに組む写しは 1 回増えるが軽い。既定を chunk にした。fetch（scheme）も近いが、知らせと取りに行く往復の分だけ遅い。
- **画面の側の受け取り（view の wasm に写す）は残る:** 370 万行の層を view の wasm の索引に入れるのは WebKit で 0.2 s（試作 2 の Chrome では
  0.3〜2.3 s）。ネイティブのコアにしても、画面の wasm に同じものを持つ限りこのコピーは消えない。

**図形の列（1 フレーム分）を IPC で取り寄せる（frameipc）:** 殻のネイティブの Scene が 1 フレームを作るのは 0.02〜1.1 ms（画面の wasm は
0.04〜5.4 ms）。1 フレームは 830〜4,400 図形・27〜760 kB。何もしていない時に 40 回続けて取ると、往復の中央値は raw 2〜6 ms、JSON 5〜10 ms
（JSON は 1.3〜1.7 倍の大きさ）。ベンチの間（画面が描き続けている間）は往復が 1 フレーム分（25〜117 ms）に伸びる: 返事が画面の
スレッドの次の番まで待つため。描くのを殻の図形にするなら、1 フレーム遅れで先に頼んでおく（パイプライン）形になる。そうすれば線の変化
（I2C で 101 MB）も解析の層も画面に渡さなくてよく、最初の絵の前の転送と画面の wasm のメモリ（I2C で 0.32 GB、1e9 で 0.7 GB）が消える。

### 11.4 良かった所

- **殻は素直に作れた:** 画面のコードは変えずに（Worker を作る所と、報告の出し先だけ）そのまま動いた。dockview、Solid、Worker、wasm、
  BroadcastChannel、日本語の文字は MiniBrowser と同じく問題なし。WebGL2 の道で注釈の 3 段まで描けた（スクリーンショット）。
- **wasm の crate をそのままネイティブで使えた:** `wasm/engine` と `wasm/view` は wasm-bindgen の属性が付いたままネイティブの rlib として
  通る。殻は 1 つの言語（Rust）で、Worker の代わりのスレッドとメッセージの組み立てを書くだけ。ブラウザ版とデスクトップ版で
  同じ crate を共有でき、画面の側は Worker か IPC かを 1 か所で選ぶ。
- **Worker の口に合わせた IPC:** メッセージの形を変えずに渡し方（json / raw / chunk / fetch）を差し替えて比べられた。Tauri 2 の channel は
  生のバイト列（`InvokeResponseBody::Raw`）を ArrayBuffer で渡せるので、型付き配列はコピーなしで見られる。
- **ネイティブで読む・解析が速く、4 GB の上限がない:** 上の表。wasm の Worker を閉じないとメモリが縮まない問題もない（殻のスレッドが
  持つものを落とせばよい）。
- **配る物:** 12 MB の実行ファイル 1 つ（Electron の 100 MB 級に比べて小さい）。

### 11.5 詰まった所・気になった所

- **WebKitGTK の WebGL のキャンバスが止まった時に 1 フレーム古いまま:** 描き続けている間は正しいが、解析が来て 1 回だけ描き直すと、
  文字（2D キャンバス）は新しいのに波形（WebGL）は前のフレームのまま（線と注釈の段がずれて見える）。MiniBrowser でも同じなので
  WebKitGTK 側の振る舞い。描いた後にもう 1 フレームだけ描き直す（requestDraw の後追い 1 回）で直した（Chrome でもそのまま動く）。
- **WebGPU は出ない:** Tauri の WebKitGTK では `navigator.gpu` 自体がない（MiniBrowser の `--features=+WebGPU` に当たる設定を殻から
  入れていない。入れてもこの機械ではアダプタが出ないのは §10.5）。Linux は WebGL2 で描く前提のまま。
- **大きな 1 つのメッセージで画面が止まる**（11.3）。区切って送る（chunk）が要る。Tauri の channel は小さな中身は eval で、大きな中身は
  画面の側からの取りに来る形になっているので、渡す側で大きさを抑えるのが確か。
- **ビルドが重い:** Tauri の依存の初回は -j1 で約 30 分、画面を変えるたびに殻の crate を作り直して 5〜11 分（画面の埋め込みの圧縮と
  thin LTO）。開発中は devUrl（Vite の dev server）を使う形にすれば画面だけ作り直せる（今回は試していない）。
- **画面の側が律速の所は速くならない:** 要約の上の段・層の索引（view の wasm）、2D キャンバスの文字は画面のスレッドのまま。ネイティブの
  コアの効き目を全部出すには、Scene も殻の側に置いて図形の列だけを渡す形（11.3）を試すことになる。
- **dockview の別の窓（popout）:** `window.open` の窓を Tauri がどう扱うかは確かめていない（確認事項）。独立した窓（list.html と
  BroadcastChannel）は殻でも同じ形で動くはずだが、Tauri の窓として開くには殻の側の口が要る。
- **Windows:** この機械では作れない（WebView2 と MSVC）。手順は README に書いた（`--log` に報告を書く。リリースの exe は端末を持たない）。

### 11.6 試作 1・2・2b を並べて

| 観点 | 試作 1: egui | 試作 2: web（ブラウザ） | 試作 2b: Tauri（WebKitGTK / WebView2） |
|---|---|---|---|
| 計算 | ネイティブ、スレッド | wasm の Worker（読む 5〜6 倍・解析 1.5 倍遅い、4 GB まで、縮まない） | wasm のままも、ネイティブのコアも（同じ crate）。ネイティブは wasm より読む約 3 倍・解析 1.3〜1.8 倍速い |
| 計算 → 画面 | 同じメモリ | Worker → 画面の wasm へコピー | IPC。1 MiB ずつなら止まり 0.5 s（Worker と同じくらい）、1 つの大きなバイト列は 3 s、JSON は使えない |
| 描画 | wgpu | WebGPU（Chrome / Edge）か WebGL2 | Linux は WebGL2（WebGPU なし、止まった時の 1 フレーム遅れを直した）、Windows は WebGPU の見込み |
| 画面の作り込み | 自前 | CSS・DOM（楽） | 試作 2 と同じ（変更なし） |
| 配る物 | 実行ファイル 1 つ | 静的なファイル（wasm 3 MB + JS 0.6 MB） | 実行ファイル 1 つ 12 MB（gzip 5 MB）+ OS の webview |
| ビルド | 初回 40 分（-j1） | wasm 5 分 + vite 5 秒 | wasm と vite に加えて殻の初回 30 分、以後 5〜11 分 |

- **見立て:** 画面は web の技術で 1 つにし、計算は同じ Rust の crate を「ブラウザでは wasm の Worker、デスクトップ（Tauri）ではネイティブ」で
  動かす形（E3）は、渡し方を区切れば成り立つ。デスクトップで大きな記録を扱う所（読む・解析・メモリ）はネイティブの利点がはっきり出た。
  一方で、画面の wasm に同じデータ（線の変化・層の索引・要約の上の段）を持つ限り、渡す量とその受け取りは残る。次の一歩は、Tauri では
  Scene を殻の側に置き、画面には 1 フレームの図形の列（数十〜数百 kB、往復 2〜6 ms）と一覧の見えている行だけを渡す形を試すこと。
- **次に確かめること:** Windows（WebView2、Iris Xe）で `bench` を流す（WebGPU が出るか、fps、IPC の止まり）。GPU のある Linux での
  WebKitGTK の WebGL2 の fps。殻の側の Scene から図形の列を描く形（パイプライン）。popout の窓。殻の側のメモリが閉じた後に戻るか。

**Slint のライセンス（本文で確かめた）:** Slint Royalty-free License 2.0 は「デスクトップ・モバイル・web のアプリ」に組み込んで配ることを無償で

Slint の印（バッジ）を出すこと、(2) Slint の API をアプリの外に見せない（ライブラリとして配らない）、(3) Slint 単体で配らない。
アプリ自身のコードは MIT にできるが、**配る実行ファイルは Slint を独自のライセンスの下で含む**ので、全体を「MIT で配る」とは言えない

商用のライセンスは有料。「同梱物を含めて MIT で配れる」（§0）を満たさないので外した。

**iced を選んだ理由:**
- 比べたい点（波形の面の GPU、ドッキング、複数の窓、日本語、wasm、Windows）が、MIT のまま一通りそろう唯一の候補だった。
- `shader` の primitive は wgpu の pipeline を自前で持てるので、試作 2 の WebGPU のインスタンスとシェーダ（WGSL）をそのまま
  ネイティブで動かせる（試作 1 の egui の Mesh・試作 2 の WebGPU と、波形の描き方を同じ形で比べられる）。
- 宣言型（Elm 型: 状態 → view）の作りが、即時描画の egui と、Solid の細粒度の反応（試作 2）の間にあり、比べる意味がある。
- Slint はライセンス（上）、GPUI は自前の GPU の描画と wasm がない、Makepad は独自のシェーダの言語と文書の少なさ、Xilem と Dioxus
  ネイティブは alpha、で外した（Makepad の Dock と GPUI の部品の多さは魅力。次に試すならこの 2 つ）。

### 12.2 作ったもの

- **iced 0.14（wgpu）の daemon**（複数の窓）。Elm 型: 状態 1 つ（記録・解析・選択・マーカー・検索・パネルとその並び・窓）、メッセージ、
  `update`、窓ごとの `view`。試作 1 と同じ中身: 波形（拡大・移動・慣性・範囲・全体、ミニマップ、目盛り、測定の吹き出し、マーカー 2 本）、
  注釈 3 段・確からしさの色・読めなかった区間、波形から独立した結果の一覧（仮想の行、列の選択、主張・層、連動の入り切り）、検索（日本語の
  言葉）、次の誤りへ、ドッキング・タブ・別の窓・レイアウトの保存と切り替え、同じ種類のパネルを複数、ダーク / ライト。

  `mouse_area` のホイール＋縦の `vertical_slider`（場所）で仮想の一覧を作った（`list.rs`、検索の当たりの一覧も同じ部品）。
- **モデル:** 試作 1 の `model.rs` の写し（再描画の頼みを抜いただけ。画面は読み込み中だけ毎フレーム見に行く）。view-core は変えていない。
- **`--bench`:** 試作 1 と同じ筋書きと形。iced が自分のデバッガ（comet）のために出す区間（update・view・layout・interact・draw・present、
  present の中の primitive ごとの prepare / render）を、`iced_debug` の "enable" で出させ、この試作が comet の代わりにサーバ

  theme 106）＋試作 1 から写した model / png / prof 830 行。依存は Cargo.lock で 389 個。初回のビルドは -j1 で約 45 分（混んだ機械で）、

### 12.4 iced で良かった所

- **波形の面を自前の GPU で描くのが素直:** `shader` の primitive は wgpu の pipeline を自分で持ち、widget の範囲に viewport を合わせて
  呼んでくれる。試作 2 の WGSL とインスタンスの形をそのまま使えた（gpu.rs 175 行）。自前の widget から `draw_primitive` と `fill_text` を
  並べて呼べるので、図形と文字が 1 つの widget に収まる。
- **複数の窓が設計の中にある:** daemon の `view(window_id)` が窓ごとに木を返すだけで、どのパネルも別の窓に出せた（状態は 1 つなので
  受け渡しがない。試作 1 の `show_viewport_immediate` と同じ利点で、どのパネルでも同じ書き方）。閉じたらドックに戻すのも数行。
- **ドッキングの土台がある:** `pane_grid` で分ける・ドラッグ・大きさ・最大化が付いてくる。タブとレイアウトの保存は自前だが、木
  （`Node` / `Configuration`）が公開されているので 100 行ほど。
- **日本語がそのまま出る:** cosmic-text が OS のフォントと代わりの字を引くので、試作 1 のようにフォントを探して足す処理が要らない
  （画面の写真で日本語の UI・検索の言葉が出ている）。`text_input` は 0.14 で IME の変換中の表示（preedit）を持つ（この機械では確かめて
  いない）。
- **状態が 1 か所:** 選択・連動・検索の当たり・マーカーを `update` 1 つで変え、波形・一覧・ミニマップは `view` で読むだけ。連動の入り切り
  も素直に書けた。
- **内訳が取れる:** iced がデバッガ向けに出す区間を受ける口（beacon の TCP）を使えば、iced を変えずに update / view / layout / draw / present と
  primitive ごとの時間が取れる（egui の profiling と同じくらいの細かさ）。
- **今風の見た目の土台:** 角丸・枠・影はスタイルの関数で 1 つずつ、テーマはパレット 6 色から派生を作る。egui よりは「道具っぽさ」が少ないが、
  CSS（試作 2）ほどは速くない。

### 12.5 詰まった所・気になった所

- **大きな表がない:** `table` は全部のセルを作る（仮想ではない）。`scrollable` も中身を全部配置するので、何十万行には自前の仮想の一覧が要る
  （`responsive` ＋ 見えている行 ＋ ホイール ＋ スライダー。約 120 行）。スクロールは行単位でなめらかではない、スクロールバーは
  スライダーで代用、列の幅のドラッグ・並べ替えは未実装。egui_extras（試作 1）や DOM（試作 2）より手間が要る所。
- **タブがない:** `pane_grid` は 1 枚に 1 つの中身。タブは自前で足した。タブのボタンを押すとパネルのドラッグも始まる（`pane_grid` は
  中身のボタンが押されても掴む）。浮いた窓（窓の中の浮いたパネル）はない（OS の窓に出すことで代えた）。
- **API の揺れと文書:** 0.13 → 0.14 で widget の trait（`on_event` → `update`）、`Space` / `rule` / `checkbox` の作り方、テーマの関数が変わる。
  文書は例（examples）が中心で、自前の widget から primitive を描く trait（`iced_wgpu::primitive::Renderer`）は iced から私的にしか
  出ておらず、iced_wgpu に直に依存した。
- **毎フレーム木を作り直す:** Elm 型なので、マウスを動かすたび（吹き出し・測定）・毎フレーム（慣性・読み込み中・ベンチ）に update と view と
  layout が走る。今の大きさでは 0.5〜2 ms で問題ないが、パネルと一覧の行が増えると効いてくる（`lazy` で区切る手はある）。
  加えて iced はメッセージの後に**すべての窓**の再描画を頼むので、別の窓を開くほど 1 フレームの仕事が増える。
- **文字の描き方:** 注釈の文字を 1 つずつ `fill_text` で積む（字形の組みは cosmic-text のキャッシュ）。倍率が変わると prep text が 6 ms
  まで上がった。文字が多い画面では、自前のアトラス（§3）にする余地がある。
- **立ち上がり:** 窓と wgpu の device を作るのに llvmpipe で 0.24〜0.97 s。GPU のある機械では短いはず（確認事項）。
- **web は試していない:** iced は wasm（WebGPU / WebGL2）に出せるが、daemon の複数の窓はブラウザにない。スレッドがない所は試作 1 の
  wasm 版と同じ問題になる見込み。
- **Windows はこの機械で作れない:** 手順は README（`--bench` のコマンド）。

### 13.1 Makepad の今（2026-11-25 に確かめた）

- **版:** crates.io は makepad-widgets / -platform / -draw とも **1.0.0（2025-05-13）** が最新で、1 年半新しい版がない。GitHub の main は
  Cargo.toml が **2.0.0**（crates.io には出ていない）で、2026-10-31 に大きくまとめて入った（widget の families、style sheets、
  「Script Engine」の新しい DSL、Splash、XR、AI など）。GitHub に release・tag はなく、`main`（確かめた区切り）と `work`（毎週 main に
  まとめて付け直す）の 2 本。**試作は crates.io の 1.0 で作った**（lock で再現できる）。2.0 では DSL（1.0 の `live_design!`）から書き方が
  変わる見込みで、1.0 で書いたものはそのまま持って行けない（API の揺れは iced より大きい）。
- **波形の面:** 作れた。DrawQuad を継いだ構造体に instance のフィールド（`seg`・`color`・`kw`）を足し、頂点シェーダを Makepad の
  シェーダ言語（Rust に似た書き方。GLSL / HLSL / Metal / WebGL に訳される）で書く（`wave.rs` の `DrawSeg`、15 行）。図形は
  `begin_many_instances` で 1 つの draw call のインスタンスの列に足す（構造体のフィールドを書いて `draw()` するとメモリをそのまま写す）。
  試作 2・3 のインスタンス（8 個の float）をそのまま使えた（色はパレットの番号でなく CPU で RGBA にした: uniform の配列は避けた）。
  描画は wgpu ではなく Makepad 自身の層: Linux は OpenGL（X11、EGL）、Windows は Direct3D 11、macOS は Metal、web は WebGL2。
- **Dock:** ある（`Dock` widget: タブ・分ける・大きさ・閉じる。状態は `DockItem` の HashMap で `load_state` / `clone_state`、
  SerRon / DeRon 付き）。ただしタブのドラッグはアプリが `DockAction`（ShouldTabStartDrag / Drag / Drop）を受けて `tab_start_drag` /
  `accept_drag` / `drop_move` を呼ぶ形で、**Linux（X11）には 1.0 でドラッグアンドドロップ自体がない**（`StartDragging` が「Not implemented」）。
  加えて **root の直下のグループの最後のタブを閉じると root ごと消える不具合**がある（`unsplit_tabs` が root の分け目を消して親がない）。
- **複数の窓:** できる。`Window` widget をテンプレート（LivePtr）から実行時に作れば OS の窓になり、`WindowAction::WindowClosed` で閉じたのが
  分かる。状態は 1 つのまま（`Scope` で渡す）。浮いた窓（窓の中のパネル）はない。
- **大きな表:** `PortalList`（見えている行だけを頼む仮想のリスト、慣性つきのスクロール、スクロールバー）。列の部品（表）はない。
- **日本語:** OS のフォントは使わない。同梱のフォント（IBM Plex、代わりの字に **LXGW WenKai**: 中国語向けの楷書体で、かな・漢字を持つ）で
  出る。日本語は出るが字の形は中国語の楷書寄り。**等幅のフォント（LiberationMono）には代わりの字がなく、日本語が豆腐になる**（一覧・測定で
  日本語を含むセルは普通のフォントにして避けた）。
- **IME:** Linux は XIM（`XIMPreeditNothing`: 変換中の文字は IME の窓に出て、確定した文字が来る。インラインの変換表示はない）。Windows は
  1.0 では `ShowTextIME` が何もしない（候補の窓の位置を合わせない。確定は WM_CHAR で来る見込み）。どちらも実際の IME では確かめていない。
- **wasm:** Makepad の得意な所（WebGL2、自前の JS の橋）だが、ビルドに `cargo makepad`（crates.io の cargo-makepad は 0.4.0・2023 年で古い。
  1.0 に合う物は GitHub の tools/cargo_makepad）が要る。加えてこの試作のモデルはスレッドと `std::time::Instant` を使う（試作 1 の wasm 版と
  同じ問題）。**今回は手を付けていない**（余力なし）。
- **Windows:** D3D11。垂直同期は 1.0 では常に切っている（`Present(0, 0)`）。この機械では作れない（MSVC）。手順とベンチのコマンドは README。
- **配る形:** フォントなどの資源（`crate://…`）は実行時に crate のソースの置き場（cargo の registry）から読む（`MAKEPAD_PACKAGE_DIR` を
  付けてビルドしない限り）。`cargo run` では問題ないが、exe だけでは文字が出ない。また既定で **ソースの `.rs` を 100 ms ごとに読み直す
  スレッド**（live design の書き換え）が release でも動く。
- **ライセンス:** MIT / Apache-2.0（同梱のフォントは IBM Plex・LXGW WenKai・Liberation・Noto Color Emoji で、どれも OFL）。

- **波形の面を自前のシェーダで描くのが短い:** DrawQuad を継いでフィールドを 3 つ足し、頂点シェーダを 15 行書くだけ。パイプライン・
  バッファ・bind group を書かない（試作 3 の iced は wgpu の pipeline を 175 行）。`begin_many_instances` で 2 万のインスタンスが 1 回の
  draw call。角丸の吹き出しも SDF で数行。シェーダは GL・D3D11・Metal・WebGL に自動で訳される。
- **Dock と PortalList が最初からある:** タブ・分ける・大きさ・閉じる・同じ種類を複数（テンプレート）、状態の HashMap（SerRon 付き）で
  保存・切り替え。PortalList は慣性つきのスクロールとスクロールバーまで付く（iced は自前で 120 行、行単位のスクロール）。
  ドロップダウン・チェックボックス・テキスト入力も揃う。
- **複数の窓が素直:** Window をテンプレートから作るだけで OS の窓。閉じたのも action で分かる。状態は 1 つのまま `Scope` で渡す（受け渡しが
  ない）。
- **依存が少なくビルドが速い:** 191 個、初回 17 分、2 回目から 1 分前後（iced 45 分 / 2〜3 分、Tauri 30 分 / 5〜11 分）。wgpu も winit も
  使わず、OS の API を直に叩く自前の層。
- **draw の CPU が小さい:** widget の木を毎フレーム作り直さない（即時描画に近い draw と、イベントは widget が自分で受ける）。全部の
  widget の draw が 0.8〜4.3 ms。
- **見た目が最初から今風:** 標準のテーマ（ダーク）が、角丸・影・グラデーションのタブ・細い文字で、egui・iced の標準より整って見える
  （画面の写真）。
- **実行中のテーマの切り替え:** link を替えて DSL を読み直すと Makepad の部品まで全部替わる（live design の道）。

### 13.5 詰まった所・気になった所

- **1.0 は古く、2.0 は別物:** crates.io の 1.0（2025-05）から 1 年半出ておらず、GitHub の 2.0 は DSL から書き換わっている。1.0 の不具合
  （下）は直らない見込みで、2.0 に移ると書き直し。release も tag もない。
- **1.0 の不具合と欠けが多い:** ライトのテーマが動かない（名前の欠けとフォントの場所。写して直した）、Dock の root が消える、X11 に
  ドラッグアンドドロップがない、Windows の IME の位置合わせがない、`Label` / `CheckBox` に DSL の `visible` がない（View で包んだ）。
- **文書が少ない:** 例とソースを読むしかない。DSL の誤りは実行時にしか出ず（`Apply error … no matching field: visible`）、正確な行は
  nightly の proc_macro_span が要る（stable では起動のたびに 20 行ほどの案内が出る）。どの部品に何の口があるかはソースを grep した
  （`DockRef` に `load_state` がなく `borrow_mut` で中に入る、など）。
- **描画の順:** 同じシェーダの draw call には後から足した物がまとめて入る（`find_appendable_drawcall` が後ろから探す）ので、重ねたい物は
  `new_draw_call` で分ける（吹き出し）。わかるまで少し迷った。
- **日本語:** OS のフォントを使わず、同梱の中国語の楷書体で出る（字の形が日本語の UI として不自然）。等幅のフォントには代わりの字がなく豆腐。
  日本語のフォントを足すには自分で `font_family` を定義してフォントを持つ（数 MB）。IME はインラインの変換表示がない。
- **配る形:** 資源を実行時に crate の置き場から読む（exe 1 つでは配れない。`cargo makepad` の道が要る）、ソースを 100 ms ごとに読む
  スレッドが release でも動く。
- **計測の口がない:** profiling の区間がなく、下の層（GL / D3D11 に渡す・swap）はメインスレッドの CPU から引くしかない。
- **メモリの床が高い（この機械）:** 0.57 GB（13.3）。
- **確かめられていない:** wasm（cargo-makepad が要る）、Windows（MSVC）、実際の IME、別の窓を OS の × で閉じて戻る所（Xvfb に窓の管理が
  なく × を押せない。コードの道はある）。

## 14. 試作の測り方を直す・Windows と wasm でビルドが通るか（2026-11-26）

§9.6.1・§12.9 で利用者の Windows に出た測り方の不具合を直し、3 つの試作（egui・iced・Makepad）の数字を同じ形で比べられるようにした。
試作の質は「数字が正しく取れて比べられる」所まで。

### 14.1 直したもの

- **メモリと CPU 時間の取り方を 1 つに:** `proto/gui/egui/src/meter.rs`（依存なし。iced と Makepad は `#[path]` で同じファイルを読む）。
  - Linux: RSS は /proc/self/statm（ページの大きさは sysconf。前は 4096 決め打ち）、スレッドの CPU は `clock_gettime(CLOCK_THREAD_CPUTIME_ID)`。
  - Windows: RSS は working set（`K32GetProcessMemoryInfo`）、スレッドの CPU は `QueryThreadCycleTime` を起動時に測った速さ（スレッドを 6 ms
    ずつ 10 回回し、cycles / 壁時計の最大）で時間に直す。`GetThreadTimes` はスケジューラの刻み（15.6 ms）でしか進まず、1 フレームの部分
    （Makepad の draw ごとの差など）には粗すぎる。代わりに流しの全体のメインスレッドの CPU を両方で出し（結果の終わりの
    `main thread CPU over the run`）、数 % で合うかを見る（速さの測り違いが出る）。kernel32 の関数は自分で宣言した（crate を足さない）。
  - 前は Windows で rss・`main CPU`・Makepad の `platform CPU` が NaN だった（Linux でしか取っていなかった）。
- **結果の頭をそろえた:** 3 つとも `# gpu:`、`# present:`、`# meter:`（取り方と、この exe を作った時刻: 古い exe で流していないかが分かる）。
- **egui の present の確かめ:** eframe（egui-wgpu）は頼んだ present mode をそのまま wgpu に渡すだけで、実際の形を外に出さない。起動時に
  同じ窓にもう 1 つ wgpu の面を作り（`create_surface_unsafe`、同じ instance と adapter）、面の持つ形を問い合わせ、wgpu の決まり
  （頼んだ形を面が持てばそれ。AutoVsync は FifoRelaxed → Fifo、AutoNoVsync は Immediate → Mailbox → Fifo）で実際の形を出す。
  例（この機械の Xvfb、lavapipe の Vulkan）: `# present: asked AutoNoVsync -> Immediate (vsync off, tearing allowed); the surface's modes [Immediate, Mailbox, Fifo, FifoRelaxed]; frame latency 1`。
  GL では 2 つ目の面を作らない（1 つの窓に 2 つは安全でない）。
- **egui の垂直同期を切って測る道:** `--backend dx12|vulkan|gl`（`WGPU_BACKEND` と同じ。PowerShell で変数を使わずに済む）。§9.6.1 で 60 fps に
  頭打ちだったのは既定の DX12、iced が 300 fps 出たのは Vulkan だった（§12.9）。wgpu 30 の DX12 は Immediate を ALLOW_TEARING で持つが、
  窓のまま（全画面でない）では DWM が合成し、フレームの遅れの待ち（waitable object、latency 1）が画面の Hz で解けると見ている（確かめる前）。
  同じ記録を egui の DX12（既定・immediate・mailbox）と Vulkan、iced の Vulkan と DX12 で流して分ける（README のコマンド）。頭打ちの回でも
  `main CPU`（1 フレームのメインスレッドの CPU 時間）が Windows でも出るので、仕事の量は比べられる。
- **egui の最初の絵:** §9.6 の手直しの後のコードは、最初の絵がなければ「-」と書き、NaN は書かない（読み直して確かめた）。§9.6.1 の NaN は、
  手直しの前の exe で流したか、別の行（Windows で NaN だった rss）と見られる。測り方も「2 フレーム目の始め」から「波形のパネルが記録を
  描いたフレームの次のフレームの始め」に変えた（描いたフレームが表示された後）。この機械の Xvfb で VCD 58 ms、mixed-1 23 ms。
  `# meter:` の作った時刻で古い exe かどうかが分かる。
- **iced の `# gpu: ?`:** iced の `system::information()` は、窓（compositor）ができる前に頼むと捨てられる（iced_winit 0.14.1 が compositor の
  ないときに答えない）。起動時に頼んでいたので、窓の立ち上がりが遅い回に `?` になった。最初の絵の後にもう一度頼み、それでも来なければ
  probe（下）のアダプタの名前を使う。
- **iced の present の見出し:** 前は `ICED_PRESENT_MODE` がなければ常に「no_vsync」と書いた（`--vsync` は settings の vsync で渡すので、
  変数は空のまま）。頼んだ形を iced_wgpu と同じ順（`ICED_PRESENT_MODE` → settings の vsync）で決め、最初の絵の後に `window::run` で主の窓の
  ハンドルを借りて 2 つ目の wgpu の instance・面・アダプタ（iced の compositor と同じ選び方）を作って面の持つ形を問い合わせ、実際の形を出す
  （`gpu.rs` の `probe`）。
- **iced の最初の絵:** 前は波形の widget の draw の中（まだ表示されていない）で取り、「窓が開くまで」は iced の窓が開いた知らせ（Msg）の
  時刻だった。知らせは最初のフレームより後に来ることがあり、この機械で「その後の最初の絵 −671 ms」と負になった（§12.9 の「最初の絵 1.15 s
  （窓 1.19 s）」も同じ）。最初の絵を「波形が描いたフレームの次のフレームの合図」に、窓の時刻を「主の窓の最初の view」（窓・device・面が
  できた所）にした。2 行目の「最初の view からの最初の絵」が試作 1 の最初の絵と同じ区間。Makepad も最初の絵を同じ意味（描いた後の次の
  NextFrame）にそろえた。
- **Makepad の `# present:`:** Makepad 1.0 は表示の仕方を選べない（makepad-platform 1.0.0 を読んだ: Windows は D3D11 の flip-discard で
  `Present(0, 0)`、Linux の EGL は `eglSwapInterval` を呼ばない）。それを頭に書く。

## 15. 試作 3（iced）をブラウザで動かす（2026-11-26）

§14.3 で wasm32-unknown-unknown のビルドが通った iced の試作を、ブラウザで実際に動かした。動いた（Chrome 157 のヘッドレス、WebGPU と
WebGL2 の両方）。試作の質は「動くか・どこで詰まるか・数字」まで。起動の手順は proto/gui-iced/README.md の「ブラウザで開く」。

### 15.1 直したもの

- **窓を 1 つに:** iced の daemon は web でも動く（`window::open` ごとにキャンバスを作って body に足す）。ネイティブの「別の窓へ」を web では
  出さない・`--detach-list` を無視する、だけで済んだ（daemon を application に書き換える必要はなかった）。
- **スレッド:** 試作 1 の model.rs の `spawn` は wasm でその場で走る形のまま。要約は開くときに作る。解析は、例とページが取ったファイルは
  バイト列からコアで（`analysis_of_bytes`、試作 1 の wasm と同じ）、合成は作り物の解析をその場で。どれも最初の絵の前に済む（その間は止まる）。
- **iced 自身のスレッド:** iced の `system::information()`（GPU の名前を聞く。sysinfo の feature）は iced_winit が `std::thread::spawn` で
  答えを作るので、web では「failed to spawn thread」で panic して止まった。web では呼ばず、ページが WebGPU のアダプタ（なければ WebGL2 の
  renderer）を聞いて渡す。
- **ファイル:** 例 mixed-1 を中に持つ（`include_bytes!`）。`?file=URL` はページが fetch してから wasm に渡す（proto/gui-web の serve.mjs の
  `--files` で tests/data を出す）。ブラウザのファイルの選択・ドロップはまだ。
- **文字:** web には OS のフォントがなく、iced も何も持たない（fira-sans の feature を入れていない）ので、何も出ない。`web/build.sh` が
  fontconfig の日本語のフォント（この機械では Noto Sans CJK の .ttc、19.5 MB）を `fonts/` に写し、ページが取って `Settings::fonts` に入れ、
  既定のフォントをその名前にした。それでも一覧の値（`Font::MONOSPACE`）が空だった: 汎用の monospace / sans-serif の名前が web では
  どのフォントも指さない。cosmic-text の fontdb の `set_monospace_family`（同じ .ttc の「Noto Sans Mono CJK JP」）で直った。
- **全体表示の幅:** 最初のフレームの時にキャンバスがまだ小さく、その幅で「全体」を合わせた倍率が残って、波形が左の 1/100 に縮んでいた
  （ネイティブは窓が最初から決まった大きさ）。全体を見ている時は幅が変わったら合わせ直すようにした（`wave.rs` の `view_of`。ネイティブでも
  窓の大きさを変えると全体のままになる）。
- **ベンチ:** `?bench=1` で試作 1 と同じ筋書き。`SystemTime::now()`・`thread::sleep`・ファイルへの書き出しは web で使えない（panic か
  失敗）ので、web_time の時計にし、結果は `window.__bench` と console へ。iced の段（update / view / layout / draw / present）は iced が
  TCP のサーバ（beacon）へ送る作りで、web には出せない。代わりに `meter` を web 用（`web_meter.rs`）にし、「main CPU」をページの
  requestAnimationFrame の中の時間（index.html で包んで数える）、rss を wasm のメモリにした。proto/gui-web の `tools/bench.mjs` に、
  ベンチの間のページの main thread の時間（CDP の TaskDuration）をフレームの数で割った行を足した（試作 2 の出力はそのまま）。
- **スクリーンショット:** ヘッドレスの Chrome は WebGPU のキャンバスを写さない（§10.4 と同じ）。iced の `window::screenshot` は
  `map_async` の直後に `poll(Wait)` して同期で読む作り（iced_wgpu 0.14）なので、ブラウザでは使えない。ページの側で WebGPU の
  `configure` に COPY_SRC を足し、描いた直後の rAF の中で今のテクスチャを読み戻して重ねた（WebGL2 は `toDataURL`）。
- **小さな詰まり:** Window の関数（requestAnimationFrame）は Window.prototype ではなく window そのものにある（[Global]）。prototype を
  包んでも何も数えなかった。
- **ネイティブは今までどおり:** web の所は `cfg(target_arch = "wasm32")` で分けた。Linux の release で mixed-1 の `--bench` が最後まで流れた
  （Xvfb + llvmpipe、44〜46 fps、main CPU 1.6〜1.7 ms / フレーム、rss 216 MB。§14.4 と同じ形）。`cargo check --target
  x86_64-pc-windows-gnu --all-targets` も警告なしで通る。

### 15.3 詰まった所・気になった所

- **iced の web の対応:** 書いたコードはほとんどそのまま動いた（ウィジェット・pane_grid・shader の primitive・WGSL）。止まったのは
  iced が中でスレッドを作る所（`system::information`）と、GPU を同期で待つ所（`window::screenshot`）。どちらもネイティブだけを前提にした
  作りで、文書には書かれていない。`Task::blocking`（iced_runtime の中も `thread::spawn`）も web では使えない見込み。
- **スレッドがない:** 要約と解析は開くときに止まって作る（1e8 で 2.4 s 何も出ない、1e9 や I2C 10 万取引の解析は事実上無理）。
  iced の中から Web Worker に出すには、wasm-bindgen で Worker を立て、データを写して戻す道（試作 2 の形）を自分で作ることになる。
  iced に Worker の口はない。wasm のスレッド（SharedArrayBuffer）は nightly の build-std が要る（§10.4）。
- **文字:** web ではフォントを自分で持たないと何も出ない。日本語を出すには数 MB〜20 MB のフォントを配る（試作 2 はブラウザのフォントで
  0）。汎用の名前（monospace）を手で結び直す必要があった。Noto Sans CJK にない字（パネルの掴みの「⠿」）は箱になる。字の幅がネイティブ
  （OS のフォント）と違い、検索の一覧の層の名前が 2 行に折れた。
- **入力:** iced の text_input は 0.14 で IME の表示を持つが、winit 0.30 の web は IME を持たない（`set_ime_allowed` が空）。ブラウザでは
  日本語を打てない（検索の言葉は `?search=` で入れて、日本語の検索そのものは通った: 「0x48 書き込み」62,377 件、147 ms）。
  キーボードの英数字・マウスはヘッドレスでは確かめていない（利用者の Chrome で確かめる）。
- **WebGPU / WebGL2:** 両方で同じ絵が出た（wgpu が WebGPU を先に試し、アダプタがなければ WebGL2。`&webgl=1` で強制）。自前の shader の
  primitive（インスタンス描画、uniform の配列の添字）は WebGL2 でもそのまま通った。WebGPU は https か localhost でしか使えないので、
  別の機械から http で開くと WebGL2 になる。この機械では WebGL2 の方が main thread を 1.6 倍使った（4.8 ms と 3.0 ms）。
- **大きさ:** wasm 12 MB（gzip 3.3 MB）は iced・wgpu（WebGPU と WebGL2 の両方）・cosmic-text・エンジンを丸ごと持つため。試作 2 の画面の
  wasm（152 KB）と比べて 2 桁大きい。
- **測る道:** iced の段の内訳（§12.3 の表）は web では取れない（iced のデバッガへの送り先が TCP）。rAF の時間と CDP の TaskDuration で
  全体だけ見た。

### 15.4 試作 1・2・3 の web を並べて

| 観点 | 試作 1 wasm（egui） | 試作 2 web（TS + wasm） | 試作 3 web（iced） |
|---|---|---|---|
| 同じコードから | ◎ ほぼそのまま（eframe の WebRunner） | – 画面は TS で別に書いた | ○ ほぼそのまま（窓 1 つ、iced のスレッドの所を外す、フォントを渡す） |
| 止まらないか | × 開くときに止まる | ◎ Worker | × 開くときに止まる（iced に Worker の口はない） |
| 文字・日本語 | egui の文字（足りない字はブラウザに頼る、§9.3） | ◎ ブラウザのフォント（何も持たない） | フォントを配る（20 MB）。汎用の名前を結び直す |
| IME | 未確認 | ◎ ブラウザの `<input>` | × winit の web に IME がない |
| 配る物 | wasm 13.7 MB（gzip 4.1） | wasm 0.15 + 2.9 MB、JS 0.6 MB | wasm 12.1 MB（gzip 3.3）＋ フォント |
| 1 フレームの CPU（1e8、ヘッドレス） | – | 2.6〜6.3 ms | 6.1 ms（main thread 全部）、rAF 2〜5 ms |
| スクリーンショット・測る道 | – | 自前の読み戻し、ベンチ | ページの側で読み戻し、iced の段の内訳は取れない |

- **見立て:** iced の web は「同じ Rust のコードがブラウザでも動く」所までは素直だった（試作 1 の egui と同じ位置）。ただしブラウザに
  出す価値（止まらない・日本語の入力・小さい配る物・ブラウザの文字）は、どれも iced の外で自分で作ることになり、試作 2（web の技術）
  の方が素直にそろう。iced を選ぶなら、ブラウザ版は「見るだけ・小さな記録」の補助に留め、重い所はネイティブ（スレッド）で、という分け方になる。
- **次に確かめること:** 利用者の Chrome（GPU）で fps と 1 フレームの CPU（README の URL、`&bench=1`）。キーボードとマウスの操作。
  フォントを小さくする（日本語の部分集合、または Noto Sans JP の 1 ウェイト）と最初の取り寄せ。要約・解析を Worker に出せるか
  （wasm-bindgen の Worker に model.rs の段を移す）。
