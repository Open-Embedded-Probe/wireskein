# アプリの画面をゼロから検討する（2026-11-25〜、方向を確かめる段階）

ユーザー（2026-11-25）:
- 今ある web（wireskein-web）は簡易表示なので使わない前提。
- 大幅に手を入れるので、ブラウザベースかネイティブかをゼロベースで検討する。
- PulseView ではなく、Saleae Logic（Logic 2）を超える使い勝手を目指す。
- かなりの作り込みと描画が要る想定。

このノートでは、要る要素と環境（画面の作り・言語・描画・届く先）を並べる。前のノート bench/notes/2026-11-23-ui-directions.ja.md（製品の形 P1〜P7、言語、画面の作り G1〜G7、機材、拡張）を土台にし、そこで開いていた「画面の共有のしかた」「波形の描き方」をこの前提で掘り下げる。**最初に決めない。案は広く並べ、§7 の試作で数字を取って比べる。**

## 0. 前提（決まっていること）

- アプリはフル Rust（コアは Rust。bench/notes/2026-11-24-rust-plan.ja.md §5）。画面の言語は開いている（Rust だけ、TS と組む、ほか）。
- 解析・取り込み（OEP のクライアントも wireskein の中）・ファイルの読み書きは、Rust の部品としてそろいつつある（rust-plan §28〜§37）。画面はそれを呼ぶ。
- 試験の道具は今の形（Python のライブラリ、verify、CLI・JSON）で育てる。アプリとはファイルの形式で繋ぐ。
- ライセンスは MIT で配れること（同梱物を含めて）。

## 1. 越える相手: Logic 2 の今

Logic 2（Electron の上に作られたアプリ。機材は Saleae の Logic 8 / Pro 8 / Pro 16 と、新しい Logic MSO）が使いやすいと言われる所と、越えられそうな所を並べる。機能の細部は版で変わるので、試作の前に今の版を触って確かめる（確認事項）。

**よい所（最低でもここまでは要る）**
- 開いた瞬間から波形が動く。拡大・移動がなめらかで、ホイールとドラッグだけで迷わない。
- デジタルとアナログを同じ時間軸に並べる。
- プロトコルの解析を足すと、波形の上に注釈が載り、右のパネルに表（データテーブル）が出る。表と波形が連動する。
- 測定: 線にマウスを載せると幅・周期・周波数が出る。区間を選ぶと統計が出る。タイミングマーカー（2 点の差）。
- 検索（解析の結果の中を）。
- トリガの設定、取りながら見る（取り込み中も波形が流れる）。
- 拡張: Python の High Level Analyzer（解析の結果の上にさらに読む）、測定の拡張、マーケットプレイス。
- 自動化の API（外のプログラムから取る・書き出す）。
- 見た目が今風で、ダーク / ライト。

**越えられそうな所（WireSkein が既に持っている力と重なる）**
- **設定なしで読む:** Logic 2 は線ごとに解析を手で足す。WireSkein はバスと役割を自動で推定し、確からしさまで出す（P3）。
- **ノイズに強い:** 安いプローブ（ESP32-P4 など）の汚れた線でも読める。読めなかった区間・疑わしい所を見せられる。
- **試験と繋がる:** 期待と照合した OK / NG を時間軸に出す（P4、verify・run の記録）。
- **大きな記録・長い流し取り:** Logic 2 は記録をメモリに載せる作りで、長い取り込みはメモリで頭打ちになると言われる（確認事項）。こちらは変化で持つ・要約の層・分割読みを既に持つ。H417 の SS（毎秒 200〜400 MB）も視野。
- **機材が開いている:** 自前の OEP のプローブが第一。各社の記録も読める。
- **重さ:** Electron のアプリは起動とメモリが重い。ネイティブなら軽くできる。
- **上の段:** UART の行、Modbus、SCPI、デバイスパック、RISC-V の DM など、バスの上の意味まで読む。
- **比べる:** 2 つの記録を並べて合わせる（align）、差を見る。
- **AI・スクリプト:** CLI と JSON が最初からある。

| 要素 | 中身 | |

### 2.7 速さの目標（試作で測る数字の候補）

- 開いてから最初の絵まで: 1 億の変化の記録で 1 秒以内、10 億で 2 秒以内（全部を読み終わる前に、要約から描く）。
- 拡大・移動: どの倍率でも 60 fps を落とさない（120 Hz の画面では 120 fps を目指す）。
- 取りながら: 毎秒 40 MB（P4X）を落とさずに描き続ける。毎秒 400 MB（H417）は受けて残すのが先で、描くのは間引いてよい。
- メモリ: 記録の大きさに比例させない（要約と見えている所だけ）。

## 3. 描画の作り（画面の作りに依らない部分）

どの環境を選んでも、重い所の作りはほぼ同じになる。ここは Rust のコアの部品として先に作れる（画面なしで試験できる）。

- **要約の層（LOD）:** 線ごとに、時間の区切り（2 の冪の幅）ごとの「最初と最後の水準、変化の数、最小・最大」の段を持つ。どの倍率でも、1 ピクセルあたり 1〜2 区切りを読めば描ける。アナログは最小・最大・平均。
  - 開くときに作るか、ファイルに持つか（.wireskein の付属物として）。
  - 取りながら足していけること。
- **注釈の層:** 解析の項目を時間で引ける形（区間木や、区切りごとの索引）に持つ。倍率ごとに、どの段を描くか、収まらない文字を畳むかを決める。
- **タイル:** 見えている範囲を、倍率ごとのタイルにして GPU に置き、移動のたびに作り直さない。
- **GPU で描く:** 線と四角はインスタンス描画、文字はアトラス。1 フレームで数十万の図形を描ける作りにする。
- **非同期:** 重い読み（ファイル、解析）は別スレッドで、描画を止めない。読み終わった所から細かくなる。

この層を `crates/` の部品にしておけば、ネイティブでも wasm でも、どの画面の作りからも使える。各案を比べるときも、この部分は共通にできる。

## 4. 環境の案

### 4.1 届く先

| 届く先 | よい所 | 引き換え |
|---|---|---|
| ネイティブのアプリ | USB を直に、ファイルを直に、メモリの上限なし、軽い、オフライン | 配布（署名・更新）、OS ごとの差 |
| ブラウザ | 置かずに開く、共有のリンク、どの OS でも | 下の §4.2 の制約。USB は WebUSB（Chromium 系のみ）、大きなファイルの扱い |
| 両方 | 使い分け | 作りによっては二重の手間 |

### 4.2 ブラウザの今の制約（2026-11 時点で確かめたもの）

- **WebGPU:** Chrome / Edge は 113（2023）から。Safari は 26（2025）から macOS・iOS など。Firefox は Windows で 141、Apple シリコンの macOS で 145 から。**Linux の Firefox と Intel の Mac はまだ途中**。WebGL2 は全部で使える。
- **wasm のメモリ:** 32 ビットの wasm は 4 GB まで（実際はもっと手前）。64 ビット（memory64）は Chrome 133・Firefox 134 から。**Safari はまだ**。記録を全部載せる作りは、ブラウザでは数 GB で止まる。要約と見えている所だけにする作り（§3）が前提になる。
- **USB:** WebUSB は Chromium 系だけ（Firefox・Safari にはない）。ブラウザから取り込むなら Chrome / Edge に限られる。
- **ファイル:** 大きなファイルを開くのは File API で読めるが、保存して書き戻す（File System Access）は Chromium 系だけ。
- **スレッド:** wasm のスレッド（SharedArrayBuffer）は、配信の側で COOP / COEP の見出しが要る。

### 4.3 画面の作りの案

| 案 | 中身 | ネイティブ | ブラウザ | 描画の自由 | 部品（表・木・入力） | 気になる所 |

| E2 宣言型の Rust の GUI | iced、Slint、Xilem / Masonry（Vello）、Makepad、Dioxus（ネイティブの Blitz）、GPUI の派生 | ○ | 案による（iced・Slint・Makepad・Dioxus は wasm も） | 案による | 案による | 成熟度がまちまち。Slint はライセンス（GPL / 独自 / 商用の 3 つ）を確かめる。GPUI は Zed の中で育っていて、単体の版は 1.0 前で派生が分かれている |

| E6 Qt | C++ / QML（Rust からは cxx-qt）。PulseView・DSView と同じ型 | ◎ | △ | ○ | ◎ | 言語が混ざる。LGPL の扱い。前のノートで遠ざけた方向 |
| E7 Flutter + Rust | 画面は Dart、コアは flutter_rust_bridge | ◎ | ○（CanvasKit） | ○ | ◎ | 言語が 2 つ。wasm のコアとの繋ぎ |

### 4.4 案ごとの「Logic 2 を越える」への効き方

- **描画の上限:** どの案でも、波形の面を GPU で自前に描けば、上限は §3 の作りで決まる（E3 の WebGPU、E1・E5 の wgpu は同じ道具の上）。差が出るのは、パネル・表・文字の作り込みの手間と、ブラウザの制約。
- **軽さ:** E1・E2・E5 がいちばん軽い。E3 の Tauri は OS の webview なので Electron よりは軽い。E4 は重い。
- **今風の見た目と作り込み:** E3・E4・E7 は部品と作り方の蓄積が多い。E1 は見た目を詰めるほど手間が増える。
- **ブラウザで同じものが動くか:** E1・E3・E4 は同じコードで動く。E2・E5 は案による。E6 はほぼ別。
- **レイアウトの自由さ:** web の技術にはドッキングの部品があり、egui にも egui_dock がある。別の窓への切り離しは、ネイティブなら OS の窓をそのまま使える。ブラウザは別の窓を開いて窓どうしで状態を受け渡す作りになる（手間と制約は確認事項）。宣言型の Rust の GUI は案ごとに差が大きい。
- **ネイティブの力（USB を直に、大きなファイル、メモリ）:** E1・E2・E5・E6・E7 は直に使える。E3・E4 は殻（Tauri / Electron）の側の Rust を通す。

## 5. 比べる軸

前のノートの §9・§11.2 に足すもの:

- §2.7 の速さの数字（最初の絵、fps、取りながら、メモリ）。
- 注釈の文字が多い所の速さと読みやすさ（文字の描画の質、日本語）。
- 部品の作り込みの手間（表 1 万行のスクロール、木、検索の入力、設定のフォーム）。
- レイアウトの自由さ（§2.6）: ドッキング、別の窓への切り離し、同じ種類のパネルを複数、保存と切り替えが、どれだけの手間でできるか。ネイティブの複数の窓とブラウザの別の窓（ポップアップと窓どうしの受け渡し）の差も。
- ネイティブとブラウザで共有できるコードの割合。
- 起動の速さ、配る物の大きさ、メモリ。
- Linux（作る人の主な環境）・Windows・macOS での動き。とくに Linux のブラウザと webview。
- IME とアクセシビリティ。
- 作る人の数と言語の数（Rust だけで済むか）。
- 依存の寿命（成熟度、1.0 前か、作っている所が続くか）。

### 9.2 数字（Xvfb の上。fps はソフトウェア描画なので参考にならない）

  ただし 10 億の要約が全部できるのは 15.6 s 後（2 スレッド）。そこまでは右の方が「要約 n%」。

  GPU のある画面の fps はまだ測っていない（この機械の Xvfb は DRI3 がなく llvmpipe。1600×960 を CPU で塗って 10〜20 fps）。

  GUI では最初の絵はすぐでも、一覧が出るまで 2 分待つ。**大きな記録では解析の速さとメモリが先の問題**（GUI の描画ではない）。

### 9.4 詰まった所・気になった所

- **文字:** ネイティブは日本語のフォントを自分で探して足す（Noto Sans CJK の .ttc を読む）。web に同じ見た目を求めるなら数 MB の
  フォントを持つことになる。egui 0.37 は harfrust で字形を組むので文字の質は前より良いが、等幅の数字列の見た目はまだ詰めていない。
- **IME:** この環境（Xvfb、入力メソッドなし）では確かめられていない。検索の欄に日本語の言葉（「書き込み 0x72」）を入れた検索は通り、欄にも正しく出る（引数から入れた。キーボードからの変換は未確認）。fcitx / ibus での
  変換中の表示は利用者の画面で確かめる（確認事項）。
- **egui の API の揺れ:** 0.37 で `App::ui(ui)`、`Panel::top`、`Id::new` の非推奨など、版ごとに書き直しが要る（1.0 前）。
- **見た目の作り込み:** 角丸・影・余白・アイコンを今風にするのは自分で一つずつ。標準の見た目は「道具」っぽい。表の行の高さ・
  選択の色・列の並べ替え（未実装）も自前。
- **重なりの多い注釈:** 項目が画素より多い所は「いちばん悪い状態」で塗ったが、50 万項目に 0.5 % の誤りでも全体表示はほぼ全部が誤りの色に
  なる。誤りの割合で塗る・誤りだけ別の細い帯にする、などの工夫が要る。検索に合った項目の枠（2 px）もライトでは見えにくい。
- **解析の層:** "all" の文書でも I2C は transactions だけ、分割読みでは final の層だけになる。3 段（取引・フレーム・ビット）は試作の中で
  クロックの立ち上がりから作った（「(GUI)」の段）。本来はエンジンの文書がフレームとビットの時刻を持つべき（wireskein 側の要件）。
- **メモリの形:** 解析の項目を serde_json の Value のまま 370 万行持ったら 4 GB を超えて落ちた。一覧の行は詰めた形（ビット 1 B、
  バイト 2 B）と、文字を 1 本の String にまとめた索引にして 1.2 GB。画面に要るのは列ごとの詰めた配列。
- **web の制約:** スレッドがないので要約と解析は開くときに止まって作る（1e8 で数秒）。ファイルを開く道（File API）と大きな記録の
  分割読みはまだ。wasm は 13.7 MB（gzip で 4.1 MB）: エンジンと解析を丸ごと持つため。
- **fps の計測:** GPU のある画面で測る道（ヘッドレスで DRI3 のある X か、利用者の画面で `--bench`）がこの機械にない。

### 9.6 1 フレームの内訳を測り、図形を減らした（2026-11-25、試作 1 の改良）

§9.2.1 の「合成 1e8 で 1 フレーム 34〜41 ms なのに波形 CPU は 1.3〜2.2 ms」を分けるため、`--bench` に 1 フレームの内訳を足した
（中身と列の意味は proto/gui/README.md の「--bench の内訳」）。

- **測り方:** egui・eframe・egui-wgpu・wgpu は `profiling` の区間を持つ。`profiling` を tracing の後ろで動かし、自前の小さな subscriber で
  区間ごとの時間を足す（`--bench` のときだけ）。egui の組み立て（`Context::run`）、三角形にする処理（`Context::tessellate`）、バッファの更新
  （`Renderer::update_buffers`）、命令を作る・提出・表示（`get_current_texture` / `Queue::submit` / `present`）が別々に出る。パネルごと
  （波形・ミニマップ・一覧・測定）はアプリが自分で測る。図形・頂点・三角形・描画の単位（prims）は、1 フレームの図形を egui の層から写して
  三角形にして数える。メインスレッドの CPU 時間（Linux）も出す: この機械は他の仕事で混んでいて（load 10〜15）、壁時計の時間は倍ほど揺れる。

     配置からやり直していた）。1 フレーム 1.5〜3 ms → 0。
  3. 注釈の文字を 1 つずつの切り抜き（clip）で描くのをやめ、箱に収まる文字だけを波形の切り抜き 1 つで描く（文字ごとに描画の単位が
     分かれていた）。
  - `--old-draw` で前の描き方に戻せる（同じ機械で前後を比べるため）。
- **やらなかったもの（数で決めた）:** タイルの Mesh の使い回し・egui_wgpu の callback で頂点を GPU に置いたままにする案は、手直しの後で
  三角形にする処理とバッファの更新が合わせて 1 フレーム 1〜3 ms（波形の分はその一部）しかなく、この機械では効く所がない。利用者の
  機械で `upload` / `encode` / `submit` が大きければ次に試す。見えていないパネルは egui_dock がもともと描かない（同じ葉の後ろのタブは
  ui が呼ばれない）ので止める仕事がない。
- **利用者の機械の 34〜41 ms の見立て（確かめる前）:** mixed-1 が `--bench`（vsync を切るつもりの AutoNoVsync）でも 60 fps で頭打ちなので、
  Windows では垂直同期が切れていない（DX12 の窓では Immediate が使えず Fifo に落ちる、など）と見られる。すると 1 フレームの仕事が
  16.7 ms を少しでも越えると 2 つ分の 33.3 ms に丸まり、p50 34〜41 ms と合う。加えて eframe の既定（LOW_LATENCY）は
  `desired_maximum_frame_latency = 1` で、CPU が前のフレームの GPU の終わりを待つ（CPU と GPU が重ならない）。`--latency 2` と
  `--present immediate` を流してもらって、`acquire` / `present` の待ちがどこに出るか、結果の頭の `# gpu:`（API・表示の仕方）と
  合わせて見る。
- **流しの長さ:** 倍率ごとに 24 フレームを超えて 3 秒経てば次へ、掃引は 12 秒まで。合成 1e9 は全体で 85〜90 s（要約を待つのが 18 s、
  この機械で 1 フレーム 150〜300 ms の所が多いので）。GPU のある機械では倍率ごとに 96 フレームで 1〜2 秒ずつ。

## 10. 試作 2: web の技術（2026-11-25）

proto/gui-web（本番の workspace の外。使い捨て）。中身・起動・速さの測り方の詳細は proto/gui-web/README.md。試作 1 と同じ中身を、
画面は TypeScript、波形は WebGPU（なければ WebGL2）、計算は view-core と wireskein の Rust の部品を wasm にして作った。

### 10.1 作ったもの

- **画面:** TypeScript + Solid 1.9 + dockview-core 8.9（MIT）、ビルドは Vite。中身は試作 1 と同じ: 波形（拡大・移動・慣性・範囲・全体、
  ミニマップ、目盛り、マーカー 2 本、カーソルの測定）、注釈 3 段・確からしさの点・読めなかった区間、波形から独立した結果の一覧
  （仮想の行、列の選択と幅、主張・層の切り替え、連動の入り切り）、検索（日本語の言葉）、次の誤りへ、ドッキング（分ける・タブ・
  大きさ・浮かせる・同じ種類を複数・名前を付けて保存と切り替え）、一覧を別の窓に（2 通り: 下）、ダーク / ライト、ファイルを開く
  （File API とドラッグアンドドロップ、URL）。
- **フレームワークの選び方:** 重い所（波形のキャンバス、何十万行の一覧）は結局どれでも自前の命令的なコードになる。周りの UI は
  細かく何度も変わる（状態の表示、測定、検索の件数）ので、仮想 DOM の差分を取らない細粒度の反応（Solid のシグナル）が合う。
  React はフレームごとに変わる値で再描画を抑える工夫（memo）が要り、配る物も大きい。Svelte 5 も同じ方向の候補（比べてはいない）。
  素の TS は表示の同期を手で書く量が増える。Solid 2.0 は出たばかりで vite-plugin-solid がまだ 1.x しか受けないので 1.9 にした。
  dockview は素の TS の版（dockview-core）があり、別の窓（popout）・浮いた窓・保存（toJSON / fromJSON）を持つので選んだ
  （golden-layout も候補だが古い）。
- **wasm 2 つ:** `wasm/view`（画面のスレッド、152 KB）は view-core の薄い口。`Scene.frame` が見えている所を GPU のインスタンスの列
  （8 個の float: 矩形か太さのある線分、色はパレットの番号）にし、文字は「どこに何を」だけ返す。`wasm/engine`（Worker、2.9 MB、gzip
  0.9 MB）は wireskein-io / -core / -analysis（本番の crates を path で読むだけ）と、試作 1 の model.rs の解析の読み方・フレームとビットの段・
  検索をほぼそのまま移したもの。
- **スレッド:** 画面のスレッドは受け取るだけ。ファイルを読む・要約の段 0 を作る（合成は 2 つの Worker で 16 本を分ける）・解析・
  検索はすべて Worker（型付き配列を移す。コピーしない）。要約の上の段は画面のスレッドで受け取りながら作る（`Lod::append`）。
  注釈の索引は Worker で作ったものを部品のまま渡す（view-core に `Track::parts / from_parts`、`AnalogLine::levels / from_parts`
  を足した。どちらも足しただけで、試作 1 はそのまま）。
- **描画:** 波形の図形は 1 回の draw（インスタンス描画）。WebGPU と WebGL2 で同じ形のシェーダ（WGSL と GLSL、各 40 行ほど）。
  文字は上に重ねた 2D キャンバスにブラウザのフォントで描く（日本語のフォントを持たなくてよい）。目盛りの線は wasm 側で波形の下に敷く。

### 10.3 web で良かった所

- **画面が止まらない:** ファイルを読む・要約・解析・検索を Worker に出すのは素直に書けた（Worker 2 種、メッセージは型付き配列を移すだけ）。
  試作 1 の wasm 版は開くときに止まって作っていたが、ここでは 1e9 の要約（24 s）も I2C 10 万取引の解析（200 s）も、その間ずっと
  波形を動かせる。要約は 2 つの Worker で線を分け、作れた所から描く（試作 1 のネイティブの 2 スレッドと同じ形）。
- **wasm が小さい:** 画面の側 152 KB、Worker の側 2.9 MB（gzip 0.9 MB）。試作 1 の wasm 13.7 MB（gzip 4.1 MB）の大半は egui と wgpu。
  JS は main 562 KB（gzip 116 KB。うち dockview が大きい）。
- **見た目の作り込みが速い:** 色・余白・角丸・影・メニュー・ツールチップは CSS で数行ずつ。ダーク / ライトは CSS 変数と、波形は
  GPU のパレット（uniform）の差し替えだけ。試作 1 で「道具っぽい」と書いた所が、同じ時間でずっと今風に寄る。
- **表:** 仮想の行は自前（行の要素を使い回して scroll で埋める。約 360 行）。320 万行（ビットの層）も、要素の高さの上限（Chrome で
  約 3,300 万 px）を越える分は scroll を縮めて読む。列の幅のドラッグ、色の印、当たりの色付けは CSS で簡単。試作 1 の egui_extras と
  同じく見えている行しか作らないので、50 万行・320 万行でも引っかからない。
- **ドッキング:** dockview-core が分ける・タブ・大きさ・浮いた窓・別の窓（popout）・保存（toJSON / fromJSON）を一通り持つ。
  既定のレイアウト 3 つ、名前を付けて保存（localStorage）、同じ種類を複数、がそれぞれ十数行。egui_dock と同じくらいの手間で、
  別の窓まで付いてくる。
- **別の窓（2 通り）:** (1) dockview の popout: パネルの要素ごと別のブラウザの窓に移す。JS の状態は同じものなので受け渡しは要らない
  （ネイティブの egui の `show_viewport_immediate` に近い）。(2) 独立した窓（list.html）: BroadcastChannel で層のデータを写して受け取り、
  選択・検索の当たり・テーマを送り合う。メインの窓を読み直しても残り、つなぎ直す。Tauri や別の画面でも同じ形で動くのは (2)。
- **日本語:** 文字はすべてブラウザが描く（OS のフォント。何も持たない）。検索の欄は普通の `<input>` なので IME の変換もブラウザの
  もの（変換中は composition のイベントで検索を止める）。試作 1 のようにフォントを探して足す処理が要らない。
- **ファイルを開く:** File API とドラッグアンドドロップがそのまま使える（File を Worker に渡すと Worker が読む）。URL でも開ける。
- **測る道具:** ヘッドレスの Chrome（puppeteer-core）で開いて、ベンチの結果・スクリーンショット・Chrome のプロセスのメモリを取れる。

### 10.4 詰まった所・気になった所

- **wasm の境目のコピー:** Worker の wasm と画面の wasm はメモリが別なので、渡すたびに写す。320 万行のビットの層を含む 370 万行を
  画面の側の索引に入れるのに 0.3〜2.3 s 画面が止まった（JS → wasm のコピーと wasm のメモリの伸び）。合成のアナログ 400 万サンプルも
  0.45 s。wasm のスレッド（SharedArrayBuffer に 1 つのメモリ、COOP / COEP は配信の道具で用意済み）にすれば写さずに済むが、Rust は
  nightly の build-std が要る（今は使っていない）。少しずつ受け取る（フレームごとに区切る）手もある。
- **wasm の遅さ:** 同じ Rust でもネイティブより遅い。ファイルを読む（zip の展開と bits → 変化）は 5〜6 倍（i2c 10 万: 0.37 s → 2.4 s、
  h417: 0.2 s → 1.1 s）、要約は 1.5〜2.7 倍、解析は 1.5 倍（136 s → 200 s）。この機械は SwiftShader が CPU を取り合うので割り引いて見る。
  wasm にはスレッドもないので、解析を分けて並べることもできない。
- **wasm のメモリは縮まない:** 解析の Worker は I2C 10 万で 0.95 GB、読む Worker は 0.2 GB のまま。使い終わった Worker は閉じる
  （読む Worker は閉じるようにした）。32 ビットの wasm の 4 GB が上限で、解析を丸ごと（3.5 GB）はブラウザでは無理（分割読みが前提）。
- **dockview-core 8.9.1 の ESM 版に CSS が入っていない:** UMD 版だけが CSS を注入する。Vite のプラグインで UMD 版から取り出した。
  popout の窓では Solid の委譲したイベント（document に付く）が効かないので、開いた窓の document に `delegateEvents` を足した。
  ResizeObserver も要素の窓のものを使う（移った先で付け直す）。
- **Solid 2.0:** 出たばかりで vite-plugin-solid が 1.x しか受けない。1.9 にした。TypeScript は 7（Go 版）がそのまま使えた。
- **ヘッドレスの Chrome:** GPU がないので WebGPU は SwiftShader（CPU）。スクリーンショットに WebGPU のキャンバスが写らない（白い）。
  1 フレームを読み戻して重ねる口を作って撮った。fps は SwiftShader と合成の速さで、GPU の画面の数字ではない（試作 1 の Xvfb と同じ注意）。
- **文字の描画:** 2D キャンバスの fillText は SwiftShader の上では重く、注釈の文字が多い倍率で 1 フレーム 15〜20 ms かかった（wasm は 1.4 ms）。
  GPU の画面では軽いはず。文字を GPU のアトラスで描く案（§3）と比べる余地。
- **2 つの言語:** 解析の読み方（model.rs）と検索は Rust に残したので、TS 側は画面だけ。それでも状態の型（層、列、選択）は両側に要る。

### 10.5 Tauri と WebKitGTK

- **Tauri の殻は作れなかった:** この機械には webkit2gtk-4.1 / javascriptcoregtk-4.1 / libsoup-3.0 の実行用のライブラリはあるが、
  開発用のヘッダ（pkg-config の .pc）がなく、webkit2gtk-sys が通らない（入れるには root が要る）。利用者の機械で
  `libwebkit2gtk-4.1-dev` などを入れれば試せる（確認事項）。
- **代わりに同じ WebKitGTK（2.52.6）の MiniBrowser で同じページを開いた**（Tauri は Linux でこれと同じ webview を使う）:
  - そのまま動いた（Worker、wasm、BroadcastChannel、dockview、Solid）。
  - WebGPU: 2.52 では「unstable」の機能。`--features=+WebGPU` で `navigator.gpu` は現れるが、この機械（DRI なし）ではアダプタが出ず、
    WebGL2 に落ちた。Linux の WebKitGTK の WebGPU は GPU のある機械でも確かめが要る（確認事項）。**Tauri の Linux では WebGL2 で
    描く前提**にしておくのが安全（同じシェーダの WebGL2 版は用意済み）。
  - 例（mixed-1、窓の幅が 768 px で Chrome の半分）: 最初の絵 0.61 s、解析 5.0 s（Worker）、要約 0.06 s。ベンチは 15〜19 fps、
    波形 CPU 2〜6 ms（wasm 0.05〜0.2）。合成 1e8: 最初の絵 0.54 s、要約 6.9 s、作り物の解析 6.0 s。
  - Chrome より llvmpipe の WebGL2 の方がこの機械では速い（Chrome の SwiftShader の WebGPU は 2〜8 fps）。
- Tauri にすると、ファイル・USB・解析は殻の側の Rust（ネイティブ、スレッドあり）で走らせ、画面へは IPC で渡す形になる。今の Worker と
  の境目（型付き配列を渡す）をそのまま IPC に置き換えられるように作ってある。wasm の遅さ（§10.4）とメモリの上限は消える。

  wasm のスレッド（SharedArrayBuffer に 1 つのメモリ: Worker 間のコピーを消す）、文字を GPU のアトラスで描く案、ファイルの記録を
  区画ごとに渡して最初の絵を早める。
